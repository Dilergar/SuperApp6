# Оборудование (сервис «Объекты», часть 3)

> Семья `Asset`: справочник моделей → экземпляры → журналы движения и обслуживания. Объект, дерево, права и штатное расписание — [objects.md](objects.md).

Код: `apps/api/src/modules/objects/assets.service.ts` + `assets.controller.ts`; веб — `apps/web/src/app/workspaces/[id]/objects/[objectId]/assets/`.

## Модель

- **`AssetModel`** — СПРАВОЧНИК моделей на организацию (`kind`: сегодня `equipment`, зарезервированы `vehicle`/`land`/`other`). Инструкция и паспорт крепятся СЮДА один раз — на все двадцать одинаковых кофемашин сети. Уникум `(workspace, kind, name)`; удаление с экземплярами → 409 `asset_model_in_use` (FK Restrict).
- **`Asset`** — ЭКЗЕМПЛЯР. Модель ОБЯЗАТЕЛЬНА, но заводится на лету из формы: «Кофемашина Jura X8» должна появиться одним движением, а не походом в отдельный справочник.
- **`AssetMove`** — append-only журнал: `kind` = `placement | custodian | holding | status`, поля «откуда → куда».
- **`AssetServiceRecord`** — обслуживание/ремонт: `kind` (maintenance/repair/inspection), `status`, `cost`, подрядчик (`counterpartyId`), `nextDueOn`. TCO = SUM(cost).

### Два независимых измерения

`Asset` разводит **ГДЕ стоит** (`branchId` + `parentAssetId` — узел внутри линии + `locationNote`) и **ЧЬЁ / на чьём балансе** (`holdingKind`: owned/leased/rented/third_party + `balanceLegalEntityId` + `holdingCounterpartyId`). Арендованная кофемашина стоит в нашем зале, но на балансе арендодателя; своя машина может стоять у подрядчика. Смешение этих осей — главная ошибка учёта, которую модель не даёт совершить.

## Несущие правила

- **Движение — запись.** Место, ответственный, владение и статус меняются ТОЛЬКО вместе с `AssetMove` в той же транзакции: «переместили» без следа кто и когда — потеря, а не экономия.
- **Ответственный — запись журнала, а не подпись.** Акт передачи с ЭЦП придёт позже отдельным документом (`core/sign`), и журнал станет его основанием.
- **Перемещение требует права на ОБА объекта** — источник и приёмник: иначе оборудование уезжало бы в чужую ветку.
- **Списание уводит из живых списков**: статусы `written_off` / `disposed` проставляют `archivedAt`, а возврат в рабочий статус его СНИМАЕТ — иначе ошибочное списание необратимо (статус вернулся, а из списков и поиска актив исчез навсегда).
- **Деньги и баланс — под `branch.payroll.view`**: без права полей `purchasePrice`, `holdingKind`, `balance*`, `cost`, `serviceCost` в ответе НЕТ; менять владение, цену и стоимость ремонта тоже нельзя. Правило стоит во ВСЕХ путях ответа, включая ЖУРНАЛ ПЕРЕМЕЩЕНИЙ: записи вида `holding` без права не отдаются вовсе (раньше журнал раскрывал ось «своё → аренда» тому, кому денежные поля закрыты).
- **Чужие id не принимаются.** Внешние ключи на юрлицо, контрагента и родительский актив не скоуплены организацией, а у `custodian_user_id` ключа нет вовсе — принадлежность проверяет сервис (`assertRefsOwned`), иначе в ответе оказывалось название чужого ТОО или ФИО постороннего человека.
- **TCO считает СЕРВЕР** — агрегатом `SUM(cost)` по всем ремонтам (`AssetDto.serviceCost`), а не клиент по загруженной странице журнала.

## Ловушки

- **Инвентарный номер уникален среди ЖИВЫХ** (`UNIQUE(workspace_id, inventory_number) WHERE inventory_number IS NOT NULL AND archived_at IS NULL`) → 409 `asset_inventory_duplicate`. Списанный экземпляр номер не держит.
- **Фото приватное.** Профиль `asset_photo` — `visibility: private`, вечной ссылки нет: DTO несёт `photo: FileDto`, а веб получает временную ссылку через `useFileDisplayUrl`. Поле-ссылка в DTO было бы протухшим кэшем.
- **Право на актив = право на его ОБЪЕКТ** (грант на объект или предка). Своих tuples у актива нет — точечный шеринг добавится типом `asset` без миграции данных, если понадобится.
- **Регистрация в движке = ДВА действия.** Мало писать `chatter.log(refType)` — нужен и `chatterRegistry.register(refType)`: на незнакомый refType движок отвечает 404, и лента пишется «в стол».

## HTTP API моделей

`GET/POST asset-models` · `PATCH/DELETE asset-models/:modelId` · `GET/POST asset-models/:modelId/files` ·
`DELETE asset-models/:modelId/files/:fileId`. Справочник ведёт тот, кто управляет хотя бы
одним объектом; читают файлы модели все, кроме Подрядчика.

## Веб

Плитки `Card hoverable` с фото, чипом статуса и `PersonChip` ответственного; список — infinite-запрос (`objectAssetsKey`), карточка — свой `assetKey` (один RQ-ключ = одна форма кэша). Карточка — 4 вкладки: Данные / Документы (`AttachmentsSection`, профиль `asset_photo`) / Перемещения (журнал) / Обслуживание. Форма создания: комбобокс модели с «Создать „…“» (поиск с задержкой). Справочник моделей — отдельный маршрут `objects/models`: правка, удаление с 409 и ДОКУМЕНТЫ модели (инструкция, паспорт) — без него модель, заведённая на лету, оставалась неисправимой.

## Проверка

`node apps/api/scripts/verify-objects-assets.cjs` — модель на лету и её переиспользование, счётчик экземпляров, инвентарный дубль 409, удаление модели с экземплярами 409, журнал перемещений «откуда → куда», смена ответственного как запись, TCO, списание, права члена/постороннего, отсутствие денежных полей без права.

Миграции `core_lifecycle`, `lifecycle_partition_guards`, `lifecycle_purge_runner`, `lifecycle_actor_indexes`, `lifecycle_health_signals`, `person_refs` (+ GIN-индексы `chatter_person_ids_idx`, `notification_person_ids_idx`), `lifecycle_erasure_held_status`, `lifecycle_settings_timers_dashboard`, `lifecycle_erasure_notify_user`, `message_person_ids` (+ частичный GIN `messages_person_ids_idx`); роли — `apps/api/scripts/db-roles.sql` (часть 2). Реестр политик — `packages/shared/src/lifecycle` (`types.ts`, `registry.ts`, `limits.ts`, файлы областей `core.ts` · `messenger.ts` · `workspaces.ts` · `personal.ts` · `stores.ts`), страж — `scripts/check-lifecycle.cjs` + ратчет `scripts/lifecycle.cell-readiness.json`, страж миграций — `scripts/check-migrations.cjs`, онлайн-DDL — `apps/api/scripts/db-online-ddl.cjs`, сьюты — `verify-lifecycle.cjs`, `verify-partitions.cjs`, `verify-purge.cjs`, `verify-trash.cjs`, события журнала — `packages/shared/src/audit/lifecycle.ts`, каталог — `packages/i18n/src/messages/<locale>/lifecycle.json`.

28-й платформенный движок. Отвечает на вопрос **«сколько живут данные, почему, чьи они и что с ними делать при стирании человека и удалении организации»** — для КАЖДОГО хранилища платформы: модели Prisma, сырой таблицы (`analytics.events`, `idem.*`), профиля байтов файлового движка, семейства ключей Redis и производного хранилища вне базы (архивы, экспорты, журнал стираний, бэкапы, логи, временный каталог). Знание «что стирать и в каком порядке» живёт в реестре, а не в коде модулей (GitLab data dictionary + Meta DELF + Elastic ILM).

## Политика (`LifecyclePolicy`)

| Поле | Смысл |
|---|---|
| `id` / `store` | Имя модели Prisma, либо `table:<схема.таблица>` · `blob:<профиль>` · `redis:<семейство>` · `derived:<имя>` |
| `owner`, `version` | Модуль-владелец; сокращение срока = новая версия + dry-run + «четыре глаза», удлинение свободно |
| `dataClass` | `identity_pii · auth_secret · user_content_private · user_content_shared · tenant_record · legal_record · financial_record · security_audit · operational · analytics_event · derived · ephemeral` |
| `ownerKey` | Ключ «коло»: `user` / `workspace` / `conversation` / `ledger` + колонка, `via` родителя, `polymorphic` (`ownerType + ownerId`), `scoped` (организация, если колонка заполнена, иначе человек), `global` (с причиной) |
| `subjects[]` | Колонки людей в строке и их роль (`owner`, `author`, `recipient`, `participant`, `member`, `employee`, `actor`, …) |
| `legalBasis` | `consent` · `contract` · `legal_obligation{citation}` · `legitimate_interest{reason}` |
| `retention` | `trigger` (`created` · `lastActivity` · `parent` · `event:<имя>`) + `floorDays` (пол закона) · `defaultDays` (ОБЯЗАТЕЛЕН) · `ceilingDays` + `tenantConfigurable` / `userConfigurable` / `entitlementKey` |
| `onSubjectErasure` | `hard_delete{personalOnly?, by?, hook?}` · `crypto_shred{keyScope}` · `pseudonymize{fields, by?, hook?}` · `redact{fields, by?, hook?}` · `retain_legal{citation, untilDays, hook?}` · `none{reason, hook?}`: `hook` — шаг модуля в плане стирания, иначе общий шаг по колонкам `by` ([lifecycle_erasure.md](lifecycle_erasure.md)) |
| `onTenantPurge` | `cascade_fk` · `registry_hook{key}` · `batched_delete{column}` · `crypto_shred` · `retain_legal{citation, untilDays, hook?}` (строки остаются по закону, `hook` закрывает ОТКРЫТОЕ — подпись в ожидании) · `not_applicable` |
| `edges[]` | Граф удаления: `deep` (каскад) · `shallow` (рвётся связь) · `refcount` (файл живёт до последнего места) · `async_delete` / `async_nullify` (строки без FK добирает loose FK) |
| `enforcement` | `drop_partition{column, period}` · `batched_delete{column, filter?, handler?}` · `ttl_sweep` · `transient` · `cascade` · `none{reason}` (+ `extraRules`) |
| `holdAware`, `proofEvent`, `pause`, `rootEntity` | Legal hold перекрывает удаление; ключ журнала-доказательства; выключатель; корневая сущность (мягкое скрытие обязательно) |
| `exportable`, `exportScope`, `exportGuard` | Сторона выгрузки (человек / организация / обе); чьи строки уходят, когда ключ владельца сторону не называет (`columns` / `via` родителя / `filter`); поля под правилами видимости — `shape()` глазами заказчика ([lifecycle_export.md](lifecycle_export.md)) |
| `personIds` | Люди внутри JSON строки: SQL-функция `{ fn, args, keys }`, по ней GIN-индекс находит строки человека при стирании (имена парой с id — `person-refs.ts`) |

Нормы права — коды `LIFECYCLE_CITATIONS` (текст нормы — каталог `lifecycle.citations.<код>`, не код). Классы и пресеты — `LIFECYCLE_DATA_CLASSES`, `LIFECYCLE_RETENTION_PRESETS` («Вечно · 1 год · 90 · 30 · 7 · 1 день»), `LIFECYCLE_CHAT_TIMER_PRESETS` (1 · 7 · 30). Пределы принуждения — `LIFECYCLE_LIMITS` / `LIFECYCLE_PURGE_WINDOW` (`limits.ts`), чисел в коде раннера нет.

## Несущие правила

1. **Пустое поле срока = хранить + красный CI.** `retention.defaultDays` обязателен; урок Google / UniSuper 2024 — пустой параметр стал сроком и удалил облако.
2. **Длительность — только целые сутки в полях `*Days` или `'forever'`.** Строка `'30'` — ошибка (урок pg_partman #811: `'10'` = 10 секунд). `floorDays ≤ defaultDays ≤ ceilingDays`.
3. **Приоритет** (`resolveLifecycleRetention`): legal hold > пол закона > стирание субъекта > потолок > умолчание; несколько «хранить» — побеждает длиннее, несколько «удалить» — короче. Коридор организации — `lifecycleCorridor(policy, planCeiling)`: [пол; min(потолок политики, потолок тарифа)].
4. **«По закону» — только с нормой.** `legal_obligation` и `retain_legal` без кода из `LIFECYCLE_CITATIONS` — красный CI.
5. **Hold обязателен** у классов `legal_record`, `tenant_record`, `user_content_*` (`holdAware: false` запрещён).
6. **Всё, что не `global`, достижимо** из корней `User`, `Workspace`, `Chat` по рёбрам (DELF); у политики с `enforcement: cascade` есть входящее `deep`/`refcount`/`async_delete` ребро — иначе её никто не удалит.
7. **FK схемы = ребро удаления.** Каждый внешний ключ объявлен ребром родителя: `Cascade`/`Restrict` (и умолчание обязательной связи) → `deep`, `SetNull` (и умолчание необязательной) → `shallow`. Новый FK без решения о каскаде — красный CI.
8. **ПДн стираются.** Модель из `PII_MODELS` не может иметь `onSubjectErasure: none`. ПДн третьих лиц в записях организации (контрагенты, счета) стираются уничтожением KEK организации (`crypto_shred`).
9. **След человека по id не трогается** (`BY_REFERENCE`): строка `User` остаётся томбстоуном, имя — маркер, `PersonChip` рисует «удалённый пользователь» на языке зрителя. Псевдонимизация — только для КОПИЙ ПДн: имя актора в хронике, имена людей в JSON хроники и уведомлений (парой с id), снимок текста события — шаги оркестратора стирания `chatter.subject` / `notifications.subject` ([lifecycle_erasure.md](lifecycle_erasure.md)).
10. **B2C и B2B в одной таблице** — `ownerKey: scoped`; стирание человека `hard_delete{personalOnly}` уносит личные строки, строки организации остаются.
11. **Одна дверь принуждения.** Срок политики принуждает только раннер (общей пачкой или шагом модуля); свой крон удаления «по сроку» в модуле не заводится — страж `check:lifecycle` §10b запрещает `deleteMany`/`DELETE` с отсечкой по времени в классе с `@Cron` (осознанное исключение — пометка `lifecycle-allow:` рядом). Срок, живущий не в колонке времени, а в событии (забытое устройство, отозванная сессия Кабинета) — `extraRules` политики. Срок — из реестра: константа-дубль срока в модуле не держится (исключение — обещание человеку `WORKSPACE_LIMITS.archiveRetentionDays`: смоук бута сверяет его с реестром).

## Раннер сроков (`LifecyclePurgeRunner`, джоб `lifecycle.purge`)

Ведёт каждую политику с `enforcement: batched_delete` (кроме выключенных `pause` и ждущих этапа): **общая пачка** — SQL из реестра и схемы Prisma (DMMF: таблица, колонки, их тип — `timestamp` через `utcTs`, `timestamptz`, `date`), **шаг модуля** — `handler` из `LifecyclePurgeHandlerRegistry`. Очередь `lifecycle` (2 слота), бюджет захода 4 минуты — остаток продолжает снуз того же прогона.

- **План ночи** — `LifecycleCron` 01:10 по Алматы: джоб на политику (`uniqueKey purge:<policy>`, живой дубль не ставится), строка прогона `lifecycle_runs` — в той же транзакции. **Окно** 01:00–06:00 по Алматы: вне окна джоб ждёт открытия (`JobSnoozeError`); стирание субъекта и каскад организации окна не ждут.
- **Общая пачка**: `WITH doomed AS (SELECT pk … WHERE col < срок AND col > граница AND фильтр AND NOT EXISTS (заморозка) ORDER BY col LIMIT n FOR UPDATE SKIP LOCKED) DELETE … USING doomed`, `SET LOCAL lock_timeout 1 с / statement_timeout 5 с`, прогресс прогона — в транзакции пачки. **Keyset**: граница `after` (последнее значение колонки срока) живёт в состоянии прогона и сбрасывается при смене правила — удерживаемые строки в голове индекса и мёртвые записи удалённых не перечитываются каждой пачкой. У каждого конечного правила общей пачки ОБЯЗАН быть b-tree индекс, ведущий колонкой срока (или `(колонка фильтра | status, колонка срока)`) — иначе пачка читает и сортирует таблицу целиком; страж `check:lifecycle` это требует. Заморозка класса на всю платформу у holdAware-политики — `stopped: held` до первой пачки (не ночь таймаутов). `extraRules` — отдельные правила по очереди. Срок, выбранный организацией (`tenantConfigurable`, `lifecycle_settings`, отложенное сокращение действует с момента вступления), — правила по организациям (`LifecycleSettings.tenantRetentions`), порядок пачки — индексом (организация, id).
- **AIMD**: пачка ≤ 250 мс — растёт на 10 %, дольше — делится пополам, [50; 5000]; 5 таймаутов подряд — пауза 10 минут.
- **Здоровье перед каждой пачкой** (`LifecycleHealth`): отставание реплик > 10 с, архив WAL падает, идёт VACUUM таблицы, темп WAL > 64 МБ/с, ожидающих блокировку > 20, p99 цикла событий > 200 мс → пачки ждут 10 минут (`lifecycle_purge_snoozed_total{reason}`), прогресс сохранён. Сигналы БД отдаёт функция `lifecycle_health_signals(table)` — SECURITY DEFINER под NOLOGIN-ролью `sa6_monitor` с одним `pg_read_all_stats` (`db-roles.sql`): приложение получает пять чисел, а не тексты запросов всех сессий, которые открыл бы `pg_monitor` у роли приложения. Без прав монитора (dev) сигналы чужих процессов читаются нулём — fail-open сознательно (отказ в здоровье остановил бы ретеншн навсегда; метрика отставания ретеншна видна). p99 API измеряется задержкой цикла событий процесса (`monitorEventLoopDelay`) — гистограммы HTTP пока нет.
- **Кэп радиуса** (Atlassian 2022, Google/UniSuper 2024): ожидание считается ДО первой пачки; больше половины живых строк таблицы (и ≥ 10 000) — прогон `stopped: blast_radius` до подтверждения (`force`); факт обогнал ожидание на 20 % (+ пачка) — `stopped: overrun`; ≥ 2 млн строк за прогон — хвост следующей ночью. Шаг модуля сообщает о подозрительном объёме `LifecycleBlastRadiusError` (ретеншн архива: больше 200 организаций к удалению разом). Метрика `lifecycle_purge_halted_total` — алерт на любую.
- **Dry-run** — только счёт (`expectedRows`), ни строки не удалено.
- **Доказательство** — событие журнала безопасности `lifecycle.purge.run` (политика, строки, пачки, dry-run, причина остановки) при закрытии каждого прогона; похороненный джоб закрывает прогон `failed`.

**Шаг модуля** (`LifecyclePurgeHandler`): `purgeBatch({ policy, runId, cutoff, limit, cursor, force, releasable })` — ОДНА пачка ≤ `limit`, идемпотентно, keyset-курсор (`encodeCursor` из `@superapp/shared`) раннер хранит между пачками — строки под заморозкой в голове очереди не стопорят прогон; `releasable(tx, ids)` в транзакции удаления отсеивает удерживаемое; `estimate` — ожидание. `cutoff` — срок реестра (`null` — окно решает модуль: корзины 30 дней). Регистрация — файл `<модуль>.lifecycle.provider.ts` модуля-владельца.

| Ключ | Что делает |
|---|---|
| `tasks.trash` · `calendar.trash` · `recorder.trash` · `notes.trash` · `drive.trash` · `finances.trash` · `docs.trash` | корзины: навсегда тем же путём, что «удалить навсегда» (эскроу, чаты, права, вложения, индекс); закрытые офисные документы — 30 дней (`DOCS_LIMITS.archivedPurgeDays`), с подписанной вехой — никогда |

## Каскад удаления организации (`LifecycleTenantPurgeService`)

План — `lifecycleTenantPurgePlan()` реестра: хуки модулей (`registry_hook`, один шаг на ключ) и пачки по колонке организации (`batched_delete`); порядок — дети раньше родителей по `deep`, **владельцы ссылок раньше файлов** (`refcount`; замыкание шага идёт по `deep` и `async_delete`: вложения Заметок и Мессенджера снимаются раньше `files.owned`), строка организации (`workspaces.row`) — последней. Цикл в плане — ошибка реестра (смоук бута).

- **Вид сущности** — по БД до первого шага и на каждом заходе (Atlassian 2022: 883 сайта по id не того вида); разрушительные пути принимают `WorkspaceId` / `UserId` (типизированные id, `asWorkspaceId`). Живую организацию каскад не тронет; восстановленная из архива между заходами — прогон `stopped: cancelled`.
- **Постановка каскада — под замком строки организации** (`SELECT … FOR UPDATE`): проверка «уже идёт» и вставка джоба в одной транзакции, невставленный джоб откатывает её (`409 workspace.purgeInProgress`); тот же замок берёт возврат из архива — после начала каскада он невозможен ([lifecycle_erasure.md](lifecycle_erasure.md)).
- **Здоровье и таймауты** — как у раннера: проверка `LifecycleHealth` перед шагом и перед каждой пачкой, `SET LOCAL statement_timeout` на пачке; таймаут делит пачку пополам, серия — снуз 10 минут (`lifecycle_purge_snoozed_total`). Синхронный дев-путь здоровья не ждёт.
- **Шаги идемпотентны**: пройденные копятся в `report.done`, прерванный каскад (бюджет, падение, рестарт) продолжает с первого непройденного. Незарегистрированный хук — стоп (fail-closed), кроме ждущих этапа (`LIFECYCLE_PENDING_KEYS`).
- **Заморозка организации останавливает каскад целиком** (`stopped: held`, `409 lifecycle.tenantHeld` на дев-ручке): проверка на старте, перед каждым шагом, `ctx.checkpoint()` в циклах хуков и под общим замком заморозок в финальной транзакции строки — каскад FK от строки снёс бы удерживаемое. **Заморозки ПЛАТФОРМЫ на её данных** (хранитель, класс, запись) — `workspaceHeld(deep)`: строка организации «удаляема» по всем `deep`-рёбрам; раз на прогон, перед командой Кабинета, в ретеншне архива и в транзакции строки.
- **Хук** (`LifecycleTenantHook.purge(workspaceId, ctx)`): идемпотентен, права не проверяет, большой объём — пачками с `deadline` (`{ done: false }` — продолжит следующий заход), удерживаемое — `ctx.releasable(tx, policyId, ids)`.
- **Запуск**: ретеншн архива (джоб `lifecycle.tenant-purge` на организацию), команда Кабинета `lifecycle.workspace.purge` (critical, «четыре глаза», не своя организация; предпросмотр — план с числом строк по шагам, исполнение ставит каскад в транзакции команды), дев-полигон синхронно (`purgeNow`; хвосты удалённых организаций — `orphan: true` без шага строки). Предпросмотр — `preview(workspaceId)`.

## Loose FK (`LifecycleLooseFk`)

Строки детей без внешнего ключа (полиморфные ссылки, проекции, журналы) после удаления родителя: statement-level триггер `lifecycle_track_delete` (ENABLE ALWAYS, переходная таблица, один INSERT на оператор — ловит и каскад FK, и сырой DELETE; без блока `EXCEPTION` — подтранзакция на каждый вызов переполняла бы кэш подтранзакций после 64 удалений в одной транзакции; лист дня проверяется `to_regclass`) пишет id удалённых строк в `lifecycle_deleted_rows` (дневные партиции; нет партиции дня — триггер заводит её функцией владельца и повторяет вставку). Воркер (крон каждые 5 минут → джоб `lifecycle.loose-fk`, 30 с на проход) по рёбрам `async_delete` / `async_nullify` реестра (`lifecycleLooseFkEdges()`, корень `User` не входит — его след стирает оркестратор стирания) удаляет/обнуляет детей пачками по `(tableoid, ctid)`; ребёнок под заморозкой остаётся, строка учёта откладывается на сутки (`retry_at`). Необработанная строка держит свою партицию от сброса (`require_processed`). Родители: `workspaces`, `chats`, `messages`, `tasks`, `notes`, `listings`, `fin_books`, `voice_recordings`, `staff_positions`, `staff_departments`, `staff_branches`. Метрики — `lifecycle_loose_fk_backlog` (алерт — рост дольше суток), `lifecycle_loose_fk_processed_total{table}`.

## Заморозки: протокол замка

Замок `LIFECYCLE_HOLD_LOCK` (advisory): каждая транзакция удаления (общая пачка, шаг модуля через `releasable`, пачка каскада, loose FK, строка организации) берёт его ОБЩИМ, постановка заморозки — ИСКЛЮЧИТЕЛЬНЫМ (`lockHoldsExclusive`). Заморозка, закоммиченная до пачки, видна её `NOT EXISTS`; поставленная во время — ждёт коммита пачки. Условие «строка не под заморозкой» (`holdFreeSql`): запись (`record`), класс данных (`class`), пространство (`space`: организация, чат), хранитель (`custodian`: владелец, субъекты строки, колонки-массивы, id людей в JSON); заморозка организации действует только на её строки, заморозка платформы — на все. **Организация, чат и люди-владельцы строки вычисляются по цепочке родителей** (`rowOwnerExprs`: `ownerKey.via` рекурсивно, глубина до 3, владелец передаётся вниз при обходе потомков) — у Диска, Заметок, книг финансов, версий документов и ещё ~40 политик ключ владельца задан через родителя, и без этого их держала бы только заморозка платформы. Живые заморозки читаются частичным индексом `(scope, data_class) WHERE released_at IS NULL` — история снятых (append-only) на пачки не давит. **Удалять — только «удаляемое»** (`deletableSql` / `releasableIds`): свободна сама И нет удерживаемых потомков по `deep`-рёбрам (их унёс бы каскад FK). Шаги модулей с внешними эффектами (байты, Google) проверяют заморозку в транзакции выборки; физически байты уходят только шагом `files.deleted`, который перепроверяет её. Заморозки, hold store, пути человека — [lifecycle_erasure.md](lifecycle_erasure.md).

## Страж `pnpm check:lifecycle` (шаг CI до сборок)

`scripts/check-lifecycle.cjs`, ~1–2 с, без сборки (реестр транспилируется на лету): самопроверка реестра (`lifecycleRegistryProblems()` — тот же код, что смоук бута); покрытие (каждая модель `schema.prisma`, сырая таблица миграций — с учётом `RENAME`/`DROP` по порядку операторов, профиль `FILE_PROFILES`, литерал ключа у вызова Redis); колонки политик существуют; FK ↔ рёбра; `PII_MODELS`; `drop_partition` → таблица партиционирована по этой колонке и PK её содержит; `batched_delete` → индекс ведёт колонкой времени, владельца, FK на родителя или колонкой фильтра; **пачка каскада организации** → индекс ведёт колонкой организации; **ребро loose FK** → ссылка ребёнка ведёт индекс (или вторая после колонки типа — skip scan PG18), у родителя стоит триггер учёта; `rootEntity` → мягкое скрытие (`deletedAt` / `trashedAt` / `hiddenAt`); каталоги `lifecycle.*` в en/kk/ru без сирот; каждый шаг purge и хук каскада зарегистрирован в `apps/api/src` (`.register('<ключ>'`); манифест `CANARY_STORES` = реестр; поля политики — только известные; §10b — удаление по сроку в классе с `@Cron` запрещено (одна дверь принуждения); индекс под колонку срока у каждого конечного правила общей пачки; правило `tenantConfigurable` с конечным умолчанием и коридором выше него у общей пачки — красный (умолчание резало бы строки организации, выбравшей срок длиннее).

**Ратчет готовности к ячейкам** `scripts/lifecycle.cell-readiness.json` — только сокращается: индексы P-моделей, не ведущие ключом владельца (BRIN и индекс под колонку срока раннера — не в счёт: обслуживание, не путь чтения); FK между разными владельцами (кроме `global`); `int4` PK; `findMany` без `take` в методах сервисов, возвращающих списки. Новый пункт — исправить код; `--write` только сокращает файл.

Ключи, ждущие этапа, — `LIFECYCLE_PENDING_KEYS` в shared (одна правда со смоуком бута): у каждого этап и вид, строка уходит вместе с этапом. Прочие отложенные пункты стройки — объект `PENDING` в начале стража.

## Миграции без простоя

`pnpm check:migrations` (`scripts/check-migrations.cjs`, CI) — каждая миграция после отсечки Э3: заголовок `SET lock_timeout` + `SET statement_timeout`; `CREATE/DROP INDEX CONCURRENTLY` — единственный оператор файла (Prisma исполняет файл одной транзакцией); запрещены `CREATE TABLE … PARTITION OF` (лист — функцией владельца), DEFAULT-партиция, int4-ключ, `ADD COLUMN … DEFAULT <изменчивое>`, `SECURITY DEFINER` без `SET search_path = pg_catalog, pg_temp` (функция с `public` в пути исполняла бы подложенную `public.format(text,text,text)` от владельца данных — точнее совпадение типов, чем у `pg_catalog.format`); изменение защищённого (таблицы владельца данных или журнала, их функции `lifecycle_*` / `audit_*` / `security_*`, листы) без `SET LOCAL ROLE sa6_data_owner` / `sa6_audit_owner` (у роли миграций членство в ролях-владельцах без наследования — `db-roles.sql`); на больших таблицах — `CREATE INDEX` без CONCURRENTLY, `SET NOT NULL` без `CHECK … NOT VALID` + `VALIDATE`, `ALTER COLUMN … TYPE`, `FOREIGN KEY` без `NOT VALID`. Такие изменения — `node apps/api/scripts/db-online-ddl.cjs <файл.sql>` вне `prisma migrate`: оператор за оператором на одном соединении, `lock_timeout 3 с`, повторы с бэкоффом, невалидный индекс после сбоя сносится; `--partitioned-index <имя> <схема.родитель> "<(колонки)>"` — индекс партиционированной таблицы онлайн (ON ONLY → CONCURRENTLY на листьях → ATTACH); `--dry` — план.

## Партиции журналов (`LifecyclePartitions`)

Одна дверь для ВСЕХ партиционированных журналов: `analytics.events` и `api_access_log`, `notification_deliveries` и `webhook_deliveries` (месяц), `idem.responses` и `lifecycle_deleted_rows` (день). Правило родителя — строка `lifecycle_partition_specs` (пишет только миграция): колонка, период, **пол срока**, требование архива, класс данных, hold-aware, «очередь» (`require_processed`), вперёд, lz4-колонки, ENABLE ALWAYS-триггеры листа. `security_events` — под своими функциями `core/audit` (лист — той же машиной: `CREATE (LIKE)` + CHECK + `ATTACH` под `lock_timeout 2 с` с повторами, не `PARTITION OF` — иначе ACCESS EXCLUSIVE родителя стоял бы в очереди за долгим чтением журнала и держал `audit.record(tx)` всех фактов платформы); здоровье считается и для него. Сброс каждого листа доказывается событием `lifecycle.partition.dropped` (оценка строк по каталогу); DEFAULT-партиция у любого родителя схем public/analytics/idem — смоук бута падает.

- **DDL — только SECURITY DEFINER-функции владельца данных** (`sa6_data_owner`, путь поиска функций `pg_catalog, pg_temp`, объекты `public` — со схемой): `lifecycle_ensure_partition(parent, at)` = `CREATE (LIKE родитель)` + CHECK границ + `ATTACH` (SHARE UPDATE EXCLUSIVE на родителя — вставки идут; `PARTITION OF` взял бы ACCESS EXCLUSIVE), DEFAULT-партиция запрещена, `lock_timeout 2 с` атрибутом функции; `lifecycle_drop_partition(parent, leaf)` — граница из каталога (`relpartbound`), **пол срока, архив, заморозки, необработанная очередь проверяет БАЗА**, оборванный `DETACH … CONCURRENTLY` доводится `FINALIZE`, затем DETACH + DROP; `lifecycle_analyze_partitioned(parent)`. Роль приложения таблиц не владеет.
- **Движок-владелец объявляет своё** — `LifecyclePartitions.register(parent, { retentionMs?, onDropped? })`; `forParent(parent)` отдаёт ручку `ensureFor / ensureAhead / list / dropExpired` (адаптеры `AnalyticsPartitions`, `IdempotencyPartitions`, `KeysUsageCron.partitions`).
- **Срок сброса** = max(срок владельца или `defaultDays` реестра, пол правила, `floorDays` реестра, самый длинный срок организаций у `tenantConfigurable`); ≤ 12 сбросов за прогон; каждый лист — своя попытка (5 повторов при таймауте блокировки, потом пропуск и метрика).
- **Горячий путь**: вставка в период без листа → `isMissingPartition` → `ensureFor` → повтор один раз.
- **Ночь** (`LifecycleCron`, 01:40 по Алматы, Redis-лок): вперёд, сброс по сроку, `ANALYZE` родителей, здоровье → метрики; здоровье ещё и каждые 6 часов. Метрики: `lifecycle_partitions_ahead{parent}` (алерт < 2), `lifecycle_partitions_detach_pending`, `lifecycle_partitions_total`, `lifecycle_partitions_dropped_total`, `lifecycle_partition_maintenance_errors_total{parent,op}`.
- **Поиск по одному id** в партиционированной таблице — только с подсказкой времени: `byIdWithTimeHint(id)` (UUIDv7 → окно ± 1 ч).

## Роли, append-only, событийный триггер

`db-roles.sql` (часть 2, суперпользователем после `migrate deploy`): `sa6_data_owner` владеет партиционированными журналами, деньгами (`ledger_transfers`, `escrow_*`, `card_skin_transfers`, `fin_audit_logs`) и таблицами движка, где удаление = подлог (`lifecycle_holds`, `lifecycle_erasure_journal`, `lifecycle_hold_store`, `lifecycle_hold_extractions`, правила и архивы партиций); роль приложения — только DML через родителя. `sa6_migrate`, `sa6_readonly`, `sa6_backup`, `sa6_monitor` (владелец функции сигналов здоровья, только `pg_read_all_stats`) — NOLOGIN. Каскад FK в таблицу владельца PostgreSQL исполняет от владельца — родителей, которых проверяют его триггеры, он видит колонкой `id` (`card_skin_instances`, `fin_books`). **Событийный триггер `lifecycle_guard_drop`** (`sql_drop`): DROP защищённой таблицы или листа — только от `sa6_data_owner` / `sa6_audit_owner`; осознанно — `SET ROLE sa6_data_owner`; аварийно — `ALTER EVENT TRIGGER lifecycle_guard_drop DISABLE`.

Триггеры миграции (ENABLE ALWAYS): леджер — UPDATE/DELETE/TRUNCATE запрещены (исправление — встречной проводкой); история скинов и журнал книги финансов — UPDATE запрещён, DELETE — только когда родителя уже нет (каскад/loose FK владельца); эскроу — удаления нет, у договора меняется только статус; заморозка — меняются только поля снятия, TRUNCATE запрещён; журнал стираний — меняется только `exported_at`.

## Корзина корневых сущностей

`rootEntity` реестра обязан иметь мягкое скрытие. Задачи, события календаря, записи Диктофона — `deletedAt` + корзина 30 дней по образцу Заметок и Диска: `POST …/:id/trash` → `POST …/:id/restore` → `DELETE …/:id` навсегда **только из корзины** (`400 <сервис>.trashFirst`), `GET …/trash`; каждый путь чтения — `deletedAt: null`; частичный индекс `(deleted_at) WHERE deleted_at IS NOT NULL`; авточистка через 30 дней — раннер сроков (шаги `*.trash`). ## Хранение

Очередь джобов — `fillfactor=80`, автовакуум по порогу; сессии — `fillfactor=85`; леджер — `autovacuum_freeze_min_age=0` + BRIN по `created_at`; lz4 — крупные JSON; BRIN по времени у журналов доставок и `api_access_log`. Индексы под раннер purge и каскад — страж требует индекс под колонку срока/владельца/организации. Выполненные джобы живут сутки, перестройка индексов очереди — раз в неделю ([jobs_engine.md](jobs_engine.md)).

## Наблюдаемость и готовность (`LifecycleDbWatch`, `LifecycleReadinessProvider`)

- **Сторожевые метрики БД** — раз в 5 минут КАЖДЫЙ инстанс, без замка (замок оставил бы сигнал одному процессу, и его смерть = тишина; правила берут `max without(instance)`): функции монитора `lifecycle_db_overview()` (Э5) и `lifecycle_db_metrics()` (миграция `lifecycle_db_metrics`: доля кэша, временные файлы, дедлоки, доля запрошенных чекпойнтов, удержание WAL слотами и потолок `max_slot_wal_keep_size`, архиватор WAL, самая долгая транзакция, старейший `relfrozenxid`) — только числа, владелец `sa6_monitor`, приложению EXECUTE (`db-roles.sql`). Плюс свежесть бэкапов по репозиторию и последнего успешного учения, отставание сроков (тот же допуск, что у плитки обзора). Метрики `lifecycle_db_*`, `lifecycle_backup_last_success_seconds{repo}`, `lifecycle_backup_last_drill_success_seconds`, `lifecycle_retention_*`, свежесть опроса `lifecycle_db_watch_last_success_seconds`. Опрос под `statement_timeout 5 с`; сбой не бросает — стареет метрика свежести, и тревога — на ОТСУТСТВИЕ (`infra/prometheus/alerts.yml`). Сразу, без тика — `POST /lifecycle/dev/db-watch`.
- **Готовность** (`GET /health/ready`, реестр `HealthRegistry` в `shared/health`): движок регистрирует `partitions` (минимум партиций вперёд: < 1 — провал, < 2 — предупреждение; итог живёт минуту на процесс) и `backups` (успех за 26 ч; в разработке — `skipped`). Обе НЕкритичны: беда общая для всех инстансов, и снятие их с балансировщика превратило бы деградацию в аварию.
- **Ключи Redis человека — в инстансе роли семейства**: стирание (`eraseRedis`), канарейка (посев, проверка, уборка) и её обход «всё с id человека» идут в `RedisService.clientFor(роль)` / по `instances()` — обход одного инстанса оставил бы ключи кэша стёртого человека.

## Смоук бута

`LifecycleModule` (`@Global`) на `onApplicationBootstrap`: `lifecycleRegistryProblems()` (включая цикл в плане каскада организации и в плане стирания человека), `defaultPartitionProblems()` (DEFAULT-партиций нет) и регистрации — каждый шаг purge, хук каскада и шаг стирания человека реестра зарегистрирован модулем (кроме ждущих этапа); у политик с `personIds` в живой базе есть функция, она читает каждый ключ реестра, по ней стоит GIN-индекс. Хоть одна проблема — старт API падает. Модуль организаций на старте сверяет `WORKSPACE_LIMITS.archiveRetentionDays` с реестром.

## Ловушки

- **`DETACH … CONCURRENTLY` из функции невозможен**, а DDL журналов — только функциями владельца: сброс — обычный DETACH под `lock_timeout 2 с` с повторами; `DETACH … FINALIZE` из функции работает (PG18).
- **`SET LOCAL` внутри функции утекает в транзакцию вызывающего** — таймаут блокировки задаётся атрибутом функции.
- **ENABLE ALWAYS не наследуется листом при ATTACH** — функция включает его на листе по списку правила; TRUNCATE листа — мимо родителя, поэтому свой BEFORE TRUNCATE.
- **Лист чужой роли функция не сбросит** — листья заводит только `lifecycle_ensure_partition`; сьюты тоже.
- **Переходная таблица триггера (`REFERENCING OLD TABLE`) видна и динамическому SQL** (`EXECUTE format(…)` в PL/pgSQL) — колонка организации передаётся аргументом триггера.
- **Раннер без курсора стоит на месте**, если голова очереди под заморозкой: пачка снова выбирает те же строки. Шаг модуля обязан отдавать keyset-курсор; общая пачка исключает удерживаемое прямо в `WHERE`.
- **`SET lock_timeout` + оператор через пул** Prisma могут уйти в разные соединения — онлайн-раннер держит `connection_limit=1`.
- **Проверка заморозки ВНЕ транзакции удаления — TOCTOU**: заморозка, закоммиченная между проверкой и удалением, не спасла бы строку. Только `releasable(tx, …)` / `NOT EXISTS` под общим замком.
- **Организация контекстного чата пишется при создании** (`Chat.workspaceId` = организация задачи / магазина заказа / встречи): без неё вложения уходят на личные Диски и переживают организацию, звонок считается личным, каскад не находит чат, проекция поиска теряет организацию.
- **Каскад FK в таблицу владельца исполняется ОТ ВЛАДЕЛЬЦА дочерней таблицы** (RI-триггер PostgreSQL переключает пользователя): её построчные триггеры, читающие таблицы приложения, работают с правами `sa6_data_owner`. Родителя, которого проверяет триггер, владелец обязан видеть — минимум колонок (`GRANT SELECT ("id")` в `db-roles.sql`, так у истории скинов); иначе удаление родителя падает `42501` на ВСЕХ путях (стирание аккаунта, каскад организации), а не только в тесте.
- **Кэш правил** — 5 минут на процесс; промах в горячем пути перечитывает один раз.
- **Сторожевая строка на uuid-колонке** (`{ id: '__none__' }`) падает P2023; «ничего» — `{ id: { in: [] } }`. Агрегата `max(uuid)` нет. Не-uuid от клиента → `404 db.notFound` ([api_conventions.md](api_conventions.md)).
- **Литерал похож на ключ Redis, но им не является** (AAD шифрования, метаданные декораторов): страж сканирует только файлы, работающие с Redis.
- **Точка в ключе каталога запрещена** (next-intl делит по точке): `table:analytics.events` живёт в каталоге как `tables.analytics_events`.

## Проверка

- `pnpm check:lifecycle` / `pnpm check:migrations` — на срабатывание проверены подсадками (модель без политики, `retain_legal` без нормы, `'30'`, незарегистрированный хук, пачка каскада без индекса; миграция без заголовка, с int4-ключом, `PARTITION OF … DEFAULT`, `DEFAULT now()`, индекс на большой таблице, CONCURRENTLY рядом с другим оператором) — красный; после уборки — зелёный.
- `node apps/api/scripts/verify-purge.cjs` — план раннера и каскада, триггеры учёта на родителях; общая пачка (dry-run, удаление старше срока, заморозка пространства держит, снятая отпускает, событие журнала); каждый сигнал здоровья останавливает пачки; гонка «заморозка во время прогона» (пачка ждёт коммита); кэп радиуса ретеншна архива; loose FK после сырого DELETE; каскад организации (Chat.workspaceId, предпросмотр, заморозка → 409, все шаги плана); корзина задач через раннер; временный каталог; очередь и окно; метрики; команда Кабинета (self-target, предпросмотр без эффектов, исполнение джобом).
- `node apps/api/scripts/verify-partitions.cjs` — функции владельца на пробном родителе `lc_probe.events` (ATTACH без ACCESS EXCLUSIVE, идемпотентность, владелец листа, запрет DEFAULT, пол срока, FINALIZE, заморозки, очередь, событийный триггер, append-only, реальные родители, время доставок).
- `node apps/api/scripts/verify-trash.cjs` — корзины задач и событий; записей — `verify-voice.cjs`, возврат заморозки награды — `verify-escrow.cjs`; каскад организации сквозь сервисы — `verify-workspace-restore.cjs`.
- `node apps/api/scripts/verify-lifecycle-export.cjs` — выгрузки человека и организации, страж владельца, восстановление арендатора ([lifecycle_export.md](lifecycle_export.md)).
- `node apps/api/scripts/verify-health.cjs` — пробы `/health/live|ready`, сторожевые метрики и HTTP-гистограмма (ни одного id в метке маршрута), пул через PgBouncer (подготовленные выражения, `SET LOCAL`), потолки роли и их снятие обслуживающим подключением, политики вытеснения двух Redis, ACL приложения (KEYS/CONFIG закрыты — срабатывание), кэш-ключ в инстансе кэша, env-валидация production (неполная конфигурация отвергается).
- `node apps/api/scripts/verify-lifecycle.cjs` — живые сверки: каждая таблица базы покрыта политикой; каждый FK базы объявлен ребром; каждый ключ живого Redis (оба инстанса) принадлежит семейству и лежит в инстансе СВОЕЙ роли; у семейств с потолком TTL нет ключей без срока и срок не выше потолка реестра; CHECK-ограничения движка = перечисления shared; разделы 4–6 — заморозки на всех путях, стирание до сертификата, канарейка ([lifecycle_erasure.md](lifecycle_erasure.md)); 7–8 — сроки организаций, таймер чата, дашборд ([lifecycle_settings.md](lifecycle_settings.md)).

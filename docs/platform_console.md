# core/platform — Кабинет платформы (20-й движок)

> Внутренний контур для СОТРУДНИКОВ ПЛАТФОРМЫ (поддержка, биллинг, безопасность): свой список сотрудников и ролей — НЕ `user_roles`, свой токен `aud: platform` с отдельным секретом, маршруты `/platform/*` закрыты по умолчанию, каждое действие = команда реестра с журналом, идемпотентностью, step-up и (для опасного) вторым сотрудником. Первый потребитель — тарифы ([entitlements_engine.md](entitlements_engine.md)); дальше сюда садятся любые «операции для поддержки» любого сервиса — +1 команда/панель в реестр, без новых контроллеров.

Код: `apps/api/src/core/platform/` (`platform-auth.service.ts` вход/сессия/step-up, `platform-auth.guard.ts` APP_GUARD, `platform-access.service.ts` сотрудники и способности, `platform-commands.registry.ts` + `platform-commands.service.ts` реестр и исполнитель, `platform-audit.service.ts`, `platform-lookup.registry.ts` + `platform-lookup.service.ts` поиск/360/панели, `platform-requests.service.ts` заявки «четыре глаза», `platform-policy.service.ts`, `platform.controllers.ts`, `platform.provider.ts` собственные команды, `platform.notifications.ts`, `platform.cron.ts` уборка, `platform.dev.ts`, `platform.module.ts` со смоуком). Shared: `packages/shared/src/platform/` (`capabilities.ts`, `roles.ts`, `pii.ts`, `commands.ts`, `lookup.ts`), формы — `types/platform.ts`, Zod — `validation/platform.ts`. Декораторы — `shared/decorators/platform.decorator.ts`.

## Сотрудники и роли

`PlatformStaff` (userId, status `active|suspended`, note) + `PlatformStaffRole` (role, `expiresAt?`). Роли — `PLATFORM_ROLES`: ЖИВАЯ РОЛЬ ОДНА — `platform_owner` (все способности, `sodExempt`); узкие роли (support, billing, security, auditor) реестр умеет, но пока не объявлены — новая роль = строка в `PLATFORM_ROLES` + `platform.roles.<key>` в трёх каталогах. Способности — `PLATFORM_CAPABILITIES` (`platform.lookup.read`, `platform.pii.reveal`, `platform.staff.read|write|approve`, `platform.audit.read`, `platform.policy.write|approve`, `entitlements.catalog.read|write`, `entitlements.subject.read|write`, `entitlements.grant.write`, `entitlements.override.write|approve`, `analytics.read`, `analytics.person.read`, `analytics.manage`). Способности кабинета читаются ТОЛЬКО внутри `core/platform` — продуктовый путь их не спрашивает (страж `no-restricted-imports` на `platform-access.service`/`platform-auth.service` в `apps/api/eslint.config.mjs`; единственное исключение — `core/users`, где анонимизация аккаунта снимает человека со штата). Служебная операция оформляется КОМАНДОЙ кабинета: иначе привилегия срабатывала бы по продуктовому токену — без step-up и без журнала кабинета (так было с мёртвым правом `processes.system.manage`, снятым 2026-09-12). `approvePairOf` — пара «делает / одобряет», `sodConflicts` — роли, которые нельзя совместить (кроме владельца). Первый владелец — `node apps/api/scripts/platform-bootstrap-owner.cjs +7XXXXXXXXXX` (повтор при живом владельце — отказ); дальше — команды `platform.staff.*` из кабинета. Приостановка отзывает сессии (`platform.session_revoked`) и вход (`403 platform.not_staff`).

## Вход и сессия

`POST /platform/auth/start {phone, password}` → пароль проверяется первым (5 неверных → `429 platform.login_blocked`), затем SMS-цепочка `core/verify` с purpose `platform_login` → `POST /verify/check` → `POST /platform/auth/login {verifyToken}` → токен кабинета: JWT `aud: 'platform'`, подписан парой Ed25519 движка ключей (аудитория `platform`; `PLATFORM_JWT_SECRET` — только legacy-окно HS256), срок 8 ч, `PlatformSession` с простоем 20 мин (`401 platform.session_idle`), отзыв по эпохе. Step-up: `POST /platform/auth/step-up/start {password}` → код (purpose `platform_step_up`, `expectedUserId`) → `/step-up/confirm` → `sudoUntil` = 15 мин. Пароль step-up считается так же строго, как на входе: 5 неудач по сотруднику → `429 platform.login_blocked` на 15 минут, каждая неудача = строка журнала `denied` (`platform.auth.step_up`), на пороге — `platform.security.alert` владельцам (иначе угнанная сессия перебирала бы пароль бесплатно и без следа). `POST /platform/auth/logout` отзывает сессию. Продуктовый токен на `/platform/*` и токен кабинета на продуктовых ручках → `401`; `X-Workspace-Id` на `/platform/*` → `400 platform.workspace_header_rejected` (кабинет вне B2B-контекста — chokepoint его не трогает).

## Гард: закрыто по умолчанию

`PlatformAuthGuard` (APP_GUARD) обслуживает только классы с `@PlatformRoute()`; продуктовые `JwtAuthGuard`/`RolesGuard` их пропускают. Каждый маршрут ОБЯЗАН объявить доступ: `@PlatformPublic()` (только вход), `@PlatformSession()` (живая сессия) или `@PlatformCapability('…')`; `@Public()` под `/platform` запрещён. Смоук на `onApplicationBootstrap` (`DiscoveryService`) роняет старт при контроллере под `platform/*` без `@PlatformRoute()` или маршруте без объявления — «забыл декоратор» = не поднялось, а не «открыто». Стоп-кран `PLATFORM_CONSOLE_ENABLED=false` → все `/platform/*` отвечают `404` без деплоя.

## Команды: реестр + исполнитель

```ts
PlatformCommandsRegistry.register({
  key, version, group, titleKey, descriptionKey?, input: ZodSchema, capability, risk: 'low'|'medium'|'high'|'critical',
  dualControl?, dualControlSoft?, stepUp?, reasonRequired?, dryRun?, entities?: PlatformEntity[], redact?, persistResult?,
  target(input) → { entity, id }, execute(ctx, input, tx) → { before?, after?, result?, invalidateStaff?, afterCommit? }, preview?(ctx, input, tx)
});
```

Ручки: `GET /platform/commands` (видимые актору, вход как JSON Schema — веб строит форму сам) · `POST /platform/commands/:key {input, idempotencyKey, reason?, ticketRef?}` · `POST /platform/commands/:key/preview` (dryRun: `execute` внутри транзакции с откатом-сентинелом; предпросмотр — тоже чтение чужих данных: те же ворота, что у панели, — sudo у команд `stepUp`, общий бюджет просмотров (`PlatformRateService.assertViewBudget`), запрет цели-себя и строка журнала `dryRun: true, readOnly: true`). **Эффекты ВНЕ базы в предпросмотре молчат:** транзакция откатит строки, а INCR эпохи в Redis, событие шины или письмо не откатило бы ничто — исполнитель оборачивает вызов в `DryRun.run(...)` (`shared/context/dry-run.context.ts`), и каждый такой эффект спрашивает `DryRun.active()` перед тем, как случиться (образец — `EntitlementsCache.bump/bumpCatalog`: без этого «предпросмотр публикации версии плана» сбрасывал бы кэш тарифов всей платформы, а «предпросмотр смены подписки» слал бы членам организации сокет «тариф изменился»). Конвейер исполнителя, строго по порядку: **capability** → **цель не сам актор** (`forbidSelfTarget` в паспорте: цель `user` = сотрудник либо `workspace`, которым он ВЛАДЕЕТ → `403 platform.self_target`; гвард стоит и на прямом исполнении, и на предпросмотре, и на исполнении одобренной заявки — одобрение второго не делает выдачу привилегии себе допустимой) → **step-up** (`high`/`critical` или `stepUp` → без живого sudo `403 platform.step_up_required`) → **reason** (`PLATFORM_LIMITS.reasonMinLength`, обязателен у high/critical и там, где паспорт объявил `reasonRequired: true` — `platform.pii.reveal`; веб читает флаг `reasonRequired` из витрины команд, своего списка ключей не держит) → **dual control** (политика `dualControlEnabled` И `def.dualControl` → вместо исполнения `ApprovalRequest` на адресата `platform_capability:<approve-способность>`, ответ `{status: 'pending', requestId}`; автор одобрить не может — `403 platform.author_cannot_approve`; `dualControlSoft: true` — если держателя одобряющего права НЕТ ни одного, команда исполняется напрямую: иначе кабинет с единственным владельцем запирается насмерть (второго некому добавить, политику некому выключить). Такая строка журнала отличима: `dualControl` у команды есть, а `approvalId` пуст; владельцам уходит `platform.security.alert` с событием `soloDualControl`) → **идемпотентность** (уникум `(actorId, commandKey, idempotencyKey)`; повтор с тем же `inputHash` → тот же ответ с `replayed: true`, с другим → `409 platform.idempotency_mismatch`) → **redact** (маски в `input` журнала) → **транзакция**: `execute` + строка журнала в одной `$transaction` → событие шины. `persistResult: false` — результат не пишется в журнал (раскрытие PII). Команда, меняющая штат или роли, возвращает `invalidateStaff: [userId]` — исполнитель сбрасывает кэш способностей ПОСЛЕ коммита: сброс внутри транзакции гонится с параллельным чтением, которое кладёт в кэш ещё старое состояние на минуту (отозванная роль продолжала бы действовать). Тем же каналом идёт любой эффект вне базы — `afterCommit: () => Promise<void>` (заморозка KEK организации сбрасывает эпоху keystore): хук зовётся после коммита на прямом исполнении и на исполнении одобренной заявки, предпросмотр его не зовёт, ошибка хука команду не роняет. Реестр заполняют владельцы данных в своём `onModuleInit` (`entitlements.platform.provider.ts`, `platform.provider.ts`, `users-platform.provider.ts`, `workspaces-entitlements.provider.ts`) — кабинет фичи не импортирует.

Команды сейчас: `entitlements.plan.createVersion|updateDraft` (medium) · `publishVersion` (high, dryRun) · `archiveVersion` (high) · `entitlements.subscription.set` (high, dualControl, dryRun, не себе) · `trial.extend` (high, не себе) · `grant.create` (high, dualControl, не себе) · `grant.revoke` (medium, `reasonRequired`) · `override.set` (high, dualControl, dryRun, не себе) · `override.clear` (high, dualControl, не себе) · `platform.staff.add|suspend|role.grant|role.revoke` и `platform.policy.set` (critical, `dualControl` + `dualControlSoft`: состав штата и сам тумблер four-eyes меняются вдвоём, пока владелец не один) · `platform.pii.reveal` (medium, но `stepUp` и `reasonRequired`: раскрытие персональных данных — под SMS-подтверждением и с причиной, результат не хранится) · `analytics.event.setStatus` (medium, `reasonRequired` — рубильник события аналитики) · `analytics.user.forget` (high, не себе — забвение аналитики человека) · `analytics.rollup.rebuild` (medium, dryRun — пересчёт роллапов за диапазон). Движок ключей: `keys.root.rotate` (critical, dualControl, dryRun — ротация корня), `keys.signing.rotate` (high), `keys.workspace.freeze|unfreeze` (critical, dualControl — kill-switch данных организации), `keys.workspace.rotateKek` (high), `keys.key.revoke`, `keys.bot.freeze|unfreeze` (high, с причиной); панели `workspace.keys` / `user.keys` (способность `keys.read`; сводки ключей без секретов); от `core/webhooks` — `webhooks.endpoint.disable|enable` (high, с причиной: стоп-кран исходящих запросов, организация его сама не снимает) и панель `workspace.webhooks` (адреса без query) — [webhooks_engine.md](webhooks_engine.md) — [keys_engine.md](keys_engine.md), [keys_api_access.md](keys_api_access.md). Панели аналитики `user.analytics` / `workspace.analytics` (способность `analytics.person.read`, только агрегаты за 28 дней) и раздел «Аналитика» (`analytics.read`, маршруты `/platform/analytics/*`) — [analytics_reports.md](analytics_reports.md).

ПРАВИЛО: четыре глаза и запрет цели-себя стоят на ВСЕХ дверях, которые ПОВЫШАЮТ права субъекта, а не на самой заметной из них. Подписка, грант со значением «без ограничения» и оверрайд `unlimited` дают один и тот же эффект — контроль на одной двери обходился бы соседней; снятие зеркалит установку (`override.clear` = `override.set`), иначе условие ставится вдвоём, а снимается одной рукой. Отсюда пары `.write/.approve` у `entitlements.subject`, `entitlements.grant` и `entitlements.override`.

## Четыре глаза, журнал, заявки

Заявка кабинета — обычный `ApprovalRequest` с провайдером `consoleOnly: true` в `ApprovalsRegistry`: она НЕ попадает в продуктовую стопку «Ждут решения» и не шлёт продуктовых уведомлений; адресат — вид `platform_capability` движка адресатов (все активные сотрудники со способностью). `GET /platform/requests?state=pending|mine|history`, `GET /platform/requests/:id`, `POST /platform/requests/:id/decide {decision, comment?}`, `POST /platform/requests/:id/withdraw` (автор отзывает свою — заявка становится `cancelled`) — решение по high/critical требует живого sudo решающего; одобрение исполняет команду от имени автора, строка журнала несёт `approvalId` и `onBehalfOfId`. Перед исполнением сверяются ТРИ вещи автора: он всё ещё активный сотрудник, у него всё ещё есть способность команды и `commandVersion` заявки совпадает с версией паспорта (`409 platform.command_version_changed`: одобряли одну семантику — деплой не должен подменить её другой; заявку подают заново). Уведомления `platform.request.pending|resolved`, `platform.security.alert` (`packages/shared/src/notifications/platform.ts`).

`PlatformAuditEntry` — append-only (триггер `platform_audit_entries_immutable` запрещает UPDATE/DELETE): актор, команда+версия, цель, `input` (после redact), `before/after`, `reason`, `ticketRef`, `outcome ok|denied|error`, `stepUpAt`, `dryRun`, `idempotencyKey`. Отказы по способности тоже пишутся (`denied`). `PlatformAccessLog` — каждый просмотр карточки 360, панели и карточки субъекта тарифов (кто на кого смотрел); живёт `PLATFORM_LIMITS.accessLogRetentionDays` (365 дней) и чистится ночным `PlatformCron` вместе с мёртвыми сессиями кабинета (истёкшие/отозванные старше суток). Журнал КОМАНД не удаляется никогда: триггеры роняют и UPDATE/DELETE, и TRUNCATE. `GET /platform/audit` — курсорная страница с фильтрами актор/команда/цель/период/исход.

## Поиск, карточка 360, PII

`parsePlatformQuery(q)` (shared) — `phone` (полный номер) · `idNumber` (12 цифр ИИН/БИН) · `uuid` · `text` (≥ 3 символов) · `tooShort` · `empty`; неполный номер и короткий текст НЕ ищутся — энумерации нет. `GET /platform/lookup?q=` → люди и организации, `GET /platform/entities/:entity/:id` → шапка + чипы + панели (два реестра: `PlatformLookupRegistry.register({entity, match, header})` — провайдер поиска сущности, `PlatformPanelRegistry.register({key, entity, titleKey, capability, eager, load})` — панель карточки) + команды, доступные актору для этой сущности (`entities` в паспорте команды), `GET /platform/entities/:entity/:id/panels/:key` — данные одной панели. Бюджет чтений (`entityViewsPerMinute`) и строка `PlatformAccessLog` стоят на ВСЕХ путях чтения: карточка, отдельная панель, `GET /platform/entitlements/subjects/:type/:id` и ПРЕДПРОСМОТР команды — иначе выгрузка шла бы соседней ручкой того же кабинета в обход потолка. Счётчик живёт отдельным `PlatformRateService` (`assertViewBudget` / `assertLookupBudget`) именно поэтому: принадлежи он одной витрине, следующая дверь снова считала бы свой. Отказ по способности на панели — `403` (не 400), превышение потолка — `429 platform.rate_limited`. Панель, зовущая движок, ходит его `system*`-методом: карточка тарифов берёт `entitlements.subjectDetail` → `systemSnapshot`, поэтому сотрудник кабинета видит подписку субъекта целиком (в продукте та же карточка гейтится ролью в организации). PII в ответах ТОЛЬКО масками (`maskPhoneForConsole` → `+7 700 ••• 45 67`, `maskIdNumber`, e-mail); полное значение — только командой `platform.pii.reveal {entity, id, fields}` с причиной, живёт в памяти вкладки и в журнал не попадает.

## Env, проверка, ловушки

`PLATFORM_JWT_SECRET`, `PLATFORM_CONSOLE_ENABLED` — [environment_variables.md](environment_variables.md). `node apps/api/scripts/verify-platform-console.cjs`: bootstrap владельца и отказ повтора, вход пароль→OTP→токен, блок после 5 паролей, не-сотрудник → 403, токены не взаимозаменяемы, `X-Workspace-Id` → 400, high без sudo → 403, отказ по способности → 403 + строка `denied`, выдача роли сбрасывает кэш способностей, lookup (телефон/uuid/название, маски, короткий запрос — пусто), карточки и панели, `PlatformAccessLog`, `pii.reveal` без результата в журнале, dual control: `pending` → автор не одобряет → второй без sudo → 403 → sudo → `executed` с `approvalId`/`onBehalfOfId`, повтор ключа → тот же `requestId`, продуктовые `approvals/steps/:id/decide` и `approvals/:id/cancel` по заявке кабинета → `403 approval_console_only` (и её нет в `approvals/mine`), отзыв автором в кабинете → `cancelled` + повтор → 409, предпросмотр оставляет строку `dryRun`, `pii.reveal` без причины → 400, серия неверных паролей step-up → 429 + строка `denied`, простой сессии → 401, приостановка → отзыв сессий и отказ входа, logout. Ручные стражи: подсадить маршрут под `/platform` без декоратора → бут падает; `PLATFORM_CONSOLE_ENABLED=false` → 404.

- Провайдер, который нужен APP_GUARD (`PlatformNotifier` и т.п.), обязан быть в `exports` `PlatformModule` — гард живёт в контексте `AppModule`.
- `entities` в паспорте команды — иначе карточка 360 команду не покажет; `target()` обязан вернуть цель — по ней фильтруется журнал.
- Результат команды с PII — только `persistResult: false` + `afterForAudit`: журнал вечен.
- Значения дат во входе (`validUntil`) фиксировать в одном объекте до отправки — пересчёт «сейчас + 30 дней» при повторе даёт другой `inputHash` и `409`.
- Заявку кабинета решают только через `/platform/requests/:id/decide`, отзывают — через `/platform/requests/:id/withdraw`: продуктовые `POST /approvals/steps/:stepId/decide` и `POST /approvals/:id/cancel` для `consoleOnly` типов отвечают `403 approval_console_only` (страж `assertNotConsoleOnly`, обходить его можно только внутренним флагом `fromConsole`), а `GET /approvals/mine` и стопка их не показывают. Без этого запрета адресат шага закрывал бы заявку продуктовым токеном — без step-up и без проверки разделения обязанностей.
- Права автора проверяются в МОМЕНТ исполнения одобренной заявки (`executeApproved`): приостановленный или лишённый роли автор получает отказ, заявка уходит в `failed`.
- Анонимизация аккаунта снимает человека со штата платформы и гасит его консольные сессии (`systemSuspendDeletedUser`, строка журнала `platform.staff.suspend` с `actorId = null`); плановое удаление отзывает сессии кабинета вместе с продуктовыми.

# core/approvals — движок согласований («Ждут решения»)

> «Задачник для решений»: заявка знает свой ПРЕДМЕТ, попадает в общую стопку, в чат рич-карточкой и в журнал. Три вида шага (согласование · подпись · ознакомление), три исхода (согласовать · отклонить · на доработку; причина обязательна на двух последних; у ознакомления исход один). **Ветвлений/условий/циклов НЕТ намеренно** — это Процессы; второй маршрутизатор не пишется. Относится к Процессам как Задачник: они им пользуются, но он живёт и без них.

## Модель

- **`ApprovalRequest`** — предмет refType+refId БЕЗ FK + снимок refTitle/refIcon; `originType`+`originRef` — непрозрачная пара «кто ведёт снаружи» (Процессы). Партиальный уникум «одна живая заявка на шаг ведущего» (на ВЕДУЩЕМ, не на предмете: на одном документе законны параллельные подпись и ознакомление) + идемпотентный create (P2002 → та же заявка): движок Процессов толкает at-least-once.
- **`ApprovalStep`** — **группы по `order`** (одинаковый = параллельно; следующая активируется по закрытии предыдущей — отдельного режима «последовательно/параллельно» нет намеренно); `kind` approval|signature|acknowledgement; `rule` any|all; `dueHours` → `deadlineAt` **при активации** (не от создания); `requiredSignatureKind` (null → клик закрывает; sms|ecp → публичный decide отвергается `approval_needs_signature`); **снимок адресатов `awaitingUserIds`** + GIN.
- **`ApprovalDecision`** — неизменяемо, `@@unique([stepId, userId])`, `subjectSha256` той версии предмета, что видел решающий, `signatureKind`.

## Несущие решения

- **Снимок адресатов при активации**: адресат разворачивается в людей РОВНО ОДИН РАЗ через единый словарь [audiences_engine.md](audiences_engine.md) (`APPROVAL_ASSIGNEE_TYPES`: user/position/department/branch/**manager_of**/**branch_head_of**; якорь `$initiator` = автор заявки) — вошедший позже не получает чужую обязанность, ушедший не подвешивает шаг; «руководитель на момент активации» согласуется с инвариантом снимка. **Вершина без руководителя → владелец организации** (снимок не пуст; подпись шага — «Руководитель инициатора»). Чужой отдел → пусто → `approval_empty_assignees`. Читающий путь стопки не ходит в движок прав (одно GIN-условие).
- **Пустой снимок адресатов = честный отказ** (`approval_empty_assignees`) — шаг «в никуда» не активируется; при активации СЛЕДУЮЩЕЙ группы пустой снимок откатывает транзакцию решения (решающий получает отказ и решает заново после починки маршрута — вечно висящий шаг хуже).
- **Авто-согласий по молчанию НЕТ** (подпись того, кто не открывал документ, ничего не стоит); просрочка = эскалация (`approvals.escalate`, runAt=deadlineAt; адресатам, автору И ВВЕРХ — `manager_of` каждого просрочившего) + напоминание ДО срока (`approvals.remind`, runAt = deadlineAt − min(24ч, окно/2); окно ≤2ч — не напоминаем).
- Гонки гасят индекс и статус-гвард, а не проверки в приложении. Побудка ведущего — джоб `approvals.resolved` В ТОЙ ЖЕ транзакции закрытия.
- **`decideAttested(tx, …)`** — закрывающий вход для core/sign: наружу НЕ выставлен, зовётся из транзакции финализации акта → акт подписан и шаг закрыт ОДНИМ коммитом. Публичный `decide` всегда пишет `internal` (уровень от клиента не принимается). Членство сверяется В МОМЕНТ решения (не только при открытии экрана). ЭЦП закрывает шаг, которому хватало ПЭП; наоборот — нет.
- **`releaseUserFromWorkspaceSteps`** — увольнение снимает человека со снимков шагов + пересчёт закрытия (пусто без решений → skipped + `approval.unassigned` автору). Общий хук витрины: `InboxSource.releaseUser` в реестре источников — каскад снимает и задания кампаний.

## Контракт потребителя

```ts
ApprovalsRegistry.register(refType, { describeForCreate, canView?, describeRef? })
ApprovalsService.create(userId, { refType, refId, steps }, origin?)  // из СВОЕГО кода
ApprovalsService.cancelByOrigin(type, ref)
ApprovalsRegistry.registerOrigin(...)   // хук возврата токена ведущему (Процессы)
ApprovalsRegistry.registerSource(key, { label, count, list, releaseUser? })  // своя стопка в общей витрине
```
⚠️ **Ручки `POST /approvals` НЕТ и быть не должно**: право «отправить это на согласование» знает только потребитель. Следствие: **`describeForCreate` ОБЯЗАН проверять право и возвращать null без него** — единственный проход, через который заводится заявка.

## Стопка и скоупы

`GET /approvals/inbox` (+`/count`) — витрина ПО РЕЕСТРУ источников (элемент общей формы `InboxItemDto`); источники: approvals, sign (свободные подписи), hr_campaign. **Три состояния скоупа**: `workspaceId=` · `scope=personal` · без параметров = сквозной. Правило витрин: верхние иконки топбара — СКВОЗНЫЕ; личная Главная — `scope=personal`; организация — свой workspaceId.

`GET /approvals/mine?archived=` (только queryBoolean!) · `GET /approvals/:id` · `POST /approvals/:id/cancel` · `POST /approvals/steps/:stepId/decide`. ⚠️ Статические пути ДО `:id`.

## Веб

Карточка заявки — ОДИН компонент `components/approvals/ApprovalCard` на ДВА адреса: `/workspaces/[id]/approvals/[approvalId]` и `/approvals/[id]` (личный САМ переадресует рабочую внутрь организации — самолечатся разосланные уведомления). Адрес собирает общий `approvalHref(requestId, workspaceId?)` из shared — строкой на месте не собирать. `DecisionStack` — листалка стопки («отклонить»/«на доработку» первым кликом раскрывают причину); подписной шаг вместо кнопок решения показывает «Подписать»; после подписи следующий подписной открывается сам (очередь «N из M»).

## Дев-полигон

`POST /approvals/dev/request|outcome` (только development, refType `approval_dev`) — движок проверяется сьютом ДО первого настоящего потребителя.

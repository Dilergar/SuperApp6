# Тестирование: verify-сьют

> Главный страж корректности платформы — e2e-сьют `apps/api/scripts/verify-*.cjs` (68 скриптов), гоняется в CI против живого API + живой БД. Юнит-тестов 0 — осознанная текущая реальность; каждый сервис обязан иметь свой verify-скрипт.

## Правила написания verify-скрипта

1. **Обвязка — только из общего `apps/api/scripts/_lib.cjs`** (`const { call, login, makeChecker, SUITE } = require('./_lib.cjs')`): HTTP/логин/чекер/чтение `.env`. Не копировать из соседнего скрипта (до _lib обвязка была скопирована в 58 файлах в 7 разъехавшихся вариантах).
2. **Только аккаунты сьюта** `suite1/2/3` (константа `SUITE`) — НЕ tester1/2/3: те живые, в них человек работает в браузере.
3. **БД общая живая** (dev/CI), поэтому «чистый старт» через `deleteMany` по userId/uploaderId/ownerId ЗАПРЕЩЁН — уносит реальные данные (FileLink каскадится за FileObject: вложение исчезает из задачи молча). Вместо этого: **базовая линия + проверки на дельту**, свои id в наборе, в конце — уборка ТОЛЬКО их и **штатным путём** (`DELETE /files/:id`, а не сырой deleteMany: иначе квота остаётся раздутой, байты виснут).
4. **Страницу читать строго как `json.data.items` / `json.data.nextCursor`** — сьют единственное место, где форма провода проверяется по факту; ослаблять до `json.data?.items ?? json.data` нельзя.
5. Скрипт должен быть **идемпотентен к повторному прогону** и убирать за собой (накопленный мусор упирается в лимиты и роняет ЧУЖИЕ сьюты — прецеденты: потолок «20 организаций на владельца», потолок `inboxPerSource: 50`).
6. Выбор объектов в проверках — по стабильному признаку (`assigneeId`), не по индексу массива (порядок неустойчив → плавающие падения).
7. Новый скрипт автоматически попадает в CI.

## Тестовые аккаунты — ДВЕ РАЗНЫЕ ТРОЙКИ (не смешивать)

Пароль у всех `Test1234!`; сеет `apps/api/scripts/seed-test-accounts.cjs`:

| Назначение | Аккаунты |
|---|---|
| **Ручные** (человек в браузере) | tester1 `+77001234567` · tester2 `+77012345678` · tester3 `+77023456789` |
| **Сьюта** (все verify-*.cjs) | suite1 `+77009990001` · suite2 `+77009990002` · suite3 `+77009990003` |

Весь мусор прогонов копится в аккаунтах сьюта. Уборка накопленного:
- `apps/api/scripts/gc-test-workspaces.cjs` — организации от скриптов + их задачи/чаты/хроника. ⚠️ `tasks.workspace_id` = SET NULL: голое удаление организации превращает её задачи в ЛИЧНЫЕ.
- `apps/api/scripts/gc-orphan-bytes.cjs` — байты в `storage/` без строки в БД.
- Оба по умолчанию сухие; удаляют по `--apply`.

## CI (`.github/workflows/ci.yml`)

PG16 + Redis7 service-контейнеры → build shared + api-client → prisma generate + `migrate deploy` → build api → web tsc → линт-стражи (веб-граница + страж исходящих API) → старт API → seed → полный verify-сьют.

Env CI: `VERIFY_TEST_PHONES` (тест-карта номеров: фикс-код, SMS не шлётся, лимиты скипаются) + `VOICE_STT_MOCK=true` (полный голосовой пайплайн без сети). Чеки, требующие живых сайдкаров, делают честный SKIP.

## Локальный прогон

```bash
node apps/api/scripts/verify-<name>.cjs
```
API должен быть запущен. ⚠️ Перед прогоном убедиться, что на :3001 не висит **стейл-процесс** `node dist/main.js` со старым кодом в памяти — новый параметр будет отвечать 400/не работать при полностью правильном коде.

## Что дополняет сьют

- Линт-стражи (контрактная граница веба + исходящий HTTP API) — проверены НА СРАБАТЫВАНИЕ: зелёный линтер одинаково зелен и когда правило работает, и когда селектор промахнулся → подсадить нарушение, увидеть падение, убрать.
- Браузерная проверка руками/агентом после UI-правок (0 ошибок консоли — критерий).
- Смоук DI-токенов на bootstrap.

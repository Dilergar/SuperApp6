# Тестирование: verify-сьют

> Главный страж корректности платформы — e2e-сьют `apps/api/scripts/verify-*.cjs` (CI берёт их по глобу — число не фиксируется, чтобы не дрейфовало), гоняется в CI против живого API + живой БД. Юнит-тестов 0 — осознанная текущая реальность; каждый сервис обязан иметь свой verify-скрипт.

## Правила написания verify-скрипта

1. **Обвязка — только из общего `apps/api/scripts/_lib.cjs`** (`const { call, login, makeChecker, SUITE } = require('./_lib.cjs')`): HTTP/логин/чекер/чтение `.env`; вход в Кабинет платформы и step-up — `consoleLogin(phone)` / `consoleSudo(token)` (код берётся дев-ручкой `verify`). Не копировать из соседнего скрипта (до _lib обвязка была скопирована в 58 файлах в 7 разъехавшихся вариантах).
   `call()` шлёт `X-Locale: ru` (переопределяется `SA6_SUITE_LOCALE`) — заголовок ЯВНОГО выбора языка. Не `Accept-Language`: подсказку браузера сервер маршрутизирует под рынок (русский браузер → казахский), и 70+ русских текстовых ассертов покраснели бы разом, ничего при этом не сломав. Скрипты со своей копией `http()` ставят тот же заголовок. `null` в заголовке вызывающего СНИМАЕТ его — так `verify-i18n.cjs` проверяет поведение без выбора («что увидит гость с таким браузером»). Новый ассерт пишется на ПОВЕДЕНИЕ (`details.code`, статус, `outcome` шага), а не на фразу: текст живёт в каталоге и меняется вместе с ним — ассерт на слово краснеет от чужого перевода, ничего не сломав.
2. **Только аккаунты сьюта** `suite1/2/3` (константа `SUITE`) — НЕ tester1/2/3: те живые, в них человек работает в браузере.
3. **БД общая живая** (dev/CI), поэтому «чистый старт» через `deleteMany` по userId/uploaderId/ownerId ЗАПРЕЩЁН — уносит реальные данные (FileLink каскадится за FileObject: вложение исчезает из задачи молча). Вместо этого: **базовая линия + проверки на дельту**, свои id в наборе, в конце — уборка ТОЛЬКО их и **штатным путём** (`DELETE /files/:id`, а не сырой deleteMany: иначе квота остаётся раздутой, байты виснут).
4. **Страницу читать строго как `json.data.items` / `json.data.nextCursor`** — сьют единственное место, где форма провода проверяется по факту; ослаблять до `json.data?.items ?? json.data` нельзя.
5. Скрипт должен быть **идемпотентен к повторному прогону** и убирать за собой (накопленный мусор упирается в лимиты и роняет ЧУЖИЕ сьюты — прецеденты: потолок «20 организаций на владельца», потолок `inboxPerSource: 50`).
6. Выбор объектов в проверках — по стабильному признаку (`assigneeId`), не по индексу массива (порядок неустойчив → плавающие падения).
7. Новый скрипт автоматически попадает в CI.
8. **Организацию сьют заводит только хелперами `_lib.cjs`**, голый `POST /workspaces` запрещён. У владельца потолок `workspaces.maxOwned` — 20 ЖИВЫХ организаций (архивные не считаются). Сьют, который заводит организацию каждый прогон и не архивирует её, через 20 прогонов роняет ЧУЖИЕ сьюты ответом `402 entitlement.limit_reached` на создании организации.
   - `ensureSuiteWorkspace(token, 'Сьют-X')` — одна организация на все прогоны: берётся своя живая по имени/префиксу, иначе создаётся. Годится, когда сьют не считает её содержимое (данные внутри копятся).
   - `createSuiteWorkspace(token, 'Сьют-X', body?, { purge? })` — свежая `«Сьют-X <метка>»` на каждый прогон; возвращает ответ `call()`, как голый POST. В архив её отправляет штатный `DELETE /workspaces/:id` в `finish()` и `crash()` (`main().catch(crash)`): `process.exit` не ждёт `finally`. Скрипт со своим `process.exit` зовёт `fails += await archiveSuiteWorkspaces()` в `finally`. Хвост упавшего прошлого прогона с тем же префиксом уходит в архив ДО создания новой, поэтому счётчик не растёт и после Ctrl+C.
   - `{ purge: true }` — после архива удалить насовсем штатным каскадом `purgeWorkspace` через дев-ручку `POST /workspaces/dev/purge-archives { workspaceId }` (только своя и только из архива). Для сьютов, чьи чаты встреч и задачи не должны 90 дней висеть в списках аккаунтов сьюта. Своя копия каскада в сьюте (сырые `deleteMany` по таблицам организации) запрещена: новая таблица с `workspace_id` в неё не попадёт, а голое удаление строки превращает задачи организации в ЛИЧНЫЕ.
   - Сьют, который меряет счётчик организаций ДО создания, сначала зовёт `sweepSuiteWorkspaces(token, 'Сьют-X')`: иначе уборка хвоста внутри создания сдвинет замер.
   - Архив раньше конца прогона (освободить слот, проверить purge) — `archiveSuiteWorkspace(id)`: снимает организацию с учёта прогона. Голый `DELETE` не вреден (повторный архив сервер не исполняет — переход status-guarded), но `finish()` сходит за ней ещё раз; уже удалённая насовсем (404) — не утечка.
   - Имя — только с префиксом `Сьют-`: хелпер бросает на другом, а этот префикс знает `gc-test-workspaces.cjs`. Префикс свой у каждого сьюта (`Сьют-Объекты-Чужая`, а не общий `Сьют-Чужая`). Хвосты убираются по префиксу (имя `Сьют-X` или `Сьют-X …`), и общий префикс архивировал бы организацию соседнего сьюта. По той же причине два параллельных прогона ОДНОГО сьюта архивируют организации друг друга (CI гоняет сьюты по очереди).
   - Архив — не сырой `isActive = false` через Prisma: без `archivedAt` ретеншн такую организацию никогда не удалит.
   - Прежние сьюты, архивирующие организацию сами в `finally`, правилу удовлетворяют и переходят на хелперы при следующей правке. Проверка правки: два прогона подряд, и число живых организаций владельца (suite1) не растёт.
9. **Настройки аккаунтов сьюта — снимок и возврат**, не `deleteMany` по userId: снять строки в начале прогона, в конце удалить только созданные прогоном (id вне снимка) и вернуть прежние значения (образец — `snapshotSettings`/`restoreSettings` в `verify-notifications.cjs`).
10. **Неудачный вход — номером, свежим на прогон** (диапазон `+7700998xxxx` аккаунтов не имеет). Защита входа (`core/audit`) блокирует и НЕИЗВЕСТНЫЙ номер: 5 неудач за 10 минут → `429` с удвоением блокировки до суток. Постоянный номер с тремя неудачами за прогон ложится уже на втором прогоне подряд. Проверять блокировку по известному аккаунту — только на suite3 (раздел «Журнал безопасности в сьютах»).
11. **Страница списка — не место для поиска своей сущности.** Инбокс задач сортирует по приоритету и сроку, и у накопленного аккаунта свежая задача без срока на первую страницу не попадает. Свою сущность искать по id или фильтром (`?search=<уникальное название>`), не первой страницей.

## CI (`.github/workflows/ci.yml`)

PG18 + Redis 7.4 service-контейнеры (версии = docker-compose.yml) → стражи реестров → build shared + api-client → prisma generate + `migrate deploy` → build api → web tsc → линт-стражи (веб-граница + страж исходящих API) → старт API → seed → полный verify-сьют.

Env CI: `VERIFY_TEST_PHONES` (тест-карта номеров: фикс-код, SMS не шлётся, лимиты скипаются) + `VOICE_STT_MOCK=true` (полный голосовой пайплайн без сети). Чеки, требующие живых сайдкаров, делают честный SKIP.

## Локальный прогон

```bash
node apps/api/scripts/verify-<name>.cjs
```
API должен быть запущен. ⚠️ Перед прогоном убедиться, что на :3001 не висит **стейл-процесс** `node dist/main.js` со старым кодом в памяти — новый параметр будет отвечать 400/не работать при полностью правильном коде.

## Страж документации (`scripts/check-docs.cjs`)

Механическая сверка `docs/` и корневых инструкций с кодом — без LLM, секунды, шаг CI «Docs drift guard» до сборок. Локально: `pnpm check:docs` (проверка), `pnpm check:docs --write` (перегенерировать `docs/module_graph_edges.md`), `pnpm check:docs --since <ref>` (плюс предупреждения «изменён модуль, не тронут его док»).

| Проверка | Что ловит | Исход |
|---|---|---|
| `paths` | путь `apps/…`/`packages/…`/`docs/…` в доке не существует; битая относительная markdown-ссылка на соседний `.md` | ошибка |
| `index` | `docs/*.md` без строки в `docs/README.md`; каталог `core/*`/`modules/*`, который ни один док не упоминает как `core/<имя>`/`modules/<имя>` | ошибка |
| `env` | переменная читается в `apps/api/src`, но нет в zod-схеме; есть в схеме или читается вебом (`NEXT_PUBLIC_*`), но не описана в `environment_variables.md`; `.env.example` содержит ключ, неизвестный схеме | ошибка (нет в `.env.example` / описана, но не читается — предупреждение) |
| `graph` | `docs/module_graph_edges.md` не совпадает с импортами и DI-токенами; новое ребро `core/* → modules/*` вне списка `KNOWN_CORE_TO_MODULES` (записанный долг) | ошибка |
| `size` | док > 15 КБ | предупреждение |
| `touch` | (только с `--since`) изменён код модуля, а ни один изменённый док его не упоминает | предупреждение |

Правила: закрыл долг границ движков — убери ребро из `KNOWN_CORE_TO_MODULES` (иначе страж не заметит возврата); планируемый, ещё не существующий путь в доке пишется словами («пакет `design-tokens` в `packages/`»), а не как путь; страж проверен на срабатывание на реальных нарушениях аудита 2026-09-02 (мёртвый путь, модуль без дока, переменная вне схемы, ребро `core/rich-cards → modules/messenger`).

## Что дополняет сьют

- Линт-стражи (контрактная граница веба + исходящий HTTP API) — проверены НА СРАБАТЫВАНИЕ: зелёный линтер одинаково зелен и когда правило работает, и когда селектор промахнулся → подсадить нарушение, увидеть падение, убрать.

## Сьюты ключей и вебхуков

- `verify-keys.cjs` — секции A–E: keystore и JWKS, envelope/AAD/HMAC/слепой индекс, ротация подписи без разлогина и KEK с rewrap, заморозка скоупа, учение корня (`keys-verify-root.cjs`), журнал append-only, потребители подписи (access/refresh/reuse-detection, legacy HS256, platform, files-url), envelope-потребители (карты, кредсы, OTP, webhook-токены Процессов), ключи API и боты (формат, теневой пользователь, скоупы и закрытые маршруты организации (реквизиты, приглашения, `@NoApiKeys`), контекст организации, использование и журнал обращений, заморозка/разморозка, IP-allowlist, ротация/семейство/отзыв, личные ключи, потолки `rate_limited`/`export_cap` через `POST /keys/dev/usage/throttle` + уведомление `key.throttled`, утечка и отсутствие `GET /keys/verify`, каскады ухода админа (понижение → исключение) и выхода самого (`leave`), реестр/журнал/политика, архив). Увольнение по ТК с живым ключом организации — `verify-hr.cjs` (новичок-админ создаёт ключ, приказ `dismissal` применяется, ключ → `401 keys.revoked`).
- `verify-keys-pii.cjs` — dual-write и поиск по слепому индексу (вход, приглашения, контрагенты, ИИН подписи), два полных цикла смены ключа слепых индексов (pending в противоположном слоте → двойная запись в окне → вход в окне → заполнение и переключение → уникум нового слота → вывод и очистка старого слота; второй цикл возвращает слот 0), kill-switch заморозки KEK в `encrypted`; переключает `KEYS_PII_READ_MODE` в `encrypted` и возвращает `legacy` в `finally`. Правило: сьют, сеющий ПДн сырым Prisma/SQL, зовёт `POST /keys/dev/pii/backfill` после посева.
- `verify-webhooks.cjs` — поднимает приёмник на 127.0.0.1 (нужен `WEBHOOKS_DEV_LOOPBACK=true` в `.env` API): подпись HMAC/Ed25519, ротация двумя подписями, пинг → active, провал → failed → probe, повтор с тем же `webhook-id`, аудит битой подписью → `signature_audit`, гейты, реестр, журнал; отказ адреса у формы, `tasks.task.completed` на главном пути (нужен второй человек сьюта в организации), мгновенный «Повторить», учения дев-полигона (`deliver`, `streak`): `verification`, автоотключение «штуки И сутки», предохранитель, потолок тарифа на включении, `429` ручных действий. Сьют берёт «свой» пинг/доставку по `data.endpointId` и `msg_<id>`, а не первую попавшуюся: приёмник общий на все endpoint'ы.
- Step-up окно (`keys_manage`) живёт 15 минут: перед проверкой `403 keys.step_up_required` сьют зовёт `POST /keys/step-up/end`; фанаут уведомлений — джобом, сьют ждёт (poll), а не читает сразу.

## Партиции, корзины, роли данных (`core/lifecycle`)

`verify-partitions.cjs` — функции владельца на пробном родителе `lc_probe.events` (своя схема; правило в `lifecycle_partition_specs` вставляет и удаляет сам сьют — сперва правило, потом схема, иначе событийный триггер примет листья пробы за защищённые); всё разрушительное (TRUNCATE леджера, DROP листа, заморозки) — в откатываемых транзакциях: следов в базе нет, даже если страж не сработал. Для «detach pending» — клиент Prisma с одним соединением (`connection_limit=1`: `SET statement_timeout` держится) и держатель старого снимка. Проверки событийного триггера пропускаются, если `db-roles.sql` не применён. `verify-trash.cjs` — корзина задач и событий. **Удаление задачи, события или записи Диктофона в сьютах — двумя шагами**: `POST …/:id/trash`, затем `DELETE …/:id` (навсегда — только из корзины). Листья журналов сьют заводит ТОЛЬКО функцией владельца (`SELECT lifecycle_ensure_partition(…)`): лист, созданный `PARTITION OF` от своей роли, функция сброса не тронет. **Деньги и журналы append-only** (триггеры): проводки леджера не удаляются и не меняются никогда — `verify-wallet.cjs` заводит СВОЮ валюту на прогон и в конце гасит её статусом `deleted`, как продукт; журнал книги финансов удаляется только ПОСЛЕ книги (`verify-finance.cjs`).

## Канарейки видимости полей (`core/visibility`)

`verify-visibility.cjs` — канареечный сьют: уникальные значения прогона кладутся в защищённые поля, затем зрители разных уровней обходят поверхности, и в СЫРОМ JSON ответа (`JSON.stringify(json)`) канарейки быть не должно у тех, кому поле скрыто или маскировано. Манифест `CANARY_TYPES` обязан перечислять КАЖДЫЙ тип реестра видимости — `check:visibility` сверяет его с реестром. Канарейка у каждого поля своя (адрес ≠ «О себе»): общая строка прогона, попавшая в законно видимое поле, даёт ложное падение. `verify-visibility-plan.cjs` — property-based (fast-check), без API: инварианты чистых функций решения на случайных правилах и зрителях; ужатый контрпример печатается в строке FAIL. Новый путь чтения защищённого поля = новая канарейка в сьюте — [visibility_engine.md](visibility_engine.md).

## Согласия в сьютах

Регистрация без пакета `registration` и даты рождения отвергается, поэтому сьюты, создающие людей, берут поле `consents` из `apps/api/scripts/_consents.cjs` (`registrationConsents`). `verify-consents.cjs` публикует СУЩЕСТВЕННЫЕ версии документов и ротирует ключ подписи `consents` — шлюз поднимается у всех аккаунтов базы разработки; в конце сьют принимает новое за suite1–3 и tester1–3 (`acceptAllPending`). После ручной dev-публикации (`POST /consents/dev/publish`) — `node apps/api/scripts/seed-test-accounts.cjs` (идемпотентно принимает всё, что ждёт принятия). Отчёты аналитики кэшируются на час: два прогона `verify-analytics.cjs` в пределах часа на стыке суток могут читать кэш прошлого прогона (`analytics:q:*`).

## Журнал безопасности в сьютах (`core/audit`)

- **Блокировку входа (5 неверных паролей) сьют проверяет ТОЛЬКО на suite3** и снимает её `POST /audit/dev/unlock` в `finally`: неудачные входы на suite1/2 заблокировали бы аккаунты, на которых стоят все остальные сьюты. Та же ручка сбрасывает лимит «Это не я» (3 запуска в час) — иначе повторный прогон упирался бы в 429.
- `call()` шлёт стабильный `X-Device-Id` (`SUITE_DEVICE_ID`, переопределяется `SA6_SUITE_DEVICE_ID`): без него каждый вход сьюта считался бы «новым устройством» и рождал уведомление.
- Вход в Кабинет — `consoleLogin(phone)` + `consoleSudo(token)` из `_lib.cjs`.
- Детекции проверяются посевом `POST /audit/dev/detect/seed {kind}` (синтетический субъект: счётчики Redis переживают прогоны), а не настоящим перебором.
- Журнал append-only и в dev: «сдвинуть» событие в прошлое нельзя — `POST /audit/dev/seed` вставляет синтетическое событие с моментом в прошлом.

## Ключ повтора в сьютах (`core/idempotency`)

`call()` в `_lib.cjs` ставит `Idempotency-Key` на КАЖДУЮ мутацию сам — иначе ручки `required` (деньги, отправка сообщения, подпись, кадровые действия) отвечали бы сьютам `400 idempotency.key_required`. Ключ свой на каждый вызов: сьюту нужны РАЗНЫЕ намерения. Проверяя сам повтор, скрипт передаёт свой заголовок явно: `call(..., { 'Idempotency-Key': key })`, а снять ключ вовсе — `{ 'Idempotency-Key': null }`.

Ответ `call()` дополнительно несёт `replayed` (заголовок `Idempotent-Replayed`), `shouldRetry` и `retryAfter` — ассертить исход повтора можно без разбора заголовков руками.

Свой сьют движка — `verify-idempotency.cjs`; смерть процесса моделирует дев-полигон `POST /idempotency/dev/simulate` (приводит строку ключа в состояние, в котором её оставил бы упавший инстанс), эффект — строка-маркер, счётчик `GET /idempotency/dev/effects?tag=…` (счёт идёт ПО ЧЕЛОВЕКУ — эффект сотрудника считают его же токеном). Прибирает за собой `POST /idempotency/dev/reset`.

Организацию он тоже заводит — `createSuiteWorkspace(…, 'Сьют-Идемпотентность')` — и архивирует сразу после проверки (`archiveSuiteWorkspace`). Массовый симптом «сьюты сыплются на `Cannot read properties of undefined (reading 'id')` сразу после `✗ организация создана (402)`» — это накопленные организации у владельца, а не регрессия. Виноват сьют, заводящий организацию мимо хелперов (правило 8), его и чинить; разовая уборка — `node apps/api/scripts/gc-test-workspaces.cjs --apply`.

# Резервное копирование и восстановление — рунбук

Что делает эксплуатация, когда данные потеряны или нужно доказать, что их можно вернуть. Архитектура хранения и сроков — [lifecycle_engine.md](lifecycle_engine.md); выгрузки и восстановление одной организации — [lifecycle_export.md](lifecycle_export.md); дашборд «Данные» Кабинета — [lifecycle_settings.md](lifecycle_settings.md).

## Обещания

| Что | Значение |
|---|---|
| Окно точки восстановления (PITR) | 35 дней на обоих репозиториях |
| Потеря данных при потере основного узла (RPO) | ≤ 1 минуты (`archive_timeout = 60`, WAL непрерывно) |
| Человеку после стирания | из живых систем ≤ 30 дней после запроса, из бэкапов ≤ 35 дней после стирания (журнал стираний реплеится после любого восстановления) |
| Копии | Только в Казахстане (ЗоПД ст. 12): репозиторий 1 — город 1 (другой ЦОД), репозиторий 2 — город 2 |

## Что копируется

- **PostgreSQL** — pgBackRest: полная копия раз в неделю, блочная инкрементальная каждые 6 часов, WAL асинхронно; шифрование репозиториев (`repo-cipher-type = aes-256-cbc`), пароли — из отдельной иерархии ключей (копии офлайн, два из трёх); хранение по времени 35 дней; бакеты бэкапов — Object Lock governance 36 дней; `pgbackrest verify` ежедневно.
- **Объектное хранилище (байты файлов, архивы журналов, выгрузки)** — версионирование + репликация во второй город + Object Lock; сроки жизни объектов ведёт реестр движка, а не правила бакета.
- **Redis (роль «состояние»)** — AOF `everysec` + RDB каждый час, 48 часов. Кэш не копируется. AOF хранит удалённое до перезаписи: после стирания человека эксплуатация (`sa6_ops`, ACL) делает `BGREWRITEAOF` по расписанию (ежесуточно) — иначе ключи стёртого жили бы в файле AOF и его копиях.
- **Журнал стираний** — выгружается NDJSON в `lifecycle/erasure-journal/…` объектного хранилища (оба репозитория) и живёт дольше любого бэкапа: без него восстановление вернуло бы стёртых людей.

Отчёт каждого прогона (бэкап, `verify`, учение) скрипт присылает в API: `POST /lifecycle/ops/backups/report`, Bearer `LIFECYCLE_OPS_TOKEN` + HMAC-SHA256 тела (`X-Lifecycle-Signature: t=<unix>,v1=<hex>`, окно 300 с). Дашборд «Данные» → «Бэкапы и восстановление» рисует покрытие PITR по суткам; **отсутствие** отчёта — тревога (GitLab 2017: письма об ошибках бэкапа молча отбрасывались).

## Инструменты

| Что | Где |
|---|---|
| Конфиг pgBackRest (два репозитория, шифрование, 35 дней, блочные инкременты) | `infra/pgbackrest/pgbackrest.conf`; секреты — переменными окружения сервиса (`PGBACKREST_REPO{1,2}_S3_KEY*`, `…_CIPHER_PASS`) |
| Архив WAL (только прод) | `infra/pgbackrest/postgresql.archive.conf` (`archive_timeout = 60`) |
| Бэкап и `verify` + отчёт в движок | `infra/pgbackrest/backup.sh full\|incr\|verify` (каждый репозиторий — своим прогоном и отчётом; `lib.sh` подписывает тело HMAC) |
| Ночное учение восстановления | `infra/pgbackrest/restore-drill.sh [pitr]` — scratch-кластер в чистый каталог, сверки `apps/api/scripts/lifecycle-restore-drill.cjs`, отчёт с RTO, уничтожение копии |
| Сверки восстановленной копии | `lifecycle-restore-drill.cjs`: `row_counts` (каждая таблица есть, крупная не усечена), `ledger_sum` (Σ балансов по валюте = 0), `audit_merkle` (дайджесты копии = источника, число событий = подписанному), `erasure_replay` (журнал стираний копии — префикс источника). Dev: `--dev-clone` |
| Смоук S3-кандидата | `apps/api/scripts/s3-conformance.cjs --require-versioning --require-object-lock` — многочастная загрузка, срок и подделка подписи ссылки, пагинация, версии, Object Lock ≥ 36 дней, коды ошибок |
| Тревоги (порог → действие) | `infra/prometheus/alerts.yml`: отсутствие бэкапа 26 ч и учения 2 сут, архив WAL, возраст XID, лаг реплик, удержание WAL слотами, тишина сторожевых метрик |

## Восстановление всей базы (PITR)

1. Остановить запись: API в режим обслуживания (балансировщик), кроны не трогать — они сами ждут здоровья базы.
2. Поднять кластер на точку времени ДО инцидента: `pgbackrest --stanza=<stanza> --type=time --target="<время UTC>" --target-action=promote restore` в чистый каталог данных (изолированная сеть: восстановленная копия не видна продукту до сверки).
3. Сверка до открытия трафика:
   - счётчики строк ключевых таблиц против последнего ночного снимка (`lifecycle_storage_daily`);
   - Σ = 0 по книге кошелька (`wallet.cron` — сверка двойной записи);
   - корни Меркла журнала безопасности (цепочка дайджестов; разрыв после логического переноса — отдельная тревога [audit_engine.md](audit_engine.md));
   - **реплей журнала стираний**: все стирания после точки восстановления исполняются заново (`LifecycleErasureService.replayJournal` по псевдонимам из выгруженного журнала) — ДО открытия трафика.
4. Переключить приложение на восстановленный кластер, снять режим обслуживания.
5. Байты файлов, удалённые после точки восстановления, возвращаются версиями объектного хранилища (строки `FileObject` без байтов считает импорт — `missingBlobs`).

## Восстановление одной организации (без отката базы)

Когда потеряны данные одного арендатора (скрипт удалил строки, ошибка миграции у одной организации), остальные клиенты продолжают работать.

1. Поднять **отдельный** кластер из бэкапа на точку времени до потери (шаг 2 выше, в изолированную сеть), завести в нём роль только на чтение.
2. В API задать `LIFECYCLE_RESTORE_SOURCE_URL` на этот кластер (роль только на чтение) и перезапустить инстанс, который исполнит команды.
3. Извлечение: `node apps/api/scripts/lifecycle-restore-tenant.cjs --workspace=<id> --snapshot=<точка UTC>` — предпросмотр (строк по таблицам); с `--apply` — команда Кабинета `lifecycle.restore.extract` (второй сотрудник одобряет в «Заявках»). Готовый архив подписан и виден на вкладке «Бэкапы и восстановление».
4. Импорт: `--export=<id>` — предпросмотр (сколько строк вернётся, сколько уже есть); `--apply` — `lifecycle.restore.import`. Строки возвращаются с теми же id, существующее не трогается; люди, стёртые после снимка, стираются заново; итог — в журнале организации (`lifecycle.restore.imported`).
5. Файлы без байтов (`missingBlobs`) — вернуть версиями объектного хранилища.
6. Убрать `LIFECYCLE_RESTORE_SOURCE_URL`, погасить кластер-источник.

Организацию, стёртую по заявке (горячая фаза стирания прошла), восстановить нельзя — команда отвечает `lifecycle.restoreErased`: стирание побеждает.

## Учения

| Что | Когда | Доказательство |
|---|---|---|
| Автоматическое восстановление в изолированный экземпляр + сверка (строки, Σ=0, Меркл, реплей журнала) | Каждую ночь | Отчёт `restore_drill` с проверками и фактическим RTO |
| PITR на случайную точку | Раз в неделю | Отчёт `pitr_drill` |
| Полное учение аварийного восстановления (второй город) | Раз в квартал | Отчёт `dr_drill` + разбор |
| Восстановление одной организации на копии | Раз в квартал | Прогон скрипта на тестовой организации, отчёт импорта |

## Резидентность — побочные каналы

Всё, что уносит данные из первого города, — либо в Казахстане, либо вычищено от ПДн, либо получатель объявлен (`cross_border` в [consents_engine.md](consents_engine.md)):

- логи и метрики (Prometheus/Loki) — в Казахстане, логи без ПДн (`log_parameter_max_length = 0`);
- трекер ошибок — свой в Казахстане либо без ПДн;
- CDN — приватные файлы только через API (presign/подписанная ссылка);
- SMS-провайдер — получатель в `recipients.ts`;
- бэкапы и реплики — только два города Казахстана;
- будущие AI-провайдеры — получатель `cross_border` до первого запроса.

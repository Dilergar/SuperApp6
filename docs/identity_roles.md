# Universal Identity и роли

> Один `user_id` — навсегда. Роли не в users-таблице, а в отдельной `user_roles(user_id, role, context, tenant_id)`. Найм — это запись роли; увольнение (`isActive = false`) не отнимает личную жизнь.

## Модель

Один человек одновременно может быть:
- `user` в `system` (глобальная роль),
- `staff` в `workspace:<id>` (сотрудник организации),
- `contractor` в `workspace:<другой id>` (внешний исполнитель),
- `owner` в `circle:<id>`.

Файлы: `apps/api/src/core/roles/` (RolesService, RolesModule), `apps/api/src/shared/guards/roles.guard.ts`, `apps/api/src/shared/decorators/roles.decorator.ts`.

## Лестница workspace-ролей

Одна роль на организацию; ранги — `WORKSPACE_ROLE_RANK` в `@superapp/shared`:

```
contractor < trainee (Стажёр) < staff (Сотрудник) < manager < admin < owner
```

Правила:
- **Найм ВСЕГДА в `trainee`** — приглашение не несёт выбора роли; повышение вручную (позже — процессами/Додзё).
- **Админа назначает/снимает только Владелец**; админ управляет ролями до Менеджера и не трогает других админов. Один владелец на организацию.
- **`contractor` вручную не назначается** — только программно сервисами (Тайный гость/UGC). Изолирован: не инициирует контакты через «рабочий пропуск» и не достижим через него, не видит ростер/справочники; его работа течёт через явные гранты задач/чатов.
- Роль — **единый источник `UserRole`**: у `WorkspaceMember` нет поля role (нет рассинхрона).
- Системная роль `mystery_shopper` зарезервирована под Jobs Marketplace.
- «Запускать процесс от имени» можно только сотрудника **не выше своего ранга** (защита от одалживания прав — см. [processes.md](processes.md)).

## Пять понятий «роли» (не путать)

1. **Подпись на карточке** (роль в Circle: «Муж», «Коллега») — [contacts_circles.md](contacts_circles.md);
2. **Участие в сущности** (Исполнитель/Наблюдатель задачи) — доменные таблицы + проекция в core/access;
3. **Платформенная персона** (`platform`: Продавец/Тайный Гость/UGC) — аддитивные будущие фичи;
4. **Роль компании** (лестница выше) — `UserRole`;
5. **Оргструктура** (должность/отдел/объект) — [staff.md](staff.md), три оси, проецируются в core/access; вертикаль «кто кому руководитель» и областные права — [org_structure.md](org_structure.md).

## B2B-изоляция данных — два законных пути

1. **Chokepoint**: `WorkspaceContextInterceptor` (APP_INTERCEPTOR) читает заголовок `X-Workspace-Id`, проверяет членство (**fail-closed 403**), кладёт активную организацию в AsyncLocalStorage (`WorkspaceContextService`). `DatabaseService` — Prisma-клиент через `$extends` — авто-скоупит `workspaceId` на B2B-моделях (сейчас `Task`), когда контекст активен; иначе строгий no-op (личные потоки не затронуты).
   - ⚠️ Сырые `$queryRaw` chokepoint НЕ скоупит — зеркалить фильтр workspaceId руками.
2. **Явное владение**: `ownerType + ownerId` на строке + проверка прав (пример — Shop, Wallet, Files). Используется там, где данные не принадлежат одной организации жёстко.

Кошелёк и access — НЕ в chokepoint (cross-cutting).

## «Рабочий пропуск» и достижимость

Единый гейт действий «между людьми» — `ContactsService.assertReachable`:
- личный режим = подтверждённая связь + нет блока в обе стороны;
- контекст организации (`X-Workspace-Id` в ALS) = со-членство по командным ролям (trainee+); личное окружение не требуется, личные блоки рабочие артефакты не гасят; DM передаёт `alwaysCheckBlocks` (личка уважает блок и на работе);
- `{personalOnly: true}` — отключает рабочий пропуск для ЛИЧНЫХ ресурсов (книга финансов, календарь, витрина, вишлист);
- «коллега» везде = белый список `TEAM_WORKSPACE_ROLES` (одно определение, не копировать).

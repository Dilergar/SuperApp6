# core/sign — движок электронной подписи

> Акт подписи, криптография, ВЕЧНЫЕ доказательства, экспортный пакет (ст. 62 ЦК РК) и открытая страница проверки (ст. 61). Маршрута НЕ содержит — им остаются core/approvals и Процессы.

## Юридическая рамка (Цифровой кодекс РК № 255-VIII)

Два уровня, путать нельзя нигде: **ЭЦП** (ст. 49, ключ НУЦ — QR eGov Mobile ∥ NCALayer; обязательна для кадровых по ст. 33 ТК РК, ЭСФ, госорганов) и **ПЭП** — «цифровое подтверждение» (ст. 46 п. 4 + ст. 47: SMS-код ПОД ДОКУМЕНТ после цифровой аутентификации; достаточна для гражданско-правовых по соглашению сторон).

## Два несущих решения

1. **Движок САМ замораживает то, что подписывает**: при создании заявки байты предмета кладутся ОТДЕЛЬНЫМ неизменяемым файлом (профиль `sign_subject`); подписанту показывается ЭТА копия, над ней считается CMS — «что видел = что подписал» по построению (PDF-вариант живого документа умирает при первой правке — подписанные байты иначе терялись бы физически).
2. **Доказательства ЗАМОРАЖИВАЮТСЯ, не пересчитываются**: вердикт цепочки, статус OCSP и метка TSP пишутся полями акта в момент подписи (приказ № 1187 требует проверки НА МОМЕНТ ПОДПИСАНИЯ; через год сертификат истечёт и живая проверка не докажет ничего).

## Модель

- **`SignRequest`** — предмет refType+refId БЕЗ FK + снимок названия; `subjectFileId`+`subjectSha256` замороженные; `level` ecp|pep; `methods`; `approvalStepId?`; `stampedFileId` (штампованная копия ЭДО).
- **`SignAct`** — одна подпись одного лица (`signerType` user|guest). ЭЦП: cmsFileId/cmsSha256/cert*/chainValid/ocspStatus|At/tspAt|Serial. ПЭП: verifyChallengeId (код привязан к акту), **consentText+consentVersion** — снимок соглашения сторон (без него ст. 47 не выполняется). `checkToken @unique` — токен публичной проверки (он же в QR протокола). Партиальные уникумы: «одна живая заявка на шаг», «одна живая подпись на подписанта» (failed/declined НЕ в условии — опечатка не лишает права подписать). FK акта на заявку — Restrict: доказательство вечно.
- **`SignActEvent`** — append-only протокол. **`SignQrSession`** — одноразовые dataToken/signToken (`issued→claimed→submitted`).

**ХРАНЕНИЕ ВЕЧНОЕ**: таблиц движка ретеншн-кроны не касаются; профили `sign_subject`/`sign_cms` (`EVIDENCE_FILE_PROFILES`) — вне квоты, вне реапа, **их не удаляет НИКТО** (правило стоит в ОБОИХ путях удаления файлов); через HTTP профили закрыты.

## Связка с маршрутом

Шаг закрывается **`ApprovalsService.decideAttested(tx, …)`** изнутри транзакции финализации акта — акт подписан и шаг закрыт ОДНИМ коммитом (окна «подписано, но шаг висит» не существует). approvals знает о подписи одно поле — `ApprovalStep.requiredSignatureKind`. Терминология уровней не переименовывается (`pep`→`sms` маппингом) — история неизменяема.

## Сверка личности

ЭЦП: ИИН из сертификата; заполнен `users.iin` → расхождение = ОТКАЗ (`sign_iin_mismatch`); не заполнен → фактический ИИН в акт. Неудачная попытка акт НЕ хоронит (событие в протокол). Гость ЭДО: жёсткая сверка БИН/ИИН сертификата с карточкой контрагента (`checkGuestCert`); акт работодателя ЭЦП физлица без БИН юрлица → предупреждение хроникой.

## Драйверы (fail-closed СТРОЖЕ SMS)

Верификатор `ncanode|mock` (`infra/sign-verifier/` — приватная сборка NCANode + SDK KalkanCrypt) и QR-мост `smartbridge|mock`. **В production с mock-верификатором ЭЦП-акты ОТВЕРГАЮТСЯ** (`ecpAccepted=false`), способы не показываются; ПЭП работает. Парсер вердикта NCANode — только ЯВНОЕ подтверждение (молчание = отказ); отсутствие OCSP ≠ «в порядке» (`sign_ocsp_unavailable`); неразобранная TSP не подменяется часами сервера. NCALayer живёт целиком в браузере (`wss://127.0.0.1:13579`, detached CMS + tsaProfile) — пароль ключа не видим никогда.

## Контракт потребителя

```ts
SignRegistry.register(refType, { resolveSubject, canRequestSign, canView?, describeForVerify?, onActFinished?, onRequestExpired?, checkGuestCert? })
SignService.createRequest(userId, input, opts?)  // opts: suppressOutcomeNotify, guestSigner, neverExpires, noInitialActs
SignService.systemEnsureActs(...)                // акты адресатам пачкой (кампании); кап подписантов —
                                                 // SIGN_SIGNERS_MAX=500 в Zod-схеме (validation/sign.ts)
SignService.summaryForRef(userId, refType, refId, { viewAuthorized? })
```
- `resolveSubject` отдаёт **готовый к печати файл** (PDF-отпечаток, не живой .docx; не подсовывать живой файл при неснятом отпечатке).
- **`canRequestSign` = право ОТПРАВИТЬ на подпись, не право ПОДПИСАТЬ**; при подписании шага маршрута НЕ спрашивается (`authorizedBy='approval_step'` — полномочие дал снимок адресатов).
- Уровень задаёт ПОТРЕБИТЕЛЬ (у документов — `DocType.signatureLevel`), не подписант.
- Ручки «завести заявку» НЕТ (как у approvals).
- На шаге «нужен каждый» акты заводятся сразу ВСЕМ адресатам снимка (одна заморозка — все подписывают ОДИН документ).
- ⚠️ Потребитель, зовущий `summaryForRef` из своего canView-пути, ОБЯЗАН передать `{viewAuthorized:true}` — иначе кольцо `get → summaryForRef → canViewRequest → get` (в canViewRequest стоит ALS-стоп-кран: повторный вход с тем же предметом = fail-closed false + error-лог).

## Гость (внешний подписант)

Первый потребитель слота `actions` share-links: ссылка на `sign_request` → личность по SMS (`requireIdentity` принудителен — `constraints`) → замороженный PDF → соглашение сторон + согласие на обработку ПД (ст. 8 ЗоПД, фиксируется и на ЭЦП-пути) → второй OTP ПОД ДОКУМЕНТ либо ЭЦП. Акт гостя — лениво при первом действии. Лимит открытий на подписных ссылках ЗАПРЕЩЁН (`forbidMaxOpens`).

## Артефакты

«Протокол подписания» — PDF (Gotenberg) с отпечатком, подписантами, лентой событий, QR на проверку · **экспортный ZIP** (document/ + signatures/*.cms|ocsp|tsp + protocol.pdf + manifest.json) · **штампованная копия** (джоб `sign.stamp`: pdf-lib + PT Serif — полосы + «Лист подписей» с QR; публичная проверка находит штамп по его собственному отпечатку, `matchedBy: 'stamped_copy'`).

## Публичная проверка (ст. 61)

`/check` вне каркаса, noindex: **файл НЕ покидает браузер** (sha256 считает Web Crypto, на сервер уходит только хэш) + `/check/:actId?k=<токен>` из QR. ИИН посторонним маскируется; байты документа не отдаются. Сырые CMS/квитанции — ТОЛЬКО по ссылке проверки (внутри CMS сертификат с полным ИИН — X.509 не разобрать), вердикт открыт всем.

## API (кратко)

`GET /sign/status` (@Public) · `POST /sign/requests/for-step/:stepId` (лениво+идемпотентно) · `GET /sign/requests/:id` · `GET /sign/acts/:actId/state|events` · ПЭП: `pep/start` (consentAccepted ДО отправки кода) + `pep/confirm` · ЭЦП: `cms` | `qr/start` (QR рисует СЕРВЕР) · `decline` (причина обязательна) · `protocol` / `export` · `GET /sign/check` (@Public) · мост eGov (@Public, одноразовые токены). Гость: `POST /share-links/guest/:token/actions/sign.*`. Дев-полигон `POST /sign/dev/requests` (development, refType `sign_dev`).

Веб: `SignFlowModal` · `SignStepModal` (шаг маршрута → подписание) · `SignaturesBlock` · карточка `SignRequestPage` на два адреса (`/workspaces/[id]/sign/[signId]` и `/sign/[id]` с переадресацией) · публичная `/check`.

## Внешние блокеры (не блокируют продукт)

Заявка Smart Bridge (до неё QR в mock) · SDK KalkanCrypt (тест-контур test.pki.gov.kz → боевые корни) · прод-хостинг с БД в РК. Осознанно не в v1: биометрия (слот), «печать сервиса», иностранные подписанты (ДТС), массовая рассылка (закрыта КЭДО-кампаниями), подпись файлов Диска (подключится регистрацией).

# Правила видимости полей (`core/visibility`)

> Код: `apps/api/src/core/visibility`, реестр типов записей и маски — `packages/shared/src/visibility`, константы и коды отказов — `packages/shared/src/constants/visibility.ts`, провод — `packages/shared/src/types/visibility.ts`, миграции — `20260924100000_core_visibility` (+ `…_visibility_card_rules`, `…_visibility_contact_access`), веб — `apps/web/src/components/visibility/`, `components/ui/GuardedValue.tsx`.

27-й платформенный движок. Отвечает на вопрос **«какие ПОЛЯ видимой записи зритель видит и в каком виде»**: целиком, маской («+7 70* *** *5 67», «•••• 1234», «Алматы», «2026») или никак. Видна ли сама ЗАПИСЬ и что с ней можно делать — по-прежнему решает `core/access`; видимость прав на запись не выдаёт и не отнимает. Движок стоит над `core/access` тонким слоем.

Кто решает о поле:
- **личное поле** (`control: subject` — телефон, «О себе», день рождения, город в карточке человека) решает только сам человек: настройки для Окружения и для коллег объединяются, организация их не расширяет;
- **служебное поле** (`control: controller` — ИИН, оклад, адрес, ставка, контакты контрагента) решает только организация матрицей «поле × адресат». Окружение его не расширяет никогда.

## Несущие правила

1. **Решение — одно место, чистая функция.** `visibility.plan.ts` (`decideControllerField` / `decidePersonalField` / `projectValue` / `compileRules`) не знает про БД, Redis и Nest: вход — паспорт поля, скомпилированная политика, факты о зрителе и его отношение к записи. При любой неясности решение — `hidden` (fail-closed); сбой вычисления по полю тоже `hidden` с метрикой `visibility_fail_closed_total`.
2. **На провод значение выходит только через `shape()`.** Сервис-владелец данных не собирает маски сам: он отдаёт сырые значения и получает `Guarded<T>` по каждому полю. Маркер `{ $v: 'masked' | 'hidden' }` вне движка строить запрещено линтером (в API и в вебе); маркер для витрины и тестов — `maskedMarker()` / `HIDDEN` из shared.
3. **Маска считается только на сервере, одна на вид данных.** Все маски — `packages/shared/src/visibility/masks.ts` (`maskPhone`, `maskEmail`, `maskIdLast4`, `maskCardLast4`, …). Своя маска рядом с общей запрещена линтером: две разные маски одного значения складываются в оригинал.
4. **Сам человек видит своё** (ЗоПД ст. 24, ТК ст. 113): режим поля `self: full` не переопределяется правилами организации; `self: policy` — поле «не своё» (бюджет штатной единицы); `self: hidden` — не показывается и самому.
5. **Явный запрет побеждает всё**, иначе — максимум по разрешениям всех столбцов зрителя (роль, отдел, должность, объект, относительные адресаты). Столбец без правила берёт умолчание реестра. Внутри столбца правило выбирается по специфичности: поле > группа > секция, и правило, ограниченное этапом записи, точнее правила «на все этапы» той же цели («оклад уволенным — скрыть» побеждает «оклад — целиком» на записи уволенного независимо от порядка строк).
6. **Потолки класса поля — правило платформы**, организация только сужает: `restricted` (ИИН, удостоверение, адрес, IBAN) выше маски не бывает, полное значение — раскрытием одной записи; `secret` (номер карты) — не выше маски для всех, включая самого человека, и без раскрытия. Понижение уровня потолком пересобирает решение: маска подбирается по паспорту поля, `caps` уровня `full` снимаются.
7. **Бот и ключ API** видят класс не выше `internal`; `contact` — только с флагом ключа «Доступ к контактным данным» (`contactAccess`); `personal` и выше — никогда; раскрытия нет.
8. **Внешние назначения** (`webhook`, `guest`, `ai`) — через `forExternal()`: без раскрытия, гость — только `public`.
9. **Раскрывается только маска.** `hidden` раскрытия не имеет никогда; раскрытие — только человеку, только одной записи, только через окно SMS-подтверждения `visibility_reveal` и с записью `pii.reveal` в журнал, которую видит субъект.
10. **Правка не пишет того, чего не видит** (чокпойнт W): поле ниже `full` в теле правки → `403 visibility.field_forbidden`; значение, похожее на маску, → `400 visibility.masked_value_rejected`.

## Семь чокпойнтов

| Код | Метод | Что делает |
|---|---|---|
| **D** | `visibility.plan.ts` | Решение по полю: уровень, маска, раскрытие, `caps`, «почему» |
| **Q** | `assertQueryable(viewer, type, spec)` | Фильтр / сортировка / поиск / агрегат по полю ниже `full` → `403 visibility.field_not_queryable` (иначе сортировка по скрытому окладу — оракул). Сегодня списки фильтруют и ищут только по полу типа (контрагенты — имя, юрназвание, БИН), поэтому вызовов нет; **новый фильтр, сортировка или поиск по полю реестра обязан сначала вызвать `assertQueryable`** |
| **P** | `shape()` / `shapeOne()` | Проекция пачки записей одного типа в `Guarded<T>` |
| **W** | `assertWritable(viewer, type, ref, patch)` | Правка: скрытое / маска в теле |
| **R** | `maskChanges()` + порт маскировщика хроники | Рендер при чтении: «было → стало» в хронике маскируется по плану зрителя, скрытое — «Скрыто» |
| **E** | `forExternal()` | Вебхуки, гостевые страницы, ИИ |
| **L** | `audit.record(tx, …)` | `pii.reveal`, `pii.reveal_denied`, `pii.read` (агрегат), `org.visibility.*`, `detect.pii_scrape` |

## Контракт сервиса-владельца

```ts
// «Шляпа» запроса: кто смотрит и в каком контексте (одна на запрос)
const viewer = this.visibility.viewer('card');                 // из ALS: пользователь / бот / ключ
// P: пачкой, НЕ в цикле по одной записи
const shaped = await this.visibility.shape(viewer, 'hr.employment', rows.map((r) => ({
  ref: { ownerKind: 'workspace', ownerId: wsId, recordId: r.id, subjectUserId: r.userId, branchIds: [...] },
  values: { salaryAmount: r.salaryAmount, dismissalGround: r.dismissalGround },
})));
// W: до записи
await this.visibility.assertWritable(viewer, 'hr.employment', ref, dto);
// Q: до запроса со своим where/orderBy
await this.visibility.assertQueryable(viewer, 'counterparty', { filter: ['phone'] }, wsId);
```

| Метод | Когда |
|---|---|
| `viewer(purpose, overrides?)` | Зритель запроса из контекста (ключ API несёт `contactAccess`) |
| `viewerFor(userId, wsId, purpose)` | Зритель — не автор запроса (фанаут уведомлений, джоб) |
| `roleViewer(wsId, role)` | Синтетический зритель роли — предпросмотр «как видит сотрудник» (`GET /workspaces/:id/card-preview?role=`) |
| `guestViewer()` / `systemViewer()` | Гость ссылки / системный путь (видит всё; только для внутренних вычислений, не для провода) |
| `readableFields(viewer, type)` | Какие поля зритель видит целиком — для заголовков таблиц и выборки |
| `maskValue(mask, value)` | Маска вне плана (карточки платформы) |
| `planDto(viewer, type)` | План зрителя на клиент (`GET /visibility/plan`): веб прячет колонки, которых зритель не видит |
| `explain(...)` | «Проверить сотрудника»: поле → уровень + «почему» (тариф `visibility.explain`) |

Страницы едут в `data` цельными (`CursorPage`/`OffsetPage`), `Guarded` — внутри элементов. Форма провода — тип в `@superapp/shared` (`Guarded<string>` у поля DTO); `check:visibility` требует `Guarded<…>` у чувствительных свойств DTO (телефон, e-mail, ИИН, IBAN, PAN, оклад, адрес, удостоверение) либо строку allow-list с причиной.

## Реестр типов записей

`packages/shared/src/visibility/<сервис>.ts` + `index.ts`. Тип — ключ (`staff.member`); паспорт типа: владелец (`workspace` | `user`), субъект, секции с полями, `floor` (поля, видимые всем, у кого есть право на запись), умолчания (тип → секция → поле, по ключам). Паспорт поля: `kind` (вид данных → допустимые маски), `class` (`public < internal < contact < personal < confidential < restricted < secret`), `control`, `group`, `masks`, `caps`, `self`, `mandatoryVisible`, `fallback` (личное поле: уровень «знакомому» и «постороннему»), `reciprocal` (взаимность присутствия), `pii` (связь с `PII_MODELS` движка ключей), `moneyBuckets`.

| Тип | Владелец данных (провайдер) | Что защищает |
|---|---|---|
| `user.card` | `core/users` (`UserCardService`) | Личная карточка: фамилия (знакомому — инициал), фото, день рождения, год рождения, семейное положение, телефон, e-mail, соцсети, город, «О себе», «был в сети» |
| `workspace.card` | `modules/workspaces` | Анкета организации: описание, отрасль, город, сайт, число сотрудников, контакты, реквизиты, IBAN (маской) |
| `staff.member` | `modules/workspaces` (отношения — `StaffModule`) | Реквизиты сотрудника: ИИН, удостоверение, адрес, карта (только last-4), IBAN |
| `hr.employment` | `modules/hr` | Оклад, основание увольнения; сведения ЕСУТД и параметры кадровых действий |
| `objects.staffing` | `modules/objects` | Плановая и фактическая ставка, итоги штатки |
| `objects.shift` | `modules/objects` | Факт выхода: опоздание, фактическое время, исход, заметка |
| `counterparty` | `modules/counterparties` | Телефон, e-mail, контакты, банковские счета |

Новый тип = файл реестра + ключи каталога `visibility.types.<t>.title|sections.<s>.title|fields.<f>.label` в en/kk/ru + `VisibilityTypeRegistry.register('<t>', { loadForReveal })` в модуле-владельце + строка в `CANARY_TYPES` сьюта `verify-visibility.cjs` + `shape()` на каждом пути чтения. Без провайдера бут падает.

## Модель данных

- `visibility_policies` — политика владельца по типу (`owner_type` = `workspace` | `user`). Черновик — одна строка на (владелец, тип), `draft_token` меняется на каждой правке; опубликованная версия неизменяема (меняется только статус на `archived`). Частичные уникумы `…_one_published` и `…_one_draft` — руками в миграции. Версия ≥ 1 (CHECK).
- `visibility_rules` — правило = строка: цель ровно одна из трёх (поле / группа / секция, CHECK), адресат — две колонки (`audience_kind`, `audience_id`) с индексом для уборки, `effect` allow | deny, `level`, `mask`, `reveal` none | one | delegated, `stage`. CHECK словаря `audience_kind` в миграции = `VISIBILITY_AUDIENCE_KINDS` целиком: новый вид адресата в реестре без миграции-расширения CHECK валит `check:visibility` (иначе правило с ним падало бы на вставке — `23514 → 500`).
- `workspace_visibility_settings` — 1:1 к организации: `notify_on_reveal`, `dual_control`, `allow_delegation`. Нет строки — всё выключено.
- `bots.contact_access`, `api_keys.contact_access` — флаг R9; снимок едет в JWT ключа (`contactAccess`) и в `RequestActor`.

Публикация: сначала архивируется прежняя опубликованная версия, потом черновик становится опубликованным (обратный порядок ловит `23505` на частичном уникуме). Публикация сверяет `draftToken` с диффом, который видел человек (`409 visibility.draft_changed`), и обязательную видимость (`visibility.mandatory_violation`).

## Вычисление и кэш

Скомпилированная политика `{pv, rules}` — L2 Redis (`vis:policy:*`, 120 с; строки в порядке `priority, createdAt` — при равной специфичности побеждает первая) + сброс по событию `visibility.changed`. Факты о зрителе кэшируются в два слоя (L1 LRU процесса 30 с → L2 Redis 5 мин, ключ `vis:facts:*` несёт эпоху прав `core/access`), но в кэш попадают ТОЛЬКО принципалы оргструктуры (отдел / должность / объект — их рёбра и бампают эпоху). **Роль в организации в кэш фактов не кладётся никогда**: роли живут в `user_roles`, в рёбра доступа попадают проекцией best-effort, и не всякая смена роли меняет ребро (Сотрудник ↔ Стажёр — одно `member`) — роль читается свежей из `RolesService`, чей кэш сбрасывает сама смена роли; так отзыв и понижение видны со следующего запроса. Относительные множества (подчинённые, объекты) — на запрос. `shape()` считает решение один раз на (поле × отношение зрителя к строке: сам / руководитель / объект / этап) — мемо внутри вызова, а не на каждую строку; маска считается на строку (значения разные). Замер `POST /visibility/dev/bench`: 1000 планов из кэша и `shape` 10 000 строк на тип. Метрики: `visibility_plan_total`, `visibility_policy_cache_total`, `visibility_reveals_total`, `visibility_query_denied_total`, `visibility_unshaped_total`, `visibility_fail_closed_total`, `visibility_scrape_total`, `visibility_shape_seconds`.

**Детекция скрейпинга** (`VisibilityScrapeDetector`): каждый `shape()` считает ЧУЖИЕ строки, где хоть одно поле класса ≥ `contact` (кроме присутствия, фото и флагов) ушло зрителю целиком, и учитывает их в часовом окне человека или бота (`vis:det:rows:<id>:<час>`, роль Redis «состояние»; мимо пути ответа — сбой Redis не трогает ни латентность, ни результат). Порог `VISIBILITY_LIMITS.personalRowsPerHour` (20 000) пройден → тревога `detect.pii_scrape` организации «шляпы» и платформе, один раз на окно. Блокировки нет намеренно: легитимный админ большого ростера порог тоже пройдёт; решение (заморозка аккаунта, отзыв ключа) — за организацией и безопасностью платформы. Дев-полигон: `POST /visibility/dev/scrape-probe { rows }` / `scrape-reset`.

## Раскрытие (break-glass)

`POST /visibility/reveal { recordType, recordId, fields[] }`: план зрителя даёт `masked` + `reveal: one` → окно `visibility_reveal` (SMS, 15 мин; гаснет на «выйти везде», смене пароля и «Это не я») → провайдер `loadForReveal` → значения и `showUntil` (10 мин на экране). Каждое раскрытие — `pii.reveal` в журнал (видят субъект, организация и платформа), отказ — `pii.reveal_denied`. Квота `visibility.revealsPerDay` — 100 раскрытий в сутки на человека (едет с человеком, `402 entitlement.*`). Детекция: 30 и более раскрытий за 10 минут одним человеком → раскрытия ему стоят час (`visibility.reveal_paused`, пауза ставится один раз — `SET NX`), уведомление админам, снять паузу — `POST /workspaces/:id/visibility/reveal-pause/:userId/lift`. Делегирование раскрытия руководителю (`reveal: delegated`) — только при включённой настройке и тарифе `visibility.revealDelegation`, только на «свои» записи.

## Находимость по номеру

Отдельная ось, не поле карточки: `PUT /visibility/me/discoverability { discoverableBy: everybody | circle | nobody }`. `nobody` неотличим от «номер не зарегистрирован» (не оракул); приглашения и поиск по номеру смотрят эту настройку. Ключ API и бот людей по номеру не находят никогда: вид зрителя движок берёт из контекста запроса сам, даже если путь (приглашение, перевод по номеру) его не передал.

## Политика организации

`/workspaces/:id/visibility/*`: `overview`, `settings` (владелец), `presets` (тариф `visibility.presets`: retail / office / strict), `policies/:recordType` (опубликованная), `…/draft` (PUT / DELETE), `…/diff`, `…/publish`, `…/versions`, `…/restore`, `explain` (тариф `visibility.explain`; только служебные типы — объяснение личной карточки `user.card` выдало бы организации личный граф двух людей: связь в Окружении, Группы). Правка — владелец и админ. Окно SMS-подтверждения `visibility_manage` требуется, когда публикация ослабляет строгие поля или выдаёт делегирование раскрытия, и на ослабляющих правках настроек. Адресаты оргструктуры (отдел / должность / объект) — тариф `visibility.orgAudiences`; число правил — `visibility.maxRules`.

**«Четыре глаза»** (`dual_control`): публикация, ОСЛАБЛЯЮЩАЯ строгие поля, не применяется сразу — движок создаёт согласование `core/approvals` (`refType: visibility_publish`, `origin = draftId:draftToken:requesterId`, `contentSha256` = отпечаток правил) и отвечает `{ status: 'pending_approval', approvalId }`. Одобрение второго владельца/админа публикует тот самый черновик, если его не меняли и автор заявки к этому моменту всё ещё владелец/админ живой организации (снятого с роли одобрение не публикует). Второго админа нет → `visibility.no_second_admin`.

## Личная политика

`/visibility/me` (GET / PUT), `me/circles/:circleId` («Скрыть от Группы»), `me/reset`. Порядок: сам → full; «Никогда» конкретному человеку > «Всегда» > «Скрыть от Группы» > аудитории (все / Окружение / Группа / коллеги) > запасной уровень поля (знакомому — маска, постороннему — как объявлено). Взаимность: скрыл своё «был в сети» — чужое видишь не точнее корзины.

## Веб

- Защищённое поле рисует **только** `<GuardedValue value={…} />` (кит): полное значение, маска с подписью «часть скрыта» или «Скрыто»; раскрытие — `<RevealButton>` и только в карточке одной записи. Хелперы чтения — `isVisible` / `isMasked` / `isHidden` / `visibleOr` / `guardedDisplay` из shared; свои проверки `$v` запрещены линтером.
- Заголовки колонок таблиц — по плану зрителя (`VisibilityPlanProvider` + `GET /visibility/plan`): колонку, которой зритель не видит, не показываем.
- Матрица организации — `/workspaces/[id]/profile/visibility` (`PolicyMatrix`, `PublishPolicyModal`, `PolicyVersions`, `ExplainPanel`); вход — кнопка «Правила видимости» в ростере и строка «часть скрыта» у реквизитов для владельца/админа, фильтр «Раскрытия» журнала безопасности.
- Личная карточка — `/profile/card` (`CardVisibilitySection`): предпросмотр «как видит чужой / коллега», исключения «Всегда / Никогда»; «Скрыть от Группы» — редактор Группы в `/circles`.
- Ключи и боты — поле «Доступ к контактным данным» (`ContactAccessField`).
- Сокет `visibility:changed` инвалидирует RQ-ключи `visibility*` и `workspaces/<id>/visibility*`.

## ИИ-агенты и оркестратор

Движок готов к программному потребителю без отдельного слоя: агент — обычный зритель. Действует от имени человека — `viewerFor(userId, ws, 'ai')` (кто он, тот и видит; раскрытия нет); действует как интеграция — ключ API / бот (потолок класса `internal`, `contact` только с флагом ключа, `personal` и выше — никогда). Ответ агенту собирается через `forExternal()`: скрытое ОТСУТСТВУЕТ в `values`, а `redactions[]` перечисляет, что и почему изъято (`hidden` | `masked`) — модель видит границу своих знаний вместо маркеров, которые ей пришлось бы интерпретировать. Что можно выбрать из БД — `readableFields()`; по чему можно фильтровать и сортировать — `planDto()` / `assertQueryable()`; объяснить человеку «почему не вижу» — `explain()`. Своих масок и своих правил агент не пишет: любой инструмент ИИ, который отдаёт человеку данные записи, обязан пройти `shape()` того же сервиса-владельца.

## Ловушки

- **Новый путь чтения мимо `shape()`** — главный риск. Страж ответа ловит только объекты с двумя и более защищёнными ключами одного типа; одно поле (оклад в сводке) держит канареечный сьют — канарейку на новый путь добавлять сразу.
- **Хроника пишет сырые значения** — маскируется при чтении, если у ссылки хроники объявлен `visibility` (тип и карта полей). Новый тип с хроникой без этой строки выдаст «было → стало» целиком.
- **Параметры действий и выгрузки** (ЕСУТД, кадровые действия) — те же поля в другой форме: маскировать `shapeActionParams` / `shapeEsutdPayloads`, а не надеяться на DTO.
- **Уровень `masked` без маски** на проводе = `hidden` (частично из ничего не нарисовать); потолок обязан пересобирать решение через `finalize`, а не менять уровень поверх `full` (теряется маска и остаются `caps` — фильтр по маскированному значению).
- **`full` по умолчанию у restricted-поля невозможен** не себе — ставить в реестре `masked` + `reveal`.
- **Совпадение канарейки с законно видимым полем**: канарейка у каждого поля своя (адрес ≠ «О себе»), иначе сьют ложно падает.
- **Поиск**: в полнотекстовый индекс поля класса ≥ personal не попадают — провайдеры поиска матчат только «пол». Поле выше пола в индексе = оракул перебором.
- **Вебхуки и гостевые страницы** полей шести служебных типов не несут; новое событие с таким полем — только через `forExternal()`.
- **Полного номера карты в продукте нет** ни у кого, включая владельца (PCI DSS 3.4.1): ростер не расшифровывает PAN, в проводе только last-4.
- **Публикация**: сначала архив прежней версии, потом публикация черновика; личная политика создаётся с версией 1.

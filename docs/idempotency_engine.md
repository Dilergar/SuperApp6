# Движок идемпотентности повторов (`core/idempotency`)

> Код: `apps/api/src/core/idempotency`, привязка к транзакции — `apps/api/src/shared/idempotency/binding.ts`.

25-й платформенный движок: **повтор запроса не удваивает эффект**. Три контура — HTTP-ключ повтора на мутациях, «входящий ящик» ровно-одного-раза для чужих событий и производные ключи вниз по стеку. Правило платформы: **все мутации покрыты по умолчанию**, исключение объявляется явно (`@SkipIdempotency(причина)` из закрытого списка) и обязано означать «повтор безопасен» — клиент повторяет запрос сам, не зная об исключении.

## Зачем

Клиент не знает, что случилось, когда ответа нет: обрыв сети, таймаут, перезапуск инстанса. Единственный честный ход — повторить. Без движка каждый такой повтор — второй перевод, второй заказ, второе сообщение. Движок даёт повтору правильный ответ: либо исполнить впервые, либо вернуть исход ПЕРВОЙ попытки.

## Контракт клиента

| Что | Где |
|---|---|
| `Idempotency-Key: <8–128 символов `[A-Za-z0-9_\-:.]`>` | запрос (мутация) |
| `Idempotent-Replayed: true` | ответ, собранный из снимка |
| `X-Should-Retry: true\|false` | подсказка «повторять осмысленно / бессмысленно» |
| `Retry-After: 1` | вместе с `409 idempotency.in_flight` |

Заголовки объявлены в `exposedHeaders` CORS (`apps/api/src/main.ts`) — иначе браузер не отдал бы их скрипту. В Swagger (dev) ключ объявлен глобальным параметром: интегратор видит его на каждой мутации.

Коды отказов (`details.code`, он же ключ каталога `errors.*`):

| Код | Статус | Что значит |
|---|---|---|
| `idempotency.key_required` | 400 | Необратимая ручка (`required`) без ключа |
| `idempotency.key_invalid` | 400 | Ключ не той формы либо заголовок прислан дважды |
| `idempotency.key_reused` | 422 | Тот же ключ с ДРУГОЙ формой запроса |
| `idempotency.in_flight` | 409 | Первая попытка ещё идёт |
| `idempotency.already_completed` | 409 | Эффект случился, тела ответа нет (секрет, >64 КБ, старше 72 ч, ответ не собрался) |
| `idempotency.outcome_unknown` | 409 | Попытка оборвалась на неизвестном месте; пере-исполнять небезопасно |
| `idempotency.unavailable` | 503 | Хранилище движка недоступно НА ЗАПРОСЕ С КЛЮЧОМ (запросы без ключа не затронуты) |

## Модель данных

Схема `idem` — сырой SQL миграции `20260920120000_core_idempotency` (Prisma партиций не выражает и сравнивает только `public`).

- **`idem.keys`** — заявка на исполнение, **PARTITION BY HASH (scope_hash, key_hash)**, 16 партиций, `fillfactor=80`, PK = ключ партиции. Хэш, а не время: уникальность ключа обязана быть ГЛОБАЛЬНОЙ, а на RANGE-партициях по дню один и тот же ключ до и после полуночи попал бы в РАЗНЫЕ партиции — то есть продублировал бы эффект. Поля: `scope_hash`/`key_hash` (sha256), `user_id`, `principal`, `workspace_id`, `api_key_id`, `method`, `route`, `fingerprint` (HMAC-тег), `state`, `attempt` (fencing), `lease_until`, `atomic`, `http_status`, `error_code`, `resource_id`, `response_id`+`response_at`, `replays`, `last_seen_at`, `build`, `created_at`, `completed_at`, `expires_at`. Индексы: `(expires_at)` — чистка, `(user_id, created_at)` — поиск поддержки.
- **`idem.responses`** — снимок тела, партиции **по дню**, без уникальности: `body_enc` (envelope под KEK владельца), `scope_type`/`scope_id` (нужны перешивке после ротации KEK — колонка зарегистрирована в `KeysFieldRegistry` трижды, по разу на вид скоупа), `bytes`. Нет партиции, сбой шифрования, уничтоженный вместе с аккаунтом KEK — всё это значит «тела нет», а не отказ запроса.
- **`IdempotencyInbox`** (Prisma, `public`) — `@@unique([source, account, eventId])`, ретенция 30 дней.

Состояния строки: `in_progress` → `committed` (отметка легла в бизнес-транзакцию) → `completed` (ответ собран); `released` — эффекта не было, ключ свободен.

## Жизненный цикл (интерцептор)

`IdempotencyInterceptor` — APP_INTERCEPTOR, зарегистрирован **последним** из глобальных: к моменту поиска ключа уже отработали аутентификация, эпоха токена, скоуп ключа API, шлюз согласий и **проверка членства** — и отрабатывают заново на КАЖДОМ повторе. Иначе сохранённый ответ выдавался бы тому, у кого доступ уже отозвали.

1. **Скоуп** = sha256(`sub` | `keyId ?? 'session'` | проверенный `activeWorkspaceId` | метод | шаблон маршрута). **`sid` в скоуп не входит никогда**: он меняется на refresh, и тот же ключ после обновления токена перестал бы узнаваться. `@Public`-ручки участвуют только со своим `principal`-резолвером (гость — токен ссылки + пропуск сессии, вебхук-триггер Процессов — хэш токена триггера); нет резолвера — запрос идёт мимо движка.
2. **Отпечаток** — HMAC (`KeysMacService`, имя `idempotency`) от метод|маршрут|params|сортированный query|JCS(**разобранного** тела). Разобранного, а не сырых байтов: два JSON'а с одним смыслом (порядок ключей, пробелы, дубли) разошлись бы отпечатком, хотя обработчик видит одно и то же. Заголовки (в т.ч. `X-Locale`) в отпечаток НЕ входят — иначе повтор на другом языке считался бы другим запросом. Сверка — `verifyTagged` (константное время, `kid` в строке ⇒ ротация ключа безопасна). У multipart тела нет: multer идёт ПОСЛЕ глобальных интерцепторов, и клиент такие запросы не повторяет сам.
3. **Заявка** — `INSERT … ON CONFLICT DO NOTHING RETURNING` (голый INSERT с ловлей 23505 оставлял бы мёртвые кортежи и жёг XID). Конфликт → чтение строки **без блокировки** (её может держать живая транзакция первой попытки) + `replays++`:
   - `released` → перезахват С ЗАМЕНОЙ отпечатка: эффекта не было, исправленная форма с тем же ключом законна;
   - отпечаток не сошёлся → **422 `key_reused`**;
   - `completed` → реплей (нет тела / `store:'none'` / >64 КБ / старше 72 ч → **409 `already_completed`** + `resourceId`);
   - `committed` → то же 409 (эффект есть, ответа нет);
   - `in_progress` с живой арендой → **409 `in_flight`** + `Retry-After`;
   - аренда истекла → `atomic` ? перезахват (`attempt+1`, `FOR UPDATE SKIP LOCKED` — занята ⇒ 409) : **409 `outcome_unknown`**.
4. **Аренда** 30 с + heartbeat каждые 10 с, пока обработчик жив: долгая ручка заявку не теряет, смерть процесса — теряет (в этом и смысл).
5. **Итог**. Правда — строка в БД, не память процесса: release и finalize status-guarded по `(attempt, state)`. «Коммит прошёл, ack потерян» ⇒ строка уже `committed`, release даёт 0 строк, повтор получает `already_completed`.
   - успех + (`bound` | `dirty` | `required` | `effects:'external'`) → снимок + `completed`;
   - успех без наблюдаемого эффекта → `released` без снимка (read-only POST: поиск, предпросмотр);
   - отказ: эффект закоммичен → **финал** (статус + код + параметры, БЕЗ текста); иначе `released`. 401/403/429 и ошибки формы финальными не становятся никогда.
6. **Реплей**: успех — тот же JSON; отказ — восстановленный `ApiError` (фильтр соберёт фразу в языке ЭТОГО запроса). Заголовки `Idempotent-Replayed: true`, `Cache-Control: no-store`. `Set-Cookie` и заголовки авторизации не хранятся.

## Привязка отметки к бизнес-транзакции

Несущее: отметка «эффект закоммичен» обязана лечь **в ту же транзакцию, что и сам эффект**. Иначе остаётся щель: процесс умирает между коммитом эффекта и отметкой, и повтор отвечает неправдой.

Примитив живёт в `shared/idempotency/binding.ts` (фабрика клиента базы движки не импортирует) и работает двумя частями:

- обёртка `$transaction` объявляет ВЛАДЕЛЬЦА отметки — первую callback-транзакцию запроса;
- расширение Prisma на каждой операции: перед ПЕРВОЙ записью владельца в ту же транзакцию уходит `UPDATE idem.keys SET state='committed' WHERE … AND attempt=$a AND state='in_progress'`. Ноль строк ⇒ `IdempotencyFencedError` ⇒ откат: попытка устарела, заявку перехватили.

Правила:
- пока идёт владелец, **вложенные и параллельные** транзакции запроса отметку НЕ трогают: второй `UPDATE` той же строки с другого соединения — само-дедлок, невидимый для Postgres. Их коммит помечает запрос `dirty`;
- запись ВНЕ транзакции (модельные операции, `$executeRaw`, консервативно `$queryRaw`) ⇒ `dirty`;
- `dirty` означает «эффект мог случиться мимо отметки» — ответ становится финальным, даже если эффекта не было (консервативно и безопасно);
- вне HTTP (джобы, крон, бутстрап) обёртка — **строгий no-op**;
- служебные запросы самого движка идут в `runInternal(…)` и записью не считаются (иначе каждое продление аренды помечало бы запрос `dirty`).

Обещание `atomic` проверяется на КАЖДОМ успехе: не больше одной отмеченной транзакции и ни одной записи мимо неё. Ноль транзакций — законный исход (ручка ничего не сделала, дубль погасил второй ремень). Нарушение — метрика `idem_atomic_violations_total`, в development — 500.

## Объявление ручки

```ts
@Idempotent({ required: true, atomic: true })          // деньги: ключ обязателен, одна транзакция
@Idempotent({ store: 'none' })                          // ответ несёт секрет — снимка не существует
@Idempotent({ effects: 'external' })                    // эффект ТОЛЬКО вне базы — ответ всегда финален
@Idempotent({ principal: (req) => …, required: true })  // @Public-ручка: кто это
@SkipIdempotency('naturally_idempotent')                // вне движка, причина из закрытого списка
```

Закрытый список причин: `auth_flow` · `inbound_webhook` · `raw_response` · `own_mechanism` · `naturally_idempotent` · `no_side_effects`. **Инвариант: причина обязана означать «повтор безопасен»** — клиент авто-повторяет, не зная об исключении.

**Страж на буте** (`idempotency.routes.audit.ts`, fail-closed) роняет старт, если: мутация сама пишет ответ (`@Res()` без passthrough) без `raw_response`; `required` стоит на `@Public` без `principal`-резолвера; причина `@SkipIdempotency` не из списка.

## Производные ключи и «входящий ящик»

```ts
this.idem.deriveKey('wallet.mint')        // 'idem:v1:<sha256(scope|key|шаг)>' либо null (ключа у запроса нет)
this.idem.stableKey('jobs.payout', jobId) // вне HTTP: детерминированный ключ из стабильных частей
await this.inbox.once(tx, { source: 'livekit', account: room, eventId: event.id })
```

- **Производный ключ** считается из СТАБИЛЬНЫХ входов, а не из id строки заявки: строка живёт 7 дней, и ключ от её id сменился бы — второй ремень денег молча отвалился бы ровно на повторе через неделю. Потребители: `LedgerService.mint/burn/transfer` (`LedgerTransfer.idempotencyKey` — уникум; дубль найден ⇒ операция ничего не делает и остатки не трогает).
- **Ящик** — примитив «ровно один раз» для того, что приходит СНАРУЖИ без нашего ключа. Отметка ложится **в транзакцию вызывающего** (`assertInTransaction`), а `firstTime()`/`forget()` — для приёмников, чья обработка в одну транзакцию не помещается (внутри есть сетевые вызовы): отметили → обработали → упали ⇒ `forget`, иначе редоставка была бы выброшена как дубль. **Отметка ставится ТОЛЬКО ПОСЛЕ проверки подписи и окна времени**: иначе кто угодно травит ящик поддельным `event.id`, и настоящее событие гасится как дубль.

## Кому ставят `required`

Критерий один: **повтор без ключа = вторая сущность, которую нельзя отменить** — деньги ушли, SMS доставлена, номер реестра сожжён, люди уже увидели второй экземпляр. «Просто создание» под него не подходит: черновик, папку, шаблон автор удалит сам.

**Первая волна**

- **`required` + `atomic` + производный ключ** — деньги: `wallet` (чеканка, сжигание, казначейская выплата), эскроу заказов и задач, покупки магазина, скины.
- **`required`** — мессенджер (`POST chats/:id/messages`, альбом вложений, отложенные), `core/sign` (ПЭП-подтверждение, CMS, отказ), `approvals steps/:stepId/decide`, кадровые действия и пакеты КЭДО, отправка в ЭДО, общие диспетчеры действий (`rich-cards :actionKey/execute`, гостевые `:token/actions/:key` — за ними стоят и деньги, и подпись).

**Вторая волна** (15 ручек — те же деньги, внешний мир, невозвратные ресурсы и рассылки):

| Ручка | Почему повтор нельзя отменить |
|---|---|
| `POST tasks` · `POST tasks/:id/accept` | награда замораживается в эскроу и выплачивается из него; исполнителям уже ушло уведомление |
| `POST …/documents/:id/assign-number` | номер реестра НЕ переиспользуется — в нумерации остаётся дыра |
| `POST …/documents/:id/external/sms` | SMS ушла наружу (и стоит денег) |
| `POST …/doc-campaigns` | кампания = рассылка ВСЕЙ аудитории; отозвать её у получателей нечем |
| `POST …/processes/:defId/start` | экземпляр немедленно ставит задачи, шлёт сообщения, зовёт внешние системы |
| `POST …/processes/instances/:instId/steps/:stepId/decide` | решение двигает маршрут дальше (симметрия с `approvals`) |
| `POST …/shift-patterns/:patId/generate` | второй комплект смен в графике людей |
| `POST contacts/invitations` · `POST workspaces/:id/invitations` | приглашение ушло человеку |
| `POST workspaces` | вторая организация ест место в тарифе; убирается только архивом с чисткой |
| `POST workspaces/:id/transfer` | владелец теряет права и вернуть их сам не может |
| `POST share-links` | вторая живая ссылка наружу, о которой автор не знает |
| `POST calendar/events` | вторая встреча в календарях участников и второе приглашение |
| `POST messenger/chats/group` | вторая группа, в которую людей уже добавили |

Осознанно НЕ в волне: личная бухгалтерия Финансов (записи удаляются самим человеком, наружу ничего не уходит), черновики и справочники (виды документов, шаблоны, отделы, должности), копии на Диске.

**Прочее**

- **`store:'none'`** — всё, чей ответ и есть секрет: выпуск и ротация ключей API и ботов, секрет вебхука, токен звонка, сессия редактора документов, подписанные ссылки на части файла.
- **`@SkipIdempotency`** — поток входа (`auth_flow`), кабинет платформы и приём аналитики (`own_mechanism`), входящие вебхуки (`inbound_webhook`), горячие «стало так»: `notifications seen/read/mute`, `PUT preferences|quiet`, `chats/:id/read`, раскладка доски Заметок, автосохранение заметки.

## Перерисовка ответа по ссылке (`IdempotencyReplayRegistry`)

Снимок хранит ответ на момент ПЕРВОЙ попытки и живёт 72 часа. Для карточки со статусом это ложь: задачу за это время взяли в работу, заказ подтвердили, документ подписали обе стороны. Владелец данных регистрирует рендерер — и повтор отдаёт СВЕЖУЮ сущность под правами ЭТОГО запроса.

```ts
// в onModuleInit владельца данных (направление «фича → движок»)
this.replay.register('POST', '/api/tasks', async (taskId, ctx) =>
  ctx.userId ? { success: true, data: await this.getTask(ctx.userId, taskId) } : undefined,
);
```

Правила:

- **ключ реестра — метод и ШАБЛОН маршрута с префиксом** (`POST /api/tasks/:id/accept`): ровно то, что видит интерцептор в `req.route.path` (алиас `/api/v1` переписывается в `/api` раньше роутинга);
- **рендерер отдаёт РОВНО то, что вернула бы ручка** — вместе с конвертом `{ success, data }`: снимок хранит значение обработчика, и форма повтора обязана совпадать с ним;
- **рендерер зовут только на успешной строке** (`http_status < 400`) с непустым `resource_id`. `resource_id` берётся из `data.id` ответа — ручка без `id` в ответе (например, короткий `SignActStateDto` с `actId`) рендерер не получит;
- **права проверяет сам сервис** — тем же способом, что и обычное чтение. Отказ доступа (403/404) — ПРАВИЛЬНЫЙ ответ повтора: снимок здесь как раз врал бы;
- **`undefined` — законный ответ** «свежего вида нет»: движок падает обратно на снимок. Туда же падает поломка рендерера (не-HTTP исключение) — баг владельца данных не вправе превращать успешный повтор в 500, и движок шумит об этом в лог.

Зарегистрировано сегодня: `POST /api/tasks`, `POST /api/tasks/:id/accept` (Задачник), `POST /api/shop/listings/:id/buy`, `POST /api/shop/listings/:id/contribute` (заказ), `POST /api/approvals/steps/:stepId/decide` (заявка с маршрутом), `POST /api/workspaces/:workspaceId/documents/:documentId/send-external` (карточка документа).

## Клиенты

- `packages/api-client/src/client.ts`: авто-ключ на КАЖДОЙ мутации с `Authorization` (анонимные — нет: без принципала защиты не существует). Ключ живёт в config запроса, поэтому и `401 → refresh`, и авто-повтор уходят с ТЕМ ЖЕ ключом. Авто-повтор ≤ 3 (full jitter 0.5 → 8 с, `Retry-After` сильнее паузы) только для: ответа нет вовсе, 502/503/504, `409 in_flight`, `X-Should-Retry: true`. Не для multipart. Опция `idempotencyKey` в хелперах.
- Веб: `useIdempotencyKey(deps)` — ключ НАМЕРЕНИЯ формы (двойной клик = один эффект); сбрасывается на успех, на изменение полей и по событию `key_reused`. Для СПИСКА (кнопка на каждой строке) — `useIdempotencyIntent()`: `keyFor('buy', listingId)` = «эта попытка × эта строка». Единая дверь отказов — `toastApiError(err)` (`apps/web/src/lib/api-errors.ts`): `already_completed` → тон УСПЕХА + перечитать данные, `in_flight` → спокойный тост, `key_reused` → отказ + сброс ключа. Старая пара «взять текст → красный тост» запрещена ESLint-стражем. `outcome_unknown` тостом не показывается вовсе — `OutcomeUnknownAlert` (развилка «плашка или тост» — `useOutcomeUnknown()`).
- Необратимые формы веба под ключом намерения: кошелёк (чеканка, сжигание), магазин (покупка), скины (покупка), подпись (ПЭП-подтверждение и отказ), решение по шагу (стопка «Ждут решения» и карточка заявки), кадровое действие и пакет КЭДО, кампания ознакомления, отправка контрагенту (ЭДО), приёмка и возврат работы по задаче. `SlowRequestNote` стоит там же, где кнопка блокируется на время авто-повтора.
- **Где ключа намерения НЕТ — и это решение, а не пропуск**: контейнер CMS у ЭЦП (каждая подпись — новые байты, один ключ на два тела дал бы `422 key_reused`) и `pep/start` (`store:'none'`: повтор получил бы `409` вместо кода из SMS). Двойной клик там закрывает `disabled`/`loading`.
- Сьюты: `apps/api/scripts/_lib.cjs` ставит ключ на каждую мутацию сам — иначе ручки `required` отвечали бы сьютам 400.

## Покрытие

Строка на буте (страж `idempotency.routes.audit.ts`) — не вера, а счёт:

```
idempotency route audit: ok — 517 mutations, 459 covered (55 require a key, 13 store nothing),
58 declared out (own_mechanism: 32, naturally_idempotent: 11, auth_flow: 6, raw_response: 5,
inbound_webhook: 3, no_side_effects: 1), none unprotected
```

Читается так:

- **459 из 517 мутаций под движком** — по умолчанию, без единой строки у автора ручки. Прислал клиент ключ — защита работает; не прислал — запрос идёт как раньше;
- **55 требуют ключ** (`required`) — две волны, критерий ниже. Там отсутствие ключа — отказ, а не «как получится»;
- **58 выведены явно**, каждая — с причиной из закрытого списка, и каждая причина означает «повтор безопасен»;
- **`none unprotected`** — публичных мутаций без принципала не осталось: у каждой либо резолвер (гость, вебхук-триггер), либо объявленная причина. Появится новая — строка это покажет, а `required` на такой ручке уронит бут.

Чего движок НЕ покрывает по построению: команды кабинета платформы и приём аналитики (свои механизмы), поток входа, входящие вебхуки чужих систем (их дедуп — «входящий ящик» по идентификатору источника), ручки, отдающие байты. Всё это — не пробелы, а объявленные решения.

## Режимы, метрики, фон

`IDEMPOTENCY_MODE=off|observe|enforce` (по умолчанию `enforce`). `observe` — окно выката: заявки заводятся и считаются метрики, но отказов нет (запрос исполняется как обычно). `off` — полный стоп-кран. Остальные настройки — `IDEMPOTENCY_KEY_TTL_DAYS` (7), `IDEMPOTENCY_RESPONSE_TTL_HOURS` (72), `IDEMPOTENCY_LEASE_MS` (30 000), `IDEMPOTENCY_MAX_RESPONSE_BYTES` (65 536), `APP_BUILD` ([environment_variables.md](environment_variables.md)).

Метрики `/metrics`: `idem_requests_total{result=new|replay|in_flight|mismatch|takeover|unknown|fenced|released}`, `idem_atomic_violations_total{route}`, `idem_keys_rows`, `idem_keys_swept_total`. **Алерт ставится на всплеск `mismatch`**: это либо баг клиента, либо попытка подобрать чужой ключ.

Крон (`idempotency.cron.ts`, лок Redis): каждые 10 минут — партиции снимков вперёд и счётчик строк; ночью — чистка просроченных ключей батчами, сброс партиций снимков (`DETACH CONCURRENTLY` + `DROP`), ретенция ящика.

## Цена

Замер на дев-машине (Postgres в Docker, 300 запросов, 25 параллельных, ручка «одна транзакция — один эффект»):

| Запрос | p50 | p95 |
|---|---|---|
| БЕЗ ключа (обёртка `$transaction` — строгий no-op) | 55 мс | 73 мс |
| С ключом (заявка + отметка в транзакции + снимок ответа) | 82 мс | 94 мс |

То есть защита стоит ~27 мс на запрос: четыре дополнительных оператора (заявка `INSERT … ON CONFLICT`, `UPDATE` отметки ВНУТРИ бизнес-транзакции, вставка зашифрованного снимка, финализация). **Запрос без ключа не платит ничего** — это и есть смысл строгого no-op: движок стоит на пути каждой мутации, и цена обязана появляться только там, где клиент попросил защиту.

## Кабинет платформы

Команда `idempotency.key.lookup` (способность `platform.lookup.read`, причина обязательна, ключ в журнале замаскирован) — «мой запрос прошёл?» от интегратора: по сырому ключу находятся его заявки. Панель `user.idempotency` карточки 360 — сводка «спорных операций» человека за окно. **Тела ответов не раскрываются никогда**: они лежат под KEK владельца, а спор решают факты.

## Ловушки

- **Скоуп ключа составной.** Тот же ключ у другого человека, в другой организации, по другому ключу API или на другой ручке — это РАЗНЫЕ ключи, и все исполнятся. Так и задумано: чужой ключ обязан быть «невиданным».
- **Отпечаток включает query и params.** `?ms=0` и `?ms=12000` — разные запросы, и один ключ на них даст 422. Это правильно, но легко забыть в сьютах.
- **Реплей расходует лимит троттлера** (как у Stripe): ответ отдаётся из снимка, но запрос всё равно посчитан.
- **Снимок хранит форму DTO на момент исполнения.** В течение 72 часов после деплоя повтор может отдать старую форму — контракт меняется аддитивно, `build` в строке помогает разобраться. Карточке со статусом этого мало — ей нужен рендерер в `IdempotencyReplayRegistry`.
- **`409 already_completed` ≠ «человек добился своего».** Первая попытка могла закоммитить эффект и упасть — снимка тела нет, и код тот же. Настоящий исход лежит в `details.completedStatus`; веб красит тост по нему (`apiErrorCompletedStatus`), а не «всегда зелёным».
- **Дубли НЕденежных сущностей возможны при повторе позже 7 дней**: строка заявки к тому времени уже вычищена. У денег второй ремень бессрочный.
- **Ручка с эффектом ТОЛЬКО вне базы обязана объявить `effects:'external'`** — привязка к транзакции такого эффекта не видит, и ответ иначе не станет финальным.
- **Отдельного журнала реплеев нет** — только счётчик `replays` на строке.
- `@SkipIdempotency` на КОНТРОЛЛЕРЕ покрывает все его ручки: добавляя в такой контроллер необратимую операцию, снимайте исключение точечно.

## Проверка

`node apps/api/scripts/verify-idempotency.cjs` (dev, аккаунты сьюта, база не чистится): форма ключа и два заголовка; 20 параллельных с одним ключом ⇒ ровно один эффект; другое тело ⇒ 422; скоуп по человеку/ручке; реплей после смены сессии; язык реплея отказа; отказ без коммита ⇒ ключ свободен; read-only POST ⇒ `released`; горячая skip-ручка ⇒ ноль строк; `store:none` и секрет вне снимка; снимок — конверт; тело > потолка; смерть после заявки (atomic ⇒ пере-исполнение, иначе `outcome_unknown`); смерть после коммита ⇒ `already_completed` и ОДИН эффект; fencing; вложенная и параллельные транзакции без дедлока; долгая ручка и heartbeat; **второй ремень денег** (строку заявки сносим руками — второй проводки нет); реплей проходит гарды **двумя разными способами** — мёртвый токен ⇒ 401 и **отзыв членства между попытками** (организация → сотрудник исполнил мутацию с ключом → его исключили → повтор ТЕМ ЖЕ ключом ⇒ `403 workspace.noAccess`, без заголовка реплея и без второго эффекта); **перерисовка по ссылке** (задачу двинули между попытками ⇒ реплей отдал свежий статус, а не снимок); ящик не травится поддельным id; партиции.

Дев-полигон движка — `idempotency.dev.ts` (только development/test): ручки `effect|atomic|required|secret|big|readonly|fail|nested|slow`, `simulate` (привести строку ключа в состояние, в котором её оставил бы упавший инстанс) и `reset`.

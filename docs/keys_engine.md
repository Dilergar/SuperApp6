# Движок ключей (`core/keys`)

22-й платформенный движок. ЕДИНСТВЕННАЯ дверь ко всей криптографии платформы: подпись токенов, шифрование секретов и ПДн, слепые индексы, HMAC, ключи API организаций и людей, боты, реестр ключей, журнал. Правило: **секрет, ключ, шифрование или подпись — только через движок**; свой `crypto.createCipher`/`jsonwebtoken`/`JWT_SECRET` в сервисе запрещён линтером (`KEYS_SECRET_SELECTORS` в `apps/api/eslint.config.mjs`). Части: [keys_api_access.md](keys_api_access.md) (ключи API, боты, реестр), [keys_pii.md](keys_pii.md) (ПДн), [webhooks_engine.md](webhooks_engine.md) (исходящие вебхуки, 23-й движок).

## Модель

- **`CryptoKey`** (`scope` · `purpose` · `name`) — логический ключ; **`CryptoKeyVersion`** — версии с состояниями `pending → active → disabled | destroy_scheduled → destroyed`; материал версии хранится ОБЁРНУТЫМ корнем (`wrapped`, AAD = `kid|purpose`), в памяти — кэш 5 мин с эпохой в Redis (`keys:epoch`, микрокэш 1 с) — kill-switch работает на всех инстансах за секунду.
- **Скоупы**: `platform` (KEK платформы, пары подписи, HMAC-ключи), `workspace:<id>` (KEK организации — секреты Процессов, вебхуков, реквизиты), `user:<id>` (KEK человека — ПДн, карты, Google-токены). KEK создаётся лениво при первом шифровании (`ensureKey` под advisory-локом).
- **Назначения** (`purpose`): `kek` (AES-256), `sign` (Ed25519, пара на аудиторию), `mac` (HMAC-SHA256, `MAC_KEY_NAMES`: `verify_otp`, `oauth_state`, `blind_index`, `api_key_pepper`, `idempotency`, `google_channel`, `audit` — псевдонимы журнала безопасности, `lifecycle` — псевдоним стёртого субъекта в журнале стираний и сертификате).
- **Корень** (`KeyProvider`): `software` — 32 байта в файле `KEYS_ROOT_KEY_FILE` (dev-дефолт `apps/api/.keys/root.key`, создаётся сам только в development); `pkcs11` — заглушка (`KEYS_PKCS11_*`), интерфейс тот же (`wrap/unwrap/generate/sign/verify`). Отпечаток корня `rootKid` (16 hex) — в каждой обёртке; версия, обёрнутая чужим корнем, роняет бут (fail-closed).

## Артефакты (самоописываемые, с `kid`)

| Префикс | Форма | Где |
|---|---|---|
| `sa6e:1:<kek_kid>:A256GCM:<dek_wrapped>:<iv>:<ct+tag>` | envelope: DEK на запись, обёрнут KEK; **AAD = `entity|field|ownerType|ownerId|kek_kid`** — шифротекст не переставить в чужое поле/строку | `KeysEnvelopeService.encrypt/decrypt/tryDecrypt/rewrap` |
| `sa6b:1:<mac_kid>:<hmac>` | слепой индекс (поиск по равенству без расшифровки; нормализация значения — у колонки); живёт в ДВУХ колонках-слотах `_bi` / `_bi_alt` | `blindIndexPlan()` (слот и значения на одну операцию), `blindIndexWith` |
| `sa6m:1:<mac_kid>:<hmac>` | HMAC-строка (OTP-коды, state OAuth) | `KeysMacService.tagged/verifyTagged/verifyAny` |
| `sa6_<bot|pat|whs>_<live|test>_<43 base62>_<crc32 6>` | секреты API-ключей и вебхуков (в БД — HMAC-хеш pepper-ключом либо envelope) | [keys_api_access.md](keys_api_access.md) |

Реестр шифрованных колонок — `KeysFieldRegistry.register({table, idColumn, idNumeric?, column, scope, scopeColumn, scopeDiscriminator?, entity, field, blindIndex?: {column, altColumn, name, normalize}, literal?, legacyDecrypt?})` из модуля-владельца: по нему работают rewrap при ротации KEK, реиндекс слепых индексов и перешивка legacy-строк (`keys.legacy.reencrypt` на старте). `scopeDiscriminator` — полиморфный владелец (`owner_type` + `owner_id`): колонка регистрируется по разу на вид скоупа, каждая со своим равенством. `literal` — служебная заглушка без конверта (`deleted:<id>`, `bot:<id>`). `idNumeric` — числовой id (bigint журнала безопасности): курсор перешивки сравнивает числа, а не строки — текстовый курсор по bigint давал бы порядок «1, 10, 100, 2…» и O(n²) проходов по миллионам строк. Все `_enc`-колонки ПДн регистрирует сам `KeysPiiService` из `PII_MODELS` ([keys_pii.md](keys_pii.md)). Колонка вне реестра при ротации KEK НЕ перешивается: старая версия KEK из-за неё останется `active` навсегда (страж остатка ниже), а строки под ней — вне плановой ротации.

## Подпись токенов

- JWS compact, `alg: EdDSA`, `kid` в заголовке, `typ` по аудитории (`at+jwt`, `refresh+jwt`, `platform+jwt`, `wopi+jwt`, …). Верификатор называет `typ` ЯВНО (`verify(aud, token, { typ })`): новый вид токена той же аудитории не пройдёт как access по умолчанию; legacy HS256 `typ` не различал — для него `legacy.typOptional`. Allow-list алгоритмов: EdDSA (+ HS256 только на legacy-окне); заголовки `jku/jwk/x5u/x5c/crit` — отказ. Своя реализация на `node:crypto` (`keys.jwt.ts`), без `jose`/`jsonwebtoken`.
- **Аудитории** (`SIGNING_AUDIENCES`): `product` (access/refresh), `platform` (кабинет), `wopi`, `share_link`, `files_url`, `webhook`, `consents`, `audit` (дайджесты журнала), `lifecycle` (сертификаты стирания — [lifecycle_erasure.md](lifecycle_erasure.md)) — у каждой своя пара; три последние — архивные: подпись проверяется годами (`verifyArchival` по окну жизни версии) (урок Storm-0558: один ключ на всё = один инцидент на всё). Токен чужой аудитории отвергается ДО подписи.
- **JWKS**: `GET /.well-known/jwks.json` (вне префикса `/api`, `Cache-Control: max-age=600`) и алиас `/api/v1/keys/jwks`; публикуются `active` + `pending` версии всех аудиторий (OKP/Ed25519, `use: sig`).
- **Ротация без разлогина**: `signing.rotate(audience)` → версия `pending` (уже в JWKS) → джоб `keys.signing.activate` через `signingActivateDelayMin` (кэш JWKS у потребителей успел обновиться) → новая версия подписывает, старая `active` проверяет до `retireAfterSec` (= максимальный TTL токенов аудитории) → `keys.signing.retire` → `destroy_scheduled` → через 30 дней `destroyed`. Плановая ротация — крон раз в день по `signingRotationDays` (90), KEK — по `kekRotationDays` (365; выборка по возрасту PRIMARY-версии, старейшие первыми, до `kekRotationsPerRun` за прогон; `keys.rewrap` перешивает колонки реестра батчами по 500). Джоб активации/перешивки ставится В ТОЙ ЖЕ транзакции, что и новая версия (`createVersion(…, inTx)`): падение между шагами не оставляет версию `pending` навсегда.
- **Вывод старой версии — только пустой.** `keys.rewrap` стартует через `rewrapDelaySec` (кэш старого primary протух на всех инстансах) и после прохода считает строки, оставшиеся под другими версиями: `0` → старые версии уходят в `destroy_scheduled`; остались только заведомо битые (формат/AAD/уничтоженная версия) → версии остаются `active`, в лог — предупреждение; иначе джоб падает и повторяется. Самолечение: версия уже в `destroy_scheduled`, а строки под ней есть → проход возвращает её в `active`, перешивает и выводит заново. `scheduleDestroy` никогда не трогает primary.
- **Смена ключа слепых индексов — без простоя, двумя слотами.** У каждого индекса две колонки: `_bi` (слот 0) и `_bi_alt` (слот 1); версия mac-ключа `blind_index` несёт свой слот (`crypto_key_versions.slot`) и пишет ТОЛЬКО в него — в колонке всегда ровно одна версия ключа, поэтому уникальные индексы и `findUnique` по номеру работают в любой момент. Ход (`keys.blindindex.rotate`, critical, dualControl; только при компрометации): (1) `rotateBlindIndex` — версия `pending` в противоположном слоте; расширение ПДн с этого момента пишет ОБА индекса (primary — в рабочий слот, pending — во второй), поиск идёт по primary; (2) `keys.reindex` через `rewrapDelaySec` (все инстансы уже знают про pending) заполняет второй слот у старых строк под оптимистичным гардом (`AND <enc> = прочитанное`) и, когда незаполненных не осталось, активирует версию — поиск одним движением переключается на заполненный слот; (3) `keys.blindindex.retire` ещё через `rewrapDelaySec` выводит прежнюю версию и очищает её слот порциями (он свободен под следующую смену). Вне окна второй слот пишется `null` — запись инстанса с протухшим кэшем не оставит в нём индекс старого значения. Строки, которые не открыть (замороженный/уничтоженный KEK), и конфликты уникальности смену не держат: `keys.reindex` без pending — «починка рабочего слота», идёт ежедневно и досчитывает их после разморозки. Вторая смена, пока первая не завершена, — `409 keys.rotation_in_progress` (слотов два). Сразу-`active` вторая версия `blind_index` запрещена в keystore: она стала бы primary с пустым слотом.
- **Тяжёлый джоб укладывается в аренду.** Заполнение слота, очистка слота и перешивка корня работают заходами по `heavyJobBudgetMs` (20 мин < аренды очереди `keys`): не успел — ставит себе продолжение и выходит, иначе reaper отдал бы джоб второму воркеру параллельно.
- **Legacy-окно HS256** (`JWT_SECRET_LEGACY`/`JWT_SECRET` + `KEYS_LEGACY_HS256_UNTIL`): старые токены и производные HMAC читаются до даты; в production окно обязано быть датированным, не истёкшим и не длиннее 45 дней вперёд (страж env: дата «в 2099 году» сделала бы временный допуск постоянным), после даты секрет удаляется из окружения. Прочие потребители `JWT_SECRET` (docs, share-links, files-url, platform, verify, google state, кредсы Процессов, карты) переведены на движок.

## Заморозка и уничтожение

- `freezeScope(scope)` → все версии `disabled` → любое чтение/запись данных скоупа = `403 keys.key_unavailable` (организация под расследованием, аккаунт в споре); состояние ДО заморозки запоминается в `frozen_from`, и `unfreezeScope` возвращает ровно его: `pending` — в `pending`, а версия, выключенная поштучно (`disable(kid)`, подозрение на утечку; `frozen_from` пуст), остаётся выключенной. Команды кабинета `keys.workspace.freeze|unfreeze` (critical, dualControl).
- `scheduleScopeDestroy(scope)` при purge организации и анонимизации аккаунта: через `destroyDelayDays` (30) материал стирается — crypto-shredding зашифрованных данных без обхода таблиц.
- **Ротация корня — окно двух корней, перешивка порциями** (`keys.root.rotate {newRootKid}`, critical, dualControl, dryRun). Одной транзакцией keystore не перешить: у каждого человека и организации свой KEK. Ход: (1) церемония создаёт новый файл (две офлайн-копии у двух людей), печатает отпечаток; (2) файл выкладывается на КАЖДЫЙ инстанс как `KEYS_ROOT_KEY_FILE_NEXT` — инстанс держит оба корня и открывает версию тем, что назван в её строке (`root_kid`); (3) команда сверяет отпечаток с загруженным следующим корнем и «перекличку» инстансов (`keys:instances`: каждый раз в минуту объявляет свои корни; живой инстанс без следующего корня → `400 keys.root_fleet_not_ready`; нет Redis → тоже отказ) и ставит `keys.root.rewrap`; (4) джоб перешивает версии порциями по `rootRewrapBatch` (каждая — свой UPDATE под гардом `root_kid = текущий`); ротация НАЧАТА ⇔ в keystore есть версия под следующим корнем — с этого момента новые версии оборачиваются им (хвост под старым не растёт); рестарт посреди перешивки и версии-опоздавшие добивает `resumeRootRewrap` (бут и ежедневный крон); (5) джоб пишет `root.rotated` и предупреждение в лог → `KEYS_ROOT_KEY_FILE` = новый файл, `KEYS_ROOT_KEY_FILE_NEXT` убрать, перезапустить инстансы, старый файл уничтожить. Бут со старым корнем после ротации падает (версии под чужим корнем — fail-closed). Учения: `keys-root-rotation-drill.ps1` (полный цикл на временной базе) и `keys-verify-root.cjs` (копия файла открывает keystore; обязательно перед прод-запуском и раз в квартал).

## Журнал и наблюдаемость

- Действия с ключами, ботами, вебхуками и криптодействия движка — события `keys.*` журнала безопасности ([audit_engine.md](audit_engine.md)): `KeysAuditService.record(tx, …)` — тонкий адаптер над `AuditService` (DI-цикл `keys ↔ audit` разорван ленивым `DI_TOKENS.AuditService`), детали — по схеме реестра, без материала и секретов. Лента организации — `GET /workspaces/:id/keys/journal` (вкладка «Журнал» раздела «Интеграции и ключи», фильтр по предмету) — проекция журнала с `workspace_id` организации; события движка (ротации, заморозки, rewrap) пишутся без организации либо с ней.
- Журнал объёма — `api_access_log` (обращения ключами, 90 дней) — **месячные партиции** (миграция `keys_journal_partitions`, руками; составной PK `(id, <ts>)` зеркалом в схеме): партиции на три месяца вперёд и сброс по сроку политики `ApiAccessLog` реестра (90 дней, пол 30) ведёт `core/lifecycle` функциями владельца данных ([lifecycle_engine.md](lifecycle_engine.md)), не `DELETE` строк; вставка в месяц без партиции заводит её (`LifecyclePartitions.isMissingPartition`) и повторяется один раз. `key_id` — uuid ключа.
- **Метрики Prometheus** (`shared/metrics`, `GET /metrics` у корня хоста; гейт `METRICS_TOKEN` — Bearer в константное время, в production без токена маршрут отвечает 404, в development открыт): `keys_unwrap_total{purpose}` (распаковки корнем), `keys_cache_hit_total{result}` (кэш версий), `keys_decrypt_latency_seconds{result}` (гистограмма расшифровки поля), `keys_api_auth_total{result}` (исходы аутентификации ключом: `ok`, `invalid`, `revoked`, `expired`, `frozen`, `ip_denied`, `rate_limited`), `keys_root_present` (корень загружен), `webhooks_delivery_ok_total`/`webhooks_delivery_fail_total{outcome}`/`webhooks_delivery_snoozed_total`; плюс стандартные `sa6_process_*`/`sa6_nodejs_*`. Метки — только коды, ни id, ни ПДн. Отсутствие корня на старте — строка лога `event=keys.root.missing provider=… code=…` (алерт по логам) и отказ бута.
- **Бэкапы и crypto-shredding (правило ops)**: бэкап БД содержит только ОБЁРНУТЫЕ версии ключей, поэтому уничтожение версии в keystore (`destroyed`, материал = NULL) делает данные нечитаемыми и в бэкапах — при условии, что бэкап keystore (таблицы `crypto_keys`/`crypto_key_versions`) подчиняется тому же ретеншну, что и `destroy_scheduled` (30 дней): снимок старше 30 дней с живой версией ключа воскресил бы стёртое. Файл корня в бэкап БД не входит никогда — только офлайн-копии церемонии.

## Дев-полигон и сьюты

`/keys/dev/*` (только development/test): `status`, `signing/rotate|activate|retire|sign` (`rotate` ставит джоб активации с БОЕВОЙ задержкой `signingActivateDelayMin`, учение активирует явно `activate`: джоб «сейчас» гонялся с проверкой «до активации подписывает старая»), `kek/rotate`, `scope/freeze|unfreeze`, `roundtrip` (envelope + AAD + mac + blind index), `blind-index/status|rotate|reindex|retire` (смена ключа слепых индексов по шагам), `root/status|rewrap` (окно двух корней), `legacy/reencrypt`, `pii/status|mode|backfill`, `usage/flush|daily|throttle|partitions` (`throttle` — посев корзины минуты / суточного счётчика выгрузки ключа для учения 429; `partitions` — партиции журналов вперёд и сброс по ретеншну). Ручки `/keys/dev/webhooks/*` принадлежат движку вебхуков (`core/webhooks/webhooks.dev.ts`): движок ключей модуль вебхуков не импортирует даже в dev — [webhooks_engine.md](webhooks_engine.md). Сьюты: `verify-keys.cjs` (секции A–E: keystore, JWKS, ротации, заморозка, учение корня, журнал append-only, потребители подписи, envelope-потребители, ключи API и боты), `verify-keys-pii.cjs`, `verify-webhooks.cjs`; скрипты `keys-init-root.cjs` (церемония), `keys-verify-root.cjs` (учение восстановления) и `keys-root-rotation-drill.ps1` (учение ротации корня на временной базе `sa6_rootdrill` и Redis-БД 9: корень A → окно A+B → корень B → отказ бута под A; живой keystore не трогает).

## Ловушки

- **Prisma `Bytes`** принимает только `Uint8Array` — `Buffer` из `node:crypto` заворачивать `Uint8Array.from`.
- **AAD привязан к `ownerType|ownerId`**: перенос строки в другую организацию = перешифрование (`rewrap` с новым контекстом), иначе `decrypt` даст `format`/`auth` ошибку.
- **`disabled` ≠ «старая версия»**: заморозка — состояние kill-switch; ротация оставляет старую версию `active` до retire, иначе токены и шифротексты умирают раньше срока.
- **Кэш KEK 5 мин**: заморозка доходит через эпоху Redis (микрокэш 1 с); при недоступном Redis инстанс живёт на своём кэше до TTL.
- **Эпоха сбрасывается ПОСЛЕ коммита.** Мутация keystore в чужой транзакции (`freezeScope(scope, actor, tx)`, `scheduleScopeDestroy`, `disable/enable/scheduleDestroy` с `tx`) эпоху сама не трогает: сброс до коммита гонится с чтением, которое вернуло бы в кэш ещё живую версию уже под новой эпохой — замороженный ключ работал бы до TTL. Вызывающий зовёт `store.bumpEpoch()` после коммита (команды кабинета — `afterCommit` в `CommandOutcome`, purge/анонимизация — `KeysCascadesService.afterScopeDestroyCommitted()`); забытый вызов страхуют отложенные сбросы `foreignTxEpochBumpsMs` (2 с / 15 с / 60 с).
- **GCM-тег — всегда 16 байт** (`authTagLength` у каждого шифра): без него Node принимает и 4-байтовый тег. Части AAD не содержат разделитель `|` (страж в `aad()`).
- Все `keys.*` env — [environment_variables.md](environment_variables.md); секреты в логах и конвертах ошибок гасит `redactSecrets` (`shared/utils/redact.ts`).

## Архивная проверка подписи и компрометация версии

Аудитория `consents` подписывает версии документов платформы ([consents_engine.md](consents_engine.md)) — подпись ставится один раз и обязана проверяться годами, а версии ключа ротируются раз в 90 дней и уходят в `destroyed` (стирается `wrappedMaterial`, публичный ключ остаётся). Поэтому рядом со строгой `verifyRaw` (только `active`) есть **`verifyArchival(audience, { kid, data, sig, signedAt })`**: принимает `active | destroy_scheduled | destroyed`, отвергает `pending`/`disabled`, любую версию с меткой `compromisedAt` и подпись, чей `signedAt` лежит вне окна жизни версии (активирована … выключена, допуск `archivalClockToleranceSec`). Момент подписи потребитель обязан включать В ПОДПИСАННОЕ — иначе его можно поправить в базе.

`crypto_key_versions.compromised_at` — отдельная колонка, а не `state = disabled`: `disabled` уходит в `destroy_scheduled` → `destroyed`, и без метки компрометация «отмывалась» бы для архивной проверки. Метка ставится при любом состоянии, не снимается никогда; `enable` скомпрометированную версию не оживляет. `KeysSigningService.compromise(audience, kid)` для primary сначала создаёт новую `active`-версию и помечает старую В ОДНОЙ транзакции keystore. Команда Кабинета — `keys.signing.compromise` (critical, dualControl); артефакты перезаверяет их владелец (`consents.versions.reattest`). Дев-полигон: `/keys/dev/signing/disable|compromise`.

# Выгрузки данных и восстановление арендатора (core/lifecycle)

Часть движка жизненного цикла ([lifecycle_engine.md](lifecycle_engine.md)): **переносимость** (ЗоПД ст. 24, GDPR ст. 20, Google Takeout) — человек забирает свои данные целиком, владелец — данные организации; **восстановление одной организации** из бэкапа без отката всей базы (Atlassian 2022: 14 дней без такого инструмента). Одна упаковка на оба вида: `manifest.json` + `data/<политика>.<nnn>.jsonl` + `files/<fileId>/<имя>`.

| Вид | Кому | Строки | Контейнер | Импорт |
|---|---|---|---|---|
| `portable` | Человек (свой архив), владелец (архив организации) | Форма для зрителя: без секретов, ПДн расшифрованы, поля видимости глазами заказчика, без удалённого и вне срока | ZIP-части ≤ 2 ГБ; манифест и README — в последней части | Нет |
| `restore` | Только Кабинет (`lifecycle.restore.*`) | Как есть (`to_jsonb(t)::text`, шифротекст остаётся шифротекстом) | Объекты `exports/<id>/data/*.jsonl` + манифест, подписанный Ed25519 (аудитория `lifecycle`) | Да |

## Реестр: что и чьё уходит в архив

Политика реестра размечает выгрузку тремя полями ([lifecycle_engine.md](lifecycle_engine.md)):

- `exportable: 'user' | 'workspace' | 'both'` — сторона архива;
- `exportScope.{user|workspace}` — когда ключ владельца сторону не называет: `columns` (любая колонка = субъект), `via` (колонка указывает на строку политики-родителя этого же субъекта), `filter`, `personalOnly`. Без него сторона отбирается ключом владельца: человек, полиморфный владелец, `scoped` (организация / человек без организации), беседа организации, родитель по `via` (область родителя — своя, рекурсивно);
- `exportGuard[]` — поля под правилами видимости: `fields` (колонка или `колонка.ключ` внутри JSON → поле типа реестра видимости), `subject` / `branch` / `stage` — колонки ссылки записи. Сборщик прогоняет их `shape()` глазами заказчика (`viewerFor(заказчик, организация строки, 'export')`): маска уходит объектом `{ "masked": "…" }`, скрытое не уходит, сбой проекции — поле не уходит.

Провайдер модуля (`LifecycleExportRegistry.register(policyId, side, { page, verify, skip? })`) — где правил чтения больше, чем у реестра:

| Политика | Провайдер | Правило |
|---|---|---|
| `ChatterEntry` | `core/chatter` | «Было → стало» маскируется глазами заказчика, текст — в его языке, payload с id людей не уходит. Человеку — его действия вне организаций, организации — журнал в сроке |
| `Chat`, `Message` | `messenger` | Человеку — личные чаты целиком (с его `visibleFromSeq`, в сроке чата), в чатах организации — только свои сообщения; чужой автор — имя без id, чужие вложения — числом, упоминания `@[Имя](id)` → `@Имя`, системная плашка — без id людей. Организации — её чаты в сроке |
| `SecurityEvent` | `core/audit` | Человеку — его лента за весь срок (IP — только свой), организации — её лента в окне тарифа `audit.retentionDays` и только при фиче `audit.export` (иначе пропуск с причиной в манифесте) |

Смоук бута (`LifecycleExportCollector`): каждая экспортируемая сторона политики отбирается реестром или провайдером — иначе старт падает. `lifecycleRegistryProblems()`: поле видимости, чья колонка ПДн (`pii → модель`) живёт в экспортируемой модели, обязано стоять в `exportGuard`. `check:lifecycle`: колонки `exportScope`/`exportGuard` существуют, путь внутрь значения — только у колонки `Json`.

## Несущие правила

1. **Заказ и КАЖДАЯ ссылка — под окном SMS-подтверждения `data_export`** (пароль + код, 15 минут; [verify_engine.md](verify_engine.md)). Угнанная сессия без SIM архив не унесёт. Ключ API не пускается (`@NoApiKeys`).
2. **Раз в сутки на субъекта**: замок субъекта в транзакции заявки + проверка последней неупавшей выгрузки → `429 lifecycle.exportTooSoon` (`details.retryAt`). Упавшая сборка окно не занимает.
3. **Организацию выгружает только владелец** (`403 lifecycle.exportOwnerOnly`; не член — 404); список видят владелец и админы, качает заказчик (`canDownload`). Фича `lifecycle.export` (на всех планах — рубильник Кабинета) и квота `lifecycle.export.bytesPerDay`: предпроверка остатка на заказе, остаток меньше архива — сборка падает `quota` до упаковки, факт байтов списывается в транзакции «готово». Выгрузка человека своих данных от тарифа не зависит никогда.
4. **Перепроверка владельца независимо от выборки** (Google Takeout 2019): общий сборщик сверяет ЗНАЧЕНИЯ загруженных строк с субъектом (колонки, полиморфный владелец; строки по `via` — отдельным запросом «эти id родителей — субъекта»); провайдер — своим `verify`; байты файла — по свежей строке `FileObject` перед упаковкой (удалён — пропуск, чужой — провал). Чужая строка → вся сборка `failed owner_mismatch`, байты удалены.
5. **Секретов нет ни на каком уровне**: слова имени поля (`password`, `hash`, `token`, `secret`, `cipher`, `signature`, `enc`, `hmac`, `pin`, …; сравниваются СЛОВА, не подстрока — `thumbhash` не секрет) и поля Bytes; то же внутри JSON-колонок и строк провайдеров — одна дверь (`exportSafeValue`) перед записью куска.
6. **Скачивание только со страницы**: ссылка на 5 минут на каждое нажатие (presign — токен на предъявителя, недельных ссылок нет); ≤ 5 выдач на часть (атомарный счёт в `parts[i].downloads`), шестая — `409 lifecycle.exportDownloadsExhausted`; каждая выдача — `data.export{source: lifecycle, format: zip}` в журнал (человеку — в его ленту, организации — в её журнал) и `lifecycle.export.downloaded`. Local-драйвер — подписанная ссылка на `GET /lifecycle/exports/:id/parts/:n/raw?exp&k&sig` (Ed25519 аудитории `lifecycle`, сообщение `lifecycle.export.part:<id>:<n>:<exp>`, Range поддерживается).
7. **Срок**: готовый архив — 7 дней (`expiresAt`), затем шаг раннера `lifecycle.exports` (политика `derived:lifecycle_exports`) переводит в `expired` и удаляет байты; строка заявки — месяц (политика `LifecycleExport`); сборка, потерявшая джоб, через 2 дня — `failed internal`. Заморозка держит архив. Стирание человека и каскад организации удаляют выгрузки целиком (`deleteExports`: части, манифест, промежуточные куски — только под префиксом выгрузки).

## Сборка (джоб `lifecycle.export`)

Фазы в `progress` строки, бюджет захода 4 минуты, снуз продолжает с сохранённого места; заход — под замком Redis `lifecycle:export-lease:<id>` (протухшая аренда и новый воркер не собирают вдвоём):

1. `collect` — политики плана стороны (`lifecycleExportPolicies`: родители раньше детей) кусками ≤ 20 000 строк: временный файл → объект `exports/<id>/staging/<политика>.<nnn>.jsonl` (sha256 и байты считаются при записи); ссылки на файлы — отдельным куском. Прогресс сохраняется после каждого куска — обрыв повторит только незаписанный (тот же ключ).
2. `package` — план частей по известным размерам (≤ 2 ГБ, крупный файл — своей частью; потолок архива 100 ГБ → `too_large`), одна часть за заход: yazl лениво открывает потоки (тысячи файлов не открываются разом), сжатые форматы байтов — без повторного сжатия, хэши файлов считаются на лету. Последняя часть: `manifest.json` (+ копия объектом) и `README.txt` в языке заказчика.
3. `finish` — одна транзакция: `ready`, части, срок, квота организации, уведомление `lifecycle.export.ready` (без ссылки — только страница); после коммита — промежуточные куски удалены, событие шины → сокет `lifecycle:export.updated` заказчику. Архив восстановления: манифест подписан (`lifecycleExportManifestPayload` — канонический JSON без поля подписи), части = куски данных.

Провал — `failed` + код (`owner_mismatch` · `too_large` · `quota` · `subject_gone` · `internal`), уведомление `lifecycle.export.failed`, байты под префиксом удалены.

## Восстановление арендатора (Кабинет)

`LIFECYCLE_RESTORE_SOURCE_URL` — кластер, поднятый из бэкапа на точку времени, роль только на чтение ([operations_backup_dr.md](operations_backup_dr.md)). Без него в production обе команды отказывают `lifecycle.restoreSourceMissing`; в development источником служит основная база (сьют).

- `lifecycle.restore.extract {workspaceId, snapshotAt?}` — critical, «четыре глаза», не своя организация. Предпросмотр — строк по моделям в источнике. Исполнение — архив восстановления В транзакции команды; `snapshotAt` обязателен при отдельном источнике (`lifecycle.restoreSnapshotRequired`: кластер своего «когда» не знает).
- `lifecycle.restore.import {exportId}` — critical, «четыре глаза». Предпросмотр — подпись (архивная проверка: ключ мог уйти ротацией) и хэши каждого куска сверены, «строк в архиве / уже есть». Исполнение — прогон `lifecycle_runs{kind: restore}` + джоб `lifecycle.restore` (под замком `lifecycle:restore-lease:<run>`): куски по внешним ключам ЖИВОЙ базы (`pg_constraint`, родители раньше детей), пачками по 500 — сначала проверка на значениях «все строки этой организации» (область реестра над `jsonb_populate_recordset`; чужая строка — стоп всего импорта), затем `INSERT (колонки без генерируемых) OVERRIDING SYSTEM VALUE SELECT … ON CONFLICT DO NOTHING` (id сохраняются, существующее — пропуск); пачку, отвергнутую базой, — по строке, отвергнутые — повтор в конце (родитель пришёл позже), дальше `failed`. Файлы без байтов — счёт `missingBlobs` (байты — версиями S3 по рунбуку).
- **Реплей стираний**: люди из вернувшихся строк, чья заявка на стирание исполняется или прошла горячую фазу после снимка, стираются заново (`replayUser`: по живой заявке шаги плана проходят ещё раз без смены статуса, корень пропускается — строку аккаунта восстановление организации не возвращает; по завершённой — новая заявка). Журнал стираний — этап `replayed`.
- **Стёртую организацию не восстановить**: заявка на её стирание прошла горячую фазу → `409 lifecycle.restoreErased` (предпросмотр и исполнение).
- Итог — `lifecycle.restore.imported` в журнал организации (вставлено / пропущено / отвергнуто / стираний повторено), вкладка «Бэкапы и восстановление» дашборда «Данные» (`GET /platform/data/restores`).

Повтор импорта сходится к тому же состоянию: живое — пропуск; строки стёртого человека (членство, приглашение) вставляются и тут же стираются реплеем снова.

Скрипт рунбука — `apps/api/scripts/lifecycle-restore-tenant.cjs` (`--workspace` → предпросмотр/извлечение, `--export` → предпросмотр/импорт, `--apply`; токен сотрудника `LIFECYCLE_CONSOLE_TOKEN`, в development — вход сьюта).

## HTTP

| Ручка | Что |
|---|---|
| `POST /lifecycle/exports` · `GET /lifecycle/exports` | Заказ и список «Мои данные целиком» (`CursorPage<LifecycleExportDto>`) |
| `POST /workspaces/:id/lifecycle/exports` · `GET …` | Заказ (владелец) и список (владелец, админ) архива организации |
| `POST /lifecycle/exports/:id/parts/:n/link` | Ссылка на часть (заказчик, окно `data_export`) |
| `GET /lifecycle/exports/:id/parts/:n/raw` | Байты по подписанной ссылке (без входа) |
| `GET /platform/data/restores` | Архивы восстановления и их импорты (право `data.read`) |
| `POST /lifecycle/dev/exports` · `…/exports/:id/run` · `…/restores/:runId/run` | Дев-полигон: заказ без окна и суточного предела (`injectForeign` — подсадка чужой строки), сборка и импорт сейчас |

Веб: блок «Мои данные целиком» в `/profile/my-data` и раздел `/workspaces/[id]/profile/data/exports` — один компонент `components/lifecycle/DataExports.tsx` (неймспейс `dataExports`); карточка «Восстановление организаций» на вкладке бэкапов `/platform/data`; панели карточки 360 показывают последние выгрузки. Рич-карта `lifecycle_export` — статус, объём, срок; кнопок нет (скачивание мимо окна подтверждения невозможно).

## Ловушки

- **Уникальная живая заявка на стирание** (`subject_type, subject_id` среди незавершённых): реплей не заводит вторую — повторяет шаги по существующей.
- **Разбор и повторная сериализация строк восстановления теряют точность bigint** — архив восстановления пишет `to_jsonb(t)::text` как есть, импорт собирает пачку из сырых строк.
- **Сохранение `readline` + `'\n'`** — хэш куска при чтении считается по строкам с переводом строки: так же, как их писал сборщик.
- **Уведомление приходит фанаутом (джоб)** — сразу после провала сборки строки уведомления ещё нет; сьют ждёт.
- **Команды Кабинета с `forbidSelfTarget` не берут организацию, которой владеет сам сотрудник** — сьют держит организацию на другом аккаунте.
- **Окно подтверждения закрывается раньше ссылки** — диалог `useStepUp` ловит `403 lifecycle.step_up_required` и повторяет действие.

## Проверка

`node apps/api/scripts/verify-lifecycle-export.cjs` — человек (окно подтверждения, сутки, сборка, ZIP: манифест и хэши, без секретов и удалённого, без id чужих людей в переписке, пять выдач и шестая 409, ссылка без окна 403, истечение и шаг срока), страж владельца (подсадка чужой строки → `owner_mismatch`, байтов нет, уведомление), организация (только владелец, IBAN маской, хроника раздела, фича 402, квота на заказе и на сборке), восстановление (предпросмотр, архив подписан, стирание после снимка, потеря строк → импорт с теми же id, реплей стирания, журнал организации, повтор сходится, подменённый манифест 409).

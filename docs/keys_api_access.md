# Ключи API, боты и реестр (`core/keys/api-keys`)

Часть движка ключей ([keys_engine.md](keys_engine.md)): программный доступ к API `/api/v1` для интеграций (1С, склад, CRM, скрипты). Два вида носителей — **бот организации** и **личный ключ человека**; всё видно в **реестре ключей** организации; всё пишется в журнал.

## Принципалы

- **Бот** (`Bot` + теневая строка `users` с `kind='bot'`, телефон `bot:<id>`, пароль-заглушка, вход/SMS/кабинет закрыты). Ранг `member|manager` проецируется ролью `staff|manager` в `user_roles(workspace)` — бот работает в задачах, календаре, документах как сотрудник того же ранга, а `core/access`, хроника, уведомления и все FK на `users` работают без переписывания. Владение — у организации: уход создателя не удаляет бота, а **замораживает** (`frozen`, `creator_left`) до решения владельца; разморозка — только owner со step-up; «удалить» = архив (ключи отозваны, роль снята, история остаётся). Аудитории и места тарифа исключают `kind='bot'`; в UI бот — **`BotChip`**, не `PersonChip` (хроника и уведомления несут `kind` актора).
- **Личный ключ (PAT)**: для СОБСТВЕННЫХ данных человека (`workspaceId = null`, `/keys/personal`) — любому; для ДАННЫХ ОРГАНИЗАЦИИ (`/workspaces/:id/keys/keys`) — только owner/admin (`403 keys.role_required`). Ключ действует от имени человека с его правами, суженными скоупами. **Держатель — единственный, кто правит и перевыпускает личный ключ**: owner/admin видят чужой ключ в реестре и могут его ОТОЗВАТЬ, но `PATCH`/`rotate` отвечают `403 keys.holder_only` — перевыпуск отдаёт новый секрет вызывающему, и админ получил бы ключ с правами и именем владельца (веб действие «Перевыпустить» у чужих строк не показывает).

## Ключ

`sa6_<bot|pat>_<live|test>_<43 base62>_<crc32 6 base62>` (среда — по `NODE_ENV`). В БД — только HMAC-SHA256 pepper-ключом `api_key_pepper` (`hash`, `hashKid`), `prefix` и `last4` для реестра; секрет показывается **один раз** (`KeyRevealOnce`), повторно не выдаётся — только ротация. Аутентификация: `Authorization: Bearer sa6_…` → `JwtAuthGuard` → `ApiKeyAuthService.authenticate` (формат + CRC → хеш всеми живыми pepper-версиями → снимок в Redis 60 с → отзыв/срок/grace → бот не заморожен → IP-allowlist) → `req.user = {sub: <users.id носителя>, kind: 'bot'|'user', keyId, botId, keyWorkspaceId, scopes}`. Отказы считаются двумя счётчиками: связка IP + префикс (`authFailPerHour`) и IP целиком (`authFailPerIpPerHour` — перебор тел ключей меняет префикс на каждой попытке) → 429. **Потолки живого ключа**: обращений в минуту (`requestsPerMinute`, корзина минуты в Redis → `429 keys.rate_limited`, `resendInSec`) и строк списков в сутки UTC (`exportRowsPerDay`, счётчик в `ApiKeyAccessInterceptor` по `data`/`data.items` ответа → чтения отвечают `429 keys.export_cap` до конца суток; аномалия объёма по модели Salesloft); первое пересечение за сутки — уведомление `key.throttled` держателю. Использование — в Redis (`keys:last-used`: время, IP, страна из гео-заголовка CDN; счётчик обращений — `keys:use-count` через `HINCRBY`; слив в БД раз в минуту атомарным `RENAME` обоих хешей), журнал обращений `api_access_log` (метод, шаблон маршрута, статус — в т.ч. отказы по скоупу; месячные партиции, ретеншн 90 дней сбросом партиции). Метрики — `keys_api_auth_total{result}` ([keys_engine.md](keys_engine.md), «Наблюдаемость»).

- **Срок**: PAT — дефолт 90 дней, потолок 365 (и политика организации); ключ бота — дефолт год; «бессрочно» — только owner, только с IP-allowlist и только без потолка политики (`keys.no_expiry_*`). Уведомления `key.expiring` за 14 и 1 день (idempotencyKey на порог), `key.expired`.
- **Ротация с перекрытием**: новый секрет того же семейства, старый живёт `graceHours` (0 — отзыв сразу); в семействе не больше `familyMaxLive` (2) живых → `409 keys.family_full`.
- **Отзыв** (`revokedReason`): `owner`, `rotated`, `leaked`, `member_left`, `token_epoch`, `bot_archived`, `platform`, `policy` — status-guarded `updateMany` (два отзыва разом не переписывают причину). Кэш снимка гасится сразу, и сброс безопасен ВНУТРИ транзакции: `invalidateByHash` ставит «надгробие» (`keys:api-tomb:<hash>`, `keyCacheTombstoneSec` > срока кэша) — пока оно живо, снимок не читается и не пишется, решение идёт из БД; откат транзакции стоит полутора минут без кэша, а не минуты жизни отозванного ключа. Заморозка/разморозка/архив бота гасят снимки его ключей внутри `freezeTx/unfreezeTx/archiveTx` — на всех путях (владелец, каскад ухода, кабинет платформы).
- **IP-список**: запись не шире `/8` (IPv4) и `/16` (IPv6) — `0.0.0.0/0` формально «список», но пускает всех, а наличие списка служит условием (бессрочный ключ, политика). Снять список нельзя, пока он условие: политика `requireIpAllowlist` либо живой бессрочный ключ бота.
- **Утечка**: `POST /keys/leaked [{token, source?, url?}]` (public, троттлинг) — найденные ключи отзываются с `leaked` + уведомление `key.leaked` (critical, SMS-eligible); `POST /keys/verify {key}` — validity-check без раскрытия владельца. **Только POST**: секрет в query-строке осел бы в логах балансировщика, CDN и истории браузера, и проверка утечки сама стала бы утечкой (`GET /keys/verify` отвечает 404). Регистрация префикса `sa6_` в GitHub secret scanning — после публичного запуска ([roadmap.md](roadmap.md)).
- **Новый адрес** при IP-allowlist — `403 keys.ip.denied` + `key.newLocation` (троттлинг раз в час на ключ).

## Скоупы и контекст организации

- Реестр `KEY_SCOPE_SERVICES` (`packages/shared/src/keys/scopes.ts`) — **явный белый список**: шаблон пути → сервис (`:id` — uuid-сегмент; `$` на конце — точное совпадение: `/workspaces/:id$` — карточка организации, но не `/workspaces/:id/requisites`); уровень по методу (GET/HEAD → `read`, иначе `write`, write ⊇ read). Catch-all по `/workspaces` запрещён: у `workspaces` ровно список организаций, карточка, ростер и журнал; реквизиты (`requisites`, IBAN) и приглашения (`invitations`, номера) — отдельные сервисы только для личных ключей. Ботам открыты tasks, calendar, notes, drive (read), files, documents, counterparties, objects (вся вертикаль: площадки, штат `staffing`, смены `shifts`/`shift-templates`/`shift-patterns`/`attendance`, оборудование `assets`/`asset-models`), staff (read), search (read), workspaces (read), chatter (read); «между людьми» (messenger, circles, finance, shop, approvals, sign, hr, processes, office, recorder, share, requisites, invitations) — только личным ключам. Новый сервис, открытый ключам, = +1 строка реестра (и он же — строка матрицы в UI, `GET /keys/scope-matrix`).
- **Страж на буте `KeysRoutesAudit`** (fail-closed, как страж маршрутов кабинета): каждый маршрут `/workspaces/…` обязан быть решён — строка реестра, `@NoApiKeys()` (только живая сессия: управление ключами и вебхуками, `notification-policy`, `restore`/`transfer`/`leave`, dev-ручки) или `@Public()`; иначе API не поднимается со списком нерешённых маршрутов. Новый контроллер под `/workspaces/:id/…` не откроется ботам молча и не останется «как получится».
- **`KeyScopeGuard`** (APP_GUARD после `PlatformAuthGuard`): для запроса по ключу — deny-by-default: сервис вне реестра, `@NoApiKeys()` (управление ключами, auth, verify), закрытый ботам сервис или недостаточный уровень → `403 keys.scope.denied`. `GET /users/me` — любому живому ключу. Живых сессий гард не касается. Право по объекту дальше решают сервисы и `core/access`: **фактическое право = скоуп ∩ права носителя ∩ организация**.
- **Организация** — в самом ключе (`WorkspaceContextInterceptor`): ключ бота и PAT данных организации работают только в ней (заголовок `X-Workspace-Id` обязан совпасть или отсутствовать → иначе `403 keys.workspace_mismatch`); PAT собственных данных с организацией не работает (`403 keys.personal_needs_workspace`). Дальше — та же проверка членства и роли, что у живой сессии.

## Step-up

Создание бота/ключа, ротация, разморозка, архив, а также правка СИЛЫ уже выпущенных ключей — ранга, скоупов и IP-списка бота, IP-списка личного ключа — под «сильным подтверждением» (имя и назначение правятся без него; сервер сравнивает с текущим значением — прежние значения в запросе подтверждения не требуют) (`KeysStepUpService`): пароль + SMS-код (`core/verify`, цель `keys_manage`) → окно 15 минут в Redis (`GET /keys/step-up`, `POST /keys/step-up/confirm {verifyToken}`, `POST /keys/step-up/end`). Без окна — `403 keys.step_up_required`; веб-хук `useKeysStepUp().withStepUp(action)` открывает диалог сам и повторяет действие. Сюда же позже встанут passkeys/ЭЦП — потребители зовут только `assert(userId)`.

## Реестр, политика, каскады

- **Реестр** `GET /workspaces/:id/keys/registry?kind=bot|personal|webhook&filter=frozen|idle90|noExpiry|expiring14` — одна таблица на ботов, личные ключи для данных организации и вебхуки: носитель (BotChip/PersonChip/адрес), кто создал, когда, «для чего» (обязательное поле), скоупы, статус (`active|expiring|expired|revoked|frozen` / статусы endpoint'а), последнее использование (когда · страна из гео-заголовка CDN · IP — как «last used from» у GitHub; `lastUsedLocation`/`lastUsedIp`), срок; сортировка по последнему использованию (в памяти: объём реестра ограничен тарифом), курсор — смещение. `GET …/pending` — «N ботов ждут решения» (значок в навигации, сокет `keys:changed` владельцу и админам). **Журнал** `GET …/journal?subjectType=bot|api_key|webhook_endpoint&subjectId=` — фильтр по виду предмета или по одному предмету (веб: чипы на вкладке «Журнал», действие «Журнал» в строке реестра и карточке бота).
- **Политика** (`WorkspaceKeyPolicy`, только owner): `maxPatDays`, `maxBotKeyDays` (`null` — бессрочно разрешено владельцу с IP-списком), `requireIpAllowlist`.
- **Каскады** (`KeysCascadesService`, правило «на всех путях»): `onMemberLeft` — исключение (`removeMember`), выход (`leaveWorkspace`), понижение с admin (`updateMember`), **увольнение по ТК** (`hr-actions.service` — в транзакции применения приказа `dismissal`, независимо от галочки «снять членство»: человек мог остаться в системе подрядчиком, но его ключи организации гаснут сразу): личные ключи человека в организации гаснут (`member_left`), его боты → `frozen` (`creator_left`) + `bot.frozen` владельцу, именной ответственный снимается (`bot.responsible.left`); `onTokenEpochBump` (смена пароля, logout-all) и `onDeletionScheduled` — все PAT человека отозваны (`token_epoch`); `onWorkspacePurge` — ключи отозваны, боты в архив, KEK на уничтожение; `onAccountAnonymize` — то же для человека.
- **Тариф**: `keys.maxBots` (организация), `keys.maxPersonalTokens` (человек), `webhooks.maxEndpoints` (`402 entitlement.*`, замки в UI). **Аналитика**: `keys.bot.created`, `keys.key.created`, `keys.key.first_used`, `keys.key.revoked`. **Уведомления** (`packages/shared/src/notifications/keys.ts`): `key.created|expiring|expired|revoked|leaked|newLocation|throttled`, `bot.frozen|unfrozen|responsible.left`, `webhook.endpoint.disabled`. **Кабинет**: панели `workspace.keys`/`user.keys` (`keys.read`), команды `keys.key.revoke`, `keys.bot.freeze|unfreeze` (high, с причиной).

## Веб

Раздел организации **«Интеграции и ключи»** (`/workspaces/[id]/integrations`, пункт `ws-integrations` — только owner/admin; остальным пункта нет, прямой заход — экран «нет доступа»): вкладки Реестр · Боты (мастер 3 шага: карточка → матрица прав → секрет show-once; правка, второй ключ, заморозка, архив) · Вебхуки · Журнал (чипы по виду предмета; «Только «…»» из строки реестра или карточки бота) · Политика. Профиль → **«Ключи и приложения»** (`/profile/keys`) — личные ключи для собственных данных. Компоненты `components/keys/`: `BotChip`/`BotAvatar`, `KeyStatusChip`, `KeyRevealOnce`, `ScopeMatrix`/`ScopeSummary`, `KeysStepUpProvider`/`useKeysStepUp`/`StepUpWindowChip`, `BotWizard`, диалоги ключей. Хелперы — `lib/keys-api.ts`, ключи RQ — `lib/queries.ts` (`keys*`, `webhooks*`), бейдж — `useKeysPending` (`keys:changed`).

## Ловушки

- Ключом нельзя управлять ключами и входить: контроллеры ключей, auth и verify — `@NoApiKeys()`.
- Скоуп решает «в какой сервис пускать», не «что можно»: бот с `tasks:write` всё равно не увидит задачу, к которой у него нет права в `core/access`.
- Снимок ключа кэшируется 60 с; все пути изменения (ротация, отзыв, заморозка, смена скоупов/allowlist бота) зовут `invalidateByHash`, иначе изменение «не работает» до минуты.
- Step-up окно живёт 15 минут поверх перезапусков клиента; сьют перед проверкой `403` закрывает его `/keys/step-up/end`.
- Регистрация в `KEY_SCOPE_SERVICES` — по шаблону пути (`$` — точное совпадение); маршрут вне реестра ключам закрыт (`403 keys.scope.denied`), а маршрут организации вне реестра и без `@NoApiKeys()` роняет бут (`KeysRoutesAudit`) — новый контроллер под `/workspaces/:id/…` требует решения в коде.
- Секрет ключа никогда не кладётся в URL: проверка `verify` только POST; `redactSecrets` гасит `sa6_…` в логах и конвертах ошибок; заголовок `authorization` в логах ловит ESLint.
- Потолки `requestsPerMinute`/`exportRowsPerDay` считаются в Redis и при недоступном Redis не применяются (аутентификация при этом уже прошла по БД); учение — `POST /keys/dev/usage/throttle`.

## Ключ повтора — правило для интеграторов

Любая мутация внешнего API принимает заголовок **`Idempotency-Key`** (8–128 символов `[A-Za-z0-9_\-:.]`, обычно UUID). Повтор запроса с тем же ключом не создаёт второго эффекта: сервер либо исполнит операцию впервые, либо вернёт исход ПЕРВОЙ попытки.

- **На необратимых ручках ключ ОБЯЗАТЕЛЕН** (деньги, отправка сообщения, подпись, кадровые действия, общие диспетчеры действий): без него — `400 idempotency.key_required`.
- Ключ скоупится принципалом: у бота, личного ключа и человека это РАЗНЫЕ ключи, даже если строка одна. Чужой ключ подобрать нельзя.
- Тот же ключ с другим телом → `422 idempotency.key_reused` (это ошибка клиента, а не повтор). Тело сравнивается по смыслу: порядок ключей JSON и пробелы значения не имеют, но **query и path-параметры входят в сверку**.
- Ответ повтора помечен `Idempotent-Replayed: true`; `X-Should-Retry` подсказывает, осмысленно ли повторять; `409 idempotency.in_flight` приходит с `Retry-After`.
- Окно защиты — 7 дней; тело ответа доступно 72 часа (потом повтор отдаёт `409 idempotency.already_completed` со ссылкой на созданную сущность).
- Вебхук-триггер Процессов (`POST /processes/webhook/:token`) — единственная точка, где **без заголовка дедуп невозможен**: у произвольной внешней системы нет ни подписи, ни своего идентификатора события.

Полный контракт, коды и ловушки — [idempotency_engine.md](idempotency_engine.md).

# core/rich-cards — интерактивные карточки

> Переиспользуемый реестр «тип → рендер + действия» (путь Slack Block Kit / MS Adaptive Cards). Если у сущности сервиса есть статусы и действия (заказ, задача, событие, заявка…) — она ОБЯЗАНА уметь рендериться рич-картой (Принцип 3 платформы).

## Модель

Реестр: тип → рендерер (живая карточка для зрителя; кнопки фильтруются по правам+статусу) + действие → обработчик + способность. Один эндпоинт execute с **перепроверкой прав в момент нажатия**; карточка обновляется на месте.

## API

- `GET /rich-cards/:refType/:refId` — живая карточка для зрителя.
- `POST /rich-cards/:actionKey/execute` `{ref, payload?}` — выполнить (перепроверка способности → обновлённая карточка).
- `POST /rich-cards/share` `{chatId, refType, refId}` — кинуть карточку в чат.

## Зарегистрированные типы/действия

order (confirm/reject/cancel/refund) · listing (buy/talk) · crowdfunding (contribute/withdraw) · task (accept/return/take) · event (rsvp_*) · office_room (статус «Идёт сейчас · N», href = присоединиться, без действий) · approval_request (решение прямо из чата; у «отклонить» поле причины) · fin_transaction / fin_month (модель-СНИМОК: payload фиксируется при шаринге, живой рендер только при праве) · counterparty («В чат», без действий) · drive-узел (без действий) · документ.

## Правило

Карточка — не скриншот: права перепроверяются на КАЖДОМ execute; поделённая в чат карточка не расширяет доступ (рендер для зрителя без права — деградация или снимок, в зависимости от типа).

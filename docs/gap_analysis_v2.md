## Часть 1 — Документная вертикаль (главная стройка; порядок строгий)

**Зафиксированные решения:** Диск первым · Диск v1 полный · гостевые ссылки v1 без SMS-гейта (гейт появляется в ЭДО) · шаблоны = свой конструктор + DOCX-путь · подпись v1 = все три метода + слот биометрии · маршруты ЭДО = свой лёгкий линейный (канвас Процессов подключится позже нодой, two-tier) · КЭДО v1 = полный контур.

### - [ ] Шаг 1. «Диск» (сервис) + core/share-links (движок гостевых ссылок)

- **Диск** — аналог Google Drive для B2C («Мой диск») и B2B («Диск организации»): папки (новая модель Folder), загрузка/скачивание (core/files готов), офисные файлы открываются в core/docs, шеринг людям/Группам/отделам через core/access (тип `folder` с наследованием parent — паттерн showcase←shop), корзина, провайдер core/search, фото = те же файлы видом «сетка» (thumb-превью готовы). Зачем: документам сейчас негде жить, кроме вложений чатов/задач. Частично закрывает и B2C-«вольт документов».
- **core/share-links** — общий движок «поделиться наружу» (один для Диска, ЭДО, магазина, счетов): токен → гостевая страница просмотра/скачивания (не сырые байты), срок действия, отзыв, счётчик открытий. Полиморфный refType (паттерн FileLink). Первый потребитель — Диск.

### - [ ] Шаг 2. Шаблоны документов (движок + конструктор)

- Зачем: документы, которые «сами заполняются» данными — до ЭДО (приказ/договор генерируется, не перенабирается) и до Счетов.
- **Конструктор** (веб, блочный, Doodocs-стиль) → готовый **PDF**; поля `{{сотрудник.имя}}`, `{{организация.БИН}}`, `{{контакт.телефон}}` из **реестра источников данных** (user/workspace/staff/contact; расширяется регистрацией — паттерн calendar-layers).
- **Второй путь**: загруженный готовый DOCX с {{плейсхолдерами}} → подстановка → DOCX/PDF (docxtemplater-класс) — у бизнесов уже есть бланки в Word.
- Результаты ложатся в Диск.

### - [ ] Шаг 3. core/sign (движок подписи)

- **Реестр методов** (паттерн STT-драйверов), в v1 все три:
  - **QR-ЭЦП** через eGov mobile — юридически полноценная ЭЦП без установок, главный способ КЗ (SIGEX API либо прямая интеграция — решит ресёрч);
  - **NCALayer** — файл-ключ на компьютере (привычка бухгалтеров);
  - **SMS-ПЭП** — простая подпись кодом через готовый core/verify (ознакомления/внутреннее).
- **Слот «биометрия»** — будущий метод: подпись отпечатком/лицом с телефона или сканера/камеры ПК (см. движок «Биометрия» в Части 3).
- Хранение: подпись (CMS/CAdES) + штамп-визуализация на PDF + страница проверки подписи. Заготовки в схеме уже есть (`DocumentVersion.signed`, `reason='pre_sign'`, место кнопки «Подписать ЭЦП» в редакторе).
- **Перед стройкой — отдельный ресёрч** (как было с Отзывами): SIGEX vs НУЦ напрямую, юр. рамка ПЭП в РК, формат хранения подписей у Doodocs/idocs.

### - [x] Шаг 4. ЭДО — ПОСТРОЕН 2026-08-16 (внешний контур «Документооборота» + сервис «Контрагенты»)

- **Решение реализации**: не отдельная сущность «Конверт», а РАСШИРЕНИЕ сервиса «Документы» (переименован в **«Документооборот»**): категория вида `external` («С контрагентами»), статусы `sent`/`declined_external`, кнопка «Отправить контрагенту» с карточки. Плюс новый сервис-справочник **«Контрагенты»** (`modules/counterparties`: карточка с реквизитами + контактные лица + счета с основным; читают Документооборот, дальше — Счета, Финансы B2B, ЭСФ, CRM).
- **Сделано**: три пути создания (шаблон / конструктор / **загрузка готового PDF+DOCX**) · номер печатается в тексте ДО отправки (кнопка «Присвоить номер») · отправка = заморозка + заявка core/sign (внутренние подписанты + **акт-ожидание второй стороны**, `suppressOutcomeNotify`) + автоссылка core/share-links + SMS (`SmsOutboundService` в core/verify — зародыш канального движка) · гость: личность по SMS → ПЭП/ЭЦП (**жёсткая сверка БИН/ИИН сертификата с карточкой контрагента**, `sign_counterparty_mismatch`; мягкая сверка номера у ПЭП) · **штампованная копия** (джоб `sign.stamp`: pdf-lib + PT Serif, полосы + «Лист подписей» с QR) · публичная проверка находит штамп по своему отпечатку (`matchedBy: 'stamped_copy'`) · гость скачивает штамп и экспортный ZIP по своей ссылке · подшивка штампованной копии в реестр Диска · отказ → возврат → отзыв → авто-истечение (хук `onRequestExpired`) · свободные подписи в стопке «Ждут решения» (источник `sign`) · rich card документа.
- **Не в v1** (осознанно): входящие/обмен workspace↔workspace, конверт с несколькими документами, нода Процессов «Отправить контрагенту» (external-виды по маршрутам не ходят), пер-подписант уровень, последовательный порядок, мостик гость→юзер, ЭСФ/ЭАВР через гос-ИС, массовая рассылка.
- Сьюты: `verify-edo.cjs` (54, сквозной), `verify-counterparties.cjs` (23); браузер двумя ролями + мобильный гость.

### - [ ] Шаг 5. КЭДО

- Поверх ЭДО + Staff (должности/отделы/филиалы готовы):
  - **кадровые шаблоны** (приказ о приёме/отпуске/увольнении, заявления, трудовой договор) с данными из Staff;
  - **массовая рассылка** на подпись/ознакомление с адресацией по осям core/access (отдел/должность/филиал — оси уже проецируются);
  - **ознакомления под подпись** (ПЭП/биометрия — для внутренних документов);
  - **личный архив «Мои документы»** у сотрудника: B2C-сторона видит подписанное навсегда, даже после увольнения — суперсила одного user_id (у Doodocs работник живёт в тенанте работодателя).
- Юр. рамка: ТК РК допускает электронные кадровые документы с ЭЦП; что можно ПЭП — сверить в ресёрче шага 3.
- Связка вперёд: HR-«отпуска» полного цикла (заявление → одобрение → приказ → подпись) собираются из КЭДО + Процессов.

**Что разблокирует вертикаль:** Счета (шаблон + ссылка + позже оплата) → ЭСФ (нужна ЭЦП) → договоры в будущем CRM → «подписать протокол собрания» (Диктофон).

## Часть 3 — Остальные пробелы (термин — зачем — пример)

### Движки

- **Биометрия** — подтверждение действия отпечатком/лицом с телефона или сканера/камеры ПК; нужно много где (ознакомления КЭДО, опасные действия, вход). Путь решается при стройке движка: WebAuthn/passkeys (устройство само сканирует, биометрия не покидает телефон; бонусом 2FA и вход без пароля) vs своё распознавание лица камерой (= KYC-класс, биометрические ПД по ЗоПД, сильно дороже).
- **KYC/идентификация незнакомца** — селфи + liveness (как Kaspi при регистрации); отдельный второй движок; понадобится к Jobs Marketplace / реальным деньгам.
- **Канбан + лёгкая автоматизация** — доски + правила «если → то» (Bitrix24-роботы); tier-1 над Процессами (принятый фидбек); строить перед CRM (воронка = доска).
- **Кастомные поля** — «своё поле в задаче/сделке без программиста» (Salesforce-суперсила); строить ВМЕСТЕ с CRM (правило «движок извлекается на 2–3-м потребителе»).
- **Импорт/экспорт** — CSV/Excel; первый потребитель — Kaspi-выписка (Часть 2), затем импорт сотрудников/контактов при онбординге организаций.
- **Формы/опросы** — конструктор форм; кормит Додзё (тесты), HR-заявления, intake записи клиентов; фундамент — анкеты Процессов.
- **Отчёты-конструктор** — сводки/графики по любым данным + Excel-выгрузка (Salesforce Reports); после CRM/склада, когда есть что считать.
- **Движок ключей** — разделить JWT_SECRET (сейчас мастер-ключ 7 подсистем, ротация невозможна — отложено security-ревью), шифрование Google-токенов; до прод-запуска.
- **Email-канал** — отложен осознанно: КЗ живёт на SMS/WhatsApp; приглашение внешнего подписанта = SMS со ссылкой.

### Сервисы B2B

- **CRM + канальный слой WhatsApp Business** — крупнейший пробел «ERP»; лиды КЗ-МСБ живут в WhatsApp (Telegram-вход у Процессов уже есть); после канбана.
- **Склад** — приход/расход/партии/инвентаризация/себестоимость (`stockLimit` лота — это не склад).
- **HR-хвост** — графики/смены, отпуска (полный цикл — после КЭДО), табель; зарплата — рельсы казны Wallet готовы.
- **Тикеты/helpdesk** — обращения клиентов (внешний вход: виджет/Telegram).
- **Проекты** — фазы/вехи/гант над задачами (Bitrix24-модель).
- **Запись клиентов (booking)** — механика брони Resource готова; не хватает клиентской витрины по гостевой ссылке.
- Запланированные в силе: **Jobs Marketplace**, **Отзывы** (research готов), **Додзё**, **Лента новостей**.

### Сервисы B2C

- **Заметки** (Часть 2).
- **Детские профили** — без SIM ребёнок в системе не существует, а ядро сценария — «Мама ставит задачу Сыну»; модель Google Family Link; связка с family-планом подписки.
- **Здоровье**, **Авто** (ТО/страховка/штрафы — напоминания через слой календаря) — по мере роста.

### Платформенные

- **Админка platform_admin** — сейчас роль проверяется в одном месте (system-ноды Процессов); модерации/жалоб/саппорта нет; до публичного запуска.
- **Биллинг + entitlements** — Subscription пишется, но НИКТО не читает (все лимиты захардкожены константами); нужен резолвер «план → лимиты/фичи» + B2B-подписка за сотрудника/мес (модель Bitrix24).
- **Платёжные рельсы Kaspi Pay / Halyk ePay** — включают реальные деньги везде (магазин, счета, зарплата, подписки); external-счета в схеме Wallet готовы.

### Архитектура (долги)

- **Прод-минимум**: /health, CORS из env (захардкожен localhost в main.ts), Dockerfile API/web, бэкапы БД, Sentry + метрики, TURN/TLS звонков, верификация Google-вебхука. Резидентность данных РК при выборе хостинга.
- **Согласия при регистрации** (оферта + ЗоПД РК, фиксация версии) — до публичной беты.
- **Аудит безопасности** (журнал входов: когда/откуда/устройство) и **2FA входа** — 2FA частично закроет биометрия-движок (passkeys).
- **0 юнит-тестов** — точечно на чистые функции (деньги, RRULE, диффы); 52 verify-скрипта остаются основной сеткой.
- **packages/api-client** — до mobile-этапа (блок 8; mobile также заблокирован отсутствием OTP-экрана).
- ~~**Egress-шлюз** — запрет прямого fetch линтером; из security-ревью.~~ ✅ **Закрыто 2026-08-30.** Оказалось не движком, а правилом + стражем: наружу из `apps/api` ведут ровно ДВЕ двери в `src/shared/http/` — `safeFetch` (адрес пришёл ИЗ ДАННЫХ: конфиг ноды, настройка организации → SSRF-щит) и `trustedFetch` (адрес пришёл ИЗ .env: сидекары → щита нет намеренно, их адреса приватны by design, зато таймаут обязателен по сигнатуре). Голый `fetch` и сторонние HTTP-клиенты запрещены `apps/api/eslint.config.mjs` во ВСЕХ формах — статический import, `require()`, динамический `import()`, `globalThis.fetch` и его деструктуризация (каждая форма найдена подсаженной пробой, а не чтением конфига); запуск — `pnpm lint:guard` из корня (гоняет и стража границы в вебе) + шаг CI «Lint API (страж исходящих)»; исключений по файлам НЕТ — законных `fetch` ровно два, по одному внутри каждой двери, разрешены точечными директивами на СТРОКЕ, и протухшая директива в этих файлах роняет линтер. Попутно `safeFetch` переехал из `modules/processes` в `shared/http`: движки `core/*` не имеют права зависеть от фичи.

### Экосистема

- **Монетизация**: рельс → биллинг → B2B-подписка (сейчас платят только скины).
- **Казахский язык**: i18n-фундамент (next-intl; `lang="ru"` захардкожен, User.locale не используется) — дешевле до 100+ сервисов, чем после.
- **KZ-compliance**: ЭЦП (в вертикали) → ЭСФ (для НДС-плательщиков Счетов) → фискализация/ОФД (если POS).
- **Исходящие вебхуки + API-ключи организаций** — путь интеграции с 1С и «открытой платформы» (входящие вебхуки у Процессов есть, исходящего контура нет).
- **Онбординг-шаблоны организаций** — «Ресторан», «Салон»: преднастроенные должности/отделы/процессы/доски.
- **Продуктовая аналитика** (PostHog self-host) — на этапе прода, иначе приоритеты 100+ сервисов расставляются вслепую.

## Часть 4 — Хронологическая шпаргалка (что ДО чего)

- Диск → до Шаблонов (документам нужен дом) → до ЭДО
- Шаблоны → до ЭДО и до Счетов
- core/share-links → до ЭДО (внешний подписант) и до Счетов
- Подпись (ЭЦП) → до ЭДО, ЭСФ, КЭДО
- ЭДО → до КЭДО; КЭДО → до полного цикла «отпуска» в HR
- Канбан → до/вместе с CRM; Кастомные поля → с CRM
- Push + api-client + OTP-экран mobile → до mobile-этапа
- Платёжный рельс → до биллинга и онлайн-оплаты Счетов
- Админка + согласия + движок ключей + прод-минимум → до публичного запуска
- i18n → чем раньше, тем дешевле
- KYC-движок → к Jobs Marketplace / реальным деньгам

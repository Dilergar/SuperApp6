# Виртуализация ленты сообщений (2026-08-01)

**Файл:** `apps/web/src/app/messenger/MessageList.tsx` (новый). Из `Conversation.tsx` туда
переехали `MessageBubble` / `SystemPlaque` / меню-хелперы — Conversation похудел 1472 → 890 строк.
Потребителей трое и правка одна: `/messenger`, деталька задачи, комната офиса.

## Решение
`react-virtuoso` v4 (MIT, поддерживает React 19). Взят не «за скорость», а за готовую механику
обратной прокрутки: прижим-к-низу, якорь догрузки сверху, ResizeObserver под меняющиеся высоты.
Именно там живут баги, и писать это руками поверх `@tanstack/react-virtual` (~4 КБ против ~20 КБ)
значило бы переписать ту же логику, что уже была ручной и хрупкой.

## Как устроено
- `key={detail.id}` на компоненте: смена чата = чистый лист (позиция, замеры высот, все ref'ы).
- **Прижим к низу** — `followOutput(isAtBottom)`. Своя отправка — разовый флаг `stickRef`,
  который снимается в `atBottomStateChange(false)`: иначе вложение, летевшее на сервер секунду,
  выдернуло бы человека из чтения, куда он успел уйти.
- **Догрузка без прыжка** — `firstItemIndex`, уменьшаемый РОВНО на число доклеенных сверху.
  Число считается диффом «где в новом массиве прежняя первая запись» ПРЯМО В РЕНДЕРЕ: индекс и
  данные обязаны приехать движку одним коммитом, иначе вставка видна на кадр позже и лента дёргается.
  Прежняя голова исчезла целиком (рефетч после разрыва сокета отдаёт только последнюю страницу) →
  сбрасываем базу и уезжаем вниз.
- **Отступы** переехали с прокручиваемого контейнера на строку (`paddingBottom` вместо flex-`gap`):
  движок меряет `offsetHeight`, внешние отступы в него НЕ входят. Верхний/нижний отступ — `Header`/`Footer`.
- **Вспышка подсветки** рисует «поля» растянутой тенью `0 0 0 8px`, а не `padding` + отрицательный
  `margin`: размер строки при подсветке обязан остаться прежним, иначе перемер дёргает ленту.
- Наружу — только `stickToBottom()` и `scrollToMessage(id): boolean` (false = сообщение старше
  загруженного окна, зовущий тянет страницы и повторяет).

## ЛОВУШКИ (обе найдены проверкой в браузере, не чтением кода)
1. **`startReached` на монтировании — ЛОЖНЫЙ.** До первых замеров отрисовка начинается с нулевого
   элемента, то есть «верх достигнут» сразу, и каждая догруженная страница снова начинается с нуля.
   Симптом: открытие чата тянет ВСЮ историю (по сети — 7 запросов на 332 сообщения), DOM при этом
   мал, поэтому глазами не видно. Засов: грузить старые только после того, как лента встала в конец
   (`atBottomStateChange(true)`) ИЛИ прокрутка сдвинулась с нуля (`scrollerRef`). Гейт по
   `requestAnimationFrame` НЕ помогает — он закрывает только первый кадр.
2. **`getElementById` для перехода к сообщению больше не работает** — половина загруженной истории
   в DOM не смонтирована. Ищем индекс в массиве → `scrollToIndex`. Плавно только если пузырь уже
   смонтирован; дальний прыжок мгновенный (плавный через тысячу неизмеренных строк идёт рывками).
3. **Индексы асимметричны.** `itemContent`/`startReached` получают АБСОЛЮТНЫЙ индекс (данные +
   `firstItemIndex`), а `scrollToIndex`/`initialTopMostItemIndex` ждут индекс В МАССИВЕ (внутри
   клампится к `totalCount-1`). Поэтому в `itemContent` используется аргумент-ЭЛЕМЕНТ, не индекс.
   Проверено по исходникам: `t.map(d => ({...d, index: d.index + n, originalIndex: d.index}))`.
4. **`initialTopMostItemIndex` читается один раз при монтировании** → Virtuoso не монтируется,
   пока сообщений нет: иначе открытый чат встал бы на самом СТАРОМ сообщении.

## Замеры (диалог 350 сообщений, 27 215 px содержимого)
Смонтировано **20 строк / 283 узла DOM** вместо ~4900. Догрузка: сдвиг якоря 2–3 px при вставке
~3400 px сверху. Одиночное фото ВЫШЕ экрана меняло высоту на 128 px → сдвиг содержимого ниже **0 px**
(virtuoso сам правит `scrollTop`). Альбомы из 2+ фото высоту не меняют вовсе — плитки на `aspect-ratio`.

## Побочно закрыто
`hasMore` сбрасывался только в `selectChat` (клик по списку), поэтому после дип-линка `?chat=`/`?dm=`/
упоминания история вверх в новом чате не догружалась ВООБЩЕ. Теперь сброс — эффектом на `activeChatId`.

## Короткий чат прижат к низу (`alignToBottom`, решение пользователя)
Переписка, которая короче окна, лежит У ПОЛЯ ВВОДА, пустое место — сверху (модель Telegram/
WhatsApp): лента растёт снизу вверх, новое сообщение появляется там, где его ждут. Замер: 275 px
содержимого в окне 552 px → 264 px пустоты сверху, 12 px снизу (это Footer). Длинную переписку не
затрагивает — прижим включается, только когда содержимое короче окна. Перехода «было коротко →
стало длинно» на практике не бывает: страница = 50 сообщений, а это всегда выше любого окна.

## Намеренно НЕ сделано
Кнопки «↓ к новым» нет. Ctrl+F браузера теперь находит только видимые сообщения — как в Telegram
Web; для истории есть поиск в чате.

## Проверка
Живьём в браузере (панель предпросмотра ОБЯЗАНА быть развёрнута: при `document.hidden` нет ни rAF,
ни ResizeObserver — virtuoso не рисует НИ ОДНОЙ строки, и это не баг кода). Сцены: открытие внизу и
ровно одна страница; три догрузки подряд; входящее при чтении истории (0 px) и внизу (доезжает);
отправка из середины истории; переход по цитате через 6 страниц; поиск в чате; фото выше экрана;
меню «⋯» в середине ленты; телефон; встроенный чат задачи. Регрессии API: messenger 29/0, socket 10/0,
task 19/0, search 22/0, quickactions 20/0, mentions 18/0.

## Доводка по замечаниям (та же сессия, вторая волна)

### Подсветка перехода — на пузыре и пульсирует
Было: заливка `--secondary-container` по ВСЕЙ строке `.msg-row` (она тянется во всю ширину ленты
вместе со временем и кнопкой «⋯») — читалось как «выделен кусок экрана», а не «вот это сообщение».
Стало: класс `.msg-bubble--flash` на самом пузыре + `@keyframes msg-flash-pulse` в globals.css,
3 удара по 0.75с (совпадает с окном `flashId` в 2300 мс).
- Кольцо — ТОЛЬКО тень: `0 0 0 3px var(--surface-container-low)` (зазор цветом полотна) +
  `0 0 0 9px color-mix(--primary 55%)`. Размер пузыря не меняется — иначе виртуализатор перемерил
  бы строку прямо во время вспышки.
- Тень карточки (`--shadow-card`) повторена в КАЖДОМ кадре: CSS-анимация перебивает inline-стиль
  целиком, и без неё пузырь на время вспышки терял бы свою тень.
- Зазор цветом полотна — то, что делает кольцо одинаково читаемым и на синем «своём» пузыре,
  и на светлом чужом.
- `prefers-reduced-motion` → статичное кольцо без пульсации.
- Строка при подсветке поднимается `zIndex:1` — кольцо выходит за её границы.

### Переход из ГЛОБАЛЬНОГО поиска / «упоминаний» — три причины, две старше виртуализации
1. **[старая]** Эффект дип-линка бросал работу, если сообщение старше загруженного окна
   (`if (!messages.some(...)) return;`) — а это ЛЮБОЙ переход к старой переписке. Теперь дип-линк
   идёт тем же путём, что клик по цитате: `jumpToMessage` ставит отложенный переход и тянет страницы.
2. **[старая, коварная]** `onHighlightConsumed()` гасит запрос у родителя СРАЗУ → меняется
   зависимость эффекта → React зовёт уборщик → тот отменял СОБСТВЕННЫЙ `setTimeout` перехода до
   срабатывания. Таймер вынесен в ref, чистится только при размонтировании.
   **Правило:** если эффект гасит собственный триггер, его таймеры нельзя держать в уборщике.
3. **[виртуализационная]** Последняя догруженная страница приходит ТЕМ ЖЕ коммитом, в котором мы
   уводим ленту к цели, `followOutput` видит «человек внизу» и утаскивает обратно. Лечение:
   `jumpUntilRef` гасит прижим к низу на 1.2с после перехода + повтор `scrollToIndex` следующим
   кадром. `stickToBottom()` окно сбрасывает — явная просьба уехать вниз важнее.
   **Диагностика неочевидная:** страницы дотягивались (scrollHeight рос), `scrollToMessage`
   возвращал true, pending очищался — но пузырь не монтировался, потому что прокрутки не было.

Проверено: поиск → клик по «Сообщение #12» из 196 → 4 страницы дотянуты, лента встала на цели
за 0.7с, подсвечен ровно ОДИН пузырь. Регрессии: открытие внизу и одна страница, входящее внизу
и при чтении истории (0 px), отправка из середины, шаги поиска в чате — зелёные, консоль чиста.

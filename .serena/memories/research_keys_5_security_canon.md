## 1. Executive summary (20 пунктов)

1. **Текущее состояние — архитектурный блокер №1:** один `JWT_SECRET` служит и HMAC-ключом для
   JWT, и источником для деривации AES-256-GCM-ключа. Это прямо нарушает OWASP Key Management
   («A single key should be used for only one purpose») и RFC 8725 §3.1 («MUST bind each key to
   exactly one algorithm»). Следствие — **ротация невозможна**, что само по себе нарушает
   ASVS 11.1.1 (документированный жизненный цикл ключей по NIST SP 800-57).
2. **Storm-0558 — это ровно наш сценарий:** Microsoft остановила ротацию потребительских MSA-ключей
   в 2021 после аварии и не сделала автооповещения о возрасте активных ключей; ключ 2016 года
   подписал корпоративные токены, потому что валидация не проверяла *область* ключа. Урок:
   **ротация, которую больно делать, не делается**, и **ключ обязан быть привязан к аудитории**.
3. **Переходить на асимметрию для JWT.** ES256/EdDSA + JWKS + `kid`, отдельная пара ключей на
   каждую аудиторию (product API / platform console / WOPI / share-links / device / agent).
   Ресурс-сервер обязан проверять `aud` (RFC 9068) и `typ: at+jwt`.
4. **Промежуточный шаг, если асимметрия не сегодня:** HKDF (RFC 5869) от корневого секрета с
   РАЗНЫМИ `info`-метками (`superapp:jwt:v1`, `superapp:field-aead:v1`, `superapp:webhook:v1`).
   Это даёт domain separation, но **не решает** проблему ротации — решает только версия ключа в `kid`.
5. **AES-256-GCM: жёсткий потолок 2^32 вызовов на ключ** при случайном 96-битном IV
   (SP 800-38D §8.3, вероятность повтора J0 = 2^-32). При per-record DEK этот потолок не достигается;
   при одном «глобальном» ключе шифрования полей — достигается быстро. Отсюда — envelope encryption
   как обязательная форма.
6. **Криптопериоды (SP 800-57 Rev.5):** симметричный DEK — OUP ≤ 2 года; KEK — ≤ 2 года;
   приватный ключ подписи — 1–3 года; корневой CA — 10–20 лет. Для JWT-ключей подписи практика
   индустрии жёстче: 30–90 дней с overlap-окном.
7. **AAD — не украшение, а защита от подмены шифротекста.** В AAD обязаны входить
   `tenant_id | entity_type | entity_id | field_name | key_id`. Без этого шифротекст из чужой строки
   расшифруется в вашу.
8. **Формат шифротекста должен быть версионированным и самоописывающимся:** `v1:<kek_id>:<wrapped_dek>:<iv>:<ct>:<tag>`.
   Модель Tink (5-байтовый префикс `0x01` + 4-байтовый big-endian key id) и Vault (`vault:v1:`) —
   проверенные образцы. «Дешифруй любой версией, шифруй первичной» — базовое правило ротации.
9. **API-ключ = 256 бит энтропии + префикс + CRC32-чексумма.** GitHub: `ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`,
   разделитель `_` (не входит в base64 — не совпадёт со случайным SHA), чексум CRC32/base62 в
   последних 6 символах, false-positive rate секрет-сканирования упал до 0.5%. Нам нужен свой
   префикс (`sa6k_`, `sa6p_`, `sa6s_`, `sa6w_`) и регистрация в GitHub Secret Scanning Partner Program.
10. **Хранить только SHA-256 (или HMAC с pepper) от ключа, искать по хешу, а не bcrypt.** bcrypt/Argon2 —
    антипаттерн для высокоэнтропийных секретов: платится на КАЖДОМ запросе, а защита от перебора
    и так обеспечена 256 битами. Сравнение — constant-time. Показ — ровно один раз.
11. **Refresh-токены: ротация + reuse detection + отзыв всего семейства** (RFC 9700 §2.2.2 «MUST be
    sender-constrained or use refresh token rotation»; Auth0-паттерн). Обязателен **grace/leeway
    интервал** (единицы секунд), иначе потеря сети у мобильного клиента выглядит как кража.
12. **Вебхуки:** подпись HMAC-SHA256 по `msg_id.timestamp.raw_body`, заголовки `webhook-id`,
    `webhook-timestamp`, `webhook-signature` (Standard Webhooks), секрет `whsec_` длиной 24–64 байта,
    окно допуска 5 минут (как у Stripe), **несколько активных подписей** на время ротации,
    constant-time сравнение, идемпотентность по `webhook-id`, доставка только через safeFetch (SSRF).
13. **AI-агенты — это делегирование, а не имперсонация.** RFC 8693 token exchange: `subject_token`
    (пользователь) + `actor_token` (агент) → токен с вложенной цепочкой `act`. Права =
    права пользователя ∩ права агента ∩ выданный scope. MCP-спека 2025-06-18 уже это кодифицирует:
    OAuth 2.1 + RFC 9728 + RFC 8707 `resource`, **запрет token passthrough**, обязательная проверка `aud`.
14. **Confused deputy — главный класс атак на «приложения в организации».** Эффективное право =
    `право приложения ∩ право пользователя ∩ tenant`. MCP-спека прямо требует согласия пользователя
    для каждого динамически зарегистрированного клиента у прокси со статическим `client_id`.
15. **Ключ без владельца — запрещён.** OWASP NHI Top 10 (2025) — NHI1 Improper Offboarding,
    NHI5 Overprivileged, NHI7 Long-Lived Secrets, NHI9 Reuse. Cloudflare (ноябрь 2023) пострадала
    ровно потому, что **4 из тысяч** учёток/токенов не ротировали, «решив, что они не используются».
16. **Инвентарь ключей обязателен (ASVS 11.1.2, L2)** — включая алгоритмы и сертификаты, с
    документом «где ключ можно и где нельзя применять». Без инвентаря невозможны ни ротация, ни IR.
17. **Crypto-agility закладывается сейчас (ASVS 11.2.2, L2 + 11.1.4, L3):** `kid`, метка алгоритма
    в шифротексте, версия формата — чтобы миграция на ML-DSA/ML-KEM (FIPS 204/203, 13.08.2024) была
    сменой конфигурации. NIST IR 8547 (draft): RSA-2048/ECC-256 **deprecated к 2030, disallowed после 2035**.
18. **Казахстан: локализация — да, обязательный ГОСТ-СКЗИ — скорее нет, но с оговоркой.** Закон 94-V
    ст.12 п.2 требует, чтобы БД с перс. данными граждан РК физически находилась в РК (с 01.01.2016).
    ПП РК №832 «Единые требования» распространяется на госорганы, квазигосcектор, **владельцев
    негосударственных ИС, интегрируемых с государственными**, и объекты КВОИКИ. Требование
    СТ РК 1073-2007 там привязано к защищаемой (служебной/ограниченного доступа) информации.
    Вывод: AES-256-GCM для собственных данных частной компании законом РК напрямую не запрещён,
    **но интеграция с ЭЦП НУЦ РК / ЭДО может втянуть нас в периметр ПП 832** — см. §6 (открытый вопрос,
    требует юриста).
19. **Публичный облачный KMS, вероятно, недоступен → self-hosted.** Рабочий стек без HSM:
    **HashiCorp Vault Transit / OpenBao** (rewrap без раскрытия plaintext, `min_decryption_version`,
    derived keys, `vault:vN:` версия в шифротексте, auto-unseal или Shamir M-of-N). Второй контур —
    YubiHSM 2 / SoftHSM2 по PKCS#11 для корневого KEK и ключей подписи.
20. **Crypto-shredding как механизм «права на забвение»:** per-subject DEK → удаление DEK = удаление
    данных во всех копиях и бэкапах. Ловушка: если бэкап KEK/DEK переживает удаление — шреддинг
    фиктивен; удаление ключа обязано распространяться на все реплики и бэкапы хранилища ключей.

## 2. Находки по разделам

### 2.1. Стандарты управления ключами

**NIST SP 800-57 Part 1 Rev.5** `[official]` (полнотекстовый PDF извлечь не удалось — числа ниже
подтверждены вторичным изложением, помечены `[secondary]`).

| Тип ключа | Originator Usage Period (OUP) | Recipient Usage Period |
|---|---|---|
| Symmetric Data Encryption Key (DEK) | ≤ 2 года | дольше OUP (совокупно ≈ до 4 лет) |
| Symmetric Key-Wrapping Key (KEK) | ≤ 2 года | дольше OUP |
| Symmetric Authentication Key (HMAC) | ≤ 2 года | + период верификации |
| Private Signature Key | 1–3 года | — |
| Private Key-Agreement Key | 1–2 года | — |
| CA signing key | зависит от иерархии | 5–20 лет |
| Root CA key | 10–20 лет | — |

> ⚠️ Вторичный источник даёт RUP как «≤2 года сверх OUP»; в самом SP 800-57 Table 1 для DEK
> формулировка «OUP + 3 года». **Расхождение не разрешено primary-источником в этой сессии** —
> берите консервативное значение (OUP ≤ 2 года, суммарный срок жизни ≤ 4–5 лет) и фиксируйте
> собственное решение в документе политики.

Состояния ключа и переходы (SP 800-57 §7): **pre-activation → active → (suspended) → deactivated →
destroyed**, плюс аварийный переход **→ compromised → destroyed**. Практический вывод для схемы БД:
у `core/keys` должна быть колонка `state` именно с этим перечнем, а не булев `is_active`.

**Split knowledge / dual control** — два разных контроля: split knowledge = ни один человек не знает
ключ целиком; dual control = операция требует двух человек. У нас уже есть «четыре глаза» в
Кабинете платформы — это dual control; split knowledge отдельно нужен для key ceremony (Shamir).

**NIST SP 800-130** `[official]` — «A Framework for Designing CKMS»: перечень тем и требований к
**документации** проекта системы управления ключами. **SP 800-152** `[official]` — федеральный профиль
поверх 800-130 (требования к тестированию, закупке, установке, эксплуатации). Практика: 800-130 —
это оглавление нашего будущего `docs/keys_engine.md`.

**NIST SP 800-38D (GCM)** `[official]`:
- §8.3: при **RBG-based IV construction** (случайный 96-битный IV) число вызовов на один ключ
  ограничено **2^32**; это гарантирует вероятность повтора 128-битного значения `J0` не выше **2^-32**.
- NIST в pre-draft call for comments прямо пишет: «Applications with sufficiently many invocations
  may therefore require frequent rekeying».
- Ожидаемая первая коллизия для равномерно случайных 96-битных IV — ≈ 2^48.3 вызовов; предел 2^32
  сознательно консервативен.
- Максимум plaintext на один вызов — 2^39−256 бит (≈ 64 ГиБ) `[inference: общеизвестная константа
  стандарта, дословно из PDF в этой сессии не извлечена]`.
- Vault документирует это же правило: «For AES-GCM, rotation should occur before approximately
  2^32 encryptions per key version» `[official vendor]`.

**NIST SP 800-108 Rev.1 (KBKDF)** `[official/draft]`: KDF in Counter Mode, fixed input data =
`Label || 0x00 || Context || [L]₂`, итерация `K(i) := PRF(KI, {dataBeforeCounter} || [i]₂ || {dataAfter})`.
Разделитель `0x00` и явная длина `L` — защита от неоднозначности склейки.

**RFC 5869 (HKDF)** `[official]`: `PRK = HMAC-Hash(salt, IKM)` (extract), затем
`OKM = HKDF-Expand(PRK, info, L)` с итеративным счётчиком `0x01, 0x02, …`, максимум `255 × HashLen`
октетов. **`info` — «context and application specific information»**, именно она даёт domain separation:
одинаковый IKM в разных протоколах не даёт одинаковых ключей. Salt желателен даже низкокачественный.

**NIST SP 800-63B-4** `[official]`:
- пароли: ≥ 15 символов при однофакторной, ≥ 8 при MFA; **SHALL NOT** навязывать composition rules;
  **SHALL NOT** требовать периодическую смену; **SHALL** сверять с blocklist скомпрометированных.
- хранение: salt ≥ 32 бит + подходящая password hashing scheme; **SHOULD** дополнительная итерация
  keyed hash с ключом в HSM/TEE, хранимым отдельно (это и есть «verifier compromise resistance» —
  утечка БД не даёт офлайн-перебора без ключа из HSM).
- lookup secrets: ≥ 6 десятичных цифр (или эквивалент энтропии).
- OTP: сессия аутентификации **SHALL** считаться недействительной, если не завершена за **10 минут**;
  OTP принимается **ровно один раз**; ≤ **100 последовательных неудачных попыток** до блокировки
  аутентификатора. SMS/PSTN — **RESTRICTED**.
- таймауты сессии: AAL1 — 30 дней (рекоменд.), AAL2 — 24 ч / 1 ч неактивности, AAL3 — 12 ч / 15 мин.
  *(Rev.3 давал для AAL2 12 ч / 30 мин — при ссылках указывайте редакцию.)*

**FIPS 140-3 уровни** `[secondary]`: L1 — корректные алгоритмы, физической защиты нет (software на
general-purpose железе); L2 — tamper **evidence** + role-based аутентификация; L3 — tamper
**resistance**, identity-based аутентификация, **зануление CSP при вскрытии**, приватные ключи входят
и выходят только в зашифрованном виде, физическое/логическое разделение интерфейсов ввода-вывода CSP;
L4 — активный tamper **response** с оболочкой вокруг всего модуля + защита от side-channel/fault-injection.
**Что реально даёт «HSM-backed»:** ключ не покидает модуль в открытом виде, значит компрометация
хоста приложения (heap dump, RCE) не даёт материал ключа — только возможность вызывать операции,
пока доступ жив. Это сдвигает задачу с «украсть ключ» на «обнаружить аномальное использование».

**Post-quantum** `[official + secondary]`: **13 августа 2024** NIST опубликовал FIPS 203 (ML-KEM),
FIPS 204 (ML-DSA), FIPS 205 (SLH-DSA). NIST IR 8547 (draft, ноябрь 2024): RSA-2048 и ECC-256 —
**deprecated к 2030, disallowed после 2035**. CNSA 2.0: новые закупки НСС поддерживают PQC с 01.01.2027,
подпись firmware — PQC к 2030. **Что делать СЕЙЧАС:** не внедрять PQC, а обеспечить crypto-agility —
`kid`, явная метка алгоритма в каждом артефакте, версия формата шифротекста, инвентарь (ASVS 11.1.4).

**PCI DSS v4.0.1, req. 3.6–3.7** `[secondary]` — актуально, т.к. мы храним PAN/IBAN зашифрованными:
- 3.6.1.2 — секретные/приватные ключи хранятся в минимуме форм и мест;
- **KEK не слабее защищаемого DEK**; KEK хранится **отдельно** от DEK;
- **3.6.1.4** — ключи хранятся в минимальном числе мест;
- ручные операции с ключами в открытом виде — **только split knowledge + dual control**;
- **3.7.4** — смена ключей по истечении криптопериода, определяемого владельцем ключа и
  индустриальными практиками (время ИЛИ объём шифротекста);
- **3.7.5** — вывод/замена ключей при подозрении на компрометацию;
- **3.7.9** — кастодианы ключей формально подтверждают понимание своих обязанностей.

**ISO/IEC 27001:2022 A.8.24** `[inference]` — «Use of cryptography»: требуется политика применения
криптографии, включая управление ключами на всём жизненном цикле. Дословный текст контроля не
извлекался; при ссылке в доках проверьте формулировку по самому стандарту.

**Казахстан** — см. §2.10 и §6.

### 2.2. OWASP

**Key Management Cheat Sheet** `[official]`:
- ключи генерируются внутри криптомодуля, соответствующего FIPS 140-2/140-3; RBG — внутри того же модуля;
- **«A single key should be used for only one purpose»** (шифрование / аутентификация / key wrapping /
  RNG / подпись) — прямо про наш `JWT_SECRET`;
- KEK **не слабее** оборачиваемого ключа; ключи никогда не хранятся в открытом виде;
- прикладной код **не читает ключи напрямую** — только через библиотеку KM; операции — внутри «sealed vault»;
- план восстановления при компрометации: контакты, методика re-key, **инвентарь ключей**, проверка отзыва;
- никогда не сдавать в escrow ключи подписи; бэкап ключей шифрования — обязателен;
- логировать: кто видел открытый ключевой материал, кто имеет доступ, даты/время/что защищено;
  уникальный идентификатор у каждого ключа.

**Cryptographic Storage Cheat Sheet** `[official]`: AES ≥128 бит (лучше 256), режимы GCM/CCM;
ECB и PKCS#1 v1.5 — запрещены; ECC — Curve25519, RSA ≥ 2048 c OAEP; CSPRNG — `crypto.randomBytes`,
`crypto.randomInt`, `crypto.randomUUID`; **KEK и DEK хранятся в РАЗНЫХ местах**; триггеры ротации —
компрометация, истечение криптопериода, объём (≈2^35 байт для 64-битных блочных шифров), новость об
алгоритме. **Явно запрещено:** хардкод ключей в коде, ключи в VCS, **ключи в переменных окружения**,
«случайность» набитая руками.

**Secrets Management Cheat Sheet** `[official]`: пользовательские пароли ротируются только при
компрометации, **прикладные секреты — регулярно**; предпочтительны **динамические** короткоживущие
секреты; ротация автоматизируется («manual maintenance increases risk of leakage and human error»);
отзыв — немедленный; аудит обязан фиксировать кто/что/когда запрашивал, отказы, попытки переиспользования;
в контейнерах env-переменные **не рекомендуются** (видны всем процессам), лучше sidecar/смонтированный том;
проблема «secret zero» решается вторичным хранилищем + break-glass; в логах — маскирование;
IR-последовательность: **revoke → rotate → delete (включая историю git и логи) → review logs**.

**JSON Web Token Cheat Sheet** `[official]`:
- `alg: none` не должен приниматься парсером;
- algorithm confusion: **выбирать ключ по запрошенному алгоритму**, хардкодить список алгоритмов,
  не смешивать MAC и public-key алгоритмы, использовать строго типизированные ключи;
- **HMAC-секрет: ≥ 160 бит энтропии, длина = размеру выхода (256/384/512 бит для HS256/384/512),
  CSPRNG, никогда не переиспользовать между issuer/audience, пароли в качестве секрета запрещены**;
- `jwk` / `jku` / `x5u` / `x5c` из заголовка — не доверять без цепочки доверия; предпочитать
  out-of-band trust anchors (пиннинг, `jwks_uri` из метаданных issuer); `kid` **валидировать до**
  запроса в БД (инъекция);
- рекомендуемые алгоритмы: **EdDSA, ES256/384/512, PS256/384/512**; RS256 (PKCS#1 v1.5) — избегать;
- отзыв: denylist по `jti`+`iss` (**не по хешу токена** — ECDSA-подпись malleable),
  Token Status Lists; короткий `exp`;
- ключи не переиспользовать для шифрования, приватные не публиковать, ротировать регулярно.

### 2.3. IETF / OAuth канон

**RFC 9700 (OAuth 2.0 Security BCP, 2025)** `[official]` — дословные нормы:
- §2.1: AS **MUST** использовать exact string matching для redirect URI (исключение — порты для
  `localhost` в native-приложениях);
- §2.1.1: публичные клиенты **MUST** использовать PKCE; AS **MUST** поддерживать PKCE; AS **MUST**
  митигировать PKCE downgrade — принимать `code_verifier` только если был `code_challenge`;
- §2.1.2: клиенты **SHOULD NOT** использовать implicit grant;
- §2.4: **ROPC MUST NOT be used**;
- §2.2.2: refresh-токены публичных клиентов **MUST** быть sender-constrained **или** ротироваться;
- §2.2.1: AS и RS **SHOULD** применять sender-constraining (mTLS или DPoP);
- §2.3: access-токены **SHOULD** быть audience-restricted;
- §4.3.2 / RFC 6750 §2.3: клиенты **MUST NOT** передавать access-токен в query-параметре;
- §2.1: клиенты **SHOULD** использовать параметр `iss` (RFC 9207) против mix-up.

**OAuth 2.1 (draft-ietf-oauth-v2-1-16, сентябрь 2026)** `[official]`: PKCE обязателен для
authorization code; exact-match redirect URI (исключение — loopback); **implicit grant удалён**
(§10.1); **ROPC удалён**; чувствительные параметры только в теле запроса, **MUST NOT** в URI;
sender-constrained токены — SHOULD (DPoP/mTLS).

**RFC 8725 (JWT BCP)** `[official]` — атаки и нормы (см. таблицу §3.x в источнике):
`alg: none` и RS256→HS256 confusion (§2.1) → §3.1 **MUST** проверять соответствие `alg`
криптооперации и **MUST** привязывать каждый ключ ровно к одному алгоритму; слабые симметричные
ключи (§2.2) → §3.5 **MUST NOT** использовать пароли как HMAC-ключи; невалидация вложенных JWS в JWE
(§2.3) → §3.3; invalid curve (§2.5) → §3.4 валидация эфемерных ключей по SP 800-56A §5.6.2.3.4;
неоднозначность кодировок (§2.6) → §3.7 **только UTF-8**; substitution (§2.7) и cross-JWT confusion
(§2.8) → §3.8 **MUST** проверять принадлежность ключа заявленному issuer, §3.9 **MUST** включать и
проверять `aud`, §3.11 явный `typ`, §3.12 правила валидации разных типов JWT взаимно исключающие;
`kid`/`jku`/`x5u` как вектор SQLi/LDAPi/SSRF (§2.9) → §3.10 **SHOULD** санитизировать `kid`,
whitelist для `jku`/`x5u`, отключать cookies при их загрузке.

**RFC 9068 (JWT profile for access tokens)** `[official]`: заголовок `typ` **SHOULD** = `at+jwt`;
RS **MUST** проверять `typ` = `at+jwt`/`application/at+jwt` и отвергать остальное. Обязательные
claims: `iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti`. RS **MUST** отвергать токен, если
`aud` не содержит его resource indicator. Разным ресурсам — **разные `aud`**.

**RFC 9449 (DPoP)** `[official]`: заголовок запроса **`DPoP`** несёт proof-JWT:
`typ: dpop+jwt`, асимметричный `alg` (никогда `none`/симметричный), `jwk` с ПУБЛИЧНЫМ ключом;
claims: `jti` (уникальный, для реплей-детекта), `htm` (метод), `htu` (target URI без query/fragment),
`iat`, `ath` (base64url SHA-256 от access-токена) и `nonce` (если сервер требует).
Access-токен связан через `cnf.jkt` = base64url JWK SHA-256 Thumbprint.
Сервер выдаёт nonce через **`DPoP-Nonce`**, ошибка — `use_dpop_nonce`.
Реплей: серверы **MUST** принимать proof только ограниченное время после создания
(«on the order of seconds or minutes») и отслеживать `jti` в окне приёма.

**RFC 8693 (Token Exchange)** — основа делегирования для AI-агентов `[official]`:
- `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`;
- **обязательные**: `subject_token`, `subject_token_type`;
- **опциональные**: `actor_token`, `actor_token_type` (обязателен при наличии actor_token),
  `requested_token_type`, `resource`, `audience`, `scope`;
- **Impersonation** = только `subject_token` (агент неотличим от пользователя — для нас плохо);
- **Delegation** = `subject_token` + `actor_token` → composite token (**наш случай**);
- claim **`act`** выражает делегирование; цепочка — вложением: внешний `act` = текущий актор,
  вложенные = предыдущие;
- claim **`may_act`** — кто имеет право действовать за субъекта (предварительная авторизация делегата).

**MCP Authorization spec 2025-06-18** `[official]` — образец для наших AI-агентов:
- AS **MUST** реализовать OAuth 2.1; MCP-сервер **MUST** реализовать **RFC 9728** (Protected Resource
  Metadata) и **MUST** возвращать `WWW-Authenticate` с `resource_metadata` при 401;
- клиенты **MUST** использовать RFC 8414 (AS metadata); DCR (RFC 7591) — SHOULD;
- клиенты **MUST** передавать параметр **`resource`** (RFC 8707) и в authorization-, и в token-запросе,
  с канонической URI сервера — **независимо от того, поддерживает ли его AS**;
- **«MCP servers MUST only accept tokens specifically intended for themselves»**; токен без них в `aud` —
  отклонить; **`MUST NOT` пробрасывать полученный токен вверх по цепочке (token passthrough запрещён)**;
- токен **MUST NOT** в query-строке; авторизация **MUST** в каждом HTTP-запросе;
- PKCE **MUST**; redirect URI **MUST** зарегистрирован и проверяться точным сравнением;
- AS **SHOULD** выдавать короткоживущие access-токены; для публичных клиентов **MUST** ротировать refresh;
- **Confused deputy**: прокси со статическим `client_id` **MUST** получать согласие пользователя для
  каждого динамически зарегистрированного клиента.

**Прочие RFC, релевантные каркасу** `[official, использованы по ссылкам выше]`: RFC 6749/6750 (база и
запрет токена в URI), RFC 7009 (revocation endpoint), RFC 7662 (introspection), RFC 7517 (JWK/JWKS),
RFC 8414 (AS metadata), RFC 9728 (Protected Resource Metadata), RFC 8705 (mTLS client auth и
certificate-bound tokens), RFC 9126 (PAR), RFC 9396 (RAR), RFC 8707 (Resource Indicators),
RFC 9207 (`iss` в ответе).
> `[inference]` Специализированных RFC «AI agent identity / delegation chains» на момент исследования
> не найдено как завершённых стандартов; фактический канон сегодня = RFC 8693 (`act`/`may_act`) +
> MCP authorization spec. Заявлять наличие отдельного IETF-стандарта по агентам **нельзя**.

### 2.4. Дизайн API-ключей / токенов

**Энтропия и формат.** GitHub `[official]`:
- префиксы: `ghp_` (PAT), `gho_` (OAuth), `ghu_` (user-to-server), `ghs_` (server-to-server),
  `ghr_` (refresh); первые две буквы — компания, третья — тип токена;
- разделитель `_` выбран намеренно: **не входит в base64**, поэтому токен не воспроизведётся
  случайно (например, SHA-строкой);
- тело — **base62** (a-z, A-Z, 0-9);
- **CRC32-чексум в последних 6 символах**, закодированный base62 с ведущими нулями:
  «32 bit checksum in the last 6 digits… strikes the optimal balance»;
- эффект: false positive rate секрет-сканирования **до 0.5%** только от префикса; чексум позволяет
  офлайн-валидацию без запроса в БД;
- энтропия OAuth-токена выросла со **160 до 178 бит** без увеличения длины.

**GitHub Secret Scanning Partner Program** `[official]` — чтобы наши ключи ловились у клиентов,
нужно предоставить: **уникальный префикс, высокоэнтропийную случайную часть, 32-битную чексумму,
тестовый аккаунт** и URL эндпоинта для уведомлений (`secret-scanning@github.com`).

**Хранение.** `[secondary, консенсус]`
- хранить **только SHA-256** (лучше — HMAC-SHA256 с серверным pepper из KMS/HSM) от ключа;
- **искать по хешу** (детерминированный индекс) либо по открыто хранимому короткому префиксу;
- **bcrypt/Argon2 для API-ключей — антипаттерн**: стоимость платится на каждом запросе, а защита
  от перебора уже обеспечена ≥128–256 битами энтропии; плюс bcrypt-хеш нельзя использовать для lookup;
- сравнение — **constant-time**;
- ключ показывается **ровно один раз** при создании;
- `last_used_at` — батчить (не писать на каждый запрос; окно 60 с) во избежание write amplification.

**Жизненный цикл.** `[official: OWASP NHI7 + Secrets Cheat Sheet]` дефолтный срок жизни обязателен
(не «бессрочно»); напоминания об истечении; ротация с **grace-периодом** (старый и новый ключ
одновременно валидны ограниченное время); отзыв — немедленный.

**JWT vs opaque.** `[secondary]` JWT: stateless, но отзыв только через denylist/эпоху и размер растёт;
opaque: тривиальный отзыв, но нужен lookup. **Phantom token pattern** (Curity): наружу — opaque,
на API-шлюзе интроспекция обменивает его на JWT (`Accept: application/jwt`), внутрь идёт JWT. Это
даёт приватность opaque + эффективность JWT и один центр кеширования. Вариант — split token
(наружу отдаётся только сигнатура).

**Дисциплина прав.** `[official: NHI5/NHI9 + MCP confused deputy]` ключ-на-цель (no god keys);
scope, привязанный к `tenant_id`; эффективное право = `scope ∩ права приложения ∩ права пользователя`;
rate limit на ключ; IP allow-list — полезен, но **не контроль доступа** (NAT, мобильные сети, обход
через SSRF в доверенной сети); для высокоценных операций — sender-constrained токены (DPoP/mTLS).

### 2.5. Envelope encryption и KMS

**Иерархия.** Root KEK (HSM/Vault/sealed file) → per-tenant или per-purpose KEK → **per-record DEK**.
OWASP Cryptographic Storage: **KEK и DEK хранятся в разных местах**, KEK не слабее DEK.
PCI DSS 3.6: то же самое, нормативно.

**AAD.** `[inference, но обязателен по логике AEAD + ASVS 11.3.4]` в Associated Data включать
`tenant_id | owner_type | owner_id | entity_type | entity_id | field_name | key_id | format_version`.
Без этого: атакующий с доступом к БД переносит шифротекст из своей строки в чужую, и расшифровка
проходит успешно — «ciphertext swapping».

**Формат.** Tink `[official]`: keyset = список ключей, ровно один **primary**; у каждого ключа
уникальный ID и статус (можно **disable** без удаления); wire format = 5-байтовый префикс
`0x01 || key_id (big-endian uint32)`; envelope = `len(encDEK)[4 байта BE] || encDEK || ciphertext`.
Все ключи keyset'а — один primitive (AEAD), но **типы могут различаться** (AES-GCM и XCHACHA20-POLY1305
в одном keyset) — это и есть механическая crypto-agility.
Vault `[official]`: префикс `vault:v1:` с номером версии ключа.
**Наш вывод:** `v<fmt>:<kek_id>:<alg>:<wrapped_dek>:<iv>:<ct+tag>` — версия формата, идентификатор
KEK, метка алгоритма. Всё, что понадобится при миграции, должно быть в шифротексте.

**Ротация.** `[official: Vault]`
- «Periodic rotation of the encryption keys is recommended, even in the absence of compromise»;
- `min_decryption_version` — отсечка старых версий (архивация); `min_encryption_version`;
- эндпоинт **`rewrap`** перешифровывает старый шифротекст новой версией ключа **не раскрывая
  plaintext** — значит перешифровку может выполнять недоверенный фоновый процесс;
- `datakey` возвращает высокоэнтропийный DEK, обёрнутый named key, опционально с plaintext-копией;
- derived keys с `context` — один ключ на несколько назначений через деривацию;
- convergent encryption v3 — устойчив к offline plaintext-confirmation;
- типы: `aes256-gcm96` (по умолчанию), `aes128-gcm96`, `chacha20-poly1305`.

**Стратегия перешифровки:** «decrypt with any version, encrypt with primary» + фоновый bulk-job с
прогрессом (у нас есть `core/jobs` — идемпотентный обработчик, `enqueue(tx)`). Lazy re-encrypt на
чтении — дополнение, не замена: он никогда не добьёт холодные записи, а значит `min_decryption_version`
не поднять.

**Seal / key ceremony.** Vault `[official]`: master key разбивается по **Shamir** на N shares с
порогом T (классика 5/3); auto-unseal через внешний KMS/HSM выдаёт вместо unseal-ключей
**recovery keys** (тоже Shamir); `operator rekey` меняет набор и порог без простоя, но требует
кворума текущих ключей; миграция seal Shamir↔Auto поддерживается. **Для нас (self-hosted, KZ):**
ceremony с M-of-N кастодианами, протокол, свидетели, разнесённое хранение долей — это ровно
«split knowledge» из PCI DSS 3.6 и SP 800-57.

**Доступные HSM.** `[secondary]` SoftHSM2 (софтовый, для разработки и как PKCS#11-абстракция),
YubiHSM 2, Nitrokey HSM — доступны по цене и дают FIPS-подобный барьер «ключ не покидает модуль».
Интерфейс — **PKCS#11**; абстрагировать его сразу, чтобы переезд «софт → железо» не требовал
переписывания сервисов. **OpenBao** — open-source форк Vault, вариант при лицензионных ограничениях.

**Crypto-shredding.** `[secondary]` per-subject DEK, удаление DEK = стирание данных во всех копиях.
Ловушки: (1) бэкапы **хранилища ключей** должны подчиняться удалению, иначе шреддинг фиктивен;
(2) шреддинг не сильнее использованного шифра; (3) не признан явно ни NIST, ни регулятором как
эквивалент удаления — решение юридическое, не техническое.

**Node.js specifics.** `[secondary + inference]`
- `crypto.webcrypto` / `KeyObject` — ключ может жить вне JS-кучи и не быть extractable; это
  предпочтительнее «Buffer с ключом»;
- `Buffer.fill(0)` в `finally` сокращает окно экспозиции, но **не гарантирует** стирание: строки в V8
  иммутабельны, GC-компактизация могла скопировать байты. Это defense-in-depth, не гарантия;
- **отключить core dump / heap snapshot на проде** — урок Storm-0558 (крэш-дамп как канал утечки
  ключа, пусть CSRB и не нашёл доказательств именно этого пути);
- секреты **никогда** в сообщения ошибок, стектрейсы, `JSON.stringify` моделей, APM-трейсы;
- **env-переменные для ключей OWASP не рекомендует** (видны всем процессам, попадают в дампы и
  child-process-окружение) — предпочтительны смонтированный файл с правами или обращение к KMS на старте;
- разделение процессов: «крипто-сервис» отдельно от бизнес-процесса — компрометация API-процесса
  не даёт ключевой материал (это ровно то, что даёт Vault Transit без HSM).
- кеш расшифрованных DEK: короткий TTL (минуты), ограниченный размер, ключ кеша — `key_id`,
  инвалидация при ротации и при отзыве доступа.

### 2.6. Ротация ключей подписи JWT

**Почему HS256 с одним секретом плох** `[official: OWASP KM + RFC 8725 §3.1]`:
- один секрет = и подписант, и верификатор; любой сервис, который проверяет токен, может его **выписать**;
- переиспользование того же секрета для деривации AES-ключа нарушает «один ключ — одно назначение»
  и **делает ротацию невозможной** (смена секрета расшифровать старые данные не позволит);
- секрет в `.env` попадает в дампы, логи CI, child-process-окружение.

**Куда идти:** ES256 (или EdDSA) + JWKS (`/.well-known/jwks.json`) + `kid` у каждого ключа.
Приватный ключ — только у issuer'а (или в HSM); верификаторы имеют только публичный.
**Отдельные пары ключей на аудиторию:** product API, Кабинет платформы, WOPI, share-links,
device/POS, agent-delegation. Это ровно тот контроль, отсутствие которого дало Storm-0558
(потребительский ключ подписал корпоративные токены).

**Процедура ротации без разлогина** `[secondary, консенсус практик]`:
1. сгенерировать новую пару, **опубликовать публичный ключ в JWKS**, ещё НЕ подписывая им;
2. подождать ≥ (JWKS cache TTL); `Cache-Control: public, max-age=600, must-revalidate` — типовой выбор;
3. переключить подпись на новый `kid`;
4. старый публичный ключ держать в JWKS ещё **grace = JWKS cache TTL + max token lifetime + буфер**
   (для нас: 10 мин + 15 мин + запас ⇒ ~1 час для access; для refresh-эпох — дольше);
5. удалить старый ключ, перевести в состояние `deactivated`, затем `destroyed`.
Верификатор при неизвестном `kid` делает **однократный** re-fetch JWKS с rate-limit (иначе `kid`
становится DoS-вектором).

**Интерим для HS256, если асимметрию нельзя сегодня:** HKDF-Expand от корневого секрета с разными
`info`-метками и **версией**: `info = "superapp6:v1:jwt-hs256:aud=product"`,
`info = "superapp6:v1:field-aead"`, `info = "superapp6:v1:webhook"`. Это даёт domain separation
и развязывает подпись от шифрования, но **ротация корневого секрета всё ещё ломает старые данные** —
поэтому шифрование полей обязано мигрировать на envelope с собственным KEK, **иначе интерим
превращается в постоянное состояние**.

**Отзыв.** `tokenEpoch` на пользователя — правильный паттерн (bump = мгновенный отзыв всех access-токенов).
Дополнить: эпоха на **организацию** (отзыв при увольнении/исключении из tenant), на **ключ/устройство**,
на **приложение**. Denylist — по `jti`+`iss`, **не** по хешу токена (OWASP: ECDSA malleability).

**Refresh-токены.** RFC 9700 §2.2.2 `[official]`: sender-constrained **или** ротация.
Auth0-паттерн reuse detection `[official vendor]`: первый использовавший получает новый токен,
второй предъявляет уже израсходованный ⇒ нарушение политики ⇒ **инвалидация всего семейства**,
все дальнейшие запросы отклоняются до повторной аутентификации.
Обязателен **leeway/grace window** (единицы секунд, идемпотентный повтор возвращает тот же
замещающий токен) — иначе нестабильная мобильная сеть выглядит как кража. Событие reuse — в SIEM
и в `core/notifications` владельцу.

### 2.7. Безопасность вебхуков

**Standard Webhooks** `[official]` — берём как базу:
- заголовки: **`webhook-id`**, **`webhook-timestamp`** (unix seconds), **`webhook-signature`**
  (список подписей через пробел);
- подписываемая строка: **`msg_id.timestamp.payload`** (payload — **сырое тело**);
- симметрично: **HMAC-SHA256**, идентификатор схемы `v1`, формат элемента `v1,<base64-подпись>`;
  секрет base64 с префиксом **`whsec_`**, рекомендуемая длина **24–64 байта (192–512 бит)**;
- асимметрично: **Ed25519**, схема `v1a`, ключи `whsk_` (приватный) / `whpk_` (публичный) —
  **предпочтительнее симметрики** (получатель не может выписать подпись от нашего имени);
- «Use a constant time comparison function»;
- проверять, что timestamp в допустимом окне (реплей);
- **`webhook-id` как ключ идемпотентности** (хранить, например, 5 минут);
- ротация без простоя: **подписывать одновременно старым и новым секретом**, получатель перебирает
  подписи до совпадения;
- SSRF: проксировать исходящие через фильтрующий сервис;
- **ключи уникальны на endpoint, никогда не переиспользуются между клиентами**.

**Stripe** `[official]` — подтверждающие числа:
- заголовок `Stripe-Signature: t=<ts>,v1=<hex>,...`;
- `signed_payload = timestamp + "." + raw_body`; HMAC-SHA256, ключ — endpoint secret (`whsec_`);
- **игнорировать все схемы, кроме `v1`** (downgrade-атака);
- **дефолтный допуск — 5 минут**; «Don't use a tolerance value of 0» (отключает проверку свежести);
- при ротации секрета старый остаётся активен **до 24 часов**, в это время шлётся по одной подписи
  на каждый секрет;
- фреймворк **не должен трогать raw body** — иначе верификация ломается;
- ретраи с экспоненциальным backoff до 3 суток; **порядок событий не гарантирован** ⇒ идемпотентность
  по `event.id`;
- рекомендуется совмещать подпись с **IP allow-list**;
- эндпоинт обязан быстро вернуть 2xx и обрабатывать асинхронно; 3xx-редирект считается провалом.

**Наши правила:** секрет **никогда не в payload**; `core/jobs` как транспорт (at-least-once +
идемпотентность); доставка только через `safeFetch` (адрес пришёл из данных ⇒ SSRF-риск, у нас это
уже закреплено в `docs/security.md`); challenge-верификация эндпоинта при регистрации.

### 2.8. Device / IoT / POS

**X.509-идентичность устройства.** AWS IoT `[official]`:
- **fleet provisioning by claim**: в прошивку зашивается **claim-сертификат** (bootstrap), **уникальный
  на партию**, не на устройство; при первом подключении он обменивается на **уникальный операционный
  X.509-сертификат** и приватный ключ;
- альтернативы при возможности персонализации на производстве: JITP / JITR / Multi-Account Registration;
- поддерживаются собственные CA (AWS Private CA, внешние, своя PKI).
**Ключевой инвариант:** приватный ключ генерируется **на устройстве** (TPM / Secure Element / TEE) и
**никогда не покидает** его; наружу уходит только CSR.

**Аттестация.** `[secondary]` Apple **App Attest**: пара ключей в Secure Enclave, Apple подписывает
аттестацию; две стадии — attestation (создание ключа) и assertion (валидация конкретного запроса).
Android **Play Integrity API**: проверка целостности устройства/приложения.
**Критично:** бэкенд генерирует **криптослучайный nonce на каждый запрос**, клиент подписывает и
возвращает его в payload — иначе аттестация реплеится. Аттестация — сигнал риска, **не** замена
авторизации.

**Отзыв.** Выбор: CRL/OCSP против короткоживущих сертификатов. Практика: **короткий срок жизни
операционного сертификата (дни–недели) + автоматическое обновление** проще и надёжнее, чем работающая
инфраструктура отзыва. mTLS — предпочтительный транспорт (RFC 8705 даёт и certificate-bound токены).

**Оффлайн-POS.** `[secondary]` EMV/платёжный мир решает это **DUKPT** (ANSI X9.24): из Base Derivation
Key (BDK) при инжекции выводится Initial Key устройства, дальше **каждая транзакция шифруется
одноразовым ключом**; KSN — 10 байт (20 hex). Компрометация одной транзакции не компрометирует ни
другие, ни BDK; из одного BDK обслуживаются сотни тысяч терминалов; инжекция ключей — **только через HSM**.
**Перенос на нас:** для оффлайн-режима POS — не «долгоживущий bearer-ключ в терминале», а
per-device ключ + счётчик + подписанный оффлайн-чек, который валидируется и дедуплицируется при
синхронизации. Оффлайн-операция **не должна** уметь то, что необратимо (списание средств) — только
накопление подписанных намерений.

**Симметричный per-device ключ как fallback** (когда X.509 не потянуть): 256 бит, уникальный на
устройство, выведенный HKDF из device-KEK с `info = device_id`; **никогда** общий на партию.

**Pairing по QR** для потребительских гаджетов: QR несёт одноразовый короткоживущий код (≤ 5 мин,
однократный), обмениваемый на device credential; сам ключ в QR не попадает.

### 2.10. Операционный канон

**Runbook ротации** (для каждого типа ключа отдельный, иначе не выполняется):
1. сгенерировать новую версию (состояние `pre-activation`);
2. опубликовать/раздать верификаторам, дождаться распространения (кеш TTL);
3. переключить «primary» на новую версию;
4. фоновая перешифровка (`rewrap`, идемпотентный джоб с прогрессом) — для KEK/DEK;
5. поднять `min_decryption_version` / удалить старый ключ из JWKS;
6. `deactivated` → (после retention) `destroyed`, запись в append-only журнал.

**Break-glass.** Отдельный набор кредов, хранимый офлайн, M-of-N, с автоматическим алертом при любом
использовании и обязательным post-mortem. OWASP Secrets Cheat Sheet прямо требует «break-glass
credentials backed up securely in secondary systems and tested routinely» — **тестируемость** здесь
ключевое слово.

**Key custodians / dual control.** У нас уже есть «четыре глаза» в `core/platform` — это dual control.
Добавить: split knowledge для долей корневого KEK (разные люди, разные хранилища), формальное
подтверждение обязанностей кастодианом (PCI DSS 3.7.9), запрет совмещения ролей «кастодиан» и
«администратор системы».

**Что логировать по ключам** `[official: OWASP KM + Secrets Cheat Sheet]`:
*логировать* — создание/ротация/отзыв/уничтожение (кто, когда, какой `key_id`, на каком основании),
кто получал доступ к открытому ключевому материалу, факт использования (`key_id`, субъект, операция,
IP/ASN, результат), отказы авторизации, попытки использования отозванного/просроченного ключа,
изменение scope'ов и владельца.
**Никогда не логировать** — сам ключ, его префикс+суффикс в объёме, позволяющем восстановление,
plaintext DEK, полные session-токены, содержимое AAD с PII. Маскирование — на уровне логгера,
не на местах вызова.

**Аномалии по ключам:** новый IP/ASN, «невозможное перемещение», всплеск частоты, выход за привычный
набор эндпоинтов, первое использование ключа спустя долгое молчание, использование после
`deactivated`. Последнее — сигнал компрометации, а не ошибки клиента.

**Honeytokens / canary keys** `[secondary]`: ключ, который никогда не используется легитимно ⇒
**любое срабатывание — инцидент с высокой достоверностью**. Работает особенно хорошо, потому что
инструментарий атакующих (TruffleHog и т.п.) автоматически валидирует найденные креды. Нужен реестр
«какой canary где размещён». Ограничение: продвинутый атакующий распознаёт canary (например,
у AWS-канареек характерное имя в ответе STS).

**Secret detection в CI:** gitleaks / trufflehog на pre-commit и в pipeline; собственный префикс
`sa6*_` + CRC32 делает наши ключи детектируемыми; стандартные тестовые секреты, чтобы снизить
false positives; корреляция нескольких детекторов.

**IR при утечке ключа:** `revoke → rotate → scan usage (по логам: где и когда этот key_id
использовался) → notify (владелец, затронутые tenant'ы) → delete из всех мест, включая git-историю
и логи → post-mortem`. Порядок именно такой: **сначала отзыв**, потом расследование.

**Инвентарь NHI** (ASVS 11.1.2 + NHI Top 10): таблица `key_registry` с полями `key_id`, тип,
назначение, владелец (человек!), tenant, scope, `created_at`, `expires_at`, `last_used_at`,
состояние, где хранится, чем обёрнут. **Правило «нет ключа без владельца»** — enforced на уровне
схемы (NOT NULL), не на уровне процесса.

## 3. Сводная модель угроз по типам ключей

| Тип ключа | Ключевые угрозы | Обязательные контроли |
|---|---|---|
| **JWT signing key** (HS256→ES256/EdDSA) | `alg:none`; RS→HS confusion; brute-force слабого HMAC; `kid` injection (SQLi/path); `jku`/`x5u` SSRF; кража ключа ⇒ форж любых токенов (Golden SAML, Storm-0558); использование ключа не по аудитории | Асимметрия + JWKS + `kid`; ключ **привязан к одному алгоритму** (RFC 8725 §3.1); allow-list алгоритмов; `typ: at+jwt` + проверка `aud` (RFC 9068); **отдельная пара на каждую аудиторию**; приватный ключ в HSM/Vault; ротация 30–90 дней с overlap; санитизация `kid` до lookup; `jku`/`x5u` не поддерживать вовсе; алерт на возраст ключа |
| **Root KEK** | Кража хоста; отсутствие бэкапа ⇒ потеря всех данных; один человек знает ключ; невозможность ротации | HSM/Vault seal; **Shamir M-of-N** (5/3) + разнесённое хранение долей; ceremony с протоколом; dual control; бэкап + регулярный тест восстановления; `operator rekey` отработан |
| **Tenant/purpose KEK** | Кросс-тенантная расшифровка; один KEK на всё ⇒ взрывной радиус | KEK на tenant (и/или на назначение); KEK **не слабее** DEK (PCI 3.6); KEK хранится **отдельно** от DEK; `rewrap` без раскрытия plaintext; `min_decryption_version` |
| **DEK (per-record)** | Nonce reuse ⇒ катастрофа GCM; ciphertext swapping между строками; превышение 2^32; утечка через кеш/дамп | AEAD + **AAD = tenant|entity|field|key_id**; per-record DEK ⇒ 2^32 недостижим; IV — CSPRNG 96 бит, никогда не переиспользуется (ASVS 11.3.4); версионированный формат; TTL-кеш расшифрованных DEK; crypto-shredding на удаление субъекта |
| **API key (организации)** | Утечка в репо/лог; перебор; god-scope; вечная жизнь; переиспользование между средами; отсутствие владельца | 256 бит CSPRNG; **префикс + CRC32**; хранить SHA-256/HMAC-pepper, lookup по хешу; constant-time; show-once; scope ⊆ tenant; дефолтный TTL + напоминания; `last_used_at` (батч); rate-limit на ключ; регистрация префикса в secret scanning; владелец обязателен |
| **PAT (личный токен)** | Человек использует NHI (NHI10); переживает увольнение; полномочия шире, чем у человека | Права PAT ⊆ прав человека **в момент выполнения**; каскадный отзыв при увольнении/смене роли/bump `tokenEpoch`; обязательный TTL (≤ 90 дней); нельзя выдавать в организации, где человек не активен |
| **Service-account secret** | Повышенные права (Dropbox Sign); хранение людьми (Okta); отсутствие ротации (Cloudflare) | Least privilege; запрет человеческого логина сервис-аккаунтом; ротация по расписанию с grace; аномалии; в инвентаре с владельцем и `last_used_at` |
| **OAuth client secret** (стороннее приложение в организации) | Confused deputy (права приложения > прав пользователя); открытый редирект; кража секрета у вендора (Salesloft Drift) | Эффективное право = `app ∩ user ∩ tenant`; exact-match redirect URI; PKCE обязателен; **отдельный секрет/токен на tenant**, зашифрованный tenant-KEK; ротация с двумя активными; консент пользователя на каждый динамический клиент; kill-switch «отозвать приложение во всех организациях» |
| **Refresh token** | Кража ⇒ бессрочный доступ; реплей; отсутствие детекта | Ротация + **reuse detection с отзывом семейства**; SHA-256 хранение (уже есть); leeway 5–10 с; sender-constrained (DPoP) для высокоценных; привязка к `tokenEpoch`; алерт владельцу при reuse |
| **Webhook secret** | Спуфинг событий; реплей; SSRF при доставке; утечка через payload; «один секрет на всех» | HMAC-SHA256 по `id.ts.raw_body` (или Ed25519); окно 5 мин; **секрет на endpoint**; ротация двумя подписями; constant-time; идемпотентность по `webhook-id`; `safeFetch`; секрет никогда в теле |
| **Device / POS cert** | Клонирование прошивки (общий claim-ключ); извлечение приватного ключа; отсутствие отзыва; оффлайн-злоупотребление | Ключ генерируется в TPM/SE и **не покидает устройство**; claim-сертификат **уникален на партию** и обменивается на операционный; короткий TTL + автообновление вместо CRL; mTLS; аттестация с server-nonce; для оффлайна — DUKPT-подобная схема «одноразовый ключ на операцию», необратимое запрещено |
| **Agent delegation token** | Excessive agency (LLM06); имперсонация вместо делегирования; token passthrough вверх по цепочке; невозможность отличить действие агента от действия человека в аудите | RFC 8693: `subject_token` + `actor_token` ⇒ claim **`act`** (цепочка вложением), **`may_act`** для предавторизации; scope узкий и явный; `aud` = конкретный ресурс (RFC 8707 `resource`); **запрет passthrough** (MCP spec); human-in-the-loop на деньгах и необратимом; TTL минуты; в `core/chatter` пишется и человек, и агент |

## 4. Чек-лист «day-one rules»

1. **Ни один ключ не служит двум назначениям.** Подпись, шифрование, деривация, webhook-HMAC —
   разные ключи. → *OWASP Key Management Cheat Sheet; RFC 8725 §3.1*
2. **Каждый ключ имеет `key_id`, версию формата, метку алгоритма и состояние** из набора
   `pre-activation | active | suspended | deactivated | compromised | destroyed`. → *NIST SP 800-57 Rev.5 §7*
3. **Каждый ключ имеет владельца-человека и срок жизни.** «Бессрочный» и «ничей» — невозможные
   состояния на уровне схемы БД. → *OWASP NHI Top 10 (NHI1, NHI7); Cloudflare 2023*
4. **Криптографический инвентарь ведётся и обновляется**, включая где ключ применять можно и где нельзя.
   → *OWASP ASVS 5.0 §11.1.2 (L2)*
5. **Шифрование полей — только envelope:** root KEK → tenant/purpose KEK → per-record DEK.
   KEK не слабее DEK и хранится отдельно. → *OWASP Cryptographic Storage; PCI DSS v4.0.1 §3.6*
6. **AAD обязателен и включает `tenant_id | entity_type | entity_id | field_name | key_id`.**
   → *ASVS 11.3.3; inference из свойств AEAD (защита от ciphertext swapping)*
7. **IV/nonce — 96 бит CSPRNG, уникальный на каждую (ключ, элемент данных).**
   Один ключ шифрования — не более **2^32** вызовов. → *NIST SP 800-38D §8.3; ASVS 11.3.4*
8. **Формат шифротекста версионированный и самоописывающийся** (`v1:kek_id:alg:…`);
   «дешифруй любой версией, шифруй первичной». → *Google Tink wire format; Vault `vault:vN:`*
9. **Ротация без раскрытия plaintext:** перешифровка — идемпотентный фоновый джоб через
   `rewrap`-подобную операцию. → *HashiCorp Vault Transit*
10. **JWT — асимметрия (ES256/EdDSA) + JWKS + `kid`; отдельная пара ключей на каждую аудиторию.**
    → *RFC 9068; урок Storm-0558 (CSRB)*
11. **Верификатор проверяет `alg` из allow-list, `typ: at+jwt`, `iss`, `aud`, `exp`.**
    `alg: none` невозможен; `jku`/`x5u`/`jwk` из заголовка не поддерживаются вовсе.
    → *RFC 8725 §3.1–3.2, §3.8–3.10; RFC 9068*
12. **Ротация подписи: публикуем ключ → ждём (cache TTL) → подписываем → держим старый
    `cache TTL + max token lifetime + буфер` → удаляем.** → *консенсус практик JWKS `[secondary]`*
13. **Refresh-токены ротируются, повторное использование отзывает всё семейство**, с leeway в
    единицы секунд. → *RFC 9700 §2.2.2; Auth0 reuse detection*
14. **Отзыв многоуровневый:** `tokenEpoch` на пользователя + эпоха на организацию + на ключ/устройство
    + на приложение. Denylist — по `jti`+`iss`, не по хешу токена. → *OWASP JWT Cheat Sheet*
15. **API-ключ: ≥256 бит CSPRNG, префикс `sa6*_`, CRC32-чексум, хранение SHA-256/HMAC-pepper,
    lookup по хешу, constant-time, показ один раз.** → *GitHub token format blog; GitHub Secret
    Scanning Partner Program; консенсус по bcrypt-антипаттерну `[secondary]`*
16. **bcrypt/Argon2 не применяются к высокоэнтропийным ключам** — только к паролям.
    → *OWASP Password Storage (область применения); `[secondary]` по производительности*
17. **PKCE обязателен, redirect URI — exact match, implicit и ROPC отсутствуют,
    токен никогда в query-строке.** → *RFC 9700 §2.1, §2.1.1, §2.1.2, §2.4, §4.3.2; OAuth 2.1*
18. **Access-токен audience-restricted; token passthrough вверх по цепочке запрещён.**
    → *RFC 9700 §2.3; MCP Authorization spec 2025-06-18*
19. **AI-агент = делегирование, не имперсонация:** `subject_token` + `actor_token` → `act`-цепочка;
    эффективное право = `agent ∩ user ∩ tenant ∩ scope`. → *RFC 8693; OWASP LLM Top 10 (LLM06)*
20. **Для денежных и необратимых операций агента — human-in-the-loop и/или sender-constrained токен
    (DPoP/mTLS).** → *RFC 9449; RFC 9700 §2.2.1; OWASP LLM06*
21. **Вебхуки: HMAC-SHA256 по `id.ts.raw_body`, окно 5 минут, секрет на endpoint, ротация двумя
    подписями, constant-time, идемпотентность по `webhook-id`, доставка через `safeFetch`.**
    → *Standard Webhooks spec; Stripe webhooks docs*
22. **Устройства: приватный ключ рождается и умирает в TPM/SE; claim-сертификат уникален на партию;
    операционный сертификат короткоживущий с автообновлением.** → *AWS IoT fleet provisioning whitepaper*
23. **Аттестация устройства всегда с server-nonce** (иначе реплей). → *Apple App Attest / Play
    Integrity practice `[secondary]`*
24. **Ключи не живут в переменных окружения** — файл с правами, смонтированный секрет или запрос к
    KMS на старте. → *OWASP Cryptographic Storage Cheat Sheet (прямой запрет); Secrets Cheat Sheet*
25. **Core dump и heap snapshot выключены на проде; секреты не попадают в ошибки, трейсы, APM.**
    → *урок Storm-0558 `[official CSRB]` + Node/V8 ограничения `[secondary]`*
26. **Ключевой материал — через `KeyObject`/WebCrypto, с `Buffer.fill(0)` в `finally`** (как
    defense-in-depth, не гарантия). → *`[secondary]`, ограничения GC явно признаны*
27. **Dual control (четыре глаза) на операции с ключами + split knowledge (Shamir M-of-N) на корневой KEK.**
    → *PCI DSS v4.0.1 §3.6/§3.7.9; NIST SP 800-57*
28. **Break-glass существует, хранится офлайн, алертит при использовании и регулярно тестируется.**
    → *OWASP Secrets Management Cheat Sheet*
29. **Аудит ключевых событий append-only; в лог никогда не попадает ключевой материал.**
    → *OWASP Key Management + Secrets Cheat Sheets*
30. **Аномалии по ключу отслеживаются** (новый ASN, всплеск, использование после `deactivated`),
    плюс развёрнуты **canary-ключи**. → *`[secondary]`; практика Thinkst/canarytokens*
31. **Secret scanning в CI (gitleaks/trufflehog) + регистрация нашего префикса у GitHub.**
    → *GitHub Secret Scanning Partner Program; Toyota 2022*
32. **dev/stage/prod — непересекающиеся ключи; ни один ключ не переиспользуется между приложениями.**
    → *OWASP NHI8, NHI9*
33. **Crypto-agility заложена сейчас:** смена алгоритма — изменение конфигурации, не переписывание.
    План миграции на PQC — в инвентаре. → *ASVS 11.2.2 (L2), 11.1.4 (L3); FIPS 203/204/205; NIST IR 8547*
34. **Все криптопримитивы ≥128 бит стойкости; сравнения constant-time; ECB и PKCS#1 v1.5 запрещены.**
    → *ASVS 11.2.3, 11.2.4, 11.3.1, 11.3.2*
35. **Runbook на утечку ключа: `revoke → rotate → scan usage → notify → delete везде → post-mortem`,
    отрепетированный.** → *OWASP Secrets Cheat Sheet; CircleCI 2023*
36. **Первичная БД персональных данных граждан РК физически в Казахстане.**
    → *Закон РК №94-V «О персональных данных и их защите», ст.12 п.2 (с 01.01.2016)*

## 5. Ловушки / чего НЕ делать

1. **Не выводить AES-ключ из `JWT_SECRET`.** Это то, что сейчас делает проект, и именно это делает
   ротацию невозможной. Самая дорогая ловушка в списке: чем дольше живёт, тем больше данных
   зашифровано ключом, который нельзя сменить.
2. **Не ротировать вручную.** Storm-0558: Microsoft остановила ручную ротацию после аварии. Ручная
   ротация — это ротация, которая однажды перестанет происходить.
3. **Не считать «ключ не используется» основанием пропустить ротацию.** Cloudflare: 4 из тысяч, и
   этого хватило.
4. **Не проверять только подпись.** Токен с валидной подписью, но чужой аудиторией — это Storm-0558.
   `aud` и `iss` проверяются всегда.
5. **Не брать ключ верификации из самого токена** (`jwk`/`jku`/`x5u`/`kid` без санитизации).
   `kid` — это ввод пользователя, попадающий в запрос к БД/файловой системе.
6. **Не хешировать API-ключи bcrypt'ом.** Платится на каждом запросе, lookup невозможен, выигрыша нет.
7. **Не хранить хеш токена как ключ denylist.** ECDSA-подписи malleable — тот же токен даёт другой хеш.
   Только `jti` + `iss`.
8. **Не использовать `z.coerce.boolean()`-подобные ловушки в верификации** (у нас уже зафиксировано
   правило `queryBoolean`): любая «истинность по умолчанию» в проверке подписи/срока — fail-open.
   Storm-0558 и `core/sign` ревью («`!== false` = fail-open») — про одно и то же.
9. **Не шифровать без AAD.** Расшифровка «просто работает» — и переносит чужие данные в вашу строку.
10. **Не использовать один AES-ключ для всей таблицы.** 2^32 вызовов при случайном IV — достижимая
    величина для большой таблицы; после неё GCM перестаёт быть безопасным.
11. **Не полагаться на `Buffer.fill(0)` как на стирание.** V8 копирует, строки иммутабельны;
    настоящая защита — не держать ключ в процессе приложения (Vault Transit / HSM).
12. **Не класть ключи в переменные окружения** — OWASP прямо перечисляет это рядом с хардкодом.
13. **Не оставлять включёнными core dump/heap snapshot на проде.**
14. **Не проверять подпись вебхука по распарсенному телу.** Только raw body (Stripe об этом пишет
    отдельным предупреждением).
15. **Не ставить tolerance = 0** для timestamp вебхука — это отключает проверку свежести целиком.
16. **Не принимать схемы подписи, кроме `v1`** — downgrade-атака.
17. **Не слать секрет вебхука в payload** и не переиспользовать один секрет на несколько получателей.
18. **Не делать имперсонацию для AI-агентов.** Если в аудите нельзя отличить агента от человека —
    расследование инцидента невозможно, а LLM06 становится неограниченным.
19. **Не пробрасывать входящий токен во внешние API** (token passthrough) — MCP-спека это прямо
    запрещает, это классический confused deputy.
20. **Не считать IP allow-list контролем доступа.** Это сигнал риска, не граница.
21. **Не выдавать одному ключу все права** («god key»), не переиспользовать ключ между dev/prod
    и между приложениями.
22. **Не зашивать общий claim-ключ на весь тираж устройств.** Уникальность на партию — минимум,
    уникальность на устройство — цель.
23. **Не строить отзыв устройств на CRL/OCSP**, если можно обойтись короткоживущими сертификатами:
    инфраструктура отзыва, которой никто не пользуется, — фикция.
24. **Не обещать crypto-shredding, если бэкапы хранилища ключей переживают удаление.**
25. **Не логировать ключевой материал «временно, для отладки»** — логи переживут отладку.
26. **Не разрешать человеку работать сервис-аккаунтом** (NHI10) — теряется атрибуция, и это ровно
    то, через что прошла Okta.
27. **Не совмещать роли кастодиана ключа и администратора системы** — dual control превращается в
    формальность.
28. **Не внедрять PQC сейчас в продакшн-подписи**, но и не проектировать так, что смена алгоритма
    потребует переписывания: `kid` + метка алгоритма + версия формата закрывают это малой кровью.

## 6. Открытые вопросы (не подтверждено первичным источником)

1. **[КРИТИЧНО, Казахстан] Обязано ли SuperApp6 применять сертифицированные СКЗИ / ГОСТ-алгоритмы?**
   Установлено: ПП РК №832 «Единые требования в области ИКТ и обеспечения ИБ» распространяется на
   госорганы, квазигоссектор, **владельцев/операторов негосударственных ИС, интегрируемых с
   государственными или формирующих государственные электронные ресурсы**, объекты КВОИКИ и
   оперативные центры ИБ (п.2); п.48 требует применения СКЗИ по **СТ РК 1073-2007** для защищаемой
   информации; п.6(1) даёт определение СКЗИ; п.46 — требования к применяемым СКЗИ.
   **Не подтверждено:** попадает ли SuperApp6 в периметр из-за интеграции с ЭЦП НУЦ РК и ЭДО
   (является ли это «интеграцией с государственной ИС» в смысле п.2). Это **юридический вопрос,
   а не технический** — нужна консультация казахстанского юриста по ИБ. Текст ПП 832 извлечён
   через зеркало `cdb.kz`, официальный `adilet.zan.kz` в этой сессии не отдался — **формулировки
   требуют сверки по adilet.**
2. **[Казахстан] Статус СТ РК 1073-2007.** Вторичный источник указывает, что действие стандарта
   **прекращается с 01.01.2027** приказом Комитета техрегулирования и метрологии МТИ РК от 25.09.2025.
   Чем он заменяется — не установлено. Требует проверки.
3. **[Казахстан] Криптостандарт НУЦ РК.** Есть указание на переход НУЦ РК на
   **СТ РК ГОСТ Р 34.10-2015** (старые ключи ЭЦП работают до конца срока). Точная дата перехода и
   требования к клиентским библиотекам (KalkanCrypt SDK) не подтверждены первичным источником

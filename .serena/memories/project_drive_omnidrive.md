# OmniDrive («Диск») — сервис, построен 2026-08-01

B2C + B2B в одном сервисе: пространства, папки, шеринг, корзина, версии, лента «Фото».
`verify-drive.cjs` 84/0, весь сьют (56 скриптов) зелёный, `nest build` + web `tsc` чисты.

## Несущая идея

Диск — **слой имён и дерева поверх `core/files`**, а не второе хранилище. Байтами, квотой,
вариантами и антивирусом по-прежнему владеет движок файлов. Файл в чате и на Диске — ОДИН
`FileObject` с двумя `FileLink`: байты не копируются, квота не удваивается, правка через
`core/docs` видна во всех местах сразу.

## Права: кто что делает

| Слой | Обязанность |
|---|---|
| `core/access` | ХРАНИТ прямые гранты `drive_node:<id>#viewer\|editor\|manager@…` |
| `AccessService.grantSetFor(userId, type)` | **новый второй читающий путь движка**: принципалы + выданные id, 2 индексных запроса, ЛЕСТНИЦА РОЛЕЙ разворачивается ВНУТРИ метода (`ROLE_LADDERS`) |
| `DriveAccessService` | превращает грант-сет в SQL-предикат и считает права на узле |

Предикат: `владелец пространства OR n.id = ANY(:granted) OR n.ancestor_ids && :granted`.

**Почему не рекурсия в движке** (`arrow('parent', …)`): у папки до 32 предков — обход стоил бы
десятки запросов на КАЖДУЮ проверку, `MAX_DEPTH` фейлится молча, а тип-эпоха кэша сбрасывала бы
ACL всей платформы при каждом шеринге. Прецеденты «движок хранит, домен считает массово» уже
были: closure отделов и поиск сообщений (`JOIN chat_members`).

**`EPOCH_FANOUT: { drive_space: [], drive_node: [] }` — пустой, и это НЕ забывчивость.** Диск не
пользуется кэшируемым `check()`/`can()` вообще; строки обязаны существовать, потому что
незамапленный тип бьёт ГЛОБАЛЬНУЮ эпоху. Следствие: у rich card Диска НЕТ действий (движок
перепроверял бы способность через `can()` и видел бы протухший ответ до 10 минут).

## Модель

- `DriveSpace` (personal|workspace, лениво, `@@unique(ownerType,ownerId,kind)`; `rootId` без FK — цикл создания)
- `DriveNode`: `ancestorIds[]` (GIN) + `depth` ≤32 + `sortRank` (0=папка) + `nameKey` (NFC+lower,
  частичный unique «одно имя в папке» WHERE не в корзине) + `subtreeBytes` с СЕНТИНЕЛОМ `null` =
  «пересчитать» + `takenAtLocal` (стенное время съёмки) + `systemKey` + `trashedRootId`
- `DriveNodeVersion` / `DriveStar` / `DriveRecent` / `DrivePhotoBucket`
- Руками в миграции: `CREATE COLLATION natural_ru (icu, 'ru-RU-u-kn')` + коллация НА КОЛОНКЕ
  `name`, партиальные индексы листинга с ТОЧНЫМ направлением, GIN по предкам, unique имени

## Ловушки, которые уже стоили времени

1. **Prisma дропает GIN-индекс.** Партиальные (WHERE) он не видит и не трогает, а GIN выразить
   умеет — и на следующем `migrate dev` пишет `DROP INDEX`. Лечение: объявить в schema.prisma
   `@@index([ancestorIds(ops: ArrayOps)], map: "drive_anc", type: Gin)`. Коллация дрейфа НЕ даёт.
2. **Гонка ingest ↔ удаление сообщения.** Джоб читает файл вне транзакции, а соседняя транзакция
   его soft-удаляет: снимок нашей транзакции чужого удаления не видит → узел на мёртвый файл.
   Лечение: `SELECT … FOR UPDATE` строки файла + перечитать статус ПОД замком; в обработчике
   `NotFoundException` → тихий выход (постоянный отказ, не инцидент).
3. **`resolveSpace` должен брать пространство ИЗ РОДИТЕЛЯ.** Иначе «открыть чужую расшаренную
   папку» уходит в СВОЙ диск и падает «папка с другого диска» (400 вместо содержимого).
4. **Файлы перестали быть сиротами.** С автоскладыванием у файла всегда есть дом, и сьюты
   движка («не осталось мест → файл прибран») ломаются. Помощник `scripts/drive-test-helpers.cjs`
   → `dropFromDrive(prisma, fileId)` честно доводит посылку до правды. Имя файла НЕ `verify-*`,
   иначе CI прогонит его как сьют.
5. **`readEntries()` отдаёт максимум 100 записей за вызов** и не сообщает, что есть ещё —
   однократный вызов молча грузит ровно первые сто файлов папки.
6. **Фикстура членства в организации обязана писать и ребро в `core/access`** (`staff → member`):
   при настоящем найме его пишет проекция, без него команда не совпадает с корневым грантом.
7. **`pkill` не убивает Windows-процессы.** Перезапуск API — только через PowerShell
   `Stop-Process`, иначе тестируешь СТАРУЮ сборку и чинишь несуществующее.
8. Виртуализация в скрытой панели предпросмотра (`document.hidden`) не рисует НИЧЕГО — rAF и
   ResizeObserver заглушены. Это артефакт среды, а не баг (то же было на ленте мессенджера).

## Изменения в движках (переиспользуемые)

- `FilesRefRegistry.registerLinkObserver(key, {onLinked})` — ГЛОБАЛЬНЫЙ наблюдатель привязок
  (резолвер принадлежит чужому refType, подписаться в нём нельзя). Зовётся из `linkFile` и
  `linkManyInTx` — внутри транзакции, чтобы джоб уехал тем же коммитом. `linkSystemInTx` НЕ зовёт.
- `StorageDriver.copy` (S3 CopyObject / fs.copyFile) + `FilesService.copyFile` — копия без
  прогона байтов через приложение.
- `FilesService.getUsageFor(ownerType, ownerId)`, `systemDeleteFile(fileId)`.
- `canView`: ветка «член организации видит любой её файл» ВЫКЛЮЧАЕТСЯ, если у файла есть связь
  `drive_node` (решение пользователя: на диске организации решают папки).
- `FILE_LIMITS.apiSingleRequestMax` = 200 МБ — потолок ОДНОГО запроса (multer, приёмник правок
  WOPI); `hardMaxSize` = 2 ГБ ограничивает только Zod-схему и multipart-путь.
- Квоты: **15 ГБ человеку / 100 ГБ организации**.
- Конвейер картинок считает EXIF (`takenAtLocal`, стенное время) и `thumbhash`.

## Решения продукта (утверждены пользователем)

- **Права внутри диска организации — строгие**: решают папки, а не «ты сотрудник».
- **Между пространствами — «Копировать»**, оригинал остаётся (у движка нет смены владельца).
- Квоту при загрузке в чужую папку платит ЗАГРУЗИВШИЙ (модель Google Drive).
- Автоскладывание файлов из переписки — без тумблера (модель Teams). Из DM — ВСЕГДА на личный
  диск, даже в рабочем контексте.
- Окончательное удаление гасит файл ВЕЗДЕ (Google Drive / Teams); корзина 30 дней занимает место.

## Не в v1 (осознанно)

`core/share-links` (гостевые ссылки наружу) — отдельная задача и следующий шаг документной
вертикали. Ярлыки (`kind='shortcut'`) — колонка есть, интерфейса нет. В «Фото» нет поиска
дубликатов и распознавания лиц.

## Ревью Диска (2026-08-01) — 15 находок, все закрыты

Сквозное ревью сразу после стройки; две самые острые дыры подтверждены живьём на аккаунтах
сьюта, регрессии на КАЖДУЮ дописаны в `verify-drive.cjs` (+15 чеков, ALL PASS).

**Критично — `placeFile` не проверял ПРАВО НА ФАЙЛ.** `POST /drive/nodes` принимал любой
`fileId`: связь писалась через `linkSystemInTx`, у которого (в отличие от `linkFile`) проверки
владения нет. Зная чужой id — а он остаётся у всех, кто когда-то имел доступ, — человек получал
полный набор: прочитать, переписать через `core/docs` и **уничтожить у владельца везде** (узел =
дом файла). Ровно та дыра, что закрывали в ревью core/docs, зашедшая через системный вариант.
Теперь правило внутри `placeFile`: свой файл → СВЯЗЬ (те же байты), чужой видимый → КОПИЯ на
свою квоту, невидимый → 404. Копия запрещена внутри чужой транзакции (сетевой вызов держал бы
замки). Дедуп «тот же файл дважды» сужен с пространства до ПАПКИ — прежний вариант возвращал
узел из папки, которой человек не видит, раскрывая её имя и путь.

**`share()` проверял только `principalType === 'user'`.** Остальные пять типов принимались как
есть: указав ЧУЖУЮ Группу, человек раздавал личный файл людям вне окружения (проверено —
участник чужой Группы читал и переименовывал папку), указав отдел чужой организации — пробивал
B2B-изоляцию; вдобавок `PersonalGraphRegistry` снимает только `user`-рёбра, так что грант
пережил бы и удаление контакта, и блок. Теперь `assertPrincipalAllowed`: личный диск — человек
из окружения и СВОЯ Группа; диск организации — её сотрудник и её же оси.

**Удаление навсегда в организации — теперь manager+.** `purge` требовал `editor`, а корень
раздаёт `editor@workspace#member`: любой Стажёр мог необратимо стереть рабочие файлы вместе с
байтами во всех чатах. Корзина по-прежнему доступна редактору.

**Остальное:** сортировка «по размеру» обрывала список на первой грязной папке (сентинел
`subtree_bytes = NULL` кодировался курсором как «0» → следующая страница просила `< 0`) — теперь
NULLS LAST и двухфазный keyset; `restore` версии мог удалить саму возвращаемую версию (снимок →
ретеншн по бюджету) — байты читаются ДО снимка + `protectVersionId`; `touchRecent` не вызывался
ниоткуда, раздел «Недавние» был пуст всегда (0 строк в БД) — зовётся при открытии объекта,
ретеншн 90 дней; курсор корзины без тай-брейка по id перепрыгивал пачку с одинаковым `trashedAt`;
`move`/`copy` не переиндексировали поиск; месяц в ленте «Фото» фильтровался `to_char(...)=` (не
sargable — прыжок в старый месяц читал всё, что новее); счётчики месяцев считались по всему
пространству мимо прав; `canViewFile` искал drive-связь в выборке с `take: 50` (у файла с
длинным хвостом связей закрытая папка снова открывалась команде); `copyFile` терял `meta`
исходника (лента «Фото» получала копию без даты и соотношения сторон); N+1 имён в `listShares`;
`distinct` после `take` в кроне роллапов (одно активное пространство вытесняло остальные);
сверка бакетов «Фото» читала таблицу целиком в приложение — теперь один INSERT … ON CONFLICT.

**Чего не хватало сьюту** (86 чеков и всё мимо дыр): приложение чужого `fileId` через явную
ручку (проверялась только авто-укладка), шеринг на не-свой принципал, право на `purge` в
организации, вторая страница листинга, «Недавние».

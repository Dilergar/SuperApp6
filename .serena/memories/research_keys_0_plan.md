## 1. Контекст — зачем

- `JWT_SECRET` — мастер-ключ **девяти** потребителей: подпись access/refresh (HS256), WOPI-токены, гостевые пропуска share-links, подписанные ссылки файлов, HMAC OTP-кодов `core/verify`, state Google OAuth, сейф кредов Процессов (AES), карты PAN/IBAN (AES), dev-секрет кабинета. Один ключ = подпись + шифрование + деривация (нарушение OWASP KM и RFC 8725 §3.1) → **ротация невозможна**.
- Google OAuth-токены (`GoogleConnection`) открытым текстом; AES-поля без AAD (шифротекст переносим между строками/организациями); ключи производные от `JWT_SECRET`.
- Программного доступа нет: ни API-ключей организаций, ни сервисных аккаунтов, ни исходящих вебхуков; входящие вебхуки Процессов — токен в URL без подписи, Telegram без `secret_token`.
- Refresh-токены без reuse-detection (RFC 9700 §2.2.2); step-up только SMS.
- **Юридически (КЗ):** Приказ МЦРИАП № 179/НҚ от 12.06.2023 (ред. 2026): хранение и передача ПДн ограниченного доступа — СКЗИ не ниже 3-го уровня по СТ РК 1073-2007 (отменяется 01.01.2027 → СТ РК 1073-2025), журнал действий пользователей с доступом к ПДн, БД в РК (94-V ст. 12). Подтверждено двумя зеркалами текста; adilet не отрендерился — **сверка юристом до прод-запуска обязательна**. ПДн (телефон, ИИН, ДР, карты, реквизиты) сегодня лежат открытым текстом.
- Дорожная карта: AI-агенты (делегирование), mobile, Терминал/IoT, «открытая платформа», 1С/Kaspi — все требуют одного движка ключей.

## 3. Архитектура

### 3.1 Иерархия ключей и формат

```
root key (файл KEYS_ROOT_KEY_FILE | pkcs11)            ← провайдер, вне БД
  └─ CryptoKey purpose=kek  scope=platform | workspace:<id> | user:<id>   (обёрнут root)
       └─ DEK на запись (AES-256-GCM, inline, обёрнут KEK)
  └─ CryptoKey purpose=sign scope=platform audience=<product|platform|wopi|share_link|files_url|webhook>   (Ed25519, приватный обёрнут root)
  └─ CryptoKey purpose=mac  scope=platform name=<blind_index|verify_otp|oauth_state|api_key_pepper>
```

- Prisma: `CryptoKey` (id, scope, purpose, name/audience, algorithm, provider, primaryVersionId, createdAt) → `CryptoKeyVersion` (id = `kid`, version, state `pending|active|disabled|destroy_scheduled|destroyed`, wrappedMaterial bytes, publicKey?, activatedAt, deactivatedAt, destroyScheduledAt, destroyedAt). Имена не переиспользуются, версии только растут; восстановление из `destroy_scheduled` → `disabled` (модель Google).
- Формат шифротекста (text-колонка): `sa6e:1:<kek_kid>:<alg>:<wrappedDek>:<iv>:<ct+tag>` (base64url). AAD = `entity|field|ownerType|ownerId|kek_kid` — не хранится, не логируется. «Расшифруй любой активной/disabled-for-decrypt версией, шифруй primary».
- Слепой индекс: `sa6b:1:<mac_kid>:<base64url HMAC-SHA256(normalized)>`; unique-колонки `*_bi`; ротация mac-ключа = полный re-index джобом (только при компрометации).
- Кэш: распакованные KEK в памяти процесса, TTL 5 мин, сброс при ротации/заморозке (`keys:epoch` в Redis).
- Kill-switch: `disable` KEK организации → данные организации нечитаемы мгновенно; **автоудаления при недоступности ключа нет никогда**.
- Провайдер: `interface KeyProvider { wrap, unwrap, sign, verify, generate }` — `SoftwareProvider` (файл) и заглушка `Pkcs11Provider` (интерфейс + smoke, без реализации). Верификатор JWT — allow-list `['EdDSA']` (+`HS256` только legacy-окно), `alg: none` и ключ из заголовка (`jku`/`jwk`/`x5u`) невозможны; `kid` санитизируется до запроса в БД.
- **Корневой ключ: церемония, бэкап, break-glass.** `keys-init-root.cjs` генерирует файл (32 байта CSPRNG, права 0600) и печатает инструкцию: две офлайн-копии у двух разных людей (владелец + доверенное лицо; split knowledge по PCI DSS 3.6), отпечаток (SHA-256) файла хранится в кабинете платформы для сверки. `keys-verify-root.cjs` — учение восстановления: поднять API с копией → расшифровать контрольную запись. Потеря корня = потеря всех данных, поэтому учение обязательно перед прод-запуском и раз в квартал (запись в roadmap). Ротация корня — команда кабинета `keys.root.rotate` (dualControl): новый файл → rewrap всех KEK/sign/mac → старый файл уничтожается только после подтверждения.
- **Fail-closed env**: production требует `KEYS_PROVIDER` ∈ {`software`,`pkcs11`} и читаемый `KEYS_ROOT_KEY_FILE` (для `software`); отсутствие = бут не поднимается; `JWT_SECRET_LEGACY` в проде допустим только пока не истёк `KEYS_LEGACY_HS256_UNTIL` (дата в env), после — ошибка бута.
- **Секреты не текут**: отдельного логгера в API нет (Nest `Logger`), поэтому — хелпер `redactSecrets()` в `shared/utils` (маска `sa6_[a-z]+_[a-z]+_…`, `Bearer …`, `Authorization`) обязателен во всех местах, где в лог попадают заголовки/тела запросов (`AllExceptionsFilter`, логи вебхуков и джобов); ESLint-страж на `req.headers.authorization` в логах; `AllExceptionsFilter` никогда не эхоит входящий токен; AAD и plaintext DEK в логи не пишутся; core dump/heap snapshot на проде выключены (документируется в `security.md`, урок Storm-0558).
- **Crypto-shredding**: `purgeWorkspace` → KEK организации `destroy_scheduled` (30 дней, как срок архива) → `destroyed`; анонимизация аккаунта → KEK человека `destroy_scheduled`; бэкапы БД содержат только обёрнутые KEK, поэтому уничтожение версии в keystore делает данные нечитаемыми и в бэкапах (при условии, что бэкап keystore подчиняется тому же удалению — правило для ops-дока).

### 3.2 Токены и подписи

- `KeysSigningService.sign(audience, payload, {ttl})` / `verify(audience, token)` — JWT `alg: EdDSA`, `kid`, `typ: at+jwt` для access, `aud` обязателен; JWKS `/.well-known/jwks.json` (`@Public`, cache 10 мин) со всеми активными и «на выводе» версиями. Ротация: новая версия `pending` → публикация в JWKS → через ≥ TTL кэша `active` → старая `disabled` через (кэш + макс. срок токена) → destroy. Верификатор при неизвестном `kid` — однократный re-fetch с rate-limit.
- Миграция: верификатор принимает HS256 (`JWT_SECRET`) и EdDSA одновременно 30 дней (срок refresh), затем HS256 выключается и `JWT_SECRET` уходит из env-схемы (остаётся `JWT_SECRET_LEGACY` на окно).
- Refresh: `Session.familyId` + `rotatedAt`; предъявление прокрученного токена вне grace 10 с → отзыв семейства + `auth.session.reuseDetected` владельцу.
- Аудитории: product (`core/auth`), platform (`core/platform`), wopi (`DocsTokenService`), share_link (`ShareLinksTokenService`), files_url (`FilesUrlService`), webhook (Ed25519-опция). HMAC-потребители: `verify` (OTP), `oauth_state` (Google), `api_key_pepper`.

Заморозка = ключи бота отвечают `403 keys.bot.frozen`; разморозить может только owner (команда с step-up, запись в журнал).

(personal в контексте организации — только owner/admin; null = собственные данные человека), familyId, name, purpose (обязателен), prefix, last4, hash, scopes JSON, ipAllowlist JSON, expiresAt, lastUsedAt, lastUsedIp, lastUsedCountry, useCount, revokedAt, revokedReason, rotatedFromId, graceUntil, createdById, createdAt). Партиальный уникум: ≤ 2 живых ключа на familyId. Создание любого ключа с `workspaceId` — гейт ролью owner/admin (`403 keys.role_required`), остальные не видят раздела.

Deny-by-default.
- Chokepoint: для бота `activeWorkspaceId = key.workspaceId`, `role = bot.rank`; `X-Workspace-Id`, если прислан, обязан совпасть. Для personal-ключа — роли человека как сегодня.

### 3.4 Исходящие вебхуки (`core/webhooks`)

- `WebhookEndpoint` (id, workspaceId, url, events JSON, signing `hmac|ed25519`, secretEnc (через движок), prevSecretEnc, prevExpiresAt, status `pending_verification|active|disabled`, failures, disabledAt, disabledReason, createdById) · `WebhookDelivery` (id, endpointId, eventKey, payload JSON, attempts, nextAt, status, lastStatus, lastError).
- Реестр событий `packages/shared/src/webhooks/<service>.ts` (`defineWebhookEvents`), первые продюсеры: tasks (`task.created|completed|cancelled`), documents (`document.registered|signed`), workspaces (`member.joined|left`); продюсер зовёт `webhooks.emit(tx, {workspaceId, eventKey, payload, ref})` в транзакции мутации → строки `WebhookDelivery` + `core/jobs` `webhooks.deliver` (идемпотентный, backoff до 3 суток, 3xx = провал, только https, `safeFetch`).
- Подпись Standard Webhooks: заголовки `webhook-id`, `webhook-timestamp`, `webhook-signature` (`v1,<b64>` для каждого активного секрета; `v1a,` для Ed25519), подписываемая строка `id.ts.raw_body`; секрет `sa6_whs_…` показывается один раз; ротация — новый секрет + prev живёт до 24 ч.
- Верификация endpoint'а при создании (challenge `ping` → эхо) и **периодический аудит битой подписью** (джоб раз в сутки: 2xx на невалидную подпись → endpoint `disabled` + `webhook.endpoint.disabled` владельцам) — модель Discord.
- Входящие (Процессы): `secret_token` при `setWebhook` Telegram + проверка заголовка; `webhookToken` хранится хешем (lookup по хешу), в URL остаётся сам токен.

### 3.5 Шифрование ПДн (фаза D)

- Колонки: `<field>_enc` (text) + `<field>_bi` (text, unique/индекс там, где искали по plaintext): `users.phone|iin|email` (bi unique), `users.dateOfBirth|residentialAddress|idDocNumber|idDocIssuedBy` (enc), `contact_invitations.toPhone`, `workspace_invitations.toPhone`, `verify_challenges.phone`, `share_link_guests.phone` (enc+bi), `user_payment_cards.pan|iban` (перевод на движок, AAD), `workspace_bank_accounts.iban`, `counterparty_bank_accounts.iban`, `counterparties.phone|email`, `counterparty_contacts.phone|email` (enc; bi для phone контрагента), `sign_acts.certSubjectIin` (enc+bi, индекс «все подписи ИИН»).
- Миграция без простоя: (1) добавить колонки; (2) двойная запись + чтение по старым; (3) бэкфилл джобом (батчи, идемпотентно, прогресс); (4) переключить чтение/поиск на `_bi`/`_enc`; (5) дроп plaintext-колонок отдельной миграцией после сверки. Все точки поиска по равенству — через `keys.blindIndex('phone', normalizePhone(v))` (14 точек в contacts, 7 в workspaces, 3 verify, 3 auth, users lookup, platform lookup по номеру/ИИН, sign сверка ИИН). `analytics.ingest` `internalPhonePrefixes.startsWith` → по расшифрованному номеру консьюмера (сервер).
- Журнал действий с ПДн (требование 179/НҚ): чтение расшифрованных полей ПДн через один хелпер `keys.readPii(ctx, …)`, который пишет агрегированную запись в `pii_access_log` (кто, какую сущность, какие поля, когда; батч на запрос) — retention по политике; в кабинете платформы уже есть `PlatformAccessLog`.
- Уникумы и индексы переезжают на слепые: `users.phone @unique` → `phone_bi @unique`, `users.email @unique` → `email_bi @unique`; партиальные уникумы `contact_invitations_one_pending_per_phone (from_user_id, to_phone)` и активная цепочка `verify_challenges (phone, purpose)` → по `*_bi` (руками в миграции + коммент в схеме, прецедент approvals); индексы `contact_invitations(to_phone)`, `sign_acts(cert_subject_iin)` → по `*_bi`. Нормализация до индекса: телефон E.164 (`normalizePhone` из shared), ИИН — 12 цифр, e-mail — lower-case/trim.
- Производительность чтения: расшифровка списков (ростер 100 строк, Окружение 100/страница) — один unwrap KEK из кэша на организацию/человека, дальше AES в памяти (микросекунды на поле); `readPii` принимает массив строк и расшифровывает батчем, а не в цикле по одной. Логин/поиск — один HMAC.
- Dual-write окно: пока читаем старые колонки, `keys` пишет обе; переключение чтения — фича-флагом `KEYS_PII_READ_MODE=legacy|encrypted` на один деплой; дроп plaintext — отдельная миграция после `verify-keys-pii.cjs` на проде.

### 3.7 Масштабируемость и эксплуатация

- Горизонтально: в процессе только кэши (распакованные KEK, JWKS, результат проверки ключа 60 с в Redis по образцу `auth:alive`), инвалидация через эпоху `keys:epoch` в Redis (как `EPOCH_FANOUT` у access); любой инстанс читает keystore из Postgres; HSM-вызовы — один unwrap на KEK на 5 минут, не на запрос.
- Запись: `last_used_at`/`use_count` — батч раз в 60 с из Redis (без write amplification); `ApiAccessLog` и `pii_access_log` — партиции по месяцам (прецедент `core/analytics`), retention кроном; `KeyAuditEntry` — вечный append-only, объём мал.
- Фон: `keys.rewrap`/`keys.reindex`/бэкфилл ПДн — батчи по 500 строк с курсором, идемпотентно, прогресс в строке джоба, своя очередь (тяжёлый тип → своя очередь, правило `jobs_engine.md`); доставка вебхуков — своя очередь, backoff, потолок попыток.
- Лимиты: троттлер по ключу (RedisThrottlerStorage, ключ = `apiKey:<id>`), отдельный счётчик 401/403 на IP+префикс, потолок объёма выгрузки на ключ в сутки (аномалия Salesloft) → 429 + `key.newLocation`-класс уведомления.
- Crypto-agility: алгоритм и `kid` в каждом артефакте (шифротекст, слепой индекс, JWT header, подпись вебхука `v1`/`v1a`); смена алгоритма = новая версия ключа + перешифровка джобом, без правки схемы; заделы PQC — только метки.
- Мультиарендность: KEK на организацию и на человека → взрывной радиус утечки одного KEK = один субъект; заморозка/шреддинг — на уровне KEK; AAD несёт владельца → перенос шифротекста между арендаторами невозможен криптографически, не только проверкой в коде.
- Наблюдаемость: метрики `keys_unwrap_total`, `keys_decrypt_latency`, `keys_cache_hit`, `webhooks_delivery_fail`, событие `keys.root.missing` при старте; dev-полигон `keys.dev.ts` для учений ротации.

### 3.8 Сверка с каноном безопасности и законами РК

| Требование | Где в плане |
|---|---|
| Один ключ — одно назначение (OWASP KM, RFC 8725 §3.1) | §3.1 иерархия: kek / sign / mac — разные ключи; `JWT_SECRET` уходит |
| Ключ имеет `kid`, версию формата, алгоритм, состояние (SP 800-57 §7) | `CryptoKeyVersion.state`, формат `sa6e:1:<kid>:<alg>:…` |
| Ключ имеет владельца и срок (OWASP NHI1/NHI7) | `ApiKey.expiresAt` NOT NULL кроме owner-исключения; бот → организация + owner/admin; реестр |
| Envelope + AAD + IV CSPRNG, ≤ 2^32 на ключ (SP 800-38D) | DEK на запись, AAD `entity|field|owner|kid` |
| Асимметрия + JWKS + отдельная пара на аудиторию (Storm-0558) | §3.2 |
| Refresh rotation + reuse detection (RFC 9700 §2.2.2) | §3.2 `familyId` |
| API-ключ ≥ 256 бит, префикс + CRC32, хеш-хранение, show-once (GitHub) | автодефолты, `ApiKey.hash` |
| Право ключа = скоуп ∩ права носителя ∩ организация, 401 ≠ 403 (Shopify, MCP) | скоуп-гард + chokepoint |
| Отзыв многоуровневый: на ключ, на человека (`tokenEpoch`), на организацию (freeze KEK), на бота | каскады §3.3, kill-switch §3.1 |
| Вебхуки: подпись по сырому телу + timestamp, секрет на endpoint, ротация двумя подписями, safeFetch, аудит битой подписью | §3.4 |
| Dual control на ключевые операции, split knowledge на корень (PCI DSS 3.6/3.7) | команды кабинета `dualControl`, церемония §3.1 |
| Break-glass и учение восстановления | `keys-verify-root.cjs`, roadmap |
| Аудит append-only, ключевой материал в лог не попадает | `KeyAuditEntry` + маскирование логгера |
| Секреты не в env (OWASP) | корень — файл; `.env`-секреты сайдкаров — записанный долг |
| Crypto-agility / PQC-заделы (ASVS 11.2.2) | §3.7 |
| **Закон 94-V ст. 12** — БД в РК | хостинг (roadmap, вне движка) |
| **Приказ 179/НҚ**: СКЗИ ≥ 3 уровня для ПДн ограниченного доступа | разъём под сертифицированный провайдер; список полей §3.5; **юрист до прод-запуска** |
| **Приказ 179/НҚ**: журнал действий пользователей с доступом к ПДн | `pii_access_log` + `PlatformAccessLog` |
| **Приказ 179/НҚ (изм. 100/НҚ 2024)**: уведомление уполномоченного органа об инциденте в 1 рабочий день; интеграция с государственным сервисом контроля доступа (ГСКД) | не предмет движка; в roadmap «прод-минимум» + вопрос юристу: обязательна ли ГСКД частному оператору |
| **ПП РК № 832** — периметр «ИС, интегрируемых с государственными» (НУЦ РК, ЕСУТД, Smart Bridge) | вопрос юристу; движок агностичен к алгоритму |
| PCI DSS (храним PAN без CVV как реквизит выплат) | PAN/IBAN под движком, KEK человека, AAD; применимость PCI — вопрос юристу |
| СТ РК 1073-2007 → 1073-2025 с 01.01.2027 | провайдер `pkcs11`/ГОСТ — по заключению, до 2027 |

## 5. Проверка

1. `pnpm check:docs`, `pnpm check:i18n`, `pnpm check:analytics`, `pnpm lint:guard` (страж `JWT_SECRET` — подсадить нарушение → красный → убрать).
2. Сборка: `packages/shared → i18n → api-client → nest build` (PowerShell), `prisma migrate deploy`, `keys-init-root.cjs`, старт API; бут-смоук ключей.
3. Сьюты: `verify-keys.cjs`, `verify-keys-pii.cjs`, `verify-webhooks.cjs` + полный существующий сьют (auth/otp/share-links/docs/processes/wallet-cards/google state) — токены старого формата читаются в окне миграции.
4. Учения: ротация ключа подписи (старые access живут до `exp`, refresh — до окна), ротация KEK организации (rewrap-джоб, старые шифротексты читаются), freeze организации (403 + разморозка), reuse refresh → семейство отозвано + уведомление, сотрудник/менеджер создаёт ключ организации → `403 keys.role_required` и раздела в навигации нет, человек создаёт личный ключ для собственных данных → работает лично и отвергается с `X-Workspace-Id`, ключ бота с IP-allowlist с чужого IP → 403 + `key.newLocation`, `POST /keys/leaked` → отзыв + уведомление, уход админа (каждый путь: исключение, выход, увольнение по ТК, понижение) → его personal-ключ мёртв, его боты `frozen` + `bot.frozen` владельцу + значок в шапке → owner размораживает (step-up) → бот снова работает, запись в журнале; реестр показывает кто/когда/для чего и фильтры.
5. Браузер: раздел «Интеграции и ключи» организации и «Ключи и приложения» профиля, show-once, матрица скоупов, бот-чип в хронике; 0 ошибок консоли; mobile 375px.
6. Сверка плана построчно (опаснее всего «бэкенд есть, веб не зовёт»).

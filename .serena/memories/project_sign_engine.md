# core/sign — движок электронной подписи (15-й платформенный, 2026-08-09)

Шаг 3 документной вертикали: «Диск → шаблоны → **подпись** → ЭДО → КЭДО».
До него подпись была `ApprovalDecision.signatureKind='internal'` — нажатие
кнопки в «Ждут решения», юридической силы ноль.

Проверено: `verify-sign.cjs` **132 PASS / 0 FAIL** (идемпотентен к повторным
прогонам) + регрессии approvals / documents / share-links / otp / processes /
drive / files / doc-builder / templates / jobs / chatter + браузер (подпись ПЭП
сквозь, QR через мост, публичная `/check`) — консоль чиста в свежей вкладке.
Сборки shared → api-client → api → web tsc → eslint чистые.

## Юридическая рамка

**Цифровой кодекс РК № 255-VIII** (с 12.07.2026; закон об ЭЦП № 370-II утратил
силу). **ЭЦП** — ст. 49, ключ НУЦ (QR eGov Mobile / NCALayer), обязательна для
кадровых (ст. 33 ТК РК), ЭСФ, госорганов. **ПЭП** («цифровое подтверждение») —
ст. 46 п. 4 + ст. 47, SMS-код после цифровой аутентификации, достаточна для
гражданско-правовых **по соглашению сторон**.

Закрыто: цепочка+OCSP+TSP на момент подписания (приказ № 1187) — заморожены в
акте; открытая проверка (ст. 61) — `/check`; жизнь вне системы (ст. 62) —
экспортный ZIP; согласие на ПД «способом, позволяющим подтвердить» (ст. 8 ЗоПД) —
снимок текста в акте + событие протокола; хранение = сроку документа
(приказ № 279-НК) — таблицы вечные.

## Два несущих решения

**1. Движок САМ замораживает то, что подписывает.** PDF документа существует
лишь ВАРИАНТОМ файла и умирает при первой правке исходника (`replaceContent`
сносит производные). Поэтому байты копируются в отдельный неизменяемый файл
(профиль `sign_subject`), подписант видит ЭТУ копию, над ней же считается CMS.
Проверено прямо: сьют удаляет исходник и убеждается, что копия цела и её байты
совпадают с отпечатком.

**2. Доказательства ЗАМОРАЖИВАЮТСЯ.** `chainValid`, `ocspStatus/At`, `tspAt` —
поля акта, записанные в момент подписи. Через год сертификат истечёт, и живая
проверка не докажет ничего. Юридическое время подписи = метка TSP.

## Модель

`SignRequest` (предмет БЕЗ FK + снимок названия, `subjectFileId`+`subjectSha256`,
`level`, `methods`, `approvalStepId?`) · `SignAct` (подпись одного лица; ЭЦП:
`cmsFileId`/`cert*`/`chainValid`/`ocsp*`/`tsp*`; ПЭП: `verifyChallengeId` +
**`consentText`+`consentVersion`** — снимок соглашения, ссылка на «текущую
редакцию» доказательством не является; `checkToken @unique` — печатается в QR
протокола) · `SignActEvent` (append-only, BigInt id) · `SignQrSession`
(одноразовые `dataToken`/`signToken`, статус-машина `issued→claimed→submitted`).

Партиальные уникумы РУКАМИ: «одна живая заявка на шаг», «одна живая подпись на
подписанта» (отдельно user и guest). `failed`/`declined` в условие НЕ входят:
опечатка в выборе сертификата не должна навсегда лишать возможности подписать.
FK акта на заявку — `Restrict`.

## Хранение вечное

Ретеншн-кроны таблиц движка не касаются. Профили `sign_subject`/`sign_cms`
(`EVIDENCE_FILE_PROFILES`) — вне квоты и вне реапа сирот; сверка квот их тоже
исключает (иначе правило жило бы до 04:40 — это пришлось поправить и в
`verify-files.cjs`). Через HTTP профили закрыты: иначе подстановкой `profile`
любой клиент получил бы бесконечное вечное хранилище.

## Связка с core/approvals

Тело `decide` вынесено в приватный `applyDecision`; входов два: публичный
`decide` (всегда `internal`) и **`decideAttested(tx, stepId, userId, {...})`** —
наружу не выставлен, зовётся только из core/sign изнутри транзакции финализации
акта: акт подписан и шаг закрыт ОДНИМ коммитом. Инварианты общие (уникальный
индекс, статус-гвард, `FOR UPDATE` для `all`, активация следующей группы).

approvals знает одно поле `ApprovalStep.requiredSignatureKind`: `null` → клик;
`sms|ecp` → публичный `decide` отвергается кодом `approval_needs_signature`.
**ЭЦП закрывает шаг, которому хватало ПЭП; наоборот — нет.** Маппинг
`approvalSignatureKindOf` (`pep`→`sms`): enum не переименован, история решений
неизменяема.

⚠️ Оповещение после `decideAttested` — джобом `approvals.announce` В ТОЙ ЖЕ
транзакции: «после коммита» там наступает не у нас.

⚠️ **Имена джобов approvals вынесены в `approvals.job-names.ts` (файл БЕЗ
импортов)**: сервис ставит джобы, обработчик инжектит сервис — общий файл
разрывает кольцо ES-модулей (иначе Nest падал на старте «undefined dependency»).

## ⚠️ Право «отправить на подпись» ≠ право «подписать»

`canRequestSign` спрашивается ТОЛЬКО при самостоятельном заведении заявки. При
подписании ШАГА МАРШРУТА он НЕ спрашивается (`opts.authorizedBy='approval_step'`):
полномочие даёт снимок адресатов шага. Иначе рядовой сотрудник, которому маршрут
поручил подписать приказ, не смог бы выполнить порученное — он не вправе этот
приказ инициировать. **Поймано собственным сьютом** на шаге с двумя подписантами.

## Сверка личности

ИИН из сертификата; заполнен `users.iin` → расхождение = ОТКАЗ
(`sign_iin_mismatch`); не заполнен → фактический ИИН пишется в акт. Неудачная
попытка акт НЕ хоронит (`failAttempt` пишет событие) — человек пробует снова.

## Драйверы и fail-closed

Верификатор `ncanode|mock`, QR-мост `smartbridge|mock` (паттерн `SmsDriver`).
**Fail-closed СТРОЖЕ, чем у SMS:** в production с mock ЭЦП **ОТВЕРГАЕТСЯ**
(`ecpAccepted=false`) и ЭЦП-способы не показываются; ПЭП работает. Проверяется
частью 4 сьюта — загрузкой собранного модуля с `NODE_ENV=production`.

NCALayer живёт целиком в браузере (`wss://127.0.0.1:13579`, модуль
`kz.gov.pki.knca.basics`, detached CMS + `tsaProfile`). Пароль ключа не
спрашиваем НИКОГДА — это схема поддельных «порталов ЭЦП».

## Гостевое подписание

Первый потребитель слота **`actions`** в `ShareLinksRegistry` (реализован на
ОБЩЕМ гостевом контроллере движка ссылок, а не отдельным sign-контроллером: слот
для того и заводился). Ссылка на `sign_request` → личность по SMS → просмотр
замороженного PDF → соглашение сторон + согласие на ПД → **второй OTP под
документ** либо ЭЦП. Акт гостя — лениво при первом действии. **Лимит открытий
запрещён** (`constraints.forbidMaxOpens`): он запирал бы подписанта снаружи.

## Веб

`SignFlowModal` · `SignStepModal` (мостик «шаг → подписание») · `SignaturesBlock`
· **`SignRequestPage` — ОДИН компонент на ДВА адреса** `/sign/[id]` и
`/workspaces/[id]/sign/[signId]` (личный сам переадресует рабочую внутрь
организации). Страницы обязательны: `signRequestHref` — цель уведомлений
«Подпишите документ», и без них каждое вело бы в 404 (тот же дефект, что был у
approvals). Публичная `/check` вне каркаса + `noindex`. QR рисует СЕРВЕР.

## Ловушки, пойманные при стройке

1. Кольцо ES-модулей approvals.service ↔ approvals.jobs → файл имён без импортов.
2. Порядок проверок в `loadOwnAct`: своё состояние акта ПЕРВЫМ, иначе
   подписавшему отвечали «подписание закрыто» вместо «вы уже подписали».
3. Mock QR-моста обязан нести ОБА адреса (`?data=`) — иначе не сыграть за телефон.
4. **Анти-абьюз SMS ломает повторные прогоны**: ПЭП шлёт код на СВОЙ номер, 5/час.
   Аккаунты сьюта внесены в `VERIFY_TEST_PHONES` (.env и CI).
5. `Prisma.XGetPayload<Record<string, never>>` не работает — брать типы моделей
   напрямую из `@prisma/client`.
6. ИИН в тестах обязан проходить контрольную сумму (два прохода весов mod 11).
7. Шаги ОДНОЙ группы приходят в неустойчивом порядке (сортировка только по
   `order`) — в тестах искать по id, а не по индексу массива.
8. Кит: у `Alert` нет `style` и тона `info`; у `Button` варианты
   `primary|matte|outline|ghost` (не `secondary`/`danger` — красный это `tone`);
   `useRequireAuth` отдаёт `isReady`, у `PageHeader` — `breadcrumb`, не `eyebrow`.

## Ревью движка (2026-08-09) — 22 находки, все закрыты

7 агентов-ревьюеров по дименсиям (крипто/доступ/гонки — Fable 5 xhigh, остальное
Opus 5) + адверсариальная проверка; 4 проверяющих упали по лимиту сессии, поэтому
их дименсии перепроверены руками. Сьют `verify-sign.cjs` ALL PASS (+2 новые
проверки) и 13 смежных сьютов зелёные.

**[КРИТИЧНО] Доказательства подписи мог уничтожить сам подписант.** Правило «вне
квоты и вне ретеншна» стояло в 4 местах (init, квота ingest, реап сирот, ночная
сверка) и отсутствовало ровно в двух путях УДАЛЕНИЯ: `FilesService.softDelete` и
`FilesCron.sweepDeleted`. `ingestLocalFile` пишет `uploaderId = ownerUserId`, а
движок подписи передаёт туда актора — то есть ПОДПИСАНТА. Он проходил проверку
«владелец или загрузивший», сносил `DELETE /files/:id` контейнер CMS и
замороженную копию, а через 7 дней крон стирал байты и строки: единственное
криптографическое доказательство исчезало, отказ от подписи становился
безнаказанным. Плюс `doSoftDelete` списывал квоту, которая никогда не
начислялась. Починено: запрет в `softDelete` (403), тихий пропуск в
`systemSoftDelete`, исключение профилей в `sweepDeleted`, симметрия квоты.
Инвариант закреплён проверкой в сьюте.

**[HIGH] Парсер вердикта NCANode был fail-open.** `valid: json.valid !== false`,
`chainValid: chain === undefined ? json.valid !== false : …`, и гейт статуса,
пропускающий отсутствующее поле: ответ 200 неизвестной формы (смена версии,
прокси) давал valid=true + chainValid=true + пустой сертификат → акт закрывался
как квалифицированная подпись с замороженным «цепочка подтверждена». Заменено на
ЯВНОЕ подтверждение (`=== true`, непустой массив цепочки), молчание = отказ с
логом полей ответа. Там же: неразобранная метка TSP больше не подменяется часами
сервера (это `tspAt` — юридическое время подписи), `ocspAt` = время НАШЕЙ проверки,
а не `revocationTime`.

**[HIGH] Многоподписный шаг ломал заморозку.** `ensureForStep` заводил заявку
только на открывшего; первый подписант закрывал её своей же единственной подписью,
и второй, придя позже, не находил живой заявки → получал НОВУЮ с НОВОЙ заморозкой.
Двое подписывали формально разные документы, а карточка показывала только
последнюю заявку (первая подпись пропадала). Теперь на шаге `rule='all'` акты
заводятся сразу всем адресатам снимка (`stepForSignature` отдаёт `rule` и
`awaitingUserIds`).

**[HIGH] `decideAttested` не сверял членство** — обычный путь `decide` его
проверяет специально против уволенного, а путь подписи проверял только при
ОТКРЫТИИ экрана, при том что заявка живёт 30 суток. Добавлены сверка членства и
проверка исхода по виду шага (общий инвариант с публичным путём).

**[HIGH] Протокол и экспортный пакет были недостижимы** — веб вёл на ручку под JWT
обычной ссылкой `<a href>`, а токен живёт в localStorage: браузерная навигация не
несёт Authorization → всегда 401. Обе выгрузки ст. 62 ЦК не работали ни разу.
Переведены на `apiGetRaw`+blob.

**Прочее закрытое:** отсутствие вердикта OCSP больше не трактуется как «сертификат
в порядке» (новый код `sign_ocsp_unavailable`, отказ временный) · SMS-код привязан
к акту (`verifyChallengeId` сверяется — код «под конкретный документ», ст. 46 п. 4)
· подсчёт закрытия заявки под `FOR UPDATE` (иначе двое последних оставляли заявку
вечно pending) · подписная ссылка ПРИНУЖДАЕТ подтверждать личность
(`constraints.requireIdentity` в реестре share-links — до этого документ на подпись
читал любой обладатель адреса) · согласие на обработку ПД теперь фиксируется и на
ЭЦП-пути гостя (экран его спрашивал, обработчики выбрасывали) · текст соглашения
гостю показывается с названием организации — совпадает с сохраняемым в акт снимком
· полный ИИН убран из DTO (маскируется везде, не только на публичной странице) ·
требование подписи ставится В ОДНОЙ транзакции с созданием шага (было окно, где шаг
закрывался кликом) · `documents.resolveSubject` больше не подсовывает живой .docx
при неснятом PDF-отпечатке · `pepStart` под статус-гвардом · `failureCode`
очищается при успехе · джоб оповещения ставится в транзакции создания · отказ
гасит ждущие акты соседей · `ensureGuestAct` отвергает не-гостя (фильтр
вырождался в «любой акт заявки») · `ensureActFor` перечитывает статус в транзакции
· публичная проверка по отпечатку собирает подписи ВСЕХ заявок с этим sha256 ·
`signQrSubmitSchema` реально применяется на публичной ручке моста · порядок замков
крона выровнен с финализацией · `/check` честно говорит про http вместо «не удалось
прочитать файл».

**Фикстура сьюта, вскрытая критичным фиксом:** дев-полигон создавал файл-заглушку
«документа» с профилем ДОКАЗАТЕЛЬСТВ (`sign_subject`) — теперь `generic`.
Подписывают всегда чужой живой файл; `sign_subject` носит только копия, которую
движок делает сам.

**Подтверждено здоровым:** три партиальных уникума реально существуют в миграции
`sign_engine` · `pickVariant` падает громко, а не подсовывает оригинал вместо
PDF · fail-closed `ecpAccepted` в проде · проверка CMS против ЗАМОРОЖЕННЫХ байтов ·
общее тело `applyDecision` у обоих входов решения.

### Доводка ревью (2026-08-09, вторая волна — по вопросам пользователя)

**Сырые контейнеры на публичной проверке — только по ССЫЛКЕ, не по отпечатку.**
Внутри CMS лежит сертификат с ПОЛНЫМ ИИН: убрать его оттуда нельзя (так устроен
X.509), поэтому управлять надо тем, КОМУ контейнер вручают. Отпечаток есть у
всякого, кому переслали файл; ссылка проверки (`/check/:actId?k=`) — у того, кто
получил протокол или экспортный пакет, то есть у стороны документа. Теперь
`check()` отдаёт `downloads` только при заходе по токену; вердикт (кто, чем,
когда, цела ли цепочка, маскированный ИИН) по-прежнему открыт всем — ст. 61 ЦК
требует именно вердикта, а не раздачи персональных данных. Бенчмарк: SIGEX прямо
берёт согласие на «обработку и отображение персональных данных, содержащихся в
ЭЦП», и показывает карточку документа держателю ссылки, а не по хэшу.

**Хроника подписи идемпотентна.** `onActFinished` зовётся ДЖОБОМ (at-least-once),
и повтор после сбоя доставки уведомления писал «документ подписан» второй раз — и
в хронике, и плашкой в чат. Дедуп сделан штатным механизмом движка хроники:
`ChatterService.hasRecent({payloadPath:{path:['actId'],equals}})`, ключ — id акта
(уникален по природе), окно 30 суток с запасом на бэкофф джоба.

**Гигиена сьюта (иначе падает ЧУЖОЙ сьют).** `verify-sign` заводил заявки
согласования и не убирал их: шаги, до которых прогон не доходил, копились в стопке
аккаунта сьюта, а она обрезана потолком `inboxPerSource: 50` — накопившийся мусор
выталкивал свежую заявку, и падал `verify-approvals` в месте, никак не связанном с
причиной (3 FAIL про личный скоуп). Добавлена уборка штатным путём (`/approvals/mine`
→ cancel своих pending) — второй прогон подряд убирает уже только свои 2 заявки.

**Плавающее падение в самом сьюте:** два шага ОДНОЙ группы приходят в неустойчивом
порядке (сортировка только по `order`), а тест брал их по индексу массива — при
обратном порядке первый подписант шёл на ЧУЖОЙ шаг («Подписывает адресат шага»).
Теперь шаги выбираются по `assigneeId`. Предупреждение об этом в сьюте было, а
код ему не следовал.

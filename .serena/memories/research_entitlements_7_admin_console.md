# Кабинет платформы: как гиганты строят внутренние консоли управления

Исследование для фундамента platform admin console в SuperApp6. Факты 2024–2026, официальные доки и инженерные блоги.

---

## 1. Модель ролей и прав сотрудников платформы

### Главный вывод бенчмарка

Никто из гигантов **не** выражает права админ-консоли как «одна роль = один уровень». Все пришли к одной из двух моделей:

- **A. Много узких именованных ролей, каждая — фиксированный набор capability** (Stripe). Пользователю можно выдать несколько ролей, права складываются объединением.
- **B. Плоский каталог привилегий + роли как именованные наборы + кастомные роли + скоуп** (Google Workspace, Shopify, Salesforce, Atlassian).

Модель B — это то, куда все сходятся при росте числа продуктов. Модель A — то, с чего все начинают и что даёт лучший UX на старте.

### Stripe Dashboard: ~25 ролей, сгруппированных по продуктовым областям

Stripe публично документирует не «5 ролей», как думают, а **свыше двадцати**, разложенных по группам: Admin (Administrator, IAM Administrator, Super Administrator, Account owner), Connect (Connect Onboarding Analyst, Transfer Analyst, Connect Risk Analyst), Developer, Identity (Identity Analyst, Identity View Only), Payment (Analyst, Dispute Analyst, Refund Analyst), Support (Support Associate, Support Specialist, Support Communications, Data Migration Specialist, Terminal Specialist), Tax Analyst, View Only, Accountant, Top-up Specialist, Financial Connections Specialist, Data Engineer.

Несущие детали, которые стоит скопировать:

1. **У каждой роли есть стабильный машинный код** — `SSO Role ID`: `admin`, `iam_admin`, `super_admin`, `support_specialist`, `refund_analyst`, `view_only`… Роль — это идентификатор в коде, а не подпись в UI. Название переводимо, код вечен.
2. **Явная SoD-роль `iam_admin`**: может приглашать/удалять/назначать людей — и **больше ничего** (не видит платежи, балансы, споры, ключи). И не может назначить кого-либо Administrator или Super Administrator. Это чистое «разделение обязанностей»: кто раздаёт доступ, тот не пользуется доступом.
3. **Роль описана двумя списками — «может» и «не может»**. Отрицательный список в доке — это не косметика: он снимает 80% вопросов поддержки и делает ревью прав возможным.
4. **Права привязаны к техническому условию, а не только к роли**: «Your account must require two-step authentication in order to allow non-Administrators with this role to transfer funds» (Transfer Analyst). То есть capability может требовать свойства сессии/аккаунта.
5. **Пределы даже у самой верхней роли**: Administrator не может удалить основной банковский счёт и сменить владельца аккаунта. «God mode» нет ни у кого — есть Account Owner, но и у него ровно одна лишняя способность.
6. Stripe честно предупреждает про накопление: «If you assign a user multiple roles, they're assigned all the permissions of each individual role. Be cautious of conflicts and unintended authority.»

### Google Admin console: 12 преднастроенных ролей + до 750 кастомных + скоуп по OU

- Преднастроенные: Super Admin, Groups Admin, User Management Admin, Help Desk Admin, Services Admin, **Multi-party Approval Admin**, Mobile Admin, Storage Admin, Google Voice Admin, Directory Sync Admin, Reseller Admin, Indirect Reseller Admin.
- **Help Desk Admin** — эталон «минимальной роли поддержки»: только сброс пароля не-администраторам и просмотр профиля. Ничего больше.
- **User Management Admin** явно не может трогать администраторов — только не-админов. Эскалация привилегий через «сбросить пароль начальнику» закрыта на уровне модели.
- **Скоуп по организационным единицам доступен только для User Management Admin и Help Desk Admin.** Google сознательно не даёт скоупить всё подряд — иначе матрица прав становится непроверяемой.
- Роли можно назначать **группам безопасности**, а не только людям: доступ следует за составом команды.
- Лимит — **750 кастомных ролей** на организацию. Рекомендация Google: «несколько ролей с малым числом привилегий лучше одной роли с многими».

### Shopify: категории ролей + плоский каталог permissions + выделенные «sensitive»

- Четыре категории ролей: Store, Organization, POS app, Partner. Permission из одной категории нельзя положить в роль другой — это структурный барьер против случайной эскалации.
- **Управление пользователями и ролями не является permission вообще.** Оно доступно только через отдельные системные роли (Organization administrator, Store user administrator). Тот же приём, что у Stripe с `iam_admin`.
- Отдельный публичный список **sensitive permissions**: `Customers > Request data`, `Finance > Edit billing payment methods and pay invoices`, `Finance > Manage other payment settings`, org-level `Business entities > View sensitive information`, у партнёров — View financials, Manage credits and refunds, Customer privacy. Официальная рекомендация: **распределить чувствительные права между разными ролями и разными людьми**, чтобы ни один аккаунт не владел всем набором.

### Salesforce, Atlassian, AWS — что добавляют

- **Salesforce**: Profile (базовый набор) + Permission Sets / Permission Set Groups (аддитивные надстройки) + **делегированная администрация** (делегат управляет только заданными ролями/OU/объектами). Все изменения прав попадают в Setup Audit Trail с отдельным полем `DelegateUser`.
- **Atlassian**: три уровня — organization admin (admin.atlassian.com, всё) → site admin (один сайт, приложения, ограниченный биллинг) → product/app admin (настройки одного продукта, без доступа в админ-хаб) + узкий «user access admin» на один продукт. Иерархия скоупа, а не иерархия силы.
- **AWS**: политики как данные (JSON), возможность выразить условия (MFA-present, source IP, время), и — главное для нас — **TEAM (Temporary Elevated Access Management)**: сотрудник не имеет постоянных прав, а **запрашивает** доступ на время; заявка проходит review/approve; по истечении срока доступ снимается автоматически. Для инцидентов — авто-одобрение для дежурных с окном ~2 часа.
- **Google Cloud** формулирует четыре принципа доступа собственного персонала к данным клиентов: least privilege (по умолчанию запрет, доступ временный), **limit singular access** (единоличный доступ «крайне затруднён» — нужны несколько людей), **active justification** (доступ только при живом валидном обосновании; закрытый тикет = доступа нет), monitoring & alerting.

| Система | Как выражены права | Гранулярность | SoD | Read-only | Скоуп | Временное повышение |

## 2. Аудит

### Что пишут гиганты

**GitHub Enterprise audit log** — самый явно документированный формат. Общие поля каждого события: `@timestamp`, `_document_id`, `action`, `actor`, `actor_id`, `actor_is_bot`, `business`, `business_id`, `created_at`, `hashed_token`, `operation_type`, `org`, `org_id`, `programmatic_access_type`, `repo`, `repo_id`, `request_id`, `token_id`, `token_scopes`, `user`, `user_agent`, `user_id`. Плюс поля, специфичные для типа события. Retention — **180 дней** (git-события — 7 дней). Экспорт JSON/CSV, REST API, **стриминг** в Splunk / Azure Event Hubs / Amazon S3 / Google Cloud Storage / Datadog с 7-дневным буфером воспроизведения на случай паузы приёмника. Отдельная настройка — показывать ли IP-адреса в событиях (privacy vs forensics).

**AWS CloudTrail** — канон для «запись = вызов API»: `eventVersion`, `eventTime`, `eventName`, `eventSource`, `userIdentity` (включая `sourceIdentity` — кто был исходным человеком за ролью), `sourceIPAddress`, `userAgent`, `requestParameters`, `responseElements`, `errorCode`, `errorMessage`, `requestID`, `eventID`, `readOnly`, `recipientAccountId`. Флаг `readOnly` — дешёвый способ отделить чтение от мутаций в одном журнале.

**Salesforce Setup Audit Trail** — 180 дней скользящего окна, потом безвозвратно; поля: `Action`, `Section`, `Display` (человекочитаемое описание), `CreatedDate`, `CreatedBy.Name`, **`DelegateUser`** (кто действовал от чужого имени — при login-as и делегированной админке). Изменения прав фиксируются пофайлово: включение системного разрешения в Permission Set видно как переход disabled → enabled. Доступ к журналу — отдельное право «View Setup and Configuration».

**Stripe** — «Security history» в Dashboard, **180 дней**, и с 2026 года — **Activity Logs API** для программного доступа. Пишутся управление API-ключами, приглашения, изменения ролей, в том числе пришедшие через SCIM и SSO. Заявленные сценарии: автоматические алерты на неожиданное создание ключа/смену роли/актора и выгрузка для SOC 2 / PCI DSS.

### Канонический набор полей записи аудита

Синтез из CloudTrail + GitHub + Salesforce, адаптированный под консоль:

| Поле | Зачем |
|---|---|
| `id` (ULID/UUIDv7) | Сортируемый, ссылается из тикета/алерта |
| `occurredAt` (UTC) | Момент эффекта, не записи |
| `actorId`, `actorRolesSnapshot[]` | Кто и с какими ролями на тот момент (роли меняются — снимок нет) |
| `onBehalfOfId` | Impersonation / делегирование (`DelegateUser` Salesforce) |
| `sessionId`, `requestId` | Сшивка с логами приложения и с цепочкой действий |
| `commandKey`, `commandVersion` | **Что** сделали — машинный код операции, а не фраза |
| `input` (jsonb, редактированный) | Аргументы команды после маскирования секретов/PII |
| `targetType`, `targetId`, `targetWorkspaceId` | На чём сработало; отдельно тенант — для скоупированного поиска |
| `before` / `after` (jsonb diff) | «Было → стало» по затронутым полям |
| `outcome` (`ok` / `denied` / `error`), `errorCode` | **Отказы тоже пишутся** — половина расследований про попытки |
| `readOnly` (bool) | Отделить просмотр от мутации в одном журнале |
| `risk` (`low`…`critical`) | Фильтр для алертов и обязательных полей |
| `reason` (текст) | «Почему» — обязателен для risk ≥ high |
| `ticketRef` | Внешняя привязка (обращение клиента, инцидент) |
| `approvalId`, `stepUpId` | Доказательство four-eyes и переподтверждения |
| `idempotencyKey` | Повтор не создаёт вторую запись и второй эффект |
| `dryRun` (bool) | Предпросмотр отличается от исполнения |
| `ip`, `userAgent`, `deviceId` | Из `req.ip` при доверенном прокси |
| `durationMs` | Аномалии массовых операций |

### Правила, которые делают аудит настоящим

1. **Единственная дверь.** Гарантия «каждое действие в консоли = запись» достигается не дисциплиной, а архитектурой: у консоли ровно один путь исполнения мутаций (исполнитель команд), и он пишет аудит **в той же транзакции**, что и эффект. Нет второго пути — нет дыр. Это ровно тот же приём, что у SuperApp6 в `core/chatter` (`log(tx)` синхронно) и `core/notifications` (`send(tx)`).
2. **Append-only.** Ни UPDATE, ни DELETE. У приложения — роль БД без этих прав на таблицу аудита; ретенция — через отбрасывание партиций, не через DELETE строк.
3. **Ретенция ≠ 180 дней автоматом.** Гиганты держат 180 дней в горячем UI, но все дают стриминг/экспорт в холодное хранилище. Для финансовых и подписных действий разумный горизонт — годы (в KZ бухгалтерские и налоговые сроки от 5 лет).
4. **Отказы и чтения — тоже события.** CloudTrail пишет `errorCode`; консольный аудит без записей `denied` не позволяет увидеть разведку изнутри.
5. **Алерты на чувствительное** — не отчёт раз в квартал, а поток: создание оверрайда на крупного клиента, массовая операция, impersonation, раскрытие PII, break-glass.

## 3. Опасные действия

Пять паттернов, встречающихся у всех:

**Step-up / sudo mode.** GitHub: после подтверждения сессия входит в «sudo mode» на **2 часа**, каждое новое чувствительное действие сбрасывает таймер; подтверждение — пароль, passkey, аппаратный ключ, GitHub Mobile или 2FA-код. Google и Stripe используют переподтверждение перед сменой критичных настроек. Ключевое: sudo — свойство **сессии с TTL**, а не галочка в модалке.

**Four-eyes / dual control.** Google Workspace **Multi-Party Approval**: действие, начатое одним админом, не исполняется, пока второй уполномоченный админ не одобрит его в консоли. Запущено в апреле 2024; в июне 2025 добавлены гранулярные настройки — какие именно параметры требуют MPA, и отдельная **роль-одобряльщик** (super admin делегирует право одобрять, не раздавая супер-права); в декабре 2025 распространено на Google Vault (например, создание экспортов). Требует минимум два супер-админа. В банковском мире это «maker-checker», требуемый SOX и PCI-DSS. Важный урок реализации: старые банковские системы делали maker-checker **колонками approval в каждой бизнес-таблице** — это не масштабируется; современный подход — **централизованная очередь заявок, независимая от бизнес-таблиц**.

**Reason required + активное обоснование.** Google Cloud: доступ персонала к данным клиента возможен **только при живом валидном обосновании**; закрытый тикет — доступа нет; сотрудник должен быть напрямую связанным участником. Плюс justification reason codes (машинный код причины, не свободный текст). Access Approval позволяет **клиенту** одобрять доступ Google к своим данным.

**Dry-run / preview.** Слабое место большинства публичных админок и сильное — внутренних. Практика: команда умеет вернуть «что изменится» без изменения (список затронутых сущностей, diff, счётчик). Для массовых операций это единственный способ не узнать о масштабе постфактум.

**Защита массовых операций.** Лимит на размер батча, обязательный предпросмотр выше порога, дробление на джобы с идемпотентностью, возможность остановки, отдельная capability на «массовое» и отдельный алерт. Shopify не даёт «удалить всех клиентов» одной кнопкой; AWS требует явного подтверждения на разрушительные операции.

**Break-glass.** AWS TEAM: для критических инцидентов — условное авто-одобрение для назначенной группы дежурных с коротким окном (обычно 2 часа), при этом обычные запросы всё равно идут через менеджера. Обязательные спутники break-glass: мгновенный алерт в канал безопасности, обязательный post-mortem, автоматический отзыв.

## 4. Impersonation / «войти как пользователь»

**Salesforce Login As** — самый развитой публичный пример. Два режима политики организации:
- по умолчанию пользователь сам **выдаёт доступ** администратору/издателю на ограниченный срок (Grant Login Access);
- организация может включить **«Administrators Can Log in as Any User»** — и тогда согласие не требуется. Включение — осознанное решение, отключение делается через обращение в поддержку.
Каждое использование пишется в аудит; изменения, сделанные во время login-as, попадают в Setup Audit Trail с именем пользователя и **делегатом**; клики администратора под чужой личностью в ряде организаций тоже пишутся.

**Shopify** идёт другим путём: прямого impersonation нет — есть **collaborator accounts**. Внешний партнёр **запрашивает** доступ, мерчант одобряет **только нужные permissions**, доступ отзывается в один клик, выдать его может только владелец магазина или Administrator. То есть согласие — не опция, а конструкция.

**Zendesk** различает два разных механизма: «assuming end-users» (агент с правом редактировать профили работает как конечный пользователь — и **все действия атрибутируются самому пользователю**, что является опасной ловушкой атрибуции) и «account assumption» — временное разрешение сотрудникам Zendesk войти как агент в аккаунт клиента; **по умолчанию выключено**, включается на заданный срок, и факт включения виден в audit log как отдельное событие.

**Stripe и Google Workspace прямого impersonation персоналом не дают вовсе.** Вместо этого — Access Approval/Access Transparency (Google Cloud) и поддержка через тикеты с запросом данных у клиента. Причина проста: в платёжной и почтовой среде вход под чужой личностью неотличим от действий самого клиента, что ломает юридическую атрибуцию и non-repudiation. Это главный аргумент против полного login-as в системе, где есть деньги и подписи.

**Правильный дизайн (синтез):**

1. **Два разных режима, не один.** `view_as` — read-only проекция прав пользователя (сотрудник видит ровно то, что видит клиент, но не может ничего изменить) и `login_as` — полноценные действия. 90% задач поддержки закрывает первый.
2. **Атрибуция всегда двойная.** `actorId` = сотрудник, `onBehalfOfId` = пользователь. Ошибка Zendesk — записывать действие на пользователя — делает аудит ложным.
3. **Согласие** для `login_as`, по умолчанию — обязательно и с TTL; политика «без согласия» существует как отдельная, аудируемая, ограниченная capability (аналог Salesforce), а не как норма.
4. **Таймбокс** (30–60 мин), авто-выход, невозможность продлить без нового согласия.
5. **Уведомление пользователю** — «сотрудник поддержки просматривал ваш аккаунт по обращению №…», и запись в хронике сущности.
6. **Запреты внутри режима**: недоступны денежные операции, подписание, смена пароля/2FA, экспорт данных. Impersonation — не способ обойти SoD.
7. Визуальный маркер сессии у сотрудника (яркая рамка/плашка) — чтобы «забытая» сессия не превращалась в скрытый доступ.

## 5. Форма API и расширяемость: реестр команд против классических ручек

### Как консоли гигантов масштабируются на десятки продуктов

- **Salesforce Setup** — дерево настроек, куда каждое приложение вносит свои узлы; настройки живут как **метаданные**, а не как код страниц; отсюда и возможность аудита изменений «до поля».
- **Google Admin** — единая консоль, продукты добавляют свои разделы и свои привилегии в общий каталог; роль собирается из привилегий разных продуктов.
- **Shopify Admin** — открытая платформа расширения: **Admin UI extensions** через **App Bridge** + web-компоненты **Polaris** (унифицированы летом 2025, рендер на Preact). Приложение вставляет блоки на страницы товара/заказа, модальные действия из контекстного меню, собственные экраны настроек — и выглядит как родная часть админки.
- **Backstage (Spotify)** — «everything is a plugin»: плагин/модуль подключается через **extension points**, которые экспортируются **отдельно от самого плагина** (чтобы их можно было версионировать и депрецировать независимо), бэкенд-плагин создаётся через `createBackendPlugin`, берёт HTTP-роутер из core-сервисов и вешает свои маршруты. Модуль может расширять только точки **одного** плагина и деплоится вместе с ним.
- **Django Admin / ActiveAdmin / Forest Admin / Retool** — генерация CRUD из схемы. Дешёво и быстро; но сама документация Django прямо говорит, что админка — **внутренний инструмент управления**, не интерфейс для конечных пользователей. Ограничение генераторов известно: как только нужна доменная логика (не «поменять поле», а «вернуть деньги и разморозить эскроу»), абстракция начинает мешать, и кастомизация превращается в борьбу с фреймворком.

### Реестр команд vs классические ручки

**Классические ручки по доменам** (`POST /platform/workspaces/:id/suspend`, `POST /platform/billing/refund`): привычно, типобезопасно, но каждая ручка заново реализует проверку capability, аудит, step-up, reason, идемпотентность, форму в UI. На 100+ сервисах это гарантированно разъедется: часть ручек окажется без аудита, часть — без reason, UI разойдётся по стилю.

**Реестр админ-команд**: каждый сервис регистрирует свои операции как декларации:

```ts
PlatformCommandRegistry.register({
  key: 'entitlements.override.create',   // машинный код; он же имя AI-инструмента
  version: 1,
  group: 'billing',
  titleKey: 'platform.cmd.entitlements.override.create.title', // i18n
  input: z.object({ workspaceId: z.string(), featureKey: z.string(),
                    limit: z.number().int().positive(), expiresAt: z.date().optional(),
                    reason: z.string().min(10) }),
  capability: 'entitlements.override.write',
  risk: 'high',                 // → обязателен reason, step-up, four-eyes
  dualControl: true,
  dryRun: true,
  target: (i) => ({ type: 'workspace', id: i.workspaceId }),
  redact: ['contactPhone'],
  execute: (ctx, input, tx) => entitlementsService.createOverride(ctx, input, tx),
});
```

Что получает система бесплатно, один раз и навсегда: генерация формы из Zod-схемы; проверка capability; запись аудита с `input`/`before`/`after`; принуждение step-up и four-eyes по `risk`; идемпотентность; dry-run; i18n подписи; и — **команда автоматически становится инструментом AI-агента** (описание + JSON-схема входа + класс риска = ровно то, чем сегодня описывают MCP-инструменты; индустриальная классификация 2025–2026: auto-approve для обратимых действий низкого риска, notify-and-proceed для среднего, human-in-the-loop для необратимых, prohibited вне области).

Минусы честно: реестр — это ещё одна абстракция; сложные мастера (многошаговые операции) в сгенерированную форму не влезают; отладка через слой исполнителя менее прозрачна; версионирование команд надо продумать сразу (`commandVersion` в аудите).

**Вывод:** правильная форма — **гибрид, но с реестром как несущей конструкцией**. Все мутации консоли проходят через исполнитель команд (иначе нет гарантии аудита). Реестр даёт дефолтную форму из Zod; но декларация может указать собственный React-компонент формы для сложных случаев — как Shopify разрешает и стандартные блоки Polaris, и собственное UI-расширение. Чтения — отдельным механизмом (см. §6), их нельзя загонять в ту же дверь. Именно так устроены зрелые внутренние платформы: узкое горлышко для команд + свободная композиция для представлений. И это ровно тот же архитектурный ход, который в SuperApp6 уже применён 18 раз («движок не импортирует фичи; фичи регистрируются в реестрах движка»).

## 6. Разделение read/write, поиск и карточка 360

Админ-консоль — естественный CQRS: **запросы** (поиск, карточка, отчёты, экспорт) и **команды** (мутации). Разделять их надо не ради моды, а потому что у них разные требования: у чтений — агрегация из многих сервисов, кэш, пагинация, маскирование PII; у команд — транзакционность, аудит, идемпотентность, step-up.

**Поиск сущности** — вход в консоль. Сотрудник поддержки приходит с одним идентификатором: телефон, e-mail, БИН/ИИН, номер заказа, id платежа, ссылка. Правильный поиск: одна строка, распознавание типа по формату, ответ — типизированные группы результатов («Пользователи», «Организации», «Платежи», «Документы»), прямой переход при единственном совпадении. У Stripe и Shopify поиск по любому идентификатору ведёт на карточку сущности за один шаг.

**Карточка 360** (Stripe customer page, Shopify customer/merchant page, Salesforce record page, Zendesk user profile) — это **композиция панелей, а не одна страница**:
- шапка: идентичность, статус, тариф/план, флаги риска, быстрые действия;
- панели от разных сервисов: платежи, подписки, документы, задачи, устройства, обращения;
- **timeline** — единая лента событий сущности (у SuperApp6 это уже есть: `core/chatter`);
- слева/справа — контекст (организация, связанные люди).

Технически это **реестр панелей**: сервис регистрирует `{ key, entity, capability, order, load(ctx) }`, консоль лениво подгружает только те панели, на которые у сотрудника есть права и которые он раскрыл. Так карточка не превращается в 40 запросов при открытии и не требует правки ядра при добавлении 101-го сервиса.

**Быстрые действия на карточке** — те же команды из реестра, отфильтрованные по `entity` и по capability: кнопка не показывается, если права нет (правило «UI несуществующих фич не показывать» работает и здесь).

**Чтения обязаны идти через доменный слой прав.** Консоль, которая ходит в таблицы напрямую, неизбежно расходится с продуктом (см. §10).

## 7. Безопасность консоли

**Отдельный хост.** `dashboard.stripe.com`, `admin.shopify.com`, `admin.google.com`, `admin.atlassian.com` — все вынесены. Причины: изоляция cookie (кука без явного `domain` доступна только точному хосту), отдельный origin для CSP и same-origin policy, возможность закрыть хост по сети/IP отдельно от публичного приложения, отдельный WAF и rate limits, невозможность XSS в клиентском приложении утащить сессию консоли. GitHub Enterprise отдельно документирует «subdomain isolation» именно как меру безопасности.

**Обязательная 2FA/WebAuthn для сотрудников.** Не «рекомендуется» — принудительно на уровне входа в консоль, с passkey/аппаратным ключом как предпочтительным фактором (фишинг-устойчивость).

**Короткие сессии и отдельный токен.** Отдельная аудитория токена (консольный токен не работает против клиентского API и наоборот), абсолютный TTL 8–12 часов, idle-таймаут 15–30 минут, отдельная эпоха отзыва.

**Сетевой периметр.** IP allowlist / VPN / device trust для чувствительных ролей; как минимум — для break-glass и финансовых операций.

**No PII by default.** Телефоны, ИИН/БИН, адреса, реквизиты — маскированы по умолчанию; «раскрыть» — отдельная capability, отдельный клик и **отдельная запись аудита** с причиной. Это прямой ответ на кейсы §10: почти все скандалы — про чтение, а не про запись.

**Rate limits на чтение.** Перебор карточек — способ выгрузить базу поштучно. Лимиты на число просмотренных карточек и раскрытий PII в час, алерт на аномалию — то, чего не было у Uber (систему мониторинга доступа построили в декабре 2014, но она «не была спроектирована и укомплектована» под тысячи сотрудников).

**Экспорт — отдельная привилегия и отдельный риск.** Google в декабре 2025 специально распространил multi-party approval на создание экспортов в Vault. Экспорт — самый дешёвый способ вынести всё сразу.

## 8. UX-принципы удобной консоли

- **Command palette (⌘K) как главный вход.** Linear — эталон: любое действие доступно из палитры. Библиотека `cmdk` (на ней ⌘K у Vercel) — де-факто стандарт. Для консоли это не украшение: когда у платформы 100+ сервисов, боковое меню перестаёт масштабироваться принципиально — «меню не масштабируются: когда в продукте 200 функций, сайдбар из 8 пунктов создаёт трение». Реестр команд и палитра — две стороны одной монеты: палитра просто показывает реестр, отфильтрованный по правам.
- **Глобальный поиск по любому идентификатору** (§6) + «недавние» + закреплённые сущности.
- **Сохранённые фильтры и представления** — очередь «оверрайды на одобрении», «организации с просроченной оплатой», «подозрительные регистрации за сутки».
- **Плотные таблицы** с настраиваемой плотностью, выбором колонок, массовыми действиями с предпросмотром.
- **Timeline на карточке** — сквозная лента «что происходило», включая действия сотрудников.
- **Split view и очереди** (Salesforce Service Console): список слева в сворачиваемой колонке, запись справа; сотрудник проходит очередь, не теряя контекст. Плюс макросы (повторяющиеся действия одной кнопкой), quick text, utility bar, Omni-Channel маршрутизация по навыкам и доступности, **таймеры SLA/milestone**, которые измеряют выполнение обязательств, а не просто считают время.
- **Клавиатура и доступность.** Консоль — рабочее место на 8 часов; мышь здесь роскошь. Полная навигация с клавиатуры, видимый фокус, контраст AA.
- **Дизайн-система обязательна** (Polaris, Atlassian Design System). Для SuperApp6 это DESIGN.md и кит `components/ui/` — консоль не должна становиться вторым визуальным языком.

Что превращает консоль в «основное рабочее место»: очередь работы приходит **к** сотруднику (маршрутизация), контекст полный (карточка 360), действие — в один шаг из палитры, и видно, сколько времени осталось по SLA.

## 9. Разделы: ядро консоли vs плагины продуктов

**Ядро** (строит платформенная команда, живёт в `core`, не зависит от конкретных сервисов):
1. Аутентификация сотрудников, роли/capabilities, назначения, скоуп.
2. **Журнал аудита** — сам раздел консоли: поиск, фильтры, экспорт, алерты.
3. Исполнитель команд + палитра + генератор форм.
4. Глобальный поиск и карточка 360 (каркас + реестр панелей).
5. Очередь одобрений (four-eyes) и запросы временного повышения.
6. Impersonation/view-as с согласиями и таймбоксом.
7. Управление арендаторами: организации, тарифы, лимиты, оверрайды, кредиты — **это ядро**, потому что модель тенанта общая.
8. Feature flags / kill switches — ядро (нужен общий рубильник для любого сервиса).
9. Джобы и очереди: просмотр, ретрай, отбрасывание, DLQ — ядро (`core/jobs` один на всех).
10. Здоровье системы, инциденты, объявления/broadcast.
11. GDPR/приватность: экспорт данных субъекта, удаление, журнал раскрытий PII.

**Плагины продуктов** (регистрируются сервисом, ядро о них не знает):
- панели карточки 360 от каждого сервиса;
- команды сервиса (вернуть платёж, разморозить эскроу, отозвать подпись, переиндексировать документы);
- собственные разделы (модерация Магазина, споры, реестр контрагентов);
- провайдеры поиска;
- типы объектов для алертов.

Демаркация проста: **если раздел про людей/деньги/доступ/инфраструктуру — ядро; если про домен — плагин.**

## 10. Антипаттерны и уроки

1. **«God mode» у всех.** Snapchat: инструмент **SnapLion** создавался для ответов на законные запросы правоохранителей, но доступ расползся на Customer Ops, безопасность и антиспам; сотрудники использовали его для просмотра сохранённых снимков, локаций, телефонов и почт. Один из бывших работников назвал это «ключами от королевства». Урок: инструмент, созданный под редкий легитимный сценарий, без узкой capability и без обоснования всегда расползается.
2. **Аудит без мониторинга = аудита нет.** Uber «God View»: компания публично заявляла о политиках ограничения доступа, при этом перестала пользоваться системой мониторинга доступа менее чем через год; построенная в декабре 2014 автоматика «не была спроектирована и укомплектована» под тысячи сотрудников и подрядчиков. Итог — мировое соглашение с FTC (2017) с **20 годами независимых аудитов** и штраф от прокуратуры Нью-Йорка. Отдельно: Facebook увольнял инженеров за слежку за женщинами с использованием привилегированного доступа (2018).
3. **Правка данных руками в БД вместо команд.** Обходит доменную логику, не пишет аудит, не шлёт события, не обновляет проекции прав и поисковые индексы, не создаёт проводок. Через полгода это «нормальная практика», а расхождение данных необъяснимо.
4. **Консоль, читающая внутренние таблицы напрямую.** То же самое на чтении: консоль показывает не то, что видит продукт; изменение модели ломает консоль молча; права обходятся.
5. **Команды без идемпотентности.** Двойной клик — два возврата средств. Нужен `idempotencyKey` с уникальным индексом на `(commandKey, idempotencyKey)`.
6. **Отсутствие «почему».** Запись «admin изменил лимит с 10 на 1000» без причины и тикета бесполезна в расследовании. Google строит весь доступ персонала вокруг **активного обоснования**.
7. **Утечки PII через экспорт.** Экспорт — самая дешёвая эксфильтрация; поэтому Google завёл MPA на создание экспортов.
8. **Impersonation без согласия и без атрибуции.** Модель Zendesk, где действия под чужой личностью записываются на пользователя, ломает non-repudiation: потом нельзя доказать, кто подписал документ или потратил деньги.
9. **Нет отрицательного списка прав.** Если нигде не написано, чего роль не может, никто не может провести ревью.
10. **Роль = «уровень».** Иерархия «support < manager < admin» разваливается на первом же требовании «финансист видит деньги, но не видит переписку». Нужны ортогональные capability, а не лестница.
11. **Кастомные роли без лимитов и владельца.** Google ограничивает 750 ролями; без владельца и ревизии матрица прав через год непроверяема.
12. **Смешение прав сотрудника платформы и прав пользователя.** Если платформенные права выводятся из тех же таблиц, что и роли в организациях, любая ошибка в тенантной логике становится эскалацией на всю платформу.

## 11. Рекомендуемый фундамент для SuperApp6

### 11.1. Идентичность и роли сотрудников платформы

- **Один `user_id` сохраняется** (принцип платформы), но «сотрудник платформы» — **отдельная сущность и отдельная таблица грантов**, никак не выводимая из `user_roles`: `platform_staff(user_id, status, twoFactorRequired, …)` + `platform_staff_role(user_id, role, scope, grantedBy, grantedAt, expiresAt, reason)`. Платформенные права **никогда** не приходят из тенантных ролей.
- **Capability — строка вида `<домен>.<объект>.<действие>`**: `tenant.workspace.suspend`, `entitlements.override.write`, `entitlements.override.approve`, `billing.refund.execute`, `pii.reveal`, `impersonation.view_as`, `impersonation.login_as`, `audit.read`, `jobs.retry`, `flags.write`, `data.export`. Плоский каталог, регистрируется вместе с командами.
- **Роль = именованный набор capability, объявленный в коде** (машинный код + i18n-подпись), по образцу Stripe `SSO Role ID`. Стартовый набор (8 ролей, не 3):
  `platform_viewer` (только чтение, PII маскирован) · `support_agent` (карточка 360, view_as, создание обращений) · `support_lead` (+login_as по согласию, +мелкие возвраты) · `billing_ops` (тарифы, счета, кредиты; **предлагает** оверрайды) · `finance_approver` (**одобряет** оверрайды и крупные возвраты; сам не предлагает) · `moderator` (жалобы, блокировки контента) · `sre` (джобы, флаги, здоровье; без доступа к PII) · `staff_iam` (управляет сотрудниками и ролями — и **ничего больше**, по образцу Stripe `iam_admin`).
  Роли складываются объединением; конфликт «предлагает и одобряет» проверяется при назначении и блокируется.
- **Скоуп с первого дня**, даже если пока он один: `{ kind: 'global' }` | `{ kind: 'segment', value: 'b2b' }` | `{ kind: 'workspaces', ids: [...] }`. Позже добавятся регион и вертикаль — без миграции модели.
- **Срок у гранта** (`expiresAt`) обязателен в схеме с самого начала; JIT-повышения и break-glass — это просто гранты с коротким сроком и авто-алертом.
- **Никакого `platform_admin` со «всем»**: верхняя роль — `platform_owner`, но и она не включает `pii.reveal` и `billing.refund.execute` без step-up и не может одобрить собственную заявку.

### 11.2. Схема аудита

Таблица `platform_audit_log`, append-only, партиционирование по месяцам, поля — канонический набор из §2 целиком (включая `readOnly`, `risk`, `reason`, `approvalId`, `stepUpId`, `idempotencyKey`, `dryRun`, `onBehalfOfId`, `actorRolesSnapshot`). Отдельный лёгкий `platform_access_log` для чтений и раскрытий PII (объём на порядок больше, ретенция короче). Запись — **в транзакции команды**, тем же приёмом, что `chatter.log(tx)`. Роль БД приложения без `UPDATE`/`DELETE` на обе таблицы. Ретенция: горячие 180 дней в UI, холод — годы. Алерты на `risk >= high`, на `pii.reveal` выше порога, на break-glass, на `outcome = denied` сериями.

### 11.3. Реестр команд

`core/platform-console` — 19-й движок, устроенный ровно как остальные: движок не импортирует фичи, фичи регистрируются.

Поля декларации: `key`, `version`, `group`, `titleKey`/`descriptionKey`, `input: ZodSchema`, `capability`, `risk`, `dualControl`, `stepUp`, `dryRun`, `target(input)`, `redact[]`, `idempotent`, `execute(ctx, input, tx)`, опционально `formComponent` и `preview(ctx, input)`.

Единственная дверь: `POST /api/v1/platform/commands/:key` (и `POST …/:key/preview` для dry-run). Внутри по порядку: разрешение команды → проверка capability и скоупа → проверка step-up → проверка four-eyes → идемпотентность → транзакция {`execute` + запись аудита} → уведомления/алерты. Мимо этой двери мутаций в консоли **нет** — это то, что делает аудит полным.

Бонус: реестр команд = каталог будущих AI-инструментов (`key` + Zod-схема + `risk`), без второй реализации. Классы риска отображаются прямо на индустриальную классификацию агентских действий: `low` → авто, `medium` → выполнить и уведомить, `high`/`critical` → человек в контуре.

### 11.4. Step-up и four-eyes — на готовых движках

- **Step-up**: `core/verify` уже умеет purpose + `consume(tx)`; добавить purpose `platform_step_up`, TTL сессии sudo **15 минут** (короче GitHub'овских 2 часов — у нас деньги и подписи), сброс таймера на каждое чувствительное действие, фактор — пароль + SMS-OTP, с заделом на WebAuthn.
- **Four-eyes**: `core/approvals` уже реализует «собрать решение» с `describeForCreate`, снимком адресатов и проверкой права. Заявка команды = предмет согласования; одобряющий выбирается по capability `*.approve`; автор **не может** одобрить себя; исполнение — после одобрения, идемпотентно. Это ровно «централизованная очередь заявок, независимая от бизнес-таблиц», к которой пришли банки.
- **Reason обязателен** при `risk >= high`, минимум 10 символов, плюс поле `ticketRef`.

### 11.5. Impersonation

Только `view_as` на первом этапе: read-only проекция через `core/access` (`grantSetFor` пользователя), баннер, таймбокс 30 минут, уведомление пользователю через `core/notifications`, запись в аудит и в `chatter` сущности. `login_as` — вторым этапом, с согласием пользователя (грант с TTL, отзыв в один клик), с жёстким списком запрещённых действий (деньги, подпись, смена пароля/2FA, экспорт) и двойной атрибуцией `actorId`/`onBehalfOfId` во **всех** журналах.

### 11.6. Где живёт консоль

**Сейчас:** отдельный модуль `modules/platform` + отдельный префикс `/api/v1/platform/*` со своим guard'ом и **отдельной аудиторией токена и отдельной cookie** — это единственное решение, которое нельзя отложить, потому что оно определяет форму сессии. Веб — отдельный сегмент Next.js, изолированный от `app-nav.ts` продуктовых сервисов.
**Позже (без переписывания):** вынос сегмента в отдельный деплой на `admin.<домен>` с собственным CSP, IP allowlist и WAF. Поскольку API-префикс и токен разделены с самого начала, вынос — это деплой, а не рефакторинг.

Обязательно с первого дня: принудительная 2FA для сотрудников, TTL сессии 8 часов / idle 20 минут, `pii.reveal` как отдельная capability с аудитом, rate limits на просмотр карточек.

### 11.7. Первые разделы (в этом порядке)

1. **Поиск + карточка 360** (пользователь, организация) — каркас с реестром панелей; первые панели: профиль, организации, тариф, платежи.
2. **Тарифы/лимиты/оверрайды** (движок entitlements) — первый реальный потребитель реестра команд, `risk: high`, four-eyes на оверрайды.
3. **Журнал аудита** как раздел консоли — чтобы консоль сразу проверяла сама себя.
4. **Сотрудники платформы: роли и гранты** (`staff_iam`).
5. **Джобы/очереди** и **feature flags** — операционный минимум.
6. Дальше по мере нужды: модерация, обращения, broadcast, экспорт данных субъекта.

### 11.8. Что заложить сейчас, а что можно позже

**Сейчас (иначе переписывать):** отдельный API-префикс и отдельный токен/cookie; таблица сотрудников, отделённая от `user_roles`; capability-строки и скоуп в схеме; `expiresAt` у грантов; реестр команд как единственная дверь мутаций; полная схема аудита (все поля сразу — добавить поле в append-only журнал задним числом нельзя, старые записи останутся без него); `risk`, `reason`, `idempotencyKey`, `dryRun` в контракте команды; двойная атрибуция `actorId`/`onBehalfOfId` во всех журналах; маскирование PII по умолчанию.

**Позже (аддитивно):** кастомные роли и их редактор; JIT-повышения и break-glass; палитра ⌘K (после того как в реестре наберётся 20+ команд); сохранённые представления и очереди; стриминг аудита в SIEM; IP allowlist и device trust; макросы и SLA-таймеры поддержки; `login_as`; AI-агент над реестром команд.

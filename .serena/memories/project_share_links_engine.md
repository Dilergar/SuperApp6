# core/share-links — движок гостевых ссылок (13-й платформенный, 2026-08-01)

«Поделиться наружу» с человеком БЕЗ аккаунта SuperApp6: токен → гостевая СТРАНИЦА `/s/<токен>`
просмотра и скачивания (не сырые байты), срок действия, отзыв, пароль, лимит открытий,
счётчик и журнал визитов. Первый шаг документной вертикали: дальше на нём стоят ЭДО

## Несущие решения (и почему)

1. **core/access НЕ участвует.** Гость не принципал, строка ссылки И ЕСТЬ грант. Никаких
   типов в `ACCESS_SCHEMA`/`EPOCH_FANOUT`. (`public:*` в резолвере движка прав существует,
   но им никто не пишет, а `grantSetFor` его не сеет — вводить второй путь авторизации
   ради гостей было бы дороже и опаснее.)
2. **Право управлять ссылками решает РЕЗОЛВЕР ПОТРЕБИТЕЛЯ** (`ShareLinksRegistry`, паттерн
   `FilesRefRegistry`): `authorizeManage(userId, refId) → ShareRefContext | null` и
   `resolveGuestView(link) → view | null`. Движок не импортирует ни один функциональный модуль.
   **У отказа ДВА разных вида** (ревью 2026-08-02): `null` → 404 для ПОСТОРОННЕГО
   (существование чужого объекта не подтверждаем), брошенный `ForbiddenException` → 403 с
   причиной для того, кто объект ВИДИТ, но им не управляет. Схлопывать их в один `null`
   нельзя: на диске организации корень раздаёт роль «правит» каждому сотруднику, и «Объект
   не найден» получала вся команда — глядя на этот объект в своём же списке.
3. **Двухшаговый гостевой поток.** `peek` (жива ли, нужен ли пароль) НЕ зовёт резолвер и НЕ
   двигает счётчик — иначе запароленная ссылка раскрывала бы название цели до пароля.
   `session` считает открытие и выдаёт пропуск.
4. **Пропуск гостя — самодостаточный HMAC** (`v1.<payload>.<sig>`, ключ `SHARE_LINK_SECRET`
   либо производный от JWT_SECRET, TTL 60 мин; клон `docs-token.service.ts`). Эпохи как у
   документов НЕ нужно: строка ссылки перечитывается на КАЖДОМ запросе → отзыв гасит живую
   сессию немедленно (закреплено тестом).
5. **Открытие = сессия, а не запрос.** Пропуск лежит в sessionStorage веба → обновление
   страницы и хождение по папкам не накручивают счётчик. Одно «открытие» = один человек.
6. **Гостевые ручки НИКОГДА не отвечают 401** — только 403/404/410 + машинный `details.code`.
   Причина: перехватчик `apps/web/src/lib/api.ts` на 401 гасит токены и уводит на `/login`,
   то есть «ссылка истекла» превратилось бы в «вас разлогинило». Второй ремень — отдельный
   клиент `lib/public-api.ts` без перехватчиков. Инвариант проверяется на КАЖДОМ гостевом
   вызове verify-скрипта.
7. **Байты гостю — существующими подписанными ссылками движка файлов** (HMAC raw / presigned,
   600с). Новых байт-поверхностей нет. Заражённые/неготовые файлы движок в выдачу не кладёт
   (`available:false` вместо битой кнопки).
8. **Статус ссылки вычисляемый** (`shareLinkStatus` в shared), в БД не хранится — иначе его
   пришлось бы догонять кроном.

## Модель

- `ShareLink`: `token` (randomBytes(24) base64url, ПЛЕЙНТЕКСТОМ на @unique — паттерн
  `FileObject.publicToken`), полиморфные `refType/refId` **БЕЗ FK**, `ownerType/ownerId/workspaceId`
  (из резолвера), `label`, `expiresAt`, `revokedAt/revokedById` (null = системный отзыв),
  `passwordHash` (bcrypt 12), `maxOpens/openCount/lastOpenedAt`, `settings` Json (слот
  пер-refType опций — сюда ЭДО положит своё).
- `ShareLinkVisit`: BigInt id = курсор (наружу ВСЕГДА строкой, паттерн ChatterEntry),
  `openedAt/ip/userAgent`. Ретеншн 365 дней кроном; сами ссылки не удаляются никогда —
  «кому и когда отправляли» это история раздачи данных наружу.

**Атомарный клейм открытия** — сырой SQL: `open_count < max_opens` это сравнение колонки с
колонкой, Prisma в `updateMany` его не выражает. Время — через `utcTs` (правило платформы).
В той же транзакции пишется строка визита. Проигравший гонку перечитывает строку и получает
точную причину 410 (проверено тестом «двое за последний слот → ровно один 200»).

## Потребители

**Диск** (`drive-share-links.provider.ts` + `drive-guest.controller.ts`):
- Планка «наружу» = планка внутреннего шеринга: управляющий узлом (`requireNode(…, 'manager')`).
  На диске организации это manager+, потому что корень раздаёт им роль управляющего.
- ⚠️ `requireNode` НЕ проверяет `trashedAt` (только `hasNodeAccess`) — провайдер проверяет явно.
- Корзина ПРИОСТАНАВЛИВАЕТ ссылку (410 `share_ref_gone`), восстановление оживляет,
  окончательное удаление отзывает насовсем (`revokeAllForRefs` в `DriveTreeService.purge`,
  по корню И потомкам).
- Листинг — выделенный `DriveService.listChildrenOf(parentId, q)` (тот же keyset, без прав:
  их проверил вызывающий). `serializeNodes` НЕ переиспользуется: требует userId (звёзды) и
  светит внутренние поля — у гостя свой DTO и свой маппер.
- **Скоуп выводится из САМОЙ ссылки**: всё вне поддерева корня → **404, не 403** (проверка по
  материализованному `ancestorIds` + совпадение `spaceId` + `trashedAt`).

**Документ** (`docs-share-links.provider.ts`):
- Ссылку создаёт **ТОЛЬКО ВЛАДЕЛЕЦ** (`access.can(…, 'document.manage', id)` — тот же предикат,
  что у `update` и `archiveByUser`). Право правки часто приходит «от места» (у всех участников
  задачи), и его не должно хватать, чтобы вынести чужой файл во внешний мир.
- Гость получает **только PDF-отпечаток**: `DocsRenditionService.request(id,'pdf')` сам сверяет
  sha с текущим содержимым и идемпотентен → `ready|preparing|unavailable`. Тот же отпечаток
  позже подписывает ЭДО, значит «что видел» = «что подписал».
- `DocsService.archive` (единственная точка конца жизни документа) отзывает его ссылки.

## Волна 3 — личность гостя (2026-08-02; verify-share-links 145/0 + verify-otp 63/0 + браузер)

Решение архитектурного ревю: ссылка идентифицирует ССЫЛКУ, а подписи/оплате/опросам нужен
ЧЕЛОВЕК. Построено ПОДСИСТЕМОЙ движка (гость существует только через ссылку — прецеденты:
эскроу в кошельке, запись звонков в core/calls); переиспользование потребителями приходит
автоматически через `authorizeGuest`, ничего дополнительно не регистрируется.

- Тумблер `requireIdentity` на ссылке (создание + правка). **Включение на ЖИВОЙ ссылке
  бампает sessionEpoch** — уже открытые анонимные сессии умирают (иначе настройка не делала
  бы того, что обещает); выключение НЕ бампает (подтверждённая сессия строго сильнее).
- Поток гостя: пароль (если есть) → имя (обязательно, вводится гостем, НЕ подтверждается,
  последнее побеждает) + КЗ-мобильный номер → SMS через **core/verify** новой целью
  `share_link_guest`. Старт — ТОЛЬКО `POST guest/:token/identity/start` (гейт по живой
  ссылке; пароль проверяется ДО отправки SMS со счётчиками подбора — правило step-up);
  публичный `/verify/start` цель ОТВЕРГАЕТ (иначе SMS-пушка на любой номер). Проверка кода —
  существующий публичный `/verify/check` (challengeId знает только начавший цепочку).
- `openSession`: гашение verifyToken + upsert гостя + клейм открытия + визит — **ОДНОЙ
  транзакцией**: проигранная гонка за последний слот откатывает и consume, человек не идёт
  за новым SMS-кодом.
- `ShareLinkGuest` unique (ownerType, ownerId, phone) — запись **на ВЛАДЕЛЬЦА**: контрагент
  организации узнаваем в её журналах, но организация А не видит знакомств организации Б.
  Мостик к Universal Identity: гость с номером = будущий user_id (прецедент активации
  pending-приглашений при регистрации).
- Пропуск несёт `g` (guestId); `authorizeGuest` возвращает **`{link, guest}`** — потребители
  (подпись, оплата, опросы) берут «кто по ту сторону» отсюда и СВОИХ таблиц гостей не заводят.
  Страховка: `requireIdentity && !payload.g` → 403 (пропуск старше включения тумблера не
  существует — включение бампает эпоху, значит это подделка).
- Журнал визитов показывает «Асель · +7 777…» (номер владельцу ПОЛНОСТЬЮ — он сам отправлял
  ссылку этому человеку); уведомление «ссылку открыли» несёт имя (`{{guestSuffix}}`, пустая
  строка у анонимов — шаблонизатор условий не умеет).
- Решения грилла: SMS на каждую НОВУЮ ссылку (внутри часового пропуска не переспрашивается;
  «помнить устройство 30 дней» — v2); только КЗ-мобильные (гео-щит, иностранцы позже);
  имя обязательно; включение — тумблером на ссылке (не «всегда» и не только API).

## Волна 4 (2026-08-02): «Ссылки организации» + чужие типы уехали из движка

Два хвоста архитектурного ревью, закрытые подряд.

**(а) Гостевые вьюхи потребителей уехали к владельцам.** Было: `ShareDriveGuestView`,
`ShareDocGuestView`, `ShareGuestFile` жили в `types/share-links.ts` — то есть в «паспорте»
движка, который по определению не знает потребителей. С третьим-четвёртым сервисом файл
превратился бы в свалку чужих анкет. Стало: вьюхи Диска → `types/drive.ts`, документа →
`types/document.ts`, общая проекция файла → `types/file.ts` (она нужна ЛЮБОМУ гостевому
потребителю, показывающему файлы). У движка осталось `view: unknown` + конверт. Правок у
потребителей ноль — всё импортируется через barrel `@superapp/shared`.

**(б) «Ссылки организации»** (`/workspaces/:id/share-links`, Менеджер+). Мотив из ревью:
менеджер раздал наружу три десятка ссылок и уволился — закрыть их было НЕЧЕМ («Мои ссылки»
показывают только свои, пообъектный обход требует помнить все объекты).

- **Контроллер в `modules/workspaces`, не в движке** (образец — `journal.controller.ts` на
  core/chatter): понятие «роль в организации» принадлежит этому модулю. Движку добавлены
  системные методы `listForWorkspace` / `revokeForWorkspace` / `statsForWorkspace` с
  контрактом «право проверил вызывающий»; в `WorkspacesService` появился ПУБЛИЧНЫЙ
  `assertManagerPlus` — единственная дверь для соседних контроллеров модуля.
- **Скоуп — денормализованный `workspaceId`**, а не «владелец объекта»: организация это ещё
  и КОНТЕКСТ, в котором личный объект бывает роздан по работе. Новый индекс
  `(workspace_id, created_at)`.
- **Гейт Менеджер+ и на чтение, и на отзыв**: раздавать наружу на диске организации может
  он же, а отзыв только СУЖАЕТ доступ. Каждая отозванная строка пишется в хронику своего
  объекта — массовое закрытие не тише открытия.
- Кросс-скоуп невозможен: `workspaceId` стоит в WHERE выборки целей, а не проверяется после.
- **Веб: один обозреватель на два скоупа** — `components/share-links/ShareLinksBrowser.tsx`;
  страницы профиля и организации стали тонкими (30 и 100 строк). Копировать 300-строчную
  страницу было нельзя: это раздел, куда приходят разбираться «куда ушли данные», и он
  обязан быть одинаковым в обоих местах. Заодно появилась постраничная догрузка (раньше
  личная страница молча показывала первые 30 и всё) и колонка автора через `PersonChip`.

**Ловушка прогона:** `Start-Process npx nest start` при ЖИВОМ старом процессе тихо падает с
EADDRINUSE, health-check при этом отвечает СТАРЫЙ инстанс — и весь новый раздел даёт 404 «без
причины». Перед запуском убивать слушателя порта 3001 и сверять в логе, что новые маршруты
замаплены.

## Следствия модели, которые надо знать

- Право на ссылки даёт САМ объект → вместе с окончательным удалением объекта закрывается и
  доступ к журналу его ссылок (в тесте это ловилось как «журнал недоступен» — порядок проверок
  важен: журнал смотрят ДО удаления).
- Горячая строка счётчика при вирусной ссылке: зерно записи = сессия/час, этого хватает надолго.
  Путь эскалации — Redis INCR + периодический сброс джобом для ссылок БЕЗ maxOpens; ссылки
  С maxOpens обязаны остаться на транзакционном клейме (корректность).
- **Отзыв не догоняет уже выданные ссылки на БАЙТЫ** (~10 мин, `FILE_LIMITS.urlTtlSec`) — они
  подписаны и живут своей жизнью, как presigned S3. Осознанный размен: сверять каждую отдачу
  байтов со строкой ссылки значит запрос к базе на каждый кусок видео. Владельцу это надо
  знать: отзыв закрывает доступ, но не отменяет уже начатое скачивание.

## Что нашло ревью (2026-08-02) — 10 находок, все закрыты

1. **[крит] Гостевая страница ДОКУМЕНТА не показывала документ.** `helmet` ставит
   `X-Frame-Options: SAMEORIGIN` на КАЖДЫЙ ответ API, а iframe грузится с веба — разные порты
   (в проде домены) → `net::ERR_BLOCKED_BY_RESPONSE`: 200 в сети, пустая рамка на экране.
   Со стороны веба дыру закрыли (`frame-src ${apiOrigin}` в `next.config.ts`, с комментарием
   ровно про этот случай), со стороны API — нет. Глобально снимать `frameguard` нельзя (он
   защищает от кликджекинга остальной API с его одно-кликовыми денежными действиями), поэтому
   ТОЧЕЧНО на `/api/files/raw` и `/api/public-files` XFO заменён на `frame-ancestors` со
   списком origin'ов веба (`WEB_DEV_ORIGINS` + `WEB_URL`, один список с CORS). Диска не
   касалось: там `<img>/<video>`, им XFO не мешает.
2. **[важно] Объект в корзине СЖИГАЛ открытие.** `claimOpen` шёл ДО `resolveView`: ссылка с
   `maxOpens=1` на объект в корзине навсегда становилась «исчерпанной» — владелец возвращал
   объект, а показывать было уже некому. Резолвер (чистое чтение) переехал ПЕРЕД клеймом.
3. **[важно] Заражённый документ ронял наружу голый 403.** `buildSystemDownloadUrl` бросает
   `ForbiddenException` и был ВНЕ `try` провайдера → гость получал 403 без `details.code`,
   веб рисовал «попробуйте обновить через минуту» (обещание, которое не сбудется), и заодно
   постороннему подтверждалось, что файл заражён. Обе половины ушли под один `try` →
   `state:'unavailable'`.
4. **[важно] Пароль перебирался.** Минимум 4 символа + 30 попыток/мин на IP (у `/auth/login` —
   5 за 15 минут, в 90 раз строже) и НИ ОДНОГО счётчика на самой ссылке. Добавлены
   `pwdFailedAttempts`/`pwdLockedUntil` (миграция `share_link_password_throttle`): 5 неудач
   подряд → блокировка 15 минут, верный пароль обнуляет счёт, смена пароля владельцем снимает
   блокировку (гасить ссылку насмерть нельзя — знающий токен отрезал бы получателя). Минимум
   поднят до 6. Блокировка проверяется ДО bcrypt: иначе заблокированная ссылка остаётся
   насосом для пула из четырёх потоков libuv.
5. **[UX] Редактору отвечали «Объект не найден»** — см. решение 2 выше. В вебе модалка доступа
   Диска теперь подтягивает роль зрителя на узле (`GET /drive/nodes/:id` → `access`) и прячет
   управляющие формы, а не показывает их и отвергает.
6. Опрос готовности отпечатка был БЕЗ предела (каждые 2.5 с) — вкладка за ночь давала десятки
   тысяч запросов с конвертацией. Теперь конечный график ~2 минуты + кнопка «Проверить снова».
7. `GET /share-links` отдавал ВСЁ без предела (отозванные не удаляются никогда) → потолок
   `listPageSize` + `total` в ответе. Заодно вскрылось: `ORDER BY revoked_at ASC` в Postgres
   кладёт NULL в КОНЕЦ, то есть с потолком действующие ссылки уехали бы за страницу —
   нужен явный `nulls: 'first'`.
8. Потолок «20 на объект» считался count-then-create → 21-я ссылка в гонке. Теперь под
   `pg_advisory_xact_lock(hashtext(refType:refId))` в одной транзакции с вставкой (образец —
   `lockSpace` Диска).
9. `countActiveForRefs` был написан и не вызывался ниоткуда → в листинге Диска появился значок
   «доступно по ссылке наружу» (`DriveNodeDto.shareLinks`, один групповой запрос на страницу).
10. `PATCH /share-links/:id` был недостижим из интерфейса (продлить срок, снять пароль можно
    было только пересоздав ссылку = разослать новый адрес) → форма «Настроить» в
    `ShareLinkSection`. Плюс мелочи: `role="listitem"` поверх `<button>` в гостевой папке
    (строки не были кнопками в дереве доступности — а это единственная страница, которую
    видят посторонние), `maxOpens: "0"` уезжал строкой на сервер, ключи React Query
    пересекались по префиксу.

**Гигиена сьюта:** документная часть переведена с подделки «PK fake docx» на НАСТОЯЩИЙ
минимальный .docx (base64-константа `DOCX_MIN`) — редактор её конвертирует, и всё, что стоит
за ГОТОВЫМ PDF (в том числе выдача байтов гостю), наконец проверяется, а не пропускается.

## Волна 2 (2026-08-02): обзор, уведомления, смена адреса, скачивание, ZIP

**«Ссылки наружу»** — раздел ПРОФИЛЯ (`/profile/links`), рядом с «Безопасностью».
Не внутри Диска намеренно: ссылки выдают разные сервисы, и внутри одного список был бы
неполным — то есть врал бы ровно тогда, когда в него приходят разбираться. Сводка
считает открытия по ЖУРНАЛУ ВИЗИТОВ за 30 дней, а не по `openCount` («что происходит
сейчас», а не «за всю жизнь»); гистограмма группируется в SQL. Подписи объектов — через
`describeRef`, который до этого был написан и не вызывался ниоткуда.

**Право на «мои ссылки» — АВТОРСТВО, а не текущие права на объект.** Человек, потерявший
доступ к папке (сняли грант, уволился), обязан уметь закрыть то, что раздал сам; отзыв
только сужает доступ и потому безопасен по определению. Массовый отзыв фильтрует по
`createdById` — чужие id в списке молча игнорируются.

**Уведомления об открытии** (`share.link.opened`): тумблер ВКЛЮЧЁН по умолчанию — частый
случай «отправил документ человеку», там уведомление и есть смысл. От массовой ссылки
спасает не выключенный тумблер, а **суточный предохранитель БЕЗ КРОНА**: `notifyPerDay`
уведомлений, потом одно прощальное `share.link.opened.muted` и тишина. День (`notifyDay`
типа DATE + `notifyCount`) лежит в самой строке и сбрасывается ПЕРВЫМ открытием
следующих суток. День считается в APP_TIMEZONE, а не UTC: иначе тишина снималась бы
среди ночи по местному времени.

**Смена адреса** (`rotate`): новый токен при сохранении журнала, настроек и подписи.
⚠️ ОБЯЗАТЕЛЕН бамп `sessionEpoch` (поле `e` в пропуске): пропуск подписан по linkId, а не
по токену, поэтому без поколения тот, у кого утёк СТАРЫЙ адрес, досматривал бы содержимое
ещё час — ровно тот, ради кого адрес и меняют. Блокировка подбора пароля при смене
снимается: она относилась к старому адресу.

**«Разрешить скачивание»**: оригинал не отдаётся вовсе, остаётся `previewUrl` (средняя
копия / постер). ЧЕСТНО: это НЕ защита от копирования — байты превью у гостя в браузере,
а у встроенного просмотрщика PDF своя кнопка сохранения. Ровно так эту настройку
описывают Google Drive и Dropbox. Для этого в движок файлов добавлен
`AttachmentFileView.mediumUrl`.

**ZIP папки** (`yazl`, новая прямая зависимость): архив собирается ПОТОКОМ в ответ, без
временных файлов и очереди. Байты читаются ПО ОДНОМУ файлу за раз — каждой записи свой
PassThrough, наполняем в том же порядке, в каком yazl их забирает. Открыть тысячу потоков
к хранилищу сразу нельзя: половина отвалится по таймауту. Потолки по объёму и числу
файлов обязательны — потоковая сборка занимает соединение. Уже сжатое (image/video/audio)
кладётся без компрессии. Кнопка работает на ТЕКУЩЕЙ папке, а не только на корне ссылки.

⚠️ **ЕДИНСТВЕННОЕ место, где пропуск едет не заголовком, а в адресе** — скачивание архива:
у навигации браузера своих заголовков нет, а тянуть гигабайты в память вкладки ради blob
нельзя. Размен осознанный: пропуск живёт час, привязан к одной ссылке и по правам строго
слабее адреса `/s/<токен>`, который у гостя и так в адресной строке.

**Ловушка Nest:** статические пути (`mine`, `mine/stats`) объявлять ДО `:id`, иначе
`/share-links/mine` уедет в параметр и движок пойдёт искать ссылку с id «mine».

## Саморевью волны 2 (2026-08-02) — 11 находок, все закрыты

1. **[важно] Счётчик уведомлений был «прочитали — записали»** и обходился ровно тем, ради
   чего предохранитель заведён: вирусную ссылку открывают ПАРАЛЛЕЛЬНО, все заходы читали
   одно значение, потолок не наступал. Переехал В САМ атомарный клейм открытия
   (`UPDATE … SET notify_count = CASE WHEN notify_day = today THEN +1 ELSE 1 END RETURNING`).
2. **[важно] Ключ дедупа уведомления брал `openCount + 1` из строки, прочитанной в начале
   запроса.** У параллельных заходов эта строка ОДНА И ТА ЖЕ → ключи совпадали → уникальный
   индекс `Notification.dedupKey` схлопывал все уведомления в ОДНО. Предохранитель при этом
   работал, а уведомления просто пропадали. Поймано собственным тестом на гонку (ждали 6,
   пришло 1). Ключ стал `sl:<id>:<день>:<атомарный номер>`.
3. **[важно] ZIP не переживал ОБРЫВ скачивания.** Гость закрыл вкладку → ответ мёртв → yazl
   перестаёт вычитывать краники → `pipeline` встаёт в бэкпрешер и НЕ ЗАВЕРШАЕТСЯ: запрос
   висит вечно, держит поток к хранилищу и копит архив в памяти. Отменённые скачивания —
   обычное дело. Добавлен слушатель `res.on('close')` с проверкой `writableFinished`.
4. **[важно] ZIP был без своего троттлинга** — неаутентифицированная ручка, каждый вызов
   обходит поддерево и тянет байты всех файлов. 5/мин.
5. **[важно] Курсор «Моих ссылок» терял близнецов**: пачку ссылок выдают за одну
   миллисекунду, а `createdAt < cursor` отсекает их целиком. Составной «время|id».
6. **Снимок `refTitle`/`refIcon` на строке ссылки** вместо вызова `describeRef` на каждую
   строку списка: минус N запросов на страницу, имя переживает удаление объекта (в разделе
   «что я раздал» это важнее свежести) и не светит ТЕКУЩЕЕ имя тому, у кого доступ к объекту
   давно отобрали. Старые строки без снимка откатываются на `describeRef`.
7. **Массовый отзыв не писал в хронику**, хотя одиночный писал — закрытие доступа наружу не

9. **Сводка считала сутки в UTC**: у человека в Алматы открытия с полуночи до пяти утра
